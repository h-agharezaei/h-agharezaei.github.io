یک بازی ساده: به عددی بین ۱ تا ۱۰۰ فکر می‌کنم و شما باید حدسش بزنید. هر بار فقط می‌گویم «بالاتر» یا «پایین‌تر». اگر از ۱ شروع کنید و یکی‌یکی بروید، شاید ۱۰۰ حدس لازم شود. ولی اگر هر بار وسط بازه‌ی باقی‌مانده را حدس بزنید، هر جواب نصف احتمال‌ها را خط می‌زند و حداکثر ۷ حدس کافی است. این همان {{< term "binary-search" "جست‌وجوی دودویی" >}} است: روی داده‌ی مرتب، وسط را نگاه کن و نصفی را که نمی‌تواند جواب باشد دور بریز.

ایده در یک جمله جا می‌شود، ولی کدش به غلط‌نوشته‌شدن معروف است. مثلاً اگر `5` را با «بازه‌ی بسته» و شرط حلقه‌ی `lo < hi` در `[1 3 5]` جست‌وجو کنید، جواب `-1` می‌گیرید، با اینکه `5` همان‌جاست. درمان همان عادتی است که در [heap و priority queue](/fa/posts/algo-heaps-priority-queues/) heap را درست نگه داشت: پیش از نوشتن کد، {{< term "invariant" "invariant" >}} را بنویسید، یعنی جمله‌ای که در هر دور حلقه باید درست بماند. جست‌وجو روی یک slice مرتب کار می‌کند، مثل [آرایه‌ی پویا و slice از درون](/fa/posts/algo-dynamic-arrays/)، از [Generics در Go](/fa/posts/go-generics/) استفاده می‌کند و هزینه‌اش همان لگاریتمی است که در [تحلیل Big-O با اندازه‌گیری واقعی](/fa/posts/algo-big-o-measured/) دیدیم.

> Go 1.27، مثال محلی، برای این پست دوباره اجرا شده. ماشین مشغول بود، پس فقط تعداد عملیات (که قطعی است) را منتشر می‌کنم و زمانی نمی‌دهم.

## اول invariant را بنویسید

مشکل جست‌وجوی دودویی خود ایده نیست، مرزهاست: بازه شامل چه چیزی است؟ بعد از هر مقایسه مرز را به `mid` ببرم یا به `mid + 1`؟ جواب این سؤال‌ها از حدس‌زدن نمی‌آید، از یک جمله می‌آید که قبل از کد نوشته شود.

من بازه‌ی نیم‌باز `[lo, hi)` را جست‌وجو می‌کنم، یعنی `lo` جزو بازه است و `hi` نیست. چیزی که می‌خواهیم پیدا کنیم {{< term "lower-bound" "lower bound" >}} است: اندیس اولین عنصری که **بزرگ‌تر یا مساوی** `x` است (اگر هیچ عنصری نباشد، طول آرایه). جمله‌ی نگه‌دارنده، یعنی invariant، این است:

> هر خانه‌ی قبل از `lo` از `x` کوچک‌تر است. هر خانه‌ی `hi` به بعد بزرگ‌تر یا مساوی `x` است. فقط بازه‌ی `[lo, hi)` هنوز نامعلوم است.

و کد با همان جمله به صورت کامنت:

```go
// Invariant: a[i] < x for every i < lo; a[i] >= x for every i >= hi.
// The unknown part is [lo, hi).
func LowerBound[T cmp.Ordered](a []T, x T) int {
	lo, hi := 0, len(a)
	for lo < hi {
		mid := lo + (hi-lo)/2
		if a[mid] < x {
			lo = mid + 1
		} else {
			hi = mid
		}
	}
	return lo // lo == hi: nothing unknown is left
}
```

اول یک مثال دستی ببینیم. در `a = [1 3 3 3 5 8 8 13]` دنبال `x = 5` می‌گردیم:

```
lo=0 hi=8  mid=4  a[4]=5  آیا 5 < 5؟ نه  -> hi = 4   (از خانه‌ی ۴ به بعد >= 5 است)
lo=0 hi=4  mid=2  a[2]=3  آیا 3 < 5؟ بله -> lo = 3   (خانه‌های ۰ تا ۲ < 5 هستند)
lo=3 hi=4  mid=3  a[3]=3  آیا 3 < 5؟ بله -> lo = 4
lo=4 hi=4  حلقه تمام شد؛ جواب 4
```

حالا چرا درست است؟ سه چیز را بررسی می‌کنیم:

- **شروع:** `lo = 0` و `hi = len(a)`. قبل از `lo` هیچ خانه‌ای نیست و از `hi` به بعد هم نیست، پس جمله خالی و بی‌خدشه درست است.
- **هر دور:** اگر `a[mid] < x`، چون آرایه مرتب است همه‌ی خانه‌های تا `mid` هم کوچک‌ترند، پس `lo = mid + 1` جمله را نگه می‌دارد. وگرنه `a[mid] >= x` و همه‌ی خانه‌های بعد از آن هم همین‌طورند، پس `hi = mid` جمله را نگه می‌دارد. در هر دو حالت بازه‌ی نامعلوم کوچک‌تر می‌شود.
- **پایان:** بازه کوچک می‌شود، پس حلقه می‌ایستد، و آن لحظه `lo == hi` است. جمله می‌گوید همه‌ی خانه‌های قبل از `lo` کوچک‌اند و همه‌ی خانه‌های از `lo` به بعد بزرگ‌تر یا مساوی. پس `lo` دقیقاً اولین عنصر `>= x` است.

نیازی به اثبات پیچیده‌ای نیست؛ فقط باید جمله را نوشته باشید. `UpperBound` همین کد است با `<=` به جای `<`؛ اندیس اولین عنصر **بزرگ‌تر** از `x` را می‌دهد. از این دو اولین وقوع، آخرین وقوع و تعداد تکرارها به دست می‌آید (`Count = UpperBound - LowerBound`). برنامه‌ی نمایشی روی آرایه‌ی بالا اجرا شد:

```
a = [1 3 3 3 5 8 8 13]
x=3  lower=1 upper=4 first=1 last=3 count=3
x=4  lower=4 upper=4 first=-1 last=-1 count=0
x=8  lower=5 upper=7 first=5 last=6 count=2
```

برای `x=3` سه تا ۳ داریم که از خانه‌ی ۱ تا ۳ هستند: `lower=1` اولین است، `upper=4` اولین خانه‌ی بعد از آخری است و `count = 4 - 1 = 3`. برای `x=4` که در آرایه نیست، `lower` و `upper` هر دو ۴ هستند، یعنی «اگر می‌خواستی ۴ را اضافه کنی، جایش خانه‌ی ۴ است» و تعداد صفر. `first` و `last` برای مقدار غایب `-1` می‌دهند.

invariant را می‌شود هنگام اجرا هم چک کرد. نسخه‌ای از `LowerBound` قبل از هر دور بررسی می‌کند که `a[lo-1] < x` و `a[hi] >= x` باشد، و اگر نباشد panic می‌کند. روی همه‌ی حالت‌های بخش «تست جامع» پایین‌تر، ۵٬۳۴۴ چک اجرا شد و هیچ‌وقت panic نکرد.

## کتابخانه‌ی استاندارد

لازم نیست همیشه خودتان بنویسید. `slices.BinarySearch` مقدار `(index, found)` برمی‌گرداند که index همان lower bound است و `found` می‌گوید خود `x` همان‌جا هست یا نه. `sort.Search(n, f)` کوچک‌ترین اندیسی را برمی‌گرداند که `f` در آن درست است؛ یعنی همین ایده با شرط دلخواه شما:

```
x=3  slices.BinarySearch=(1,true)  sort.Search=1
x=4  slices.BinarySearch=(4,false) sort.Search=4
```

هر دو برای `x=3` اندیس ۱ را دادند و برای `x=4`، که وجود ندارد، اندیس ۴ را؛ فقط `BinarySearch` علاوه بر آن صریحاً `false` می‌گوید.

## باگ‌های کلاسیک، واقعی

برای هر کدام کدی را اجرا کردم که واقعاً همان اشتباه را دارد.

**سرریز نقطه‌ی وسط.** `(lo+hi)/2` اول جمع می‌کند و بعد نصف. اگر `lo + hi` از بزرگ‌ترین عدد نوع جا بزند، جمع به منفی می‌چرخد. با `int8` و اندیس‌های ۱۰۰ و ۱۲۰، و با `int32` و اندیس‌های دو میلیارد و دو میلیارد و صد میلیون:

```
(lo+hi)/2     = -18 (lo+hi wrapped to -36)
lo+(hi-lo)/2  = 110
int32 (lo+hi)/2    = -97483648
int32 lo+(hi-lo)/2 = 2050000000
```

جمع ۱۰۰ و ۱۲۰ در `int8` به ‎-۳۶ می‌پیچد و نصفش ‎-۱۸ می‌شود، اندیسی که وجود ندارد. شکل `lo+(hi-lo)/2` هیچ‌وقت از `hi` بزرگ‌تر نمی‌شود، پس سرریز نمی‌کند و جواب درست ۱۱۰ را می‌دهد. در سکوهای ۶۴ بیتی `int` در Go شصت‌وچهار بیتی است و به این مرز کمتر می‌رسید، ولی اگر برسید {{< term "integer-overflow" "سرریز" >}} بی‌صدا اتفاق می‌افتد، پس شکل امن را از اول بنویسید.

**off-by-one که تمام نمی‌شود.** نوشتن `lo = mid` به‌جای `lo = mid + 1` می‌تواند حلقه را برای همیشه گیر بیندازد. ببینیم چرا، روی `[1 3 5 7 9]` و `x = 5` با مرز `hi = len-1`: `lo=0, hi=4` -> `mid=2`، `a[2]=5` کوچک‌تر نیست -> `hi=2`. بعد `lo=0, hi=2` -> `mid=1`، `3 < 5` -> `lo=1`. بعد `lo=1, hi=2` -> `mid=1`، دوباره `3 < 5` -> `lo=mid=1`: هیچ چیز عوض نشد، پس تا ابد همین‌جا می‌چرخد. من آن را با شمارنده‌ی قدم ۱۰۰۰ محدود کردم تا برنامه گیر نکند:

```
x=1 finished=true  steps=3
x=5 finished=false steps=1001
x=9 finished=false steps=1001
x=6 finished=false steps=1001
```

`x=1` به شانس تمام می‌شود، چون `lo` هیچ‌وقت لازم نیست جلو برود. بقیه به سقف ۱۰۰۱ قدم رسیدند، یعنی هیچ‌وقت تمام نمی‌شوند.

**بازه‌ی بسته‌ای که یک عنصر را جا می‌اندازد.** وقتی بازه `[lo, hi]` است و `hi` هم جزو آن، شرط حلقه باید `lo <= hi` باشد. با `lo < hi` وقتی فقط یک عنصر مانده، حلقه همان‌جا می‌ایستد و آن عنصر را هیچ‌وقت نگاه نمی‌کند. همان مثال ابتدای پست: جست‌وجوی `5` در `[1 3 5]` با نسخه‌ی خراب `-1` داد و نسخه‌ی درست `2`.

## تست جامع

یک تست تصادفی ممکن است این باگ‌ها را نبیند. اینجا فضای ورودی آن‌قدر کوچک است که می‌شود همه‌چیز را چک کرد: همه‌ی آرایه‌های مرتب با طول ۰ تا ۷ که مقدارهایشان از ۰ تا ۳ است، و هر هدف از ‎-۱ تا ۴. هر نتیجه با یک جست‌وجوی خطی مقایسه می‌شود:

```
arrays=330 cases=1980 | LowerBound/Count failures=0 | closedOK failures=0 | broken closed failures=217
first failing case of the broken version: a=[0] target=0
```

۳۳۰ آرایه و ۱٬۹۸۰ حالت، و کد درست حتی یک بار هم شکست نخورد. نسخه‌ی بسته‌ی خراب در ۲۱۷ حالت شکست خورد، و اولین شکستش حتی روی آرایه‌ی تک‌عنصری `[0]` با هدف `0` بود (حلقه اصلاً وارد نمی‌شود). `go test -race` هم سبز است. با تستی از این نوع دیگر لازم نیست نگران باشید که یک حالت کوچک و خاص جا افتاده باشد.

## جست‌وجو روی جواب

ایده‌ی جست‌وجوی دودویی به آرایه محدود نیست. هر چیزی که **یکنوا** (monotone) باشد را می‌شود با آن جست‌وجو کرد، یعنی دنباله‌ای از نوع `false false ... false true true ... true`. اگر بتوانید شرطی بنویسید که برای مقدارهای کوچک نادرست و از یک نقطه به بعد همیشه درست باشد، کوچک‌ترین مقدار درست را با همان حلقه پیدا می‌کنید. invariant: «`ok` برای مقدارهای قبل از `lo` نادرست و از `hi` به بعد درست است»:

```go
func MinTrue(lo, hi int, ok func(int) bool) int {
	for lo < hi {
		mid := lo + (hi-lo)/2
		if ok(mid) { hi = mid } else { lo = mid + 1 }
	}
	return lo
}
```

همان `LowerBound` است؛ فقط `a[mid] < x` جایش را به `!ok(mid)` داده.

**مثال اول: ظرفیت کشتی.** بسته‌هایی با وزن‌های مشخص باید **به ترتیب** با یک کشتی حمل شوند. کشتی هر روز تا یک ظرفیت بار می‌برد. می‌خواهیم کوچک‌ترین ظرفیتی را پیدا کنیم که همه‌چیز را در حداکثر `D` روز برساند. یک ظرفیت مشخص «شدنی» است اگر بارگیری حریصانه (هر روز تا جایی که جا دارد بار بزن) حداکثر `D` روز لازم داشته باشد. کشتی بزرگ‌تر هیچ‌وقت بدتر نیست، پس شدنی‌بودن یکنواست و جست‌وجوی دودویی روی ظرفیت جواب می‌دهد. بازه‌ی جواب از بزرگ‌ترین بسته (کمتر از آن اصلاً جا نمی‌شود) تا مجموع وزن‌هاست (یک روز). با وزن‌های ۱ تا ۱۰:

```
days=1 -> capacity 55    days=2 -> capacity 28
days=5 -> capacity 15    days=10 -> capacity 10
```

یک روز یعنی همه‌چیز در یک بار: ۱+۲+...+۱۰ = ۵۵. ده روز یعنی هر روز می‌شود یک بسته، پس بزرگ‌ترین بسته (۱۰) کافی است. ۲ و ۵ روز بین این دو هستند.

**مثال دوم: جذر صحیح.** کف جذر `n` برابر است با «کوچک‌ترین `k` که `k*k > n` است، منهای یک». مثلاً برای `n=16`، کوچک‌ترین `k` با `k*k > 16` برابر ۵ است و جواب ۴. اما نسخه‌ی اول من، یعنی شرط `k*k > n`، برای `n` بزرگ سرریز کرد، چون `k*k` از بزرگ‌ترین `int` رد می‌شود. نسخه‌ی اصلاح‌شده `k > n/k` است (برای `k >= 1` و تقسیم صحیح معادل است) و سرریز نمی‌کند. برای `n = 2^40`:

```
isqrt(1099511627776)=1048576 naive=546710704328
```

جواب درست ۱٬۰۴۸٬۵۷۶ است (۲ به توان ۲۰). نسخه‌ی ساده (`naive`) عدد بی‌ربط ۵۴۶٬۷۱۰٬۷۰۴٬۳۲۸ داد، چون مقایسه‌هایش روی عددهای سرریزکرده بود. برای عددهای کوچک (۰، ۱، ۱۵، ۱۶، ۱۷، ۹۹، ۱۰۰) هر دو درست بودند؛ پس تنها تست‌های کوچک این باگ را نشان نمی‌دادند.

## چند مقایسه لازم است؟

روی یک slice مرتب با n عنصر و مقداری که در آن نیست (از همه بزرگ‌تر)، تعداد ارزیابی `a[mid] < x` را شمردم. برنامه علاوه بر آن `ceil(log2(n+1))` را هم چاپ کرد، که سقف تعداد دورهاست:

```
n=1000    9    n=10000   13
n=100000  16   n=1000000 19
```

سقف برای این چهار n به ترتیب ۱۰، ۱۴، ۱۷ و ۲۰ است؛ شمارش‌ها یکی کمتر از سقف‌اند. هزار برابر شدن n حدود ۱۰ قدم اضافه می‌کند: همان جدول دوبرابرشدن پست Big-O، ولی برعکس. برای یک میلیون عنصر، نوزده مقایسه کافی بود.

## قاعده‌هایی که جلوی off-by-one را می‌گیرند

- **invariant را قبل از کد به‌صورت کامنت بنویسید.** هر `+ 1` و هر `<=` را باید بتوان از همان جمله توضیح داد.
- **`[lo, hi)` یا `[lo, hi]` را انتخاب کنید و شرط‌هایشان را قاطی نکنید.** نیم‌باز: `lo < hi`، `hi = mid`. بسته: `lo <= hi`، `hi = mid - 1`.
- **از `lo+(hi-lo)/2` استفاده کنید** تا سرریز به شما نرسد.
- **با شرط (predicate) جست‌وجو کنید** و «پیدا کردن x» را از آن بسازید، به‌جای نوشتن چند حلقه‌ی مشابه.
- **ورودی باید واقعاً مرتب باشد.** اینکه در غیر این صورت چه می‌شود را تست نکردم.

## تمرین

برای slice مرتب از float، `Floor` و `Ceil` بنویسید (بزرگ‌ترین عنصر کوچک‌تر یا مساوی و کوچک‌ترین عنصر بزرگ‌تر یا مساوی) و یک تست جامع در برابر جست‌وجوی خطی بسازید. بعد کدتان را عمداً خراب کنید و حالت شکست‌خورده را بخوانید.
