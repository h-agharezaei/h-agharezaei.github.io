آخرین پست این مجموعه درباره‌ی دو ایده است که روی hash ساخته شده‌اند، همان ترفند [جدول هش از صفر](/fa/posts/algo-hash-tables/). {{< term "bloom-filter" "Bloom filter" >}} با حافظه‌ی خیلی کم جواب می‌دهد «این کلید در مجموعه هست؟» به این قیمت که گاهی اشتباه می‌گوید بله. {{< term "consistent-hashing" "Consistent hashing" >}} تعیین می‌کند کدام سرور صاحب کلید است، طوری که با اضافه‌شدن سرور کلید کمی جابه‌جا شود. پست قبلی [الگوریتم‌های رشته: KMP و Rabin–Karp](/fa/posts/algo-string-algorithms/) بود.

> Go 1.26، مثال محلی، تست با `go test -race`. بار ماشین کم نبود، پس شمارش و بایت منتشر می‌کنم، نه زمان. hash: FNV-1a و بعد یک گام اختلاط splitmix64.

## Bloom filter

یک آرایه‌ی m بیتی و k موقعیت hash برای هر کلید. درج، k بیت را روشن می‌کند و جست‌وجو همان‌ها را می‌خواند. یک بیت صفر یعنی «حتماً نیست»، پس منفی اشتباه نداریم. اگر همه روشن باشند یعنی «شاید». k موقعیت را از دو hash می‌سازم: موقعیت i برابر h1 + i*h2 به پیمانه‌ی m (double hashing).

فرمول‌های شناخته‌شده: نرخ مثبت اشتباه p ≈ (1 − e^(−kn/m))^k و بهترین k برابر (m/n)·ln 2 است. ۱۰٬۰۰۰ کلید درج کردم و ۱۰۰٬۰۰۰ کلیدی را که هرگز درج نشده بودند امتحان کردم (نام‌های ثابت، پس اجرا قطعی است):

```
      m      k  bytes  false+  measured%  formula%  k_opt
  40000      3   5000   14595    14.595    14.689   2.77
  80000      6  10000    2100     2.100     2.158   5.55
 100000      7  12504     793     0.793     0.819   6.93
 100000      3  12504    1736     1.736     1.741   6.93
 200000     14  25000       7     0.007     0.007  13.86
```

فرمول در حد چند درصد با اندازه‌گیری می‌خواند. ده بیت برای هر کلید با k=7 حدود ۰٫۸٪ مثبت اشتباه می‌دهد. با همان حافظه و k=3 خطا دو برابر می‌شود، دقیقاً مثل فرمول.

حافظه: فیلتر بالا ۱۲٬۵۰۴ بایت است. یک `map[string]struct{}` با همان ۱۰٬۰۰۰ کلید heap را ۴۳۵٬۳۸۴ بایت بزرگ کرد (اختلاف `runtime.MemStats`؛ رشته‌های کلید از قبل ساخته شده بودند و شمرده نشده‌اند، پس set واقعی گران‌تر است). فیلتر خیلی کوچک‌تر است ولی نمی‌تواند کلیدها را فهرست کند یا برگرداند.

یک تست ۵٬۰۰۰ کلید اضافه می‌کند و بررسی می‌کند همه پیدا شوند (بدون منفی اشتباه).

**حذف ممکن نیست**: صفر کردن یک بیت ممکن است کلید دیگری را پاک کند. نوع counting برای هر موقعیت یک شمارنده نگه می‌دارد و Remove کم می‌کند:

```
counting: after Remove(item-5) Has(item-5) = false  Has(item-6) = true
```

در اینجا هر خانه ۸ بیت است به‌جای ۱ بیت.

کاربرد: جلوی یک جست‌وجوی کند بگذاریدش. جواب «نه» از رفتن به پایگاه داده جلوگیری می‌کند و جلوی cache penetration (کلیدهایی که هرگز وجود ندارند) را در یک cache مثل [محدودسازی نرخ و caching](/fa/posts/go-rate-limiting-caching/) می‌گیرد. گمان می‌کنم پایگاه‌های LSM-tree مثل RocksDB از Bloom filter استفاده می‌کنند تا فایل‌هایی را که کلید را ندارند نخوانند، ولی اینجا بررسی نکردم. افزونه‌ی `bloom` در Postgres را هم بررسی نکردم.

## Consistent hashing

با `hash(key) % N` تغییر N تقریباً همه‌ی کلیدها را عوض می‌کند. consistent hashing نقطه‌های node ها را روی حلقه‌ای از hash های ۶۴ بیتی می‌گذارد و کلید مال نقطه‌ی بعدی در جهت ساعت است. نقطه‌ها را در یک slice مرتب نگه می‌دارم و با binary search ([جست‌وجوی دودویی و invariant](/fa/posts/algo-binary-search-invariants/)) پیدا می‌کنم و در انتها به ابتدا برمی‌گردم. هر node چند virtual node (vnode) دارد تا سهم‌ها یکنواخت شوند.

رفتن از ۴ به ۵ node با ۱۰۰٬۰۰۰ کلید:

```
mod-N        moved: 80194
ring vn=100  moved: 22588
rendezvous   moved: 20137
ring: moved keys that landed on node-4: 22588
```

mod-N حدود ۸۰٪ را جابه‌جا کرد (حالت ایده‌آل برای node پنجم ۲۰٪ است). حلقه ۲۲٫۶٪ را جابه‌جا کرد و همه‌ی کلیدهای جابه‌جاشده به node جدید رفتند؛ یک تست هم همین را بررسی می‌کند. حذف دوباره‌ی node-4 دقیقاً ۲۲٬۵۸۸ کلیدی را جابه‌جا کرد که روی آن بودند.

توازن روی ۵ node، به‌صورت بیشترین بار تقسیم بر میانگین و انحراف معیار به‌صورت درصدی از میانگین:

```
ring vn=1     2.378  71.5%
ring vn=10    1.574  35.5%
ring vn=100   1.129  11.6%
ring vn=1000  1.051  5.3%
rendezvous    1.010  0.7%
```

یک نقطه برای هر node افتضاح است: یک node ۲٫۴ برابر سهم عادلانه‌اش را داشت. vnode بیشتر درستش می‌کند، به قیمت slice مرتب بزرگ‌تر.

وزن‌دادن ساده است: به node بیشتر vnode بدهید. با وزن ۳ برای node-0 شمارش‌ها `49324 17256 18233 15187` شد، تقریباً ۳:۱:۱:۱.

## Rendezvous hashing

{{< term "rendezvous-hashing" "Rendezvous hashing" >}} حلقه نمی‌خواهد:

```go
func Rendezvous(nodes []string, key string) string {
	best, bs := "", uint64(0)
	for _, n := range nodes {
		if s := hash64(n + "|" + key); best == "" || s > bs {
			best, bs = n, s
		}
	}
	return best
}
```

۲۰٬۱۳۷ کلید را جابه‌جا کرد (نزدیک ۲۰٪ ایده‌آل) و بهترین توازن را داشت (۱٫۰۱۰). هزینه‌اش برای هر جست‌وجو O(تعداد node) است، نه O(log نقطه‌ها). برای ده‌ها node خوب است و برای هزاران node بدتر.

## چند نکته‌ی مهم

- Bloom filter را باید از قبل برای n اندازه کرد؛ بعد از آن خطا سریع بالا می‌رود.
- کیفیت hash مهم است: گام اختلاط را اضافه کردم چون FNV خام روی نام‌های شبیه هم ضعیف است.
- replica، خرابی و جابه‌جایی داده مسئله‌ای جدا از انتخاب صاحب کلید است.
- نتایج من از یک مجموعه کلید است؛ ۲۲٫۶٪ را ثابت فرض نکنید.

## تمرین

Bloom filter را قابل رشد کنید: وقتی تعداد تخمینی از n گذشت، یکی بزرگ‌تر بسازید. برای بازسازی چه چیزی باید نگه دارید؟ بعد اندازه بگیرید کسر جابه‌جاشده‌ی حلقه بین ۱۰ و ۱۱ node چقدر است.

## قدم بعدی

مجموعه‌ی الگوریتم‌ها اینجا تمام می‌شود. sharding و consistent hashing در مجموعه‌ی سیستم‌های توزیع‌شده برمی‌گردند، جایی که صاحب کلید می‌تواند خراب شود و داده باید دنبالش برود.
