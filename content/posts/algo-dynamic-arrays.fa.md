موضوع مقاله‌ی قبلِ این سری [تحلیل Big-O با اندازه‌گیری واقعی](/fa/posts/algo-big-o-measured/) بود. حالا آن را روی پرکاربردترین ساختار داده‌ای که وجود دارد امتحان می‌کنیم: {{< term "dynamic-array" "آرایه‌ی پویا" >}}. در Go این ساختار پشت slice پنهان است؛ slice را در [Slice، Map و String در Go](/fa/posts/go-slices-maps-strings/) دیده‌ایم، بحث حافظه در [اشاره‌گرها و مدل حافظه در Go](/fa/posts/go-pointers-memory/) آمده و کانتینر خودمان را با [Generics در Go](/fa/posts/go-generics/) می‌نویسیم.

> همه‌ی کدها با Go 1.26 و به‌صورت یک مثال محلی اجرا شده‌اند. فقط تعداد و دنباله چاپ می‌کنم، نه زمان. مقدار دقیق رشد جزئیات پیاده‌سازی است و تضمین زبان نیست.

## هدر slice

{{< term "slice" "Slice" >}} سه کلمه است: اشاره‌گر، `len` و `cap`. اشاره‌گر به یک {{< term "backing-array" "backing array" >}} اشاره می‌کند.

```go
var s []int
fmt.Println(unsafe.Sizeof(s), "bytes")
a := make([]int, 3, 10)
b := a[:2]
b[0] = 7
fmt.Println(a, b, &a[0] == &b[0])
```

```
24 bytes
[7 0 0] [7 0] true
```

کپی‌کردن slice یعنی کپی ۲۴ بایت، نه عنصرها. `a` و `b` دو هدر روی یک آرایه‌اند.

## append واقعاً چطور رشد می‌کند

یک مقدار صفر را هربار append کردم و هر `cap` جدید را ثبت کردم:

```
[]int : [4 8 16 32 64 128 256 512 848 1280 1792 2560]
[]byte: [32 64 128 256 512 896 1408 2048]
3-byte struct: [10 21 42 85 170]
```

دو چیز دیده می‌شود. تا ۲۵۶ ظرفیت دو برابر می‌شود و بعد از آن تقریباً ۱٫۲۵ برابر به‌اضافه‌ی یک مقدار ثابت. طبق سورس Go (تابع `growslice`) قاعده این است: زیر ۲۵۶ عنصر دو برابر، وگرنه تا وقتی کافی نشده `(cap + 3*256) / 4` اضافه می‌شود. نتیجه سپس به یک {{< term "size-class" "size class" >}} از allocator گرد می‌شود. اعداد را دستی چک کردم: از ۵۱۲ می‌شود 512 + (512+768)/4 = 832 عنصر، یعنی ۶۶۵۶ بایت؛ size class بعدی ۶۷۸۴ بایت است و 6784 / 8 = 848. همین برای ۸۴۸ به ۱۲۸۰ و ۱۷۹۲ به ۲۵۶۰ هم برقرار است. ردیف `[]byte` و struct سه‌بایتی (۳۲ بایت جای ۱۰ تا از آن را دارد) گرد‌شدن را حتی در بازه‌ی کوچک نشان می‌دهند. دلیل اینکه مقدار اول ۴، ۳۲ یا ۱۰ است را بررسی نکردم، پس به آن تکیه نکنید.

## چرا append سرشکن O(1) است

یک append تکی می‌تواند همه‌چیز را کپی کند، پس بدترین حالت O(n) است. {{< term "amortized-analysis" "تحلیل سرشکن‌شده" >}} کل دنباله را می‌بیند. هر تغییر `cap` را تشخیص دادم و عنصرهای کپی‌شده را شمردم:

```
n=1000    copies=1868     copies/n=1.87
n=10000   copies=32415    copies/n=3.24
n=100000  copies=402079   copies/n=4.02
n=1000000 copies=4154015  copies/n=4.15
```

کپی به‌ازای هر append با بزرگ‌شدن n زیاد نمی‌شود و نزدیک ۴ می‌ماند. دقیقاً همان چیزی است که ضریب ۱٫۲۵ پیش‌بینی می‌کند: کپی‌ها یک سری هندسی‌اند و جمعشان حدود n / 0.25 = 4n است. با دو برابر کردن خالص حداکثر حدود 2n می‌شود. در هر دو حالت مجموع `c·n` است، پس هر append به‌طور میانگین O(1) هزینه دارد. ضریب کوچک‌تر یعنی کپی بیشتر و ضریب بزرگ‌تر یعنی حافظه‌ی بلااستفاده‌ی بیشتر.

## Preallocation

اگر اندازه را می‌دانید، بگویید. با `testing.AllocsPerRun` روی ۱۰۰۰ append:

```
without prealloc: 9   with make([]int, 0, N): 1
```

نُه allocation شد یکی (در همین اجرا؛ اعداد، تعداد allocation هستند نه زمان).

## درج، حذف و تله‌ی aliasing

درج وسط آرایه دم را جابه‌جا می‌کند، پس O(n) است؛ حذف هم همین‌طور.

```go
x = slices.Insert(x, 1, 99)   // [1 99 2 3 4 5]
z := slices.Delete(y, 1, 3)   // result [1 4 5], y is now [1 4 5 0 0]
```

`slices.Delete` عنصرها را جابه‌جا می‌کند و از Go 1.22 دُمِ بلااستفاده را صفر می‌کند؛ بالا تأیید شد: `y`ی اصلی با دو صفر تمام می‌شود. بعد از `Delete` از slice قدیمی استفاده نکنید.

aliasing بعد از `append` دو نتیجه دارد:

```
fits:  [42 0 0] [42 0 0 1] shared: true
grows: [42 0 0 1] [-1 0 0 1 2] shared: false
```

وقتی ظرفیت اضافه هست، `append` در همان آرایه می‌نویسد و نوشتن از `q` در `p` دیده شد. وقتی پر است آرایه‌ی جدید می‌گیرد و دو slice از هم جدا می‌شوند. برای همین همیشه `s = append(s, x)` می‌نویسیم و حدس نمی‌زنیم در کدام حالت هستیم.

## DynArray[T] خودمان

کانتینر `Push`، `Pop`، `At`، `Insert`، رشد دوبرابری و شمارنده‌ی `Copies` دارد. هسته‌اش:

```go
func (d *DynArray[T]) grow(min int) {
	newCap := max(1, 2*len(d.data))
	for newCap < min {
		newCap *= 2
	}
	nd := make([]T, newCap)
	d.Copies += copy(nd, d.data[:d.n])
	d.data = nd
}

func (d *DynArray[T]) Push(v T) {
	if d.n == len(d.data) {
		d.grow(d.n + 1)
	}
	d.data[d.n] = v
	d.n++
}
```

`Pop` خانه‌ی آزادشده را صفر می‌کند تا اشاره‌گری را زنده نگه ندارد. بعد از ۱۰۰۰ بار Push: `len 1000 cap 1024 copies 1023` که مثل انتظار کمتر از 2n است. تست‌ها (push، pop، insert، pop روی خالی، کپی‌ها زیر 2n، و نمونه‌های مستقل در goroutineها) با `go test -race` پاس می‌شوند. این ساختار برای استفاده‌ی هم‌زمان امن نیست؛ تست race فقط نشان می‌دهد نمونه‌های جدا با هم تداخل ندارند.

برای مقایسه Rust را هم اجرا کردم: ظرفیت‌های `Vec<u32>` برابر `[4, 8, 16, ... 2048]` بود و `Vec<u8>` از ۸ شروع شد. آنجا هم دو برابر می‌شود، با شروع متفاوت.

## چند نکته‌ی مهم

- نتیجه‌ی `append` را همیشه انتساب بدهید.
- slice‌کردن حافظه را به‌اشتراک می‌گذارد؛ برای جداسازی از `slices.Clone` یا `a[:2:2]` استفاده کنید.
- یک slice کوچک از آرایه‌ی بزرگ، کل آرایه را زنده نگه می‌دارد.
- وقتی `n` را می‌دانید `make([]T, 0, n)` بنویسید.
- درج و حذف در وسط O(n) است؛ اگر زیاد انجامش می‌دهید شاید ساختار اشتباه است.

## تمرین

`DynArray` را طوری عوض کنید که ۱٫۲۵ برابر رشد کند (دست‌کم یکی بیشتر) و `Copies/n` را برای n = 1000000 چاپ کند. اول مقدار را پیش‌بینی کنید و با ۴ بالا مقایسه کنید. بعد `Delete(i)` اضافه کنید و خانه‌ی بلااستفاده را صفر کنید.
