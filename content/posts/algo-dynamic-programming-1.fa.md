تابع Fibonacci را به ساده‌ترین شکل بازگشتی بنویسید و `fib(35)` را صدا بزنید. این تابع فقط ۳۶ سؤال متفاوت دارد (`fib(0)` تا `fib(35)`)، ولی برای جواب دادن ۲۹٬۸۶۰٬۷۰۳ بار فراخوانی می‌شود. یعنی تقریباً همه‌ی کارش تکرار همان سؤال‌هایی است که قبلاً جواب داده است. {{< term "dynamic-programming" "برنامه‌ریزی پویا" >}} (به‌اختصار DP) راهی است که این هدررفتن را از بین می‌برد، و ایده‌ی اصلی‌اش خیلی ساده است: جواب هر سؤال را بار اول یادداشت کن و دفعه‌ی بعد فقط بخوان.

تا اینجا در این سری با ساختمان‌داده‌ها و گراف کار کردیم. در [پست قبل](/fa/posts/algo-topological-sort/) یک ترتیب روی گراف جلوی کار اضافه را می‌گرفت. این‌جا کار اضافه داخل خود بازگشت است و ربطی به گراف ندارد. DP روی چیزهایی بنا شده که قبلاً دیده‌ایم: بازگشت، [جدول هش](/fa/posts/algo-hash-tables/) (برای یادداشت جواب‌ها)، [آرایه‌های پویا](/fa/posts/algo-dynamic-arrays/) و عادت شمردن در [Big-O](/fa/posts/algo-big-o-measured/). اول با Fibonacci، که ساده‌ترین مثال است، ایده را می‌فهمیم، بعد سه مسئله‌ی واقعی را با همان روش حل می‌کنیم: شمردن راه‌های بالا رفتن از پله، ارزان‌ترین مسیر در یک جدول، و کمترین تعداد سکه.

> همه‌ی خروجی‌ها را با Go 1.27 دوباره اجرا کردم. مثال محلی است و تست‌هایش با `go test -race` سبز است. ماشین شلوغ بود، پس زمان منتشر نمی‌کنم؛ شمارش فراخوانی و تعداد allocation می‌بینید.

## Fibonacci: یک سؤال، چندین بار

دنباله‌ی Fibonacci این است: `fib(0) = 0`، `fib(1) = 1`، و هر عدد بعدی مجموع دو عدد قبلی. کدش مستقیم از تعریف می‌آید:

```go
func FibNaive(n int, calls *int) int {
	*calls++
	if n < 2 { return n }
	return FibNaive(n-1, calls) + FibNaive(n-2, calls)
}
```

(پارامتر `calls` فقط می‌شمارد تابع چند بار صدا شده.) ببینیم برای یک عدد کوچک، `fib(5)`، چه اتفاقی می‌افتد. درخت فراخوانی‌ها این است:

```
fib(5)
├─ fib(4)
│  ├─ fib(3)
│  │  ├─ fib(2)
│  │  │  ├─ fib(1)
│  │  │  └─ fib(0)
│  │  └─ fib(1)
│  └─ fib(2)
│     ├─ fib(1)
│     └─ fib(0)
└─ fib(3)
   ├─ fib(2)
   │  ├─ fib(1)
   │  └─ fib(0)
   └─ fib(1)
```

۱۵ فراخوانی برای یک سؤال ساده. به درخت نگاه کنید: `fib(3)` دو بار حساب شده، و `fib(2)` سه بار. هر بار همان جواب را از اول پیدا می‌کنیم. اینها {{< term "overlapping-subproblems" "زیرمسئله‌های تکراری" >}} هستند: مسئله‌ی بزرگ به مسئله‌های کوچک‌تر می‌شکند، ولی مسئله‌های کوچک‌تر با هم یکی‌اند. تعداد این تکرارها با بزرگ شدن n به‌شدت زیاد می‌شود. شمارش واقعی برای `fib(35)`:

```
naive  fib(35) = 9227465 calls = 29860703
```

جواب ۹٬۲۲۷٬۴۶۵ است و برای رسیدن به آن حدود ۳۰ میلیون فراخوانی لازم شد.

## راه‌حل اول: یادداشت کردن (memoization)

فرض کنید در امتحان هستید و جواب سؤال ۳ را یک بار با زحمت پیدا کردید. اگر سؤال ۵ دوباره آن را بخواهد، دوباره حلش نمی‌کنید؛ از روی یادداشتتان می‌خوانید. {{< term "memoization" "Memoization" >}} (یادداشت‌کردن) همین است: پیش از محاسبه در یک map نگاه کن که قبلاً جواب را داریم یا نه؛ اگر نداشتیم حساب کن و بعد ذخیره کن:

```go
func FibMap(n int, calls *int, memo map[int]int) int {
	*calls++
	if n < 2 { return n }
	if v, ok := memo[n]; ok { return v }   // قبلاً حساب شده
	v := FibMap(n-1, calls, memo) + FibMap(n-2, calls, memo)
	memo[n] = v
	return v
}
```

دوباره `fib(5)` را ببینید. `fib(5)` به `fib(4)` می‌رود، که به `fib(3)` و بعد `fib(2)` می‌رود و آن‌جا `fib(1)` و `fib(0)` که جواب‌شان معلوم است. وقتی `fib(3)` برمی‌گردد و `fib(4)` سراغ `fib(2)` می‌رود، جواب آماده است و در یک قدم برمی‌گردد. همین برای `fib(3)` در شاخه‌ی راست `fib(5)` هم برقرار است. با دست شمردم: ۹ فراخوانی، به جای ۱۵. روی `fib(35)`:

```
map    fib(35) = 9227465 calls = 69 subproblems = 34
slice  fib(35) = 9227465 calls = 69
```

از حدود ۳۰ میلیون فراخوانی به ۶۹ رسیدیم. ۶۹ همان 2n − 1 است (برای n=5 می‌شود ۹، که دیدیم): هر مقدار فقط یک بار حساب می‌شود و دفعه‌های بعد فقط خوانده می‌شود. map ۳۴ ورودی دارد: n از ۲ تا ۳۵ (حالت‌های پایه `fib(0)` و `fib(1)` ذخیره نمی‌شوند). نسخه‌ی slice همین کار را می‌کند، فقط با اندیس به‌جای کلید، پس {{< term "hash-table" "جست‌وجوی هش" >}} کنار می‌رود.

## راه‌حل دوم: جدول را از پایین پر کنید

در memoization از سؤال بزرگ شروع می‌کنیم و به سمت پایین می‌رویم (به آن **بالا‌به‌پایین** می‌گویند). راه دیگر برعکس است: از ساده‌ترین سؤال‌ها شروع کن و جواب‌های بزرگ‌تر را از روی آن‌ها بساز (**پایین‌به‌بالا**). برای Fibonacci یک جدول می‌سازیم و به ترتیب پرش می‌کنیم:

```go
t[1] = 1
for i := 2; i <= n; i++ { t[i] = t[i-1] + t[i-2] }
```

چیزی بازگشتی نیست و هر خانه فقط یک بار پر می‌شود. و چون `t[i]` فقط دو مقدار آخر را لازم دارد، لازم نیست کل جدول را نگه داریم: دو متغیر کافی است (نسخه‌ی `O1`). هر پنج نسخه برای `fib(35)` همان ۹٬۲۲۷٬۴۶۵ را می‌دهند. تعداد allocation هر نسخه را هم با `testing.AllocsPerRun` شمردم، که شامل ساختن memo هم می‌شود:

```
allocs map  : 7
allocs slice: 1
allocs table: 1
allocs o1   : 0
```

نسخه‌ی map هفت allocation دارد (احتمالاً چون map با اضافه شدن ورودی‌ها رشد می‌کند؛ این عدد به نسخه‌ی Go هم بستگی دارد و علتش را بررسی نکرده‌ام)، slice و جدول یکی، و نسخه‌ی دو متغیر هیچ. هیچ‌کدام حافظه‌ی زیاد نمی‌خواهند، ولی ایده‌اش مهم است: وقتی بدانید هر خانه فقط به چند خانه‌ی قبلی نیاز دارد، می‌شود جدول را دور انداخت.

یک نکته درباره‌ی عمق بازگشت: اینجا فقط ۳۵ است. پشته‌ی Go در صورت نیاز بزرگ می‌شود (طبق مستندات روی ۶۴ بیت به‌طور پیش‌فرض تا حدود ۱ گیگابایت)، پس عمق چند هزار مشکلی ندارد. در Python حد پیش‌فرض بازگشت ۱۰۰۰ است، و آنجا DP بالا‌به‌پایین برای n بزرگ مشکل واقعی است و باید پایین‌به‌بالا نوشت.

## چه مسئله‌هایی را می‌شود با DP حل کرد؟

Fibonacci را می‌شد حدس زد. برای مسئله‌هایی که این‌قدر واضح نیستند، DP وقتی کار می‌کند که دو ویژگی باشد:

- **زیرمسئله‌های تکراری**: همان چیزی که در درخت دیدیم.
- {{< term "optimal-substructure" "زیرساخت بهینه" >}}: جواب بهینه‌ی مسئله از جواب بهینه‌ی زیرمسئله‌هایش ساخته می‌شود.

مثال اول **پله‌ها**: از پله‌ی ۰ شروع می‌کنید و هر بار ۱ یا ۲ پله بالا می‌روید. به پله‌ی n به چند روش می‌شود رسید؟ با n=3 می‌شود شمرد: `۱+۱+۱`، `۱+۲` و `۲+۱`، یعنی ۳ روش. ایده: به پله‌ی i یا از i−1 می‌رسیم یا از i−2، و این دو دسته جدا هستند. پس `ways(i) = ways(i-1) + ways(i-2)`، که دقیقاً همان Fibonacci است:

```
stairs 0..8 : [1 1 2 3 5 8 13 21 34]
```

(یک روش برای رسیدن به پله‌ی ۰: کاری نکنید. برای پله‌ی ۳ عدد ۳ را می‌بینید، همان که شمردیم.)

مثال دوم **ارزان‌ترین مسیر در یک جدول**: هر خانه هزینه‌ای دارد، از بالا-چپ شروع می‌کنید و فقط به راست یا پایین می‌روید تا به پایین-راست برسید. کمترین مجموع هزینه چقدر است؟ برای رسیدن به یک خانه یا از بالا آمده‌اید یا از چپ، پس هزینه‌ی کمترِ آن خانه، هزینه‌ی خودش به‌علاوه‌ی کمتر از آن دو همسایه است. جدول هزینه‌ها (۳ ردیف، ۴ ستون):

```
1 3 1 2
1 5 1 9
4 2 1 1
```

جدول جواب را خانه‌به‌خانه پر می‌کنیم. ردیف اول فقط از چپ می‌آید (۱، ۱+۳=۴، ۴+۱=۵، ۵+۲=۷). ستون اول فقط از بالا (۱، ۱+۱=۲، ۲+۴=۶). خانه‌ی (ردیف ۱، ستون ۱) را در نظر بگیرید: از بالا ۴ می‌آید و از چپ ۲، کمترش ۲ است، پس ۲ + ۵ = ۷. بقیه همین‌طور:

```
table:  [1 4 5 7]
        [2 7 6 15]
        [6 8 7 8]
brute: 8
```

خانه‌ی پایین-راست جواب است: ۸. ردیف `brute: 8` یعنی یک بازگشت ساده که همه‌ی مسیرها را امتحان می‌کند هم همین را می‌دهد. مسیر بهینه: `۱ → ۳ → ۱ → ۱ → ۱ → ۱` (راست، راست، پایین، پایین، راست).

## یک دستور کار

از این مثال‌ها می‌شود یک الگو ساخت که برای هر مسئله‌ی DP جواب می‌دهد. پنج سؤال بپرسید:

1. **state (وضعیت)**: آرگومان‌های تابع چه معنایی دارند؟ برای سکه‌ها: `dp[a]` = کمترین تعداد سکه برای مبلغ `a`.
2. **transition (انتقال)**: هر state چطور از state‌های کوچک‌تر ساخته می‌شود؟
3. **base case (حالت پایه)**: چه چیزی بدون بازگشت معلوم است؟
4. **order (ترتیب)**: کدام stateها اول پر شوند تا وابستگی‌ها آماده باشند؟
5. **answer (جواب)**: کدام state همان چیزی است که می‌خواستیم؟

## مثال کامل: coin change

مسئله: با سکه‌هایی با ارزش ۱، ۵، ۶ و ۹، مبلغ ۱۱ را با کمترین تعداد سکه بسازید. اول وسوسه‌ی روش greedy (حریصانه) است: همیشه بزرگ‌ترین سکه‌ای که جا دارد را بردار. برای ۱۱ این ۹ را برمی‌دارد و بعد ۱ و ۱، یعنی سه سکه. ولی ۵ + ۶ فقط دو سکه است. greedy اینجا جواب بهینه را از دست می‌دهد. با DP:

1. state: `dp[a]` = کمترین تعداد سکه برای ساختن مبلغ `a`.
2. transition: برای هر سکه‌ی `c` که از `a` بزرگ‌تر نیست، یک راه این است که اول `a-c` را بسازیم و یک سکه‌ی `c` اضافه کنیم؛ پس `dp[a] = min(dp[a-c] + 1)` روی همه‌ی سکه‌ها.
3. پایه: `dp[0] = 0` (برای مبلغ صفر هیچ سکه‌ای نمی‌خواهیم).
4. ترتیب: `a = 1..11` از کوچک به بزرگ.
5. جواب: `dp[11]`.

چند خانه‌ی اول را با دست پر کنیم. `dp[1] = 1` (سکه‌ی ۱)، `dp[5] = 1`، `dp[6] = 1`، `dp[7] = dp[6] + 1 = 2`. و برای ۱۱: با سکه‌ی ۱ می‌شود `dp[10]+1 = 3`، با سکه‌ی ۵ می‌شود `dp[6]+1 = 2`، با سکه‌ی ۶ می‌شود `dp[5]+1 = 2`، با سکه‌ی ۹ می‌شود `dp[2]+1 = 3`. کمترین ۲ است. کد این حلقه (با آرایه‌ی `from` که آخرین سکه‌ی هر مبلغ را نگه می‌دارد تا بعداً انتخاب‌ها را بازسازی کنیم):

```go
for a := 1; a <= amount; a++ {
	table[a] = Inf
	for _, c := range coins {
		if c <= a && table[a-c]+1 < table[a] {
			table[a] = table[a-c] + 1
			from[a] = c
		}
	}
}
```

هر مبلغ را با هر سکه امتحان می‌کنیم، پس هزینه O(مبلغ × تعداد سکه‌ها) است. خروجی:

```
table: [0 1 2 3 4 1 1 2 3 1 2 2]
used : [5 6] true
```

`table` همان `dp[0]` تا `dp[11]` است و آخرین عدد، `dp[11] = 2`. `used` سکه‌های انتخاب‌شده را نشان می‌دهد: ۵ و ۶. برای سکه‌های ۴ و ۶ و مبلغ ۷ هیچ ترکیبی نیست و تابع «غیرممکن» برمی‌گرداند (`coins [4 6] amount 7 possible: false`).

## از کجا بدانیم درست است؟

تست ۳۰۰ ورودی تصادفی می‌سازد (۱ تا ۴ سکه با ارزش ۱ تا ۹، مبلغ کمتر از ۲۵) و جدول را با یک بازگشت brute force (امتحان همه‌ی حالت‌ها) مقایسه می‌کند. همچنین بررسی می‌کند سکه‌های بازسازی‌شده جمعشان برابر مبلغ باشد. همین کار را برای ۳۰۰ جدول تصادفی ارزان‌ترین مسیر هم می‌کند. تست سوم می‌گوید چهار نسخه‌ی Fibonacci (به‌جز نسخه‌ی ساده) تا n برابر ۴۰ یکسان‌اند. همه با `-race` می‌گذرند. این همان عادت {{< term "property-based-testing" "property-based" >}} قبلی است: یک روش سریع را با یک روش کند ولی بدیهی مقایسه می‌کنیم.

## تله‌ی memoization

memo فقط وقتی درست است که کلیدش همه‌ی ورودی‌هایی را داشته باشد که در جواب اثر دارند. عمداً نسخه‌ای بد نوشتم که memo را فقط با مبلغ کلید می‌زند، در حالی که جواب به مجموعه‌ی سکه‌ها هم بستگی دارد (و memo بین فراخوانی‌ها نگه داشته می‌شود):

```
bad memo, coins {1,5,6,9}, 11 -> 2
bad memo, coins {1,2},     11 -> 2 (correct: 6)
```

فراخوانی اول درست است. فراخوانی دوم با سکه‌های دیگر، همان جواب کهنه‌ی مبلغ ۱۱ را از فراخوانی اول برمی‌گرداند: ۲، در حالی که با سکه‌های ۱ و ۲ جواب درست ۶ است (پنج سکه‌ی ۲ و یک سکه‌ی ۱). همین در مورد تابع‌هایی با اثر جانبی یا ورودی پنهان (مثل زمان یا متغیر سراسری) هم صدق می‌کند: نتیجه‌ی cache‌شده اثر جانبی را رد می‌کند. و در Go، slice و map نمی‌توانند کلید map باشند، پس اگر state پیچیده است باید آن را به کلیدی قابل‌مقایسه (مثل یک struct یا رشته) تبدیل کنید.

## پیش از memoize کردن

- **زیرمسئله‌ها را بشمارید.** هزینه‌ی DP برابر تعداد stateها ضرب‌در کار هر state است، نه تعداد فراخوانی‌های کد ساده.
- **بالا‌به‌پایین یا پایین‌به‌بالا؟** اگر فقط تعداد کمی state واقعاً لازم می‌شوند، بالا‌به‌پایین کمتر کار می‌کند. اگر همه‌شان لازم‌اند یا سربار بازگشت و map را نمی‌خواهید، پایین‌به‌بالا.
- **همه‌ی ورودی‌های مؤثر در جواب را در کلید بگذارید**، مثل مثال بالا.

## تمرین

`Coins` را طوری عوض کنید که تعداد روش‌های متفاوت ساخت یک مبلغ را بشمارد (ترتیب سکه‌ها مهم نیست، یعنی `۱+۵` و `۵+۱` یکی است). کدام حلقه باید بیرونی باشد: مبلغ یا سکه؟ جوابتان را با brute force تست کنید.

## قدم بعدی

«برنامه‌ریزی پویا ۲: مسئله‌های کلاسیک». همین دستور کار را روی مسئله‌های معروف به کار می‌بریم: دنباله‌ها، زیرمجموعه‌ها و edit distance.
