در مقاله‌ی قبلی، [topological sort و وابستگی‌ها](/fa/posts/algo-topological-sort/)، یک ترتیب روی گراف جلوی کار اضافه را می‌گرفت. بعضی مسئله‌ها به شکل دیگری کار تکراری دارند: بازگشت بارها همان سؤال را می‌پرسد. {{< term "dynamic-programming" "برنامه‌ریزی پویا" >}} (DP) این را درست می‌کند. روی بازگشت، [جدول هش](/fa/posts/algo-hash-tables/) و [آرایه‌های پویا](/fa/posts/algo-dynamic-arrays/) از مقاله‌های قبل و عادت شمردن در [Big-O](/fa/posts/algo-big-o-measured/) بنا شده است.

> Go 1.26، مثال محلی، تست با `go test -race`. بار ماشین بالا بود، پس شمارش و allocation منتشر می‌کنم، نه زمان.

## Fibonacci: یک سؤال، چندین بار

```go
func FibNaive(n int, calls *int) int {
	*calls++
	if n < 2 { return n }
	return FibNaive(n-1, calls) + FibNaive(n-2, calls)
}
```

`fib(32)` و `fib(31)` هر دو به `fib(30)` نیاز دارند. این‌ها {{< term "overlapping-subproblems" "زیرمسئله‌های تکراری" >}} هستند. هزینه، به‌صورت شمارش دقیق:

```
naive  fib(35) = 9227465 calls = 29860703
```

نزدیک ۳۰ میلیون فراخوانی برای ۳۶ سؤال متفاوت. حالا {{< term "memoization" "memoize" >}} می‌کنیم: پیش از محاسبه در map نگاه کن، بعد از محاسبه ذخیره کن.

```
map    fib(35) = 9227465 calls = 69 subproblems = 34
slice  fib(35) = 9227465 calls = 69
```

۶۹ فراخوانی = 2n - 1: هر مقدار یک بار حساب می‌شود و بعد فقط خوانده می‌شود. map ۳۴ ورودی دارد (n از ۲ تا ۳۵؛ حالت‌های پایه ذخیره نمی‌شوند). نسخه‌ی slice همان ایده است با اندیس به‌جای کلید، پس {{< term "hash-table" "جست‌وجوی هش" >}} حذف می‌شود.

## پایین‌به‌بالا و حافظه‌ی O(1)

memoization بالا‌به‌پایین است: از سؤال شروع می‌کنیم و پایین می‌رویم. پایین‌به‌بالا جدول را از حالت‌های پایه پر می‌کند:

```go
t[1] = 1
for i := 2; i <= n; i++ { t[i] = t[i-1] + t[i-2] }
```

چون `t[i]` فقط به دو مقدار آخر نیاز دارد، دو متغیر کافی است. همه‌ی نسخه‌ها 9227465 برمی‌گردانند. خروجی `testing.AllocsPerRun` برای fib(35) با احتساب ساخت memo:

```
allocs map  : 7
allocs slice: 1
allocs table: 1
allocs o1   : 0
```

عمق بازگشت اینجا فقط ۳۵ است. پشته‌ی Go در صورت نیاز بزرگ می‌شود (طبق مستندات روی ۶۴ بیت به‌طور پیش‌فرض تا حدود ۱ گیگابایت)، پس عمق چند هزار مشکلی ندارد؛ حد پیش‌فرض بازگشت در Python برابر ۱۰۰۰ است که برای DP بالا‌به‌پایین در آن زبان مشکل واقعی است.

## دو ویژگی

DP وقتی کار می‌کند که مسئله زیرمسئله‌های تکراری و {{< term "optimal-substructure" "زیرساخت بهینه" >}} داشته باشد. پله‌ها (۱ یا ۲ قدم): ways(i) = ways(i-1) + ways(i-2):

```
stairs 0..8 : [1 1 2 3 5 8 13 21 34]
```

ارزان‌ترین مسیر در یک شبکه (حرکت به راست یا پایین) ادامه‌ی ارزان‌تر از دو همسایه است. شبکه‌ی ۳ در ۴ و جدول هزینه‌ها:

```
grid:   1 3 1 2 / 1 5 1 9 / 4 2 1 1
table:  [1 4 5 7]
        [2 7 6 15]
        [6 8 7 8]
brute: 8
```

خانه‌ی پایین‌راست جواب است و بازگشت ساده بدون cache هم با آن موافق است.

## دستور کار

1. **state**: آرگومان‌ها چه معنایی دارند؟ (`dp[a]` = کمترین تعداد سکه برای مبلغ `a`.)
2. **transition**: هر state چطور به state‌های کوچک‌تر وابسته است؟
3. **base case**: چه چیزی بدون بازگشت معلوم است؟
4. **order**: کدام stateها اول بیایند تا وابستگی‌ها آماده باشند؟
5. **answer**: کدام state نتیجه است؟

## مثال کامل: coin change

کمترین تعداد سکه برای مبلغ ۱۱ با سکه‌های ۱، ۵، ۶، ۹. state برابر `dp[a]`؛ transition برابر `dp[a] = min over c of dp[a-c] + 1`؛ پایه `dp[0] = 0`؛ ترتیب `a = 1..11`؛ جواب `dp[11]`. برای بازسازی انتخاب، آخرین سکه‌ی هر مبلغ را هم نگه می‌دارم:

```
table: [0 1 2 3 4 1 1 2 3 1 2 2]
used : [5 6] true
```

دو سکه: ۵ و ۶. روش greedy (بزرگ‌ترین اول) ۹ + ۱ + ۱ برمی‌داشت، یعنی سه سکه. برای سکه‌های ۴ و ۶ و مبلغ ۷ تابع می‌گوید ممکن نیست.

## تست

تست ۳۰۰ ورودی تصادفی می‌سازد (seed از ۰ تا ۲۹۹، ۱ تا ۴ سکه با ارزش ۱ تا ۹، مبلغ کمتر از ۲۵) و جدول را با بازگشت brute force مقایسه می‌کند. همچنین بررسی می‌کند سکه‌های بازسازی‌شده جمعشان برابر مبلغ باشد، و همین کار را با ۳۰۰ شبکه‌ی تصادفی انجام می‌دهد. تست سوم می‌گوید هر چهار نسخه‌ی Fibonacci تا n برابر ۴۰ یکسان‌اند. همه با `-race` می‌گذرند. این همان عادت {{< term "property-based-testing" "property-based" >}} قبلی است.

## تله‌ی memoization

memo فقط وقتی درست است که کلید همه‌ی ورودی‌های مؤثر در جواب را داشته باشد. عمداً نسخه‌ای بد نوشتم که فقط با مبلغ کلید می‌زند، در حالی که جواب به مجموعه‌ی سکه‌ها هم بستگی دارد:

```
bad memo, coins {1,5,6,9}, 11 -> 2
bad memo, coins {1,2},     11 -> 2 (correct: 6)
```

فراخوانی دوم ورودی کهنه‌ی فراخوانی اول را برگرداند. همین برای تابع‌هایی با اثر جانبی یا ورودی پنهان (زمان، متغیر سراسری) صادق است: نتیجه‌ی cache‌شده اثر جانبی را رد می‌کند. slice و map در Go نمی‌توانند کلید map باشند، پس state پیچیده را باید به کلیدی قابل‌مقایسه تبدیل کرد.

## چند نکته‌ی مهم

- زیرمسئله‌ها را بشمارید: تعداد state ضرب‌در کار هر state پیچیدگی است، نه تعداد فراخوانی کد ساده.
- وقتی stateهای کمی قابل‌دسترس‌اند بالا‌به‌پایین؛ وقتی همه‌شان لازم است یا سربار کمتر می‌خواهید پایین‌به‌بالا.
- همه‌ی ورودی‌های مؤثر در جواب را در کلید بگذارید.

## تمرین

`Coins` را طوری عوض کنید که تعداد روش‌های متفاوت ساخت یک مبلغ را بشمارد (ترتیب مهم نیست). کدام حلقه باید بیرونی باشد؟ با brute force تست کنید.
