در [برنامه‌ریزی پویا ۱: ایده و memoization](/fa/posts/algo-dynamic-programming-1/) زیرمسئله‌ها را از بالا به پایین cache کردیم. اینجا برای چهار مسئله‌ی کلاسیک جدول را از پایین به بالا پر می‌کنیم و مهم‌تر اینکه جدول را به عقب می‌خوانیم تا خود پاسخ را بسازیم، نه فقط اندازه‌اش را. شمارش‌ها مثل [Big-O با اندازه‌گیری](/fa/posts/algo-big-o-measured/) است و [جست‌وجوی دودویی](/fa/posts/algo-binary-search-invariants/) در مسئله‌ی آخر می‌آید.

> Go 1.26، مثال محلی، تست با `go test -race`. بار ماشین بالا بود، پس شمارش منتشر می‌کنم، نه زمان.

## LCS

برای دو دنباله، {{< term "longest-common-subsequence" "بلندترین زیردنباله‌ی مشترک" >}} (LCS) ترتیب را نگه می‌دارد ولی می‌تواند اقلام را رد کند. فرض کنید `t[i][j]` طول LCS برای i و j قلم اول باشد: اگر اقلام برابر بودند `t[i-1][j-1]+1` است، وگرنه بزرگ‌تر از `t[i-1][j]` و `t[i][j-1]`. این یک جدول {{< term "dynamic-programming" "برنامه‌ریزی پویا" >}} است:

```
      B D C A B A
    0 0 0 0 0 0 0
 A  0 0 0 0 1 1 1
 B  0 1 1 1 1 2 2
 C  0 1 1 2 2 2 2
 B  0 1 1 2 2 3 3
 D  0 1 2 2 2 3 3
 A  0 1 2 2 3 3 4
 B  0 1 2 2 3 4 4
LCS: BCBA len 4
```

گوشه‌ی جدول ۴ است. برای ساختن رشته از گوشه برمی‌گردیم: اگر برابر بودند قلم را خروجی می‌دهیم و قطری می‌رویم، وگرنه به سمت همسایه‌ی بزرگ‌تر. ممکن است چند پاسخ برابر باشند؛ کد من یکی را برمی‌گرداند.

## فاصله‌ی ویرایش

{{< term "edit-distance" "فاصله‌ی ویرایش" >}} درج، حذف و جایگزینی را می‌شمارد. سطر و ستون اول `0..n` هستند و هر خانه کمینه‌ی سه حرکت است:

```
       s i t t i n g
    0 1 2 3 4 5 6 7
 k  1 1 2 3 4 5 6 7
 i  2 2 1 2 3 4 5 6
 t  3 3 2 1 2 3 4 5
 t  4 4 3 2 1 2 3 4
 e  5 5 4 3 2 2 3 4
 n  6 6 5 4 3 3 2 3
distance: 3
sub k->s, keep i, keep t, keep t, sub e->i, keep n, ins g
```

بازگشت از گوشه، فهرست ویرایش‌ها را می‌دهد. هزینه: زمان و حافظه O(n*m).

## کوله‌پشتی 0/1

هر قلم یک بار برداشته می‌شود. با وزن‌های `[1 3 4 5]`، ارزش‌های `[1 4 5 7]` و ظرفیت ۷، جدول {{< term "knapsack" "کوله‌پشتی" >}} این را می‌دهد:

```
knapsack 2-D: 9 items [1 2]
```

یعنی قلم‌های ۱ و ۲ (وزن ۳ و ۴، ارزش ۴ و ۵). جدول دوبعدی فقط به سطر قبل نیاز دارد، پس به یک آرایه تبدیل می‌شود. جهت حلقه مهم است: در حلقه‌ی نزولی `d[c-w]` هنوز سطر قدیمی است (هر قلم یک بار). در حلقه‌ی صعودی قبلاً به‌روز شده و قلم دوباره استفاده می‌شود. روی این ورودی هر دو اتفاقاً ۹ می‌دهند، پس مثالی که فرق می‌کند: یک قلم با وزن ۳ و ارزش ۱۰ و ظرفیت ۹:

```
one item w=3 v=10 cap=9: correct 10 flipped 30
```

حلقه‌ی برعکس نسخه‌ی نامحدود را حل می‌کند که قلم می‌تواند تکرار شود: همان شکل کد، مسئله‌ای دیگر.

## بلندترین زیردنباله‌ی صعودی

نسخه‌ی O(n^2) هر عنصر قبلی را بررسی می‌کند. نسخه‌ی O(n log n) کوچک‌ترین دم هر طول را نگه می‌دارد و با جست‌وجوی دودویی جای هر عنصر را پیدا می‌کند. مقایسه‌ها و probeها را روی آرایه‌های تصادفی شمردم (seed برابر ۷):

```
LIS n=100   quad=16  ops=4950     fast=16  ops=331
LIS n=1000  quad=57  ops=499500   fast=57  ops=5121
LIS n=10000 quad=185 ops=49995000 fast=185 ops=68997
```

طول‌ها یکی است، ولی در n = 10,000 تعداد عملیات ۴۹,۹۹۵,۰۰۰ در برابر ۶۸,۹۹۷ است. نسخه‌ی سریع فقط طول را می‌دهد.

## متن فارسی: rune، نه بایت

رشته در Go بایت است و هر حرف فارسی در UTF-8 دو بایت. مقایسه‌ی «سلام» و «کلام» (یک حرف فرق دارد):

```
sub 0xd8->0xda, sub 0xb3->0xa9, keep 0xd9, keep 0x84, keep 0xd8, keep 0xa7, keep 0xd9, keep 0x85
bytes : 8 8 distance 2
runes : 4 4 distance 1 [sub س->ک keep ل keep ا keep م]
```

با بایت فاصله ۲ است و با {{< term "rune" "rune" >}} برابر ۱. توجه کنید که برای بعضی جفت‌ها (س و ع بایت اولشان یکی است) بایت اتفاقاً جواب درست می‌دهد و پیدا کردن این باگ را سخت می‌کند. توابع generic آرایه‌ی `[]T` می‌گیرند، پس `[]rune(s)` مشکل را حل می‌کند. نویسه‌های ترکیبی و normalization را بررسی نکردم.

## تست‌ها

تست `go test -race` با seed ثابت ۴۲ و ۳۰۰ ورودی تصادفی برای هر مسئله (تا ۱۰ قلم، الفبای کوچک) اجرا می‌شود. brute force برای LCS همه‌ی زیرمجموعه‌ها، برای فاصله‌ی ویرایش بازگشت ساده، برای کوله‌پشتی و LIS همه‌ی زیرمجموعه‌ها را امتحان می‌کند. همچنین بررسی می‌شود که هزینه‌ی script برابر فاصله است، اقلام کوله‌پشتی جا می‌شوند و جمعشان برابر بهترین مقدار است، و دو نسخه‌ی LIS یکی‌اند. همه پاس شدند.

## چطور مسئله‌ی DP را تشخیص بدهیم

1. بتوانید پاسخ را برای یک پیشوند، پسوند یا ظرفیت بگویید (state).
2. state بزرگ‌تر از کوچک‌ترها ساخته شود (رابطه‌ی بازگشتی).
3. state‌ها تکرار شوند (زیرمسئله‌های تکراری).
4. پاسخ بهینه شامل پاسخ‌های بهینه‌ی کوچک‌تر باشد.

| مسئله | زمان | حافظه |
|---|---|---|
| LCS و فاصله‌ی ویرایش | O(n*m) | O(n*m)، یا O(min(n,m)) فقط برای طول |
| کوله‌پشتی 0/1 | O(n*C) | O(n*C)، یا O(C) بدون اقلام |
| LIS | O(n^2) یا O(n log n) | O(n) |

کوله‌پشتی شبه‌چندجمله‌ای است: C یک عدد است، نه اندازه‌ی ورودی. پر کردن جدول به ترتیب وابستگی، همان [ترتیب توپولوژیک](/fa/posts/algo-topological-sort/) گراف زیرمسئله‌هاست.

## چند نکته‌ی مهم

- بازسازی پاسخ به جدول کامل نیاز دارد؛ نسخه‌های کم‌حافظه آن را از دست می‌دهند.
- جهت حلقه در جدول یک‌بعدی تعیین می‌کند چه مسئله‌ای را حل می‌کنید.
- رشته‌ی Unicode را هرگز با بایت اندیس نکنید.
- روی ورودی‌های کوچک با brute force تست کنید.

## تمرین

خود LIS را در O(n log n) با ذخیره‌ی اندیس قبلی بازسازی کنید. بعد LCS را فقط با دو سطر بنویسید و بررسی کنید طول همان است.

## قدم بعدی

DP همه‌ی گزینه‌ها را بررسی می‌کند. گاهی یک انتخاب محلی کافی است و گاهی باید انتخاب‌ها را پس بگیریم. مقاله‌ی بعدی «greedy و backtracking» است.
