فرض کنید در یک مارپیچ گیر کرده‌اید و می‌خواهید کوتاه‌ترین راه خروج را پیدا کنید. یا فرض کنید یک شبکه‌ی اجتماعی دارید و می‌پرسند «از من تا فلان آدم چند دوست فاصله است؟». یا یک پروژه با ده‌ها ماژول دارید که به هم وابسته‌اند و می‌خواهید بدانید آیا وابستگی دوری در آن هست. این سه مسئله ظاهراً هیچ ربطی به هم ندارند، ولی هر سه یک شکل دارند: چند چیز، و رابطه‌هایی میان آن‌ها. اسم این شکل {{< term "graph" "گراف" >}} است.

در [پست قبل](/fa/posts/algo-tries-union-find/) با union-find فقط می‌توانستیم بپرسیم «این دو چیز به هم وصل‌اند یا نه؟». اما نمی‌توانستیم بپرسیم از کدام راه، و با چند قدم. پیمایش گراف دقیقاً به همین سؤال‌ها جواب می‌دهد. در این پست اول می‌بینیم گراف را چطور در حافظه نگه می‌داریم، بعد دو روش پیمایش را یاد می‌گیریم (BFS و DFS) و در آخر می‌بینیم با آن‌ها چه چیزهایی را می‌شود حل کرد. پیمایش گراف از [queue و stack](/fa/posts/algo-stacks-queues-deques/) استفاده می‌کند و هزینه‌اش را هم به همان روشی که در [تحلیل Big-O با اندازه‌گیری واقعی](/fa/posts/algo-big-o-measured/) دیدیم، با شمارش، اندازه می‌گیریم.

> همه‌ی خروجی‌های این پست را با Go 1.27 دوباره اجرا کردم (`go.mod` مثال هنوز `go 1.26` را اعلام می‌کند)، مثال محلی است و تست‌هایش با `go test -race` سبز است. زمان‌گیری منتشر نمی‌کنم، چون ماشین شلوغ بود؛ فقط شمارش و بایت می‌بینید، که در هر اجرا یکی‌اند.

## گراف چیست؟

گراف دو چیز بیشتر نیست: یک مجموعه **رأس** (vertex) و یک مجموعه **یال** (edge). رأس‌ها «چیزها»ی ما هستند (یک آدم، یک شهر، یک خانه از مارپیچ، یک ماژول) و هر یال یک رابطه میان دو رأس است (دوستی، جاده، دیوارنداشتن، وابستگی). اگر رابطه دوطرفه باشد، مثل دوستی یا جاده‌ی دوطرفه، یال را **بدون جهت** می‌گوییم. اگر یک‌طرفه باشد، مثل «ماژول A به B وابسته است»، یال **جهت‌دار** است.

گرافی که در همه‌ی مثال‌های این پست (به‌جز چند مورد) می‌بینید این است. هشت رأس با شماره‌های ۰ تا ۷ و هشت یال:

```
        3
        |
    0 — 1 — 4
    |       |
    2       6 — 7
    |       |
    5 ——————+
```

یال‌ها اینها هستند: 0-1، 0-2، 1-3، 1-4، 2-5، 4-6، 5-6 و 6-7. این گراف بدون جهت است، یعنی 0-1 هم یعنی از ۰ می‌شود به ۱ رفت و هم از ۱ به ۰.

## گراف را چطور در حافظه نگه داریم؟

سه راه رایج هست. برای اینکه فرق‌شان را با عدد ببینید، یک گراف تصادفی بدون جهت با ۱۰۰۰ رأس و ۵۰۰۰ یال ساختم (با seed برابر ۴۲ که هر بار همان گراف بیاید) و اندازه‌ی هر ساختار را روی ماشین ۶۴ بیتی حساب کردم:

```
adjacency list: 104000 bytes (exact elements), 132640 bytes (with append capacity)
adjacency matrix [][]bool: 1024000 bytes; as bits: 125000 bytes
edge list [][2]int: 80000 bytes; with int32: 40000 bytes
```

اول **لیست یال** (edge list): فقط فهرست جفت‌ها، یعنی `[][2]int`. کوچک‌ترین است (۸۰٬۰۰۰ بایت)، ولی برای پیدا کردن همسایه‌های یک رأس باید کل فهرست را بگردید.

دوم **ماتریس مجاورت**: یک جدول V×V که خانه‌ی `[u][v]` می‌گوید «آیا یال u-v هست؟». جواب این سؤال در زمان ثابت می‌آید، ولی جدول همیشه V به توان ۲ جا می‌گیرد، چه ۵۰۰۰ یال داشته باشیم چه یکی: اینجا حدود یک مگابایت (حتی اگر هر خانه را یک بیت بگیریم، ۱۲۵٬۰۰۰ بایت). پس فقط برای گراف چگال می‌ارزد، یا وقتی سؤال «آیا این یال هست؟» را خیلی زیاد می‌پرسید.

سوم {{< term "adjacency-list" "لیست مجاورت" >}}: برای هر رأس، فهرست همسایه‌هایش. در Go همان `[][]int` است. برای گراف بالا حدود V + 2E عدد نگه می‌دارد، یعنی ۱۰۴٬۰۰۰ بایت برای خود عنصرها. (هر یال بدون جهت در فهرست هر دو سرش می‌آید، برای همین ۲E.) اگر ظرفیتی را که `append` از قبل کنار گذاشته هم بشماریم، ۱۳۲٬۶۴۰ بایت می‌شود. پیمایش گراف مدام می‌پرسد «همسایه‌های این رأس کیست؟» و لیست مجاورت دقیقاً همین را سریع می‌دهد. برای همین بقیه‌ی پست با لیست مجاورت کار می‌کند:

```go
type Graph struct {
	adj      [][]int // adj[u] = همسایه‌های u
	directed bool
}

func (g *Graph) AddEdge(u, v int) {
	g.adj[u] = append(g.adj[u], v)
	if !g.directed {
		g.adj[v] = append(g.adj[v], u)
	}
}
```

برای گراف بدون جهت، `AddEdge` یال را در هر دو فهرست می‌نویسد. برای گراف جهت‌دار فقط در فهرست مبدأ.

## BFS: اول نزدیک‌ترین‌ها

حالا سؤال اول: کوتاه‌ترین راه از رأس ۰ به بقیه. فکرش را بکنید که سنگی را وسط آب می‌اندازید: موج اول فقط نقطه‌های نزدیک را می‌گیرد، بعد موج دوم، بعد سوم. {{< term "bfs" "جست‌وجوی breadth-first" >}} (BFS، «جست‌وجوی سطح‌به‌سطح») همین موج است. اول همه‌ی همسایه‌های مبدأ، بعد همسایه‌های همسایه‌ها، و همین‌طور.

برای اینکه ترتیب را حفظ کند از یک {{< term "queue" "queue" >}} (صف) استفاده می‌کند: هر که زودتر وارد شود، زودتر بیرون می‌آید. الگوریتم این است: مبدأ را با فاصله‌ی ۰ در صف بگذار. تا وقتی صف خالی نشده، اولین رأس را بردار و همسایه‌هایی را که هنوز ندیده‌ای با فاصله‌ی «فاصله‌ی این رأس + ۱» به ته صف اضافه کن.

با دست روی گراف خودمان انجام می‌دهیم:

| رأسی که برداشتیم | همسایه‌های تازه | صف بعد از آن | فاصله‌هایی که ثبت شد |
|---|---|---|---|
| (شروع) | | [0] | 0 ← 0 |
| 0 | 1، 2 | [1, 2] | 1 ← 1، 2 ← 1 |
| 1 | 3، 4 | [2, 3, 4] | 3 ← 2، 4 ← 2 |
| 2 | 5 | [3, 4, 5] | 5 ← 2 |
| 3 | هیچ | [4, 5] | |
| 4 | 6 | [5, 6] | 6 ← 3 |
| 5 | هیچ (6 را قبلاً دیده‌ایم) | [6] | |
| 6 | 7 | [7] | 7 ← 4 |
| 7 | هیچ | [] | |

دقت کنید که صف همیشه اول رأس‌های فاصله‌ی ۱ را دارد، بعد ۲، بعد ۳. برای همین اولین باری که به رأسی می‌رسیم، از کوتاه‌ترین راه (بر حسب تعداد یال) رسیده‌ایم. این ایده‌ی اصلی BFS است. کدش همین را می‌گوید:

```go
dist[src] = 0
queue := []int{src}
for len(queue) > 0 {
	u := queue[0]; queue = queue[1:]
	for _, v := range g.adj[u] {
		if dist[v] == -1 { // هنوز ندیده‌ایم
			dist[v], parent[v] = dist[u]+1, u
			queue = append(queue, v)
		}
	}
}
```

`dist` فاصله است و مقدار `-1` یعنی «هنوز ندیده‌ام». `parent[v]` می‌گوید به `v` از کدام رأس رسیده‌ایم. خروجی دمو روی همان گراف:

```
BFS dist from 0: [0 1 1 2 2 2 3 4]
path 0 -> 7: [0 1 4 6 7]
```

خط اول دقیقاً ستون آخر جدول بالا است: رأس ۰ فاصله‌ی ۰، رأس‌های ۱ و ۲ فاصله‌ی ۱، رأس‌های ۳ و ۴ و ۵ فاصله‌ی ۲، رأس ۶ فاصله‌ی ۳ و رأس ۷ فاصله‌ی ۴. خط دوم خود مسیر است. برای ساختنش از مقصد شروع می‌کنیم و با `parent` عقب می‌رویم: پدر ۷ رأس ۶ است، پدر ۶ رأس ۴، پدر ۴ رأس ۱ و پدر ۱ رأس ۰. این را برعکس می‌کنیم و می‌شود `0 → 1 → 4 → 6 → 7`.

برای اطمینان از درستی، یک تست فاصله‌های BFS را روی ۳۰۰ گراف کوچک تصادفی (جهت‌دار و بدون جهت، با رأس‌های غیرقابل‌دسترس) با الگوریتم Floyd-Warshall مقایسه می‌کند، و طول مسیرها را هم می‌سنجد. این تست سبز است. (Floyd-Warshall یک روش کند ولی ساده‌ی محاسبه‌ی فاصله‌ی همه‌ی جفت‌هاست که فقط برای مقایسه از آن استفاده کردم.)

## DFS: تا جای ممکن عمیق

روش دوم برعکس موج است. فکر کنید در مارپیچ یک مسیر را انتخاب می‌کنید و تا بن‌بست می‌روید؛ بعد برمی‌گردید تا نزدیک‌ترین دوراهی و راه بعدی را امتحان می‌کنید. {{< term "dfs" "جست‌وجوی depth-first" >}} (DFS، «جست‌وجوی عمق‌اول») همین است. به‌جای صف از {{< term "stack" "stack" >}} (پشته) استفاده می‌کند: آخرین چیزی که وارد شده اول بیرون می‌آید. نسخه‌ی بازگشتی نیازی به stack جداگانه ندارد، چون خود فراخوانی‌های تو در تو همان stack است، و کوتاه است:

```go
visit = func(u int) {
	seen[u] = true
	order = append(order, u)
	for _, v := range g.adj[u] {
		if !seen[v] {
			visit(v)
		}
	}
}
```

روی گراف خودمان از ۰ شروع می‌کنیم: اول همسایه‌ی ۱ را می‌رویم. از ۱ اول به ۳ می‌رویم که بن‌بست است (تنها همسایه‌اش ۱ است) و برمی‌گردیم. بعد ۴، از آنجا ۶، از ۶ اول ۵ و از ۵ به ۲، که همسایه‌هایش (۰ و ۵) را دیده‌ایم. برمی‌گردیم تا ۶ و بعد ۷. ترتیب دیدن رأس‌ها می‌شود `0 1 3 4 6 5 2 7`.

نسخه‌ی غیربازگشتی یک stack صریح دارد. ترتیب همسایه‌هایی که روی stack می‌گذاریم مهم است، چون stack آخری را اول برمی‌دارد. دمو هر دو حالت را می‌زند:

```
DFS recursive : [0 1 3 4 6 5 2 7]
DFS iterative (pushed in order)  : [0 2 5 6 7 4 1 3]
DFS iterative (pushed reversed)  : [0 1 3 4 6 5 2 7]
```

خط اول همان ترتیبی است که با دست رفتیم. در خط دوم همسایه‌ها را به ترتیب روی stack گذاشتم؛ پس از ۰ اول ۲ برداشته می‌شود نه ۱ و ترتیب دیگری درمی‌آید. این ترتیب هم یک DFS معتبر است (فقط همسایه‌ها را از آخر به اول می‌رود). در خط سوم همسایه‌ها را معکوس push کردم و دقیقاً ترتیب بازگشتی درآمد. یک تست این برابری را روی ۲۰۰ گراف تصادفی بررسی می‌کند.

یک نکته درباره‌ی عمق: نسخه‌ی بازگشتی به‌ازای هر رأس روی مسیر یک فریم نگه می‌دارد. در Go stack هر goroutine در صورت نیاز بزرگ می‌شود، و یک تست در همین مثال DFS بازگشتی را روی یک گراف مسیری با ۱٬۰۰۰٬۰۰۰ رأس اجرا می‌کند و بی‌مشکل تمام می‌شود. در Python این‌طور نیست: حد پیش‌فرض عمق بازگشت ۱۰۰۰ فریم است و یک تابع بازگشتی ساده با عمق ۵۰۰۰ در همین ماشین خطای `RecursionError: maximum recursion depth exceeded` می‌دهد (دوباره اجرا کردم). در Python از stack صریح استفاده کنید.

## BFS یا DFS؟

هر دو هر رأس قابل‌دسترس را دقیقاً یک بار می‌بینند، پس هزینه‌شان یکی است. تفاوت در چیزی است که می‌خواهید. اگر «کوتاه‌ترین مسیر بر حسب تعداد یال» می‌خواهید، BFS. اگر فقط می‌خواهید «همه‌چیز را ببینید» و ساختار را کشف کنید (مؤلفه‌ها، دور، ترتیب وابستگی)، DFS معمولاً ساده‌تر است، چون راه برگشتنش (بازگشت) آماده است. در ادامه هر دو را در کار می‌بینیم.

## با پیمایش چه چیزهایی را می‌شود حل کرد؟

**مؤلفه‌های همبند.** گاهی گراف از چند تکه‌ی جدا از هم تشکیل شده، مثل چند گروه دوستی که با هم ارتباطی ندارند. هر تکه را یک {{< term "connected-component" "مؤلفه‌ی همبند" >}} می‌گوییم. برای شمردنشان از هر رأسی که هنوز ندیده‌ایم یک پیمایش شروع می‌کنیم؛ هر پیمایش یک مؤلفه را کامل برچسب می‌زند. دمو روی ۹ رأس با یال‌های 0-1، 1-2، 3-4، 5-6، 6-7 و 7-5 (رأس ۸ تنها است) این را می‌دهد:

```
components: 4 [0 0 0 1 1 2 2 2 3]
```

چهار مؤلفه: {۰، ۱، ۲}، {۳، ۴}، {۵، ۶، ۷} و {۸}. عدد جایگاه i برچسب مؤلفه‌ی رأس i است. یک تست این برچسب‌ها را روی ۲۰۰ گراف تصادفی با union-find کوچکی که خودم نوشته‌ام مقایسه می‌کند و هر دو یک گروه‌بندی می‌دهند.

**پیدا کردن دور.** در گراف بدون جهت، اگر هنگام پیمایش به رأسی برسیم که قبلاً دیده‌ایم و آن رأس همان پدری نیست که از آن آمده‌ایم، یعنی دور داریم. اما در گراف جهت‌دار این کافی نیست: دو مسیر مختلف می‌توانند به یک رأس برسند بی‌آنکه دوری باشد (مثلاً 0→1→2 و 0→2). راه درست DFS با سه رنگ است. رأس تازه **سفید** است، رأسی که الان روی مسیر فعلی DFS است **خاکستری**، و رأسی که کارش کاملاً تمام شده **سیاه**. دور دقیقاً وقتی هست که از یک رأس به رأس خاکستری برسیم، چون یعنی به جایی برگشته‌ایم که هنوز در راه رفتن از آن بودیم:

```
directed  0->1->2, 0->2, 2->3 has cycle: false
directed  0->1->2->0 has cycle: true
undirected path 0-1-2 has cycle: false
undirected triangle has cycle: true
```

خط اول همان مثال دو مسیر است: به ۲ از دو راه می‌رسیم، ولی هیچ‌وقت به رأس خاکستری برنمی‌خوریم، پس دور نیست. در خط دوم از ۲ یال به ۰ برمی‌گردد که هنوز خاکستری است، پس دور هست. دو خط آخر همین سؤال را برای گراف بدون جهت می‌پرسند: یک مسیر دور ندارد و یک مثلث دارد. تست‌ها نسخه‌ی جهت‌دار را با الگوریتم Kahn برای topological sort مقایسه می‌کنند (گراف جهت‌دار دور ندارد اگر و فقط اگر Kahn همه‌ی رأس‌ها را بردارد) و نسخه‌ی بدون جهت را با این قاعده که گراف بدون جهتِ بی‌دور حداکثر V منهای تعداد مؤلفه‌ها یال دارد. (در پست‌های بعدی به topological sort می‌رسیم.)

**گراف دوبخشی.** گاهی می‌خواهیم رأس‌ها را به دو گروه تقسیم کنیم، طوری که هر یال دو سرش در دو گروه متفاوت باشد (مثلاً «کاربرها» و «محصول‌ها»). برای این کار با BFS رأس‌ها را رنگ می‌کنیم: مبدأ ۰، همسایه‌هایش ۱، همسایه‌های آن‌ها دوباره ۰ و همین‌طور. اگر یالی پیدا شود که دو سرش هم‌رنگ است، چنین تقسیمی ممکن نیست و گراف {{< term "bipartite-graph" "دوبخشی" >}} نیست.

```
square bipartite: true [0 1 0 1]
triangle bipartite: false
```

مربع (۰-۱-۲-۳-۰) را می‌شود به `{0, 2}` و `{1, 3}` تقسیم کرد. مثلث را نه: سه رأسِ دو‌به‌دو متصل را نمی‌شود با دو رنگ طوری رنگ کرد که هیچ دو همسایه‌ای هم‌رنگ نباشند.

## یک شبکه‌ی خانه‌ها هم گراف است

همیشه لازم نیست گراف را صریح بسازید. در یک جدول، هر خانه یک رأس است و چهار همسایه‌اش (بالا، پایین، چپ، راست) یال‌هایش. اینجا دو مسئله‌ی معروف را حل می‌کنیم.

اول شمردن «جزیره»ها: گروه‌هایی از خانه‌های `#` که کنار هم هستند. از هر `#` ندیده شروع می‌کنیم، با DFS همه‌ی `#`های متصل را پیدا می‌کنیم و با یک حرف برچسب می‌زنیم (به این کار flood fill می‌گویند، مثل ابزار «سطل رنگ» در برنامه‌های نقاشی). ورودی دمو این جدول است:

```
##..#..
#...#..
..#...#
..##.##
```

و خروجی، با برچسب هر جزیره:

```
islands: 4
aa..b..
a...b..
..c...d
..cc.dd
```

جزیره‌ی `a` سه خانه‌ی بالا-چپ، `b` دو خانه‌ی ستون بالا، `c` سه خانه‌ی وسط-پایین و `d` سه خانه‌ی گوشه‌ی راست-پایین است. (خانه‌های مورب به هم وصل حساب نمی‌شوند، فقط چهار جهت.)

دوم، خود مارپیچ. چون همه‌ی قدم‌ها هزینه‌ی یکسان دارند، BFS کوتاه‌ترین راه را می‌دهد. در ورودی `S` شروع است، `E` خروج و `#` دیوار:

```
S.#.....
.##.###.
....#...
###.#.#.
....#.#E
```

خروجی دمو اولین رسیدن BFS به `E` را با `*` نشان می‌دهد:

```
maze shortest path: 15 steps
S.#*****
*##*###*
****#..*
###.#.#*
....#.#E
```

یعنی ۱۵ قدم: از `S` به پایین و راست تا ردیف سوم، بالا به ردیف اول، راست تا ستون آخر و پایین تا `E`. هیچ راه کوتاه‌تری وجود ندارد، چون BFS سطح‌به‌سطح رفته و اولین بار که به `E` رسیده، کوتاه‌ترین است.

## چرا هزینه O(V+E) است؟

تا اینجا گفتم «هر رأس یک بار دیده می‌شود». حالا بشماریم. گراف‌های تصادفی ساختم که تعداد یال‌هایشان سه برابر تعداد رأس‌ها است (seed برابر ۷)، BFS را از هر رأس ندیده شروع کردم تا همه‌ی گراف پوشش داده شود، و شمردم چند رأس از صف بیرون آمد و چند بار یال بررسی شد:

```
   V       E   vertices  edge checks  2E   V+2E
   1000    3000      1000         6000      6000      7000
  10000   30000     10000        60000     60000     70000
 100000  300000    100000       600000    600000    700000
1000000 3000000   1000000      6000000   6000000   7000000
```

ستون «vertices» دقیقاً برابر V است: هر رأس یک بار از صف بیرون می‌آید. ستون «edge checks» دقیقاً برابر 2E است: هر یال بدون جهت از هر دو سرش یک بار نگاه می‌شود. پس کل کار V + 2E است که یعنی O(V+E) (ضریب ۲ در نماد Big-O نمی‌آید). گراف ده برابر بزرگ‌تر، کار ده برابر. این شمارش برای DFS هم همین است؛ یک تست دیگر آن را برای DFS تأیید می‌کند.

## جاهایی که پیمایش خراب می‌شود

- **رأس را هنگام وارد کردن به صف علامت بزنید، نه هنگام بیرون آوردن.** وگرنه رأسی که هنوز نوبتش نرسیده ممکن است از چند همسایه‌اش دیده شود و چندبار وارد صف شود. صف بی‌دلیل بزرگ می‌شود و کار اضافه انجام می‌دهید. (در `dist[v] == -1` همین کار را می‌کنیم: فاصله‌ی ثبت‌شده یعنی علامت خورده.)
- **فاصله‌ی BFS فقط تعداد یال‌ها است.** اگر یال‌ها وزن دارند (جاده‌ی ۵ کیلومتری و جاده‌ی ۵۰ کیلومتری)، کم‌یال‌ترین مسیر لزوماً کوتاه‌ترین نیست. آن مسئله جواب دیگری دارد.
- **DFS غیربازگشتی فقط با push معکوس با بازگشتی هم‌ترتیب است.** اگر ترتیب برایتان مهم است (مثلاً در یک تست)، این را در نظر بگیرید.
- **دور در گراف جهت‌دار سه رنگ می‌خواهد، نه دو.** با «دیده/ندیده» ساده، مثال 0→1→2 و 0→2 را اشتباهاً دور می‌گیرید.
- **ماتریس مجاورت برای گراف خلوت حافظه هدر می‌دهد.** برای همین ۱۰۰۰ رأس و ۵۰۰۰ یال حدود یک مگابایت شد، در برابر ۱۰۴ کیلوبایتِ لیست مجاورت.

## تمرین

topological sort را اضافه کنید: DFS سه‌رنگ را به کار ببرید، هر رأس را وقتی سیاه شد به یک لیست اضافه کنید و لیست را در آخر معکوس کنید. بررسی کنید که همه‌ی یال‌ها رو به جلو باشند، و اگر گراف دور داشت خطا بدهد.

## قدم بعدی

«کوتاه‌ترین مسیر و Dijkstra». BFS فاصله را بر حسب تعداد یال می‌شمارد؛ وقتی یال‌ها وزن داشته باشند همان شمارش خراب می‌شود و به الگوریتم دیگری نیاز داریم.
