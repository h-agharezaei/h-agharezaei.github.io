در مقاله‌ی قبلی، [لیست پیوندی و چرا کم‌کاربرد است](/fa/posts/algo-linked-lists/)، یک map و یک لیست با هم کش LRU ساختند. map بود که کلید را بدون پیمایش پیدا می‌کرد. این بار همان بخش را خودمان می‌سازیم. {{< term "hash-table" "جدول هش" >}} ساختار پشت `map` در Go است که در [Slice، Map و String در Go](/fa/posts/go-slices-maps-strings/) دیدیم. ایده‌ی رشد را از [آرایه‌ی پویا و slice از درون](/fa/posts/algo-dynamic-arrays/) می‌گیریم.

> Go 1.26، macOS arm64، مثال محلی. عددها تعداد خانه‌های بررسی‌شده‌اند و پس قطعی‌اند؛ زمان‌سنجی منتشر نکردم.

## طراحی

یک `Map[K comparable, V any]` جنریک که تابع hash را از بیرون می‌گیرد. من **open addressing** با {{< term "linear-probing" "probe خطی" >}} را انتخاب کردم: یک آرایه‌ی تخت از خانه‌ها، و کلید به خانه‌ی `hash & (len-1)` می‌رود یا اگر پُر بود به اولین خانه‌ی آزاد بعدی. روش دیگر **chaining** است: هر خانه یک لیست از عنصرها دارد. حذف در chaining ساده‌تر است، اما هر عنصر یک node جدا است. آن را پیاده نکردم، پس چیزی درباره‌اش اندازه نگرفتم.

```go
type slot[K comparable, V any] struct {
	key K
	val V
	st  state // empty, full or tomb
}

func (m *Map[K, V]) find(k K) int {
	mask := uint64(len(m.slots) - 1)
	i := m.hash(k) & mask
	for {
		m.Probes++
		s := &m.slots[i]
		switch {
		case s.st == empty:
			return -1
		case s.st == full && s.key == k:
			return int(i)
		}
		i = (i + 1) & mask
	}
}
```

طول آرایه توان دو است، پس یک mask جای باقی‌مانده را می‌گیرد. `Probes` هر خانه‌ای را که نگاه می‌کنیم می‌شمارد. API شامل `Get`، `Put`، `Delete`، `Len` و `Range` است.

## رشد و ضریب بار

اگر عنصرهای زنده به‌علاوه‌ی tombstoneها از ۷۵٪ خانه‌ها بیشتر شوند، `rehash` آرایه‌ی تازه می‌سازد و همه‌ی عنصرهای زنده را دوباره درج می‌کند. فقط وقتی دو برابر می‌کند که عنصرهای واقعی بیش از حدود یک‌سوم خانه‌ها را پر کرده باشند؛ وگرنه فقط tombstoneها را دور می‌ریزد. هر rehash از O(n) است اما نادر است، پس درج {{< term "amortized-analysis" "سرشکن‌شده" >}} O(1) است.

## حذف: روش ساده شکست می‌خورد

اگر `Delete` فقط خانه را خالی کند، کلیدی که به‌خاطر برخورد جلوتر رفته بود پیدا نمی‌شود، چون `find` در اولین خانه‌ی خالی می‌ایستد. این را در `DeleteNaive` نوشتم و با hashی که همه‌چیز را به یک خانه می‌فرستد تستش کردم:

```
--- FAIL: TestNaiveDeleteBreaksChain (0.00s)
    table_test.go:43: key 2 lost after deleting key 1 (Get returned "", false)
```

راه‌حل {{< term "tombstone" "tombstone" >}} است: خانه را «حذف‌شده» علامت بزن، probe از رویش رد شود و `Put` بعدی بتواند از آن استفاده کند. همین تست با `Delete` واقعی سبز است. این تست فقط با `SHOW_BUG=1` اجرا می‌شود.

## تست در برابر map داخلی

یک تست property-style با seed ثابت ۴۲، ۳۰۰٬۰۰۰ فراخوانی تصادفی `Put`، `Delete` و `Get` را هم روی جدول من و هم روی `map` در Go اجرا می‌کند، بعد از هر قدم نتیجه‌ها و `Len` را مقایسه می‌کند و در پایان کل محتوا را با `Range` می‌سنجد. هم با FNV-1a (`hash/fnv`) و هم با hash افتضاح اجرا می‌شود و زیر `go test -race` سبز است.

## hash خوب در برابر hash افتضاح

۱۰۰٬۰۰۰ کلید تصادفی (seed ثابت)، FNV-1a در برابر hashی که برای همه‌ی کلیدها ۷ برمی‌گرداند. شمارش Put شامل جست‌وجو و درج است:

```
fnv-1a       put probes 733778 (7.3/op) get probes 130719 (1.3/op) slots 262144
all-collide  put probes 10000100000 (100001.0/op) get probes 5000050000 (50000.5/op)
```

با hash مناسب هر جست‌وجو حدود ۱٫۳ خانه را لمس می‌کند. وقتی همه‌ی کلیدها {{< term "hash-collision" "برخورد" >}} می‌کنند جدول یک رشته‌ی طولانی می‌شود: `Get` موفق به‌طور متوسط ۵۰٬۰۰۰ خانه را می‌بیند، نصف n، پیمایش خطی. جدول فقط وقتی خوب است که برخوردها کم باشند.

## ضریب بار و طول probe

جدولی ثابت با ۱۳۱٬۰۷۲ خانه، بدون رشد، با کلیدهای تصادفی تا {{< term "load-factor" "ضریب بار" >}}های مختلف پر شد:

| بار | probe برای یافتن | probe برای نیافتن |
|---|---|---|
| ۲۵٪ | ۱٫۱۷ | ۱٫۳۹ |
| ۵۰٪ | ۱٫۵۰ | ۲٫۵۰ |
| ۷۵٪ | ۲٫۵۴ | ۸٫۸۳ |
| ۹۰٪ | ۵٫۶۵ | ۵۷٫۷۱ |
| ۹۵٪ | ۹٫۸۴ | ۱۷۷٫۲۲ |

جست‌وجوی ناموفق از همه سریع‌تر بد می‌شود، چون باید تا یک خانه‌ی خالی برود. این با برآوردهای کتاب‌های درسی برای probe خطی (حدود ۱٫۵ و ۲٫۵ در نیمه‌پُر) جور است و دلیل رشد در ۷۵٪ است.

## ترتیب پیمایش

`Range` من خانه‌ها را می‌گردد، پس ترتیب از hash و تاریخچه‌ی درج تعیین می‌شود. با درج ۰ تا ۷، در دو اجرا ترتیب جدول من یکی بود و map در Go هر بار فرق داشت:

```
mine: [5 4 7 6 1 0 3 2] builtin: [7 0 1 2 3 4 5 6]
mine: [5 4 7 6 1 0 3 2] builtin: [2 3 4 5 6 7 0 1]
```

Go عمداً تصادفی می‌کند. درباره‌ی انتخاب hasher، [Go یا Rust؟ هرکدام برای چه کاری](/fa/posts/go-vs-rust-when-to-use/) hasher پیش‌فرض Rust را با یک FNV ساده عوض کرد و benchmark شمارش کلمه سریع‌تر شد.

## چند نکته‌ی مهم

- کلید باید comparable و قابل hash باشد. اگر hash کلید به چیزی وابسته باشد که بعداً تغییرش می‌دهید، عنصر در خانه‌ی اشتباه می‌ماند و گم می‌شود. این را نشان ندادم؛ کلیدها را immutable بدانید.
- tombstoneها در بار حساب می‌شوند، وگرنه جدولِ پر از حذف از آن‌ها پُر می‌شود.
- hash قابل‌پیش‌بینی به کسی اجازه می‌دهد کلیدهای هم‌برخورد بسازد؛ برای ورودی نامطمئن از hash اسباب‌بازی استفاده نکنید.
- جدول من برای نوشتن هم‌زمان امن نیست.

## تمرین

نسخه‌ی chaining را با همان API پیاده کنید و همان تست property را اجرا کنید. بعد طول متوسط زنجیره را با طول probe در بار ۷۵٪ مقایسه کنید. اول برنده را حدس بزنید.
