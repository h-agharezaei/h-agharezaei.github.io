فرض کنید یک اورژانس بیمارستان را اداره می‌کنید. بیمارها به ترتیب ورود می‌رسند، ولی نفر بعدی را ترتیب ورود تعیین نمی‌کند، شدت حالش تعیین می‌کند. هر وقت یک پزشک آزاد شد، باید بتوانید فوری‌ترین بیمار را از میان همه‌ی منتظرها پیدا کنید و هر لحظه بیمار تازه‌ای هم می‌رسد. در برنامه‌نویسی هم این الگو زیاد پیش می‌آید: کار فوری‌تر، کوتاه‌ترین فاصله، بزرگ‌ترین امتیاز. صفی که ترتیبش با اهمیت آیتم‌ها تعیین می‌شود نه با زمان ورود، {{< term "priority-queue" "priority queue" >}} (صف اولویت) نام دارد.

[صف و stack](/fa/posts/algo-stacks-queues-deques/) ترتیب ورود را می‌دانستند و همین. برای صف اولویت دو راه ساده هست، و هر دو کند است: آیتم‌ها را نامرتب نگه دارید و هر بار کل لیست را برای پیدا کردن کوچک‌ترین بگردید (n قدم)، یا لیست را همیشه مرتب نگه دارید و هر آیتم تازه را سر جایش بگذارید (باز هم تا n جابه‌جایی). ساختاری که هر دو کار را در حدود log n قدم انجام می‌دهد {{< term "binary-heap" "heap دودویی" >}} است، و تقریباً همه‌ی صف‌های اولویت روی آن ساخته می‌شوند. heap در یک slice معمولی زندگی می‌کند، همان که در [آرایه‌ی پویا و slice از درون](/fa/posts/algo-dynamic-arrays/) دیدیم. کانتینرش از [Generics در Go](/fa/posts/go-generics/) استفاده می‌کند و هزینه‌ها را مثل [تحلیل Big-O با اندازه‌گیری واقعی](/fa/posts/algo-big-o-measured/) با {{< term "big-o" "Big-O" >}} می‌گوییم.

> Go 1.27، مثال محلی، برای این پست دوباره اجرا شده. عددهای زیر تعداد عملیات هستند (تعداد فراخوانی تابع مقایسه‌ی `less`)، پس قطعی‌اند و به شلوغی ماشین بستگی ندارند. زمان واقعی منتشر نمی‌کنم.

## یک قاعده‌ی ساده: والد از فرزندانش بزرگ‌تر نیست

heap یک درخت است که هر گره‌اش حداکثر دو فرزند دارد، و فقط یک قاعده را رعایت می‌کند: **هر والد از هر دو فرزندش کوچک‌تر یا مساوی است.** این را مثل یک {{< term "invariant" "invariant" >}} (چیزی که باید همیشه برقرار بماند) در نظر بگیرید. نتیجه‌اش این است که کوچک‌ترین عنصر همیشه بالای درخت است؛ چون هر مسیری از ریشه به پایین فقط بزرگ‌تر می‌شود.

دقت کنید که این یعنی heap مرتب نیست. بین دو شاخه‌ی مختلف هیچ قاعده‌ای نیست؛ فقط ریشه تضمین‌شده است. همین کم‌توقعی است که نگه‌داشتنش را ارزان می‌کند.

یک مثال با شش عدد:

```
        2
      /   \
     5     3
    / \   /
   9   6 8
```

جالب اینجاست که برای ذخیره‌ی این درخت اشاره‌گر لازم نیست. درخت را سطح به سطح، از چپ به راست، در یک آرایه می‌نویسیم:

```
index:  0  1  2  3  4  5
value: [2, 5, 3, 9, 6, 8]
```

فرزندان خانه‌ی `i` در `2i+1` و `2i+2` هستند و والدش در `(i-1)/2` (تقسیم صحیح). مثلاً فرزندان خانه‌ی ۱ (مقدار ۵) خانه‌های ۳ و ۴ هستند (۹ و ۶) و والد خانه‌ی ۵ (مقدار ۸) خانه‌ی ۲ است (مقدار ۳). درخت هم همیشه «کامل» است، یعنی سطح‌ها از بالا پر می‌شوند و آخرین سطح از چپ پر می‌شود، پس آرایه هیچ‌وقت حفره ندارد.

یک نتیجه‌ی مهم: درختی با n گره حدود log₂ n سطح دارد. برای یک میلیون گره حدود ۲۰ سطح. هر کاری که فقط یک مسیر از ریشه تا برگ را طی کند، حداکثر حدود ۲۰ قدم لازم دارد.

## اضافه کردن: بالا بردن

برای اضافه کردن عدد ۱ به heap بالا: آن را در اولین خانه‌ی خالی، یعنی ته آرایه، می‌گذاریم. این کار شاید قاعده را بشکند، ولی فقط در یک جا: بین عدد تازه و والدش. پس با والد مقایسه می‌کنیم و اگر کوچک‌تر بود جایشان را عوض می‌کنیم، و همین را تا جایی که لازم باشد بالاتر ادامه می‌دهیم:

```
[2, 5, 3, 9, 6, 8, 1]     ۱ در خانه‌ی ۶؛ والدش خانه‌ی ۲ (مقدار ۳): ۱ < ۳، جابه‌جا
[2, 5, 1, 9, 6, 8, 3]     حالا ۱ در خانه‌ی ۲؛ والدش خانه‌ی ۰ (مقدار ۲): ۱ < ۲، جابه‌جا
[1, 5, 2, 9, 6, 8, 3]     ۱ به ریشه رسید؛ تمام
```

چرا درست است؟ وقتی عدد تازه با والدش جابه‌جا می‌شود، والد (که بزرگ‌تر بود) پایین می‌آید و جای عدد تازه را می‌گیرد. او قبلاً از هر چیزی زیر خودش کوچک‌تر بود، پس هنوز هم هست. قاعده در آن نقطه برقرار می‌ماند و فقط یک سطح بالاتر ممکن است دوباره شکسته باشد.

## برداشتن کوچک‌ترین: پایین بردن

برداشتن کوچک‌ترین، یعنی ریشه، سوراخی بالای درخت می‌گذارد. آن را با آخرین عنصر آرایه پر می‌کنیم، که جای ساختار را درست نگه می‌دارد، ولی حالا یک عدد احتمالاً بزرگ بالاست. باید پایین برود. هر بار با **کوچک‌ترِ دو فرزندش** مقایسه می‌شود و اگر از او بزرگ‌تر بود جایشان عوض می‌شود. مثال: از heap بالا ریشه (۱) را برمی‌داریم:

```
[1, 5, 2, 9, 6, 8, 3]     ۱ را برمی‌داریم و آخری (۳) را به ریشه می‌بریم
[3, 5, 2, 9, 6, 8]        فرزندان ۳: ۵ و ۲؛ کوچک‌تر ۲ است و ۳ > ۲، جابه‌جا
[2, 5, 3, 9, 6, 8]        فرزند ۳ حالا فقط ۸ است؛ ۳ < ۸، تمام
```

چرا باید با کوچک‌ترِ دو فرزند عوض کنیم، نه هر کدام؟ چون آن فرزند بعد از جابه‌جایی والد می‌شود، و باید از فرزند دیگر هم کوچک‌تر باشد تا قاعده نشکند.

هر دو کار یک مسیر از ریشه تا برگ را طی می‌کنند، پس O(log n) هستند. دیدن کوچک‌ترین (`Peek`) فقط خواندن خانه‌ی ۰ است و O(1).

## همین در Go

همان دو حرکت در کد. `less` را از بیرون می‌گیریم، پس همین heap برای min-heap، max-heap یا هر ترتیب دلخواه کار می‌کند:

```go
func (h *Heap[T]) up(i int) {
	for i > 0 {
		p := (i - 1) / 2
		if !h.less(h.data[i], h.data[p]) {
			break
		}
		h.data[i], h.data[p] = h.data[p], h.data[i]
		i = p
	}
}

func (h *Heap[T]) down(i int) {
	n := len(h.data)
	for {
		l := 2*i + 1
		if l >= n {
			return
		}
		m := l
		if r := l + 1; r < n && h.less(h.data[r], h.data[l]) {
			m = r
		}
		if !h.less(h.data[m], h.data[i]) {
			return
		}
		h.data[i], h.data[m] = h.data[m], h.data[i]
		i = m
	}
}
```

`up` تا وقتی عدد از والدش کوچک‌تر است جابه‌جا می‌کند و وقتی نبود (یا به ریشه رسید) می‌ایستد. `down` اول فرزند چپ را حساب می‌کند؛ اگر وجود نداشت، یعنی برگ است و کاری نمی‌ماند. بعد `m` را کوچک‌ترِ دو فرزند می‌گیرد (فرزند راست ممکن است نباشد) و اگر `m` از خود عدد کوچک‌تر نبود می‌ایستد، وگرنه جابه‌جا می‌کند و از همان‌جا ادامه می‌دهد. `Push` ته آرایه `append` می‌کند و `up` را صدا می‌زند؛ `Pop` آخرین عنصر را روی ریشه می‌نویسد، slice را یکی کوتاه می‌کند و `down(0)` را صدا می‌زند.

تست‌ها شامل یک property test است: ۵۰۰ ورودی تصادفی (با تکرار زیاد) وارد heap می‌شوند، بیرون می‌آیند و خروجی با `slices.Sort` مقایسه می‌شود. همچنین بعد از هر قدم بررسی می‌شود که قاعده‌ی والد و فرزند برقرار باشد، و چند heap مستقل هم در goroutineهای جدا امتحان شده‌اند. همه با `go test -race` سبز هستند.

## مقایسه با container/heap

کتابخانه‌ی استاندارد هم heap دارد. از شما می‌خواهد روی نوع خودتان پنج متد `Len`، `Less`، `Swap`، `Push(any)` و `Pop() any` را بنویسید، و بعد `heap.Push`، `heap.Pop`، `heap.Fix` و `heap.Remove` را صدا بزنید. یک برنامه‌ی کوچک ۲۰ عدد تصادفی را هم به heap من و هم به `container/heap` داد و هر دو را تا خالی شدن pop کرد. خروجی نشان می‌دهد هر دو یک ترتیب داده‌اند:

```
mine: [1 4 5 15 23 28 28 29 35 43 45 50 52 52 53 57 67 68 76 87]
std:  [1 4 5 15 23 28 28 29 35 43 45 50 52 52 53 57 67 68 76 87]
equal: true
```

هر دو مرتب‌شده‌اند، چون همیشه کوچک‌ترین را برداشتیم. تفاوت در نحوه‌ی استفاده است: نسخه‌ی استاندارد مقدارها را در `any` بسته‌بندی می‌کند؛ نسخه‌ی من typed است ولی نمی‌تواند اولویت یک آیتم را که از قبل داخل heap است عوض کند. این‌جا `container/heap` می‌درخشد (چند بخش پایین‌تر).

## ساختن heap از یک آرایه: heapify

فرض کنید همه‌ی داده را از اول دارید. ساده‌ترین کار n بار `Push` است، که در بدترین حالت O(n log n) هزینه دارد. راه بهتری هست: {{< term "heapify" "heapify" >}}. آرایه را همان‌طور که هست یک درخت در نظر می‌گیرید و از آخرین والد شروع می‌کنید و به عقب می‌روید و هر کدام را `down` می‌کنید. چون از ته می‌آییم، وقتی به هر گره می‌رسیم دو زیردرختش از قبل heap هستند، و `down` فقط باید خود او را جا بیندازد. کل کار O(n) است. دلیل شهودی‌اش: نیمی از گره‌ها برگ هستند و اصلاً کاری ندارند، یک چهارم فقط حداکثر یک سطح پایین می‌روند، و به همین ترتیب؛ گره‌های کمی هستند که باید راه طولانی بروند.

برنامه‌ی نمایشی روی عددهای تصادفی هر دو راه را اجرا کرد و تعداد فراخوانی `less` را شمرد:

```
n         heapify      n pushes     ratio
1000      1856         2248         1.21
10000     18778        22509        1.20
100000    188354       228196       1.21
1000000   1882279      2284797      1.21
```

ستون آخر نسبت دو ستون قبل است. اینجا هر دو راه خطی‌اند و فاصله فقط حدود ۲۱٪ است، چون عدد تصادفی معمولاً بعد از `Push` زیاد بالا نمی‌رود. (این عددها با داده‌ی تصادفی با seed ثابت‌اند؛ با داده‌ی دیگر کمی فرق می‌کنند.) بدترین حالت برای pushها وقتی است که ورودی نزولی باشد: هر عدد تازه از همه‌ی قبلی‌ها کوچک‌تر است و تا ریشه بالا می‌رود:

```
1000      heapify 1982      pushes 7987
100000    heapify 199978    pushes 1468946
1000000   heapify 1999974   pushes 17951445
```

اینجا فرق دیده می‌شود: heapify نزدیک 2n می‌ماند (برای یک میلیون، حدود دو میلیون مقایسه)، ولی pushها به حدود ۱۸ مقایسه برای هر آیتم می‌رسند، یعنی نزدیک log n. اگر همه‌ی داده را از قبل دارید، heapify کنید.

## کاربرد اول: top-K روی یک جریان داده

فرض کنید یک میلیون عدد از یک stream می‌آید و فقط ۱۰ عدد بزرگ‌تر را می‌خواهید، بدون اینکه همه را نگه دارید. ترفند، یک **min-heap به اندازه‌ی K** است که ۱۰ بزرگ‌ترِ تا اینجا را نگه می‌دارد. ریشه‌ی آن کوچک‌ترینِ همین ۱۰ تاست، یعنی «کمترین امتیازی که هنوز در جمع بزرگ‌ترین‌ها جا دارد». عدد جدید فقط وقتی مهم است که از ریشه بزرگ‌تر باشد؛ آن‌وقت ریشه را کنار می‌گذارد و جایش می‌نشیند (یک `down`):

```go
func (h *Heap[T]) ReplaceTop(v T) {
	h.data[0] = v
	h.down(0)
}
```

نکته‌ی این‌جا min-heap بودن است، با اینکه بزرگ‌ترین‌ها را می‌خواهیم: چون باید ضعیف‌ترین عضو گروه را سریع پیدا و بیرون کنیم. برنامه‌ی نمایشی این کار را روی یک میلیون عدد تصادفی با K = 10 انجام داد و با مرتب‌کردن کامل (`sort.Slice`) مقایسه کرد:

```
N = 1000000 K = 10
max heap size: 10 | heap replaced top 134 times
less calls: heap 654 | full sort 20985383
same top-K: true
```

خط دوم می‌گوید heap هیچ‌وقت بیشتر از ۱۰ آیتم نداشت و فقط ۱۳۴ بار ریشه عوض شد (بیشتر عددها از همان اول کوچک‌تر از ریشه بودند و رد شدند). خط سوم تعداد مقایسه‌ها را می‌دهد: ۶۵۴ برای heap و حدود ۲۱ میلیون برای مرتب‌کردن همه. خط آخر می‌گوید نتیجه یکی است. زمان‌گیری نکردم، فقط مقایسه‌ها را شمردم.

## کاربرد دوم: scheduler و مسئله‌ی برابرها

حالا یک scheduler ساده: هر job یک اولویت دارد (عدد کمتر زودتر اجرا می‌شود). هشت job با نام‌های `a` تا `h` به همین ترتیب اضافه شدند. `a c e g` اولویت ۰ دارند و بقیه ۱. خروجی دو بار اجرا نشان داده شده؛ بار اول فقط با اولویت، بار دوم با یک شماره‌ی ترتیب ورود هم برای شکستن تساوی:

```
tie-break = false [a(p0) e(p0) g(p0) c(p0) b(p1) d(p1) f(p1) h(p1)]
tie-break = true  [a(p0) c(p0) e(p0) g(p0) b(p1) d(p1) f(p1) h(p1)]
```

در خط اول اولویت‌ها درست رعایت شده (همه‌ی p0ها قبل از p1ها)، ولی بین برابرها ترتیب به هم ریخته: `c` بعد از `e` و `g` آمد، با اینکه زودتر وارد شد. دلیلش این است که heap پایدار ({{< term "stable-sort" "stable" >}}) نیست: به برابرها کاری ندارد، پس ممکن است جابه‌جا شوند. راه‌حل این است که به هر job یک شماره‌ی ورود بدهید و `Less` را طوری بنویسید که وقتی اولویت‌ها برابرند، شماره‌ی کوچک‌تر زودتر باشد (`x.Seq < y.Seq`). خط دوم نتیجه است: بین برابرها دوباره ترتیب ورود (FIFO) برگشت.

## عوض‌کردن اولویت وقتی آیتم داخل heap است

گاهی اولویت یک آیتم که از قبل در heap نشسته عوض می‌شود. `container/heap` اجازه می‌دهد اندیس هر آیتم را خودتان نگه دارید (در `Swap` به‌روز می‌کنید) و بعد از تغییر کلید `heap.Fix(h, i)` را صدا بزنید؛ `heap.Remove(h, i)` هم از وسط heap حذف می‌کند. هر دو O(log n) هستند. در برنامه‌ی نمایشی پنج job با اولویت‌های ۱۰ تا ۱۴ (`a` تا `e`) ساخته شد و اولویت `d` به ۱ تغییر کرد:

```
top before: a
after d.Prio=1 and Fix: d
after Remove(d), rest: [a b c e]
```

قبل از تغییر، ریشه `a` بود (اولویت ۱۰). بعد از کم‌کردن اولویت `d` به ۱ و صدا زدن `Fix`، `d` به ریشه رسید. بعد `d` را از وسط حذف کردیم و بقیه به ترتیب `a b c e` بیرون آمدند.

## heap sort

با همان ابزار یک مرتب‌سازی هم می‌شود ساخت: heapify کنید و n بار `Pop`. O(n log n) است و ساختار اضافه نمی‌خواهد. ولی در شمارش من مقایسه‌ی بیشتری از `sort.Slice` داشت: ۳٬۰۱۹٬۵۳۶ در برابر ۱٬۷۵۴٬۷۹۳ برای ۱۰۰٬۰۰۰ عدد (و ۱۶٬۸۷۴ در برابر ۱۰٬۲۳۷ برای ۱٬۰۰۰ عدد). در پست «مرتب‌سازی: quick، merge و heap» دقیق‌تر به آن می‌پردازم. الگوریتم Dijkstra هم در پستی بعدی از همین heap استفاده می‌کند.

## آنچه heap تضمین نمی‌کند

- **heap مرتب نیست.** فقط ریشه تضمین‌شده است. اگر کل heap را چاپ کنید، ترتیب خانه‌ها مرتب نیست؛ باید یکی‌یکی `Pop` کنید.
- **جست‌وجوی یک مقدار دلخواه O(n) است.** heap فقط کوچک‌ترین را سریع پیدا می‌کند. برای «آیا ۴۲ داخلش هست؟» باید همه را بگردید.
- **اولویت‌های برابر ترتیب تضمین‌شده ندارند.** اگر ترتیب ورود مهم است، شماره‌ی ترتیب اضافه کنید، مثل بخش scheduler.
- **برای top-K بزرگ‌ترین‌ها، min-heap به اندازه‌ی K بگیرید،** نه max-heap؛ دلیلش در بخش top-K آمد.
- **heap بدون قفل برای استفاده‌ی هم‌زمان امن نیست.** چند goroutine نباید هم‌زمان روی یک heap `Push` و `Pop` کنند.

## تمرین

متد `Fix(i int)` و یک map از کلید به اندیس به `Heap[T]` اضافه کنید تا بتوانید آیتم را با کلید به‌روز کنید. با property test آن را در برابر `container/heap` بیازمایید.

## قدم بعدی

«جست‌وجوی دودویی و invariant». همان عادتی که این heap را درست نگه داشت، یعنی نوشتن آنچه باید همیشه برقرار بماند، جایی است که بیشترین سود را دارد.
