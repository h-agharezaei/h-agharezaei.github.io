در کتاب‌های درسی، لیست پیوندی رقیب بزرگ آرایه است. درج در ابتدا در زمان ثابت. هیچ کپی‌ای وقت بزرگ شدن لازم نیست. به نظر می‌رسد باید زیاد برنده شود. با این حال وقتی یک میلیون عدد را جمع می‌زنم، {{< term "linked-list" "لیست پیوندی" >}} اگر nodeهایش در حافظه به ترتیب باشند حدود ۳ برابر از slice کندتر است، و اگر پخش و پلا باشند ۶۵ برابر. پس چرا آدم‌ها این‌قدر کم سراغش می‌روند؟

برای جواب دادن اول باید ببینیم لیست پیوندی چیست و چه هزینه‌ای دارد. آرایه‌ای که با آن رقابت می‌کند موضوع [آرایه‌ی پویا و slice از درون](/fa/posts/algo-dynamic-arrays/) بود، که تقریباً در همه‌چیز برد. اینجا لیست را با [Generics در Go](/fa/posts/go-generics/) می‌سازیم و طرف حافظه‌ی اشاره‌گرها در [اشاره‌گرها و مدل حافظه در Go](/fa/posts/go-pointers-memory/) آمده. در آخر یک جایی را نشان می‌دهم که لیست واقعاً به کار می‌آید و در [rate limiting و caching در Go](/fa/posts/go-rate-limiting-caching/) هم پیدایش می‌شود.

> این یک مثال محلی با Go 1.27 روی macOS arm64 است. شمارش‌ها و اندازه‌ها قطعی‌اند و برای این پست دوباره اجرا شدند. زمان‌های بخش benchmark از یک اجرای قبلی روی Go 1.26 هستند و با load‌ای که زیرش اندازه‌گیری شده‌اند برچسب خورده‌اند. آدرس‌های حافظه از اجرایی به اجرای دیگر فرق می‌کنند.

## ایده: زنجیره‌ای از nodeها

آرایه عنصرهایش را در یک بلوک حافظه کنار هم نگه می‌دارد. لیست پیوندی برعکس: هر عنصر در جعبه‌ی کوچک خودش زندگی می‌کند که اسمش **node** است، و هر node دو چیز دارد: مقدار، و یک اشاره‌گر به node بعدی.

```
head
 |
 v
[ 10 | * ]--->[ 20 | * ]--->[ 30 | * ]---> nil
```

برای رسیدن به عنصر سوم نمی‌شود جایش را حساب کرد. باید از head شروع کنید و اشاره‌گرها را دنبال کنید: node اول، دوم، سوم. این ضعف اصلی است. قوت اصلی این است که جعبه‌ها می‌توانند هرجای حافظه باشند، پس اضافه یا حذف یک جعبه فقط یعنی عوض کردن یک یا دو اشاره‌گر. چیز دیگری جابه‌جا نمی‌شود.

لیستی که هر node فقط node بعدی را می‌شناسد **یک‌طرفه** (singly linked) نام دارد. اگر هر node اشاره‌گری به node قبلی هم داشته باشد، **دوطرفه** (doubly linked) است. ما با نوع یک‌طرفه شروع می‌کنیم.

## لیست پیوندی یک‌طرفه‌ی جنریک

`List[T]` زیر `PushFront`، `PushBack`، `Find`، `Remove` و `Reverse` دارد. هم اشاره‌گر `head` و هم `tail` نگه می‌دارد، و همین `PushBack` را O(1) می‌کند: لازم نیست اول تا آخر لیست برویم.

```go
type Node[T any] struct {
	Val  T
	Next *Node[T]
}

func (l *List[T]) PushFront(v T) {
	nd := &Node[T]{Val: v, Next: l.head}
	l.head = nd
	if l.tail == nil {
		l.tail = nd
	}
	l.n++
}

func (l *List[T]) Reverse() {
	var prev *Node[T]
	l.tail = l.head
	for c := l.head; c != nil; {
		next := c.Next
		c.Next = prev
		prev, c = c, next
	}
	l.head = prev
}
```

`PushFront` یک node می‌سازد که به head قدیمی اشاره می‌کند، و بعد آن را head جدید می‌کند. `Reverse` یک بار لیست را می‌پیماید و هر اشاره‌گر `Next` را برعکس می‌کند؛ head قدیمی tail می‌شود و برای همین `l.tail = l.head` اول آمده.

تست‌ها push، find، remove، reverse (از جمله اینکه بعدش `PushBack` هنوز درست کار می‌کند، چون `Reverse` باید tail را اصلاح کند)، لیست خالی و لیست‌های مستقل در goroutineها را پوشش می‌دهند. با `go test -race` می‌گذرند.

مقایسه با آرایه‌ی پویا چطور است؟

| عملیات | لیست پیوندی | آرایه‌ی پویا |
|---|---|---|
| درج در ابتدا | O(1) | O(n) |
| اضافه در انتها | O(1) با tail | O(1) سرشکن |
| عنصر i‌ام | O(n) | O(1) |
| حذف nodeای که در دست دارید | O(1) اگر دوطرفه باشد؛ یک‌طرفه node قبلی را هم لازم دارد | O(n) جابه‌جایی |

ردیف آخر راحت اشتباه خوانده می‌شود. «nodeای که در دست دارید» یعنی از قبل ارجاعی به آن node دارید. پیدا کردنش در وهله‌ی اول هنوز یک پیمایش است.

برای اینکه O(n) در «عنصر i‌ام» را به صورت عدد ببینیم، دمو می‌شمارد `Find` در یک لیست ۱٬۰۰۰تایی چند node را می‌بیند:

```
find steps in 1000 nodes: first 1 middle 501 last 1000
```

عنصر اول ۱ قدم می‌برد، وسطی ۵۰۱ و آخری ۱٬۰۰۰ قدم. O(n) در عمل همین است: هرچه عنصر دورتر باشد قدم‌ها بیشترند.

## یک node چقدر خرج دارد

هر node کنار مقدار یک اشاره‌گر اضافه هم دارد و این حافظه می‌برد. دمو اندازه‌ی node را برای سه نوع عنصر چاپ می‌کند:

```
sizeof Node[int]: 16  elem int: 8
sizeof Node[byte]: 16 elem byte: 1
sizeof Node[big]: 136 elem big: 128
```

برای `int`، node ۱۶ بایت است و خود عنصر ۸ بایت: نصف دیگر اشاره‌گر است. برای یک `byte` بدتر است: node برای ۱ بایت داده ۱۶ بایت می‌شود، چون اشاره‌گر ۸ بایتی باید تراز باشد و بقیه را padding پر می‌کند. فقط وقتی عنصر بزرگ باشد (`big` ۱۲۸ بایت است) اشاره‌گر سهم کوچکی می‌شود. پس برای عنصرهای کوچک سربار غالب است. این‌ها اندازه‌ی struct هستند؛ allocator ممکن است بیشتر هم گرد کند و آن را اندازه نگرفتم.

هزینه‌ی دوم allocation است. هر node یک درخواست جدا از allocator حافظه است. با `testing.AllocsPerRun` شمردم، برای ساختن ۱٬۰۰۰ عنصر به سه روش:

```
allocs for 1000 elements: list 1000, presized slice 1, append-grown slice 9
```

لیست برای هر عنصر یک allocation لازم دارد. slice‌ای که ظرفیتش از قبل تعیین شده در کل یکی لازم دارد، و slice‌ای که با `append` بزرگ می‌شود ۹ تا (دلیلش را در پست قبل دیدیم). allocationهای کوچک زیاد یعنی کار بیشتر برای garbage collector هم.

## nodeها کجا زندگی می‌کنند

حالا سراغ شکاف بزرگ زمانی ابتدای پست برویم. لیست لازم ندارد nodeهایش کنار هم باشند، ولی برای سرعت خیلی فرق می‌کند که باشند یا نه. برای دیدن اینکه nodeها واقعاً کجایند، اختلاف آدرس حافظه‌ی nodeهای پشت‌سرهم را چاپ کردم. اول برای لیستی که با push کردن ۱٬۰۰۰ node پشت سر هم ساخته شده:

```
address deltas, built in order: [16 16 16 16 16 16 16 16 16 16 16 16]
```

(۱۲ تای اول را نشان داده‌ام.) هر node دقیقاً ۱۶ بایت بعد از قبلی است، پس لیست مثل یک آرایه چیده شده. بعد همان ۱٬۰۰۰ node را برداشتم، به‌هم ریختم و به ترتیب به‌هم‌ریخته دوباره به هم وصل کردم:

```
address deltas, shuffled      : [-304 1648 -8736 5408 -19504 15344 6720 -1040 1744 -16 -18944 -2432]
```

حالا node بعدی هزاران بایت جلوتر یا عقب‌تر است، بدون هیچ الگویی. عددهای دقیق از اجرایی به اجرای دیگر فرق می‌کنند، چون آدرس واقعی‌اند؛ نکته فقط این است که دیگر ۱۶ نیستند. این همان تفاوت {{< term "cache-locality" "محلیت کش" >}} خوب و بد است: پردازنده حافظه را تکه‌تکه بار می‌کند و تکه‌های اخیر را در یک {{< term "cpu-cache" "کش" >}} کوچک و سریع نگه می‌دارد. وقتی node بعدی درست کنار node فعلی است، احتمالاً از قبل بار شده. وقتی دور است، پردازنده باید منتظر حافظه‌ی اصلی بماند. برنامه‌ی واقعی‌ای که با گذشت زمان node اضافه و حذف می‌کند بیشتر شبیه حالت دوم است تا اول، ولی این را اینجا ثابت نکردم.

## benchmark زمانی

آزمایش ساده است: همه‌ی عنصرهای یک slice، یک لیست ساخته‌شده به ترتیب، و یک لیست به‌هم‌ریخته در حافظه را جمع می‌زنیم. هر عدد میانه‌ی ۷ اجرای `testing.Benchmark` است؛ باینری از قبل build شده بود و benchmark تنها و پشت یک قفل اجرا شد. **در اجرای قبلی روی همین ماشین اندازه‌گیری شده، load در شروع ۱٫۹ و در پایان ۲٫۳.** از چیزی که می‌خواستم بیشتر است، پس عددها را راهنما بدانید. این بار زمان‌گیری را تکرار نکردم چون ماشین شلوغ بود؛ این‌ها همان عددهای اصلی‌اند.

```
n         slice ns   list(ordered) ns   list(shuffled) ns
1000           323             1261               1260
100000       40997           128347             546201
1000000     418855          1318309           27327167
```

هر ردیف را از چپ به راست بخوانید. برای ۱٬۰۰۰٬۰۰۰ عنصر slice حدود ۰٫۴۲ ms می‌برد، لیست مرتب حدود ۱٫۳ ms و لیست به‌هم‌ریخته حدود ۲۷ ms. پس:

- لیست مرتب در همه‌ی اندازه‌ها ۳ تا ۴ برابر از slice کندتر است. برای هر عنصر باید یک اشاره‌گر را دنبال کند و جایی که slice ۸ بایت می‌خواند ۱۶ بایت بخواند.
- لیست به‌هم‌ریخته در ۱٬۰۰۰ عنصر ۳٫۹ برابر کندتر است، آنجا که همه‌چیز به هر حال در کش جا می‌شود. ولی در ۱۰۰٬۰۰۰ عنصر ۱۳ برابر و در ۱٬۰۰۰٬۰۰۰ عنصر ۶۵ برابر کندتر است.

چیزی که می‌توانم پشتش بایستم این است: شکاف دقیقاً وقتی بزرگ می‌شود که داده بزرگ و ترتیبش به‌هم‌ریخته باشد. توضیح معقولش cache miss است، ولی شمارنده‌های سخت‌افزاری را نخواندم، پس این یک فرضیه است. عددها روی ماشین شما فرق می‌کنند.

## جایی که لیست به کار می‌آید

یک کار هست که لیست دوطرفه خیلی خوب انجام می‌دهد: nodeای را که از قبل در دست دارید در O(1) و بدون جست‌وجو حذف می‌کند. کتابخانه‌ی استاندارد یکی دارد، `container/list`:

```
0 1 3 4 (removed known element 2 in O(1))
```

دمو لیست ۰ تا ۴ را می‌سازد، عنصر با مقدار ۲ را در دست نگه می‌دارد و مستقیم حذفش می‌کند. بقیه بدون هیچ جابه‌جایی بسته می‌شود.

کاربرد کلاسیک این {{< term "lru-cache" "کش LRU" >}} است. LRU یعنی «کمترین استفاده‌ی اخیر»: وقتی کش پر است، ورودی‌ای که از همه بیشتر دست‌نخورده مانده بیرون انداخته می‌شود. هم‌زمان دو چیز لازم داریم. باید ورودی را با کلید سریع پیدا کنیم (map این کار را می‌کند)، و باید ورودی‌ها را به ترتیب استفاده‌ی اخیر نگه داریم و هر بار که یکی خوانده شد آن را به جلو ببریم (لیست دوطرفه این کار را می‌کند، چون می‌توانیم nodeای را که در دست داریم بیرون بکشیم و در O(1) جلو بگذاریم).

```go
func (c *LRU) Get(k string) (int, bool) {
	e, ok := c.items[k]
	if !ok {
		return 0, false
	}
	c.ll.MoveToFront(e)
	return e.Value.(*entry).val, true
}

func (c *LRU) Put(k string, v int) {
	if e, ok := c.items[k]; ok {
		e.Value.(*entry).val = v
		c.ll.MoveToFront(e)
		return
	}
	c.items[k] = c.ll.PushFront(&entry{k, v})
	if c.ll.Len() > c.cap {
		last := c.ll.Back()
		c.ll.Remove(last)
		delete(c.items, last.Value.(*entry).key)
	}
}
```

`items` کلید را به عنصر لیست نگاشت می‌کند. `Get` عنصر را از راه map پیدا می‌کند و به جلو می‌برد. `Put` یا ورودی موجود را به‌روز می‌کند و جلو می‌برد، یا ورودی تازه را جلو اضافه می‌کند و اگر کش حالا از ظرفیت بیشتر شده، node آخر را که کمترین استفاده‌ی اخیر را دارد برمی‌دارد و کلیدش را از map پاک می‌کند.

با ظرفیت ۳، `a` و `b` و `c` را put کردم، `a` را خواندم و بعد `d` را put کردم:

```
LRU keys (most recent first): [d a c]
```

`b` رفته است. قدیمی‌ترین ورودی دست‌نخورده بود، چون خواندن `a` آن را تازه‌تر کرد. تست این هم می‌گذرد. map عنصر را در O(1) پیدا می‌کند و لیست در O(1) جابه‌جا و حذف می‌کند؛ هیچ‌کدام تنها هر دو کار را نمی‌کند. و map این کش چیزی است که در پست بعد دستی می‌سازیم.

## کی لیست می‌ارزد

- **پیش‌فرض را slice بگذارید.** فقط وقتی سراغ لیست بروید که nodeها را در دست نگه می‌دارید و زیاد splice می‌کنید.
- **هر node یک allocation جدا است،** و یعنی کار بیشتر برای garbage collector هم.
- **درج در ابتدا O(1) است، ولی پیدا کردن جای درج O(n).** درج سریع فقط وقتی کمک می‌کند که از قبل در جای درست ایستاده باشید.
- **`container/list` مقدار را به صورت `any` نگه می‌دارد،** پس هر خواندن یک type assertion خرج دارد؛ `List[T]` جنریک من این هزینه را ندارد.
- **به این نسبت‌ها روی سخت‌افزار دیگر یا اندازه‌ی عنصر دیگر اعتماد نکنید.**

## تمرین

`List[T]` را دوطرفه کنید و `Remove(node)` را اضافه کنید که خود node را می‌گیرد. بعد حذف یکی در میان nodeهای یک لیست ۱٬۰۰۰٬۰۰۰تایی را تست کنید و با `slices.DeleteFunc` روی یک slice مقایسه کنید. اول برنده را پیش‌بینی کنید، بعد بررسی کنید.
