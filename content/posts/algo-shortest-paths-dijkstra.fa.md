در مقاله‌ی قبلی، [گراف: BFS و DFS](/fa/posts/algo-graphs-bfs-dfs/)، {{< term "bfs" "BFS" >}} کوتاه‌ترین مسیر را با شمردن یال پیدا می‌کرد. این فقط وقتی درست است که هر یال هزینه‌ی یکسان داشته باشد. جاده، لینک شبکه و قیمت وزن دارند و آن‌وقت مسیرِ با کمترین یال ارزان‌ترین نیست. راه‌حل به یک [priority queue](/fa/posts/algo-heaps-priority-queues/) نیاز دارد؛ همان {{< term "binary-heap" "heap" >}} مقاله‌ی قبل، تا هر بار نزدیک‌ترین رأس تمام‌نشده را برداریم.

> Go 1.26، مثال محلی، تست با `go test -race`. هنگام اجرا میانگین بار ماشین بالای ۳ بود، پس فقط شمارش منتشر می‌کنم، نه زمان.

## Dijkstra روی یک گراف کوچک

{{< term "dijkstra" "الگوریتم Dijkstra" >}} برای هر رأس یک فاصله‌ی موقت نگه می‌دارد. کوچک‌ترین را برمی‌دارد و همه‌ی یال‌های خروجی‌اش را امتحان می‌کند: اگر `dist[u] + w` از `dist[v]` بهتر بود، مسیر بهتری پیدا کرده‌ایم و به‌روزش می‌کنیم. این به‌روزرسانی را {{< term "relaxation" "relaxation" >}} می‌گویند. با `container/heap` هسته کوتاه است:

```go
h := &minHeap{{src, 0}}
for h.Len() > 0 {
	it := heap.Pop(h).(item)
	if it.d > dist[it.v] { continue } // stale entry
	for _, e := range g.Adj[it.v] {
		if nd := it.d + e.W; nd < dist[e.To] {
			dist[e.To], parent[e.To] = nd, it.v
			heap.Push(h, item{e.To, nd})
		}
	}
}
```

شش رأس و این یال‌های بدون جهت را به کار بردم:

```
A-B:7 A-C:9 A-F:14 B-C:10 B-D:15 C-D:11 C-F:2 D-E:6 E-F:9
A dist= 0 path=A
B dist= 7 path=A>B
C dist= 9 path=A>C
D dist=20 path=A>C>D
E dist=20 path=A>C>F>E
F dist=11 path=A>C>F
lazy: {Pops:8 Stale:2 Checks:18 Relax:7 Fixes:0}
```

یال `A-F` هزینه‌ی ۱۴ دارد ولی مسیر از C هزینه‌ی ۱۱. هر ۹ یال از دو سر بررسی می‌شود، پس ۱۸ بررسی.

## lazy deletion یا decrease-key

کد بالا هیچ‌وقت عنصر داخل heap را تغییر نمی‌دهد؛ عنصر تازه می‌گذارد و هنگام pop عنصر قدیمی را رد می‌کند. به این کار {{< term "lazy-deletion" "lazy deletion" >}} می‌گویند: ۸ بار pop برای ۶ رأس که ۲ تایش کهنه بود. روش دیگر decrease-key است: برای هر رأس یک عنصر نگه می‌داریم، جایش را به خاطر می‌سپاریم و بعد از کم کردن فاصله `heap.Fix` را صدا می‌زنیم. روی همین گراف ۶ pop و ۲ بار `Fix` شد. روی گراف‌های جهت‌دار تصادفی با 4V یال و وزن ۱ تا ۱۰۰ (seed برابر 11):

```
V      E       lazyPops stale relax | fixPops fixes
1000   4000    1296     309   1295  | 987     309   same=true
10000  40000   12895    3087  12894 | 9808    3094  same=true
100000 400000  128790   30793 128789 | 97997   30781 same=true
```

هر دو روش فاصله‌های یکسان می‌دهند. روش lazy حدود ۳۰٪ pop بیشتر دارد، ولی کدش ساده‌تر است و نگه‌داری جای عنصرها لازم نیست. سریع‌تر بودن یکی را اندازه نگرفتم. در هر دو هزینه O((V+E) log V) است.

## چرا یال منفی آن را خراب می‌کند

{{< term "invariant" "invariant" >}} الگوریتم Dijkstra این است: رأسی که pop شد فاصله‌اش نهایی است، چون هر مسیر دیگر باید از چیزی بگذرد که دورتر یا هم‌فاصله است. یال منفی این «دورتر» را از بین می‌برد. یال‌های جهت‌دار S->A با 2، S->B با 3 و B->A با 2-:

```
settled Dijkstra: [0 2 3]  lazy-skip Dijkstra: [0 1 3]  Bellman-Ford: [0 1 3] false
```

نسخه‌ی کتاب درسی A را با ۲ نهایی می‌کند، پیش از آنکه بفهمد S->B->A فقط ۱ هزینه دارد. این یک جواب غلط واقعی است. نکته: نسخه‌ی lazy بالا اینجا اتفاقاً درست جواب داد، چون چیزی را نهایی نمی‌کند؛ به آن تکیه نمی‌کنم و روی گراف‌های بزرگ آزمایشش نکردم.

{{< term "bellman-ford" "Bellman-Ford" >}} ساده همه‌ی یال‌ها را تا V دور تکرار می‌کند: O(V·E). اگر دور V‌ام هم چیزی را بهتر کند، یک {{< term "negative-cycle" "دور منفی" >}} وجود دارد و کوتاه‌ترین مسیر معنا ندارد. با یال 1->2 به وزن 3- و 2->1 به وزن 1 خروجی `negative cycle: true` است.

## بررسی با مقایسه

یک تست ۳۰۰ گراف تصادفی می‌سازد (seed از ۰ تا ۲۹۹، ۲ تا ۱۳ رأس، وزن ۰ تا ۲۰، نصف جهت‌دار) و هر دو نسخه‌ی Dijkstra، Bellman-Ford و Floyd-Warshall (همه‌ی جفت‌ها، O(V³)) را مقایسه می‌کند. مسیر هر رأس را هم از `parent` می‌سازد و بررسی می‌کند وزن یال‌ها جمعاً برابر فاصله است. با `-race` می‌گذرد. این تست به سبک {{< term "property-based-testing" "property-based" >}} است: الگوریتم‌های مستقل باید با هم موافق باشند.

## شبکه با مانع

هر خانه‌ی باز یک رأس است و هر حرکت هزینه‌ی ۱ دارد. Dijkstra هزینه‌ی ۳۳ داد و ۳۸ خانه را گسترش داد (`*` مسیر است):

```
S****#******
.###*#*####*
.#***#*#****
.#*###*#*###
.#*****#***E
```

## A* در یک بخش

{{< term "a-star" "A*" >}} heap را بر اساس «هزینه تا اینجا + برآورد تا هدف» مرتب می‌کند. اگر برآورد هیچ‌وقت از هزینه‌ی واقعیِ باقی‌مانده بیشتر نباشد (مثلاً فاصله‌ی Manhattan روی شبکه‌ی چهارجهته)، جواب همچنان بهینه است. روی شبکه‌ی ۶۰ در ۶۰ با یک دیوار، با همان هزینه‌ی ۱۵۹:

```
60x60 wall: dijkstra cost 159 expanded 3550 | A* cost 159 expanded 1969
no wall in the way: dijkstra expanded 216 | A* cost 20 expanded 21
```

وقتی مسیر مستقیم باز بود A* فقط ۲۱ خانه را گسترش داد و Dijkstra ۲۱۶ خانه. دیوار سود را کم کرد، چون برآورد دیوار را نمی‌بیند. تابع عمومی `Search[N comparable]` برای هر دو همان کد است؛ Dijkstra یعنی A* با برآورد صفر. تست روی ۱۰۰ شبکه‌ی تصادفی هزینه‌ها را برابر یافت.

## چند نکته‌ی مهم

- Dijkstra وزن نامنفی می‌خواهد؛ وگرنه Bellman-Ford.
- در lazy deletion حتماً عنصرهای کهنه را رد کنید، وگرنه کار تکراری می‌شود.
- «بی‌نهایت» را بزرگ ولی امن بگیرید تا `Inf + w` سرریز نکند.
- برآورد بد در A* (که بیش از واقعیت می‌گوید) می‌تواند مسیری غیرکوتاه برگرداند.

## تمرین

برای `DijkstraFix` هم بررسی بازسازی مسیر را اضافه کنید، سپس گرافی بسازید که همه‌ی یال‌هایش ۱ باشد و تأیید کنید فاصله‌های Dijkstra با فاصله‌های BFS برابرند.
