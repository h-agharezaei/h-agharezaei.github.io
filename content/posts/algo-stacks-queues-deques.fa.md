یک queue از ۱٬۰۰۰ اشاره‌گر به مقدارهای ۱ کیلوبایتی را در نظر بگیرید که در یک slice نگه داشته‌ایم. ۹۹۰ تا را با `q = q[1:]` از جلو برمی‌دارید، garbage collection را اجباری می‌کنید و حافظه را نگاه می‌کنید: ۹۹۰ عنصر برداشته‌شده هنوز زنده‌اند. {{< term "queue" "queue" >}}ی وسوسه‌انگیز نشتی دارد.

این پست درباره‌ی دو ساده‌ترین ساختار داده است و اینکه چرا درست انتخاب کردن محل ذخیره‌شان مهم است. {{< term "stack" "Stack" >}} و queue عمداً دسترسی را محدود می‌کنند. hash table‌ای که در [hash table از صفر](/fa/posts/algo-hash-tables/) ساختیم اجازه می‌دهد هر کلیدی را بخواهید. stack یا queue فقط اجازه می‌دهد به یک سر یا دو سر دست بزنید. همین محدودیت است که آن‌ها را سریع و ساده برای فکر کردن می‌کند، به شرط اینکه محل ذخیره‌ی زیرشان درست باشد. روی آرایه‌های [آرایه‌ی پویا و slice از درون](/fa/posts/algo-dynamic-arrays/) سوارند و جایگزین مبتنی بر node در [لیست پیوندی و چرا کم‌کاربرد است](/fa/posts/algo-linked-lists/) آمده. کد از [Generics در Go](/fa/posts/go-generics/) استفاده می‌کند.

> Go 1.27، macOS arm64، مثال محلی، برای این پست دوباره اجرا شده. همه‌ی عددهای زیر شمارش یا اندازه‌اند، نه زمان، پس به شلوغی ماشین بستگی ندارند. تست‌ها با `go test -race` می‌گذرند.

## سه شکل

**Stack** آخرین‌ورودی‌اولین‌خروجی (LIFO) است، مثل یک دسته بشقاب: بشقاب را رویش می‌گذارید و رویی را برمی‌دارید. **Queue** اولین‌ورودی‌اولین‌خروجی (FIFO) است، مثل آدم‌های توی صف: هر که زودتر رسیده زودتر خدمت می‌گیرد. {{< term "deque" "deque" >}} (بخوانید «دک»، کوتاه‌شده‌ی double-ended queue) اجازه می‌دهد از هر دو سر اضافه و حذف کنید.

```
stack:   push -> [ a b c ] <- pop            (one end)
queue:   enqueue -> [ a b c ] -> dequeue     (two ends, different roles)
deque:   push/pop <-> [ a b c ] <-> push/pop (both ends, both operations)
```

## سه نوع کوچک

یک slice stack را عالی انجام می‌دهد: push همان `append` است و pop آخرین عنصر را برمی‌دارد. فقط یک جزئیات هست: `Pop` خانه‌ای را که آزاد می‌کند هم پاک می‌کند تا slice ناخواسته اشاره‌گری را زنده نگه ندارد.

```go
func (s *Stack[T]) Pop() (T, bool) {
	var zero T
	n := len(s.items)
	if n == 0 {
		return zero, false
	}
	v := s.items[n-1]
	s.items[n-1] = zero // do not keep a reference alive
	s.items = s.items[:n-1]
	return v, true
}
```

Pop یک مقدار و یک bool برمی‌گرداند، `false` وقتی stack خالی است؛ پس خالی بودن یک جواب عادی است و panic نیست.

برای queue و deque چیزی هوشمندتر از slice می‌خواهیم، چون هر دو از جلو حذف می‌کنند. انتخاب خوب {{< term "ring-buffer" "ring buffer" >}} است: یک آرایه‌ی ثابت، یک اندیس `head` که می‌گوید عنصر اول کجاست، و یک شمارنده. آرایه مثل یک دایره دیده می‌شود: وقتی اندیسی از انتها رد شد، با `%` به ۰ برمی‌گردد. مثلاً با آرایه‌ی ۴ خانه‌ای، بعد از چند dequeue و enqueue عنصرها می‌توانند این‌طور بنشینند:

```
index:    0    1    2    3
        [ e ][ . ][ c ][ d ]      head = 2, count = 3
                       ^ first    (c, d, then wraps around to e)
```

هیچ‌چیز هیچ‌وقت نباید جابه‌جا شود. حذف از جلو فقط `head` را یکی جلو می‌برد. وقتی آرایه پر شد دو برابر می‌شود، مثل آرایه‌ی پویای قبل.

```go
func (d *Deque[T]) PushBack(v T) {
	if d.n == len(d.buf) {
		d.grow()
	}
	d.buf[(d.head+d.n)%len(d.buf)] = v
	d.n++
}

func (d *Deque[T]) PopFront() (T, bool) {
	var zero T
	if d.n == 0 {
		return zero, false
	}
	v := d.buf[d.head]
	d.buf[d.head] = zero
	d.head = (d.head + 1) % len(d.buf)
	d.n--
	return v, true
}
```

`PushBack` در جای `head + count` (دور زده) می‌نویسد و `PopFront` در `head` می‌خواند، خانه را پاک می‌کند و `head` را جلو می‌برد. `Queue[T]` یک پوشش نازک دور deque است که فقط `Enqueue` و `Dequeue` را نشان می‌دهد. تست‌ها deque را روی ۵٬۰۰۰ عملیات تصادفی با یک مدل slice مقایسه می‌کنند و ترتیب FIFO را در طول رشد چک می‌کنند.

## تله‌ی `q = q[1:]`

برگردیم به ابتدای پست. queue وسوسه‌انگیز یک slice است: `append` برای enqueue و `q = q[1:]` برای dequeue. درست به نظر می‌رسد و کوتاه است. آزمایش اول نشان می‌دهد طول و ظرفیت چه می‌شوند:

```
start      len 8 cap 8
5 dequeues len 3 cap 3
5 enqueues len 8 cap 8 (reallocated)
```

با ۸ عنصر شروع می‌کنیم. بعد از ۵ dequeue با برش، `len` برابر ۳ است و `cap` هم ۳: برش ابتدا را جلو برده، پس جای جلو از دست رفته و دوباره قابل استفاده نیست. وقتی ۵ عنصر دیگر enqueue می‌کنیم slice پر است و `append` باید آرایه‌ی جدیدی بگیرد.

بدتر، عنصرهای قدیمی هنوز از {{< term "backing-array" "backing array" >}} ارجاع داده می‌شوند. برای دیدنش، ۱٬۰۰۰ اشاره‌گر به مقدارهای ۱ کیلوبایتی ساختم، ۹۹۰ تا pop کردم، garbage collection را اجباری کردم و `HeapAlloc` یعنی اندازه‌ی heap زنده را برحسب کیلوبایت خواندم:

```
990 of 1000 items popped with q = q[1:]: ~1000 KB still live
same, but q[0] = nil before reslicing:   ~0 KB still live
```

(برنامه تا نزدیک‌ترین ۱۰۰ کیلوبایت گرد می‌کند.) بدون پاک کردن، هر ۱٬۰۰۰ مقدار هنوز زنده‌اند، حدود ۱٬۰۰۰ KB، با اینکه فقط ۱۰ تا در queue مانده. garbage collector کل backing array را در حال استفاده می‌بیند، پس هر چیزی که به آن اشاره دارد می‌ماند. اگر پیش از برش `q[0] = nil` بگذاریم، مقدارهای pop‌شده آزاد می‌شوند و تقریباً چیزی نمی‌ماند. `Pop` من همین کار را می‌کند و برای همین آن خط `zero` را دارد.

نشتی فقط نصف ماجرا است. نصف دیگر رفت‌وآمد allocation است. ۱۰۰٬۰۰۰ جفت enqueue/dequeue اجرا کردم، با اینکه هیچ‌وقت بیش از ۵ عنصر هم‌زمان منتظر نبود:

```
slice queue: new arrays allocated = 25000
ring queue: cap = 8 copies = 4
```

queue مبتنی بر slice تقریباً هر ۴ عملیات یک آرایه‌ی تازه می‌گیرد، چون هر برش از ظرفیت جلو می‌خورد. ring buffer روی ظرفیت ۸ می‌ماند و یک بار ۴ عنصر کپی کرد، وقتی از ۴ به ۸ رفت، و دیگر هیچ‌وقت. برای همیشه از همان خانه‌ها استفاده می‌کند.

## allocationها و رشد سرشکن

`testing.AllocsPerRun` برای ۱٬۰۰۰ push و ۱٬۰۰۰ pop، به سه روش:

```
slice stack 12, presized 1, container/list 1745
```

stack مبتنی بر slice با دو برابر شدن بزرگ می‌شود و ۱۲ allocation لازم دارد. slice‌ای که با ظرفیت درست ساخته شود یکی لازم دارد. `container/list`، لیست دوطرفه‌ی کتابخانه‌ی استاندارد، برای هر عنصر یک node می‌گیرد، و ۷۴۵ تای اضافه خود لیست به‌علاوه‌ی ۷۴۴ int جعبه‌شده است: وقتی به جای آن یک ثابت کوچک push کردم، شمارش ۱٬۰۰۱ شد. عدد ۷۴۴ با مقدارهای ۲۵۶ تا ۹۹۹ جور است. تا جایی که می‌دانم runtime برای مقدارهای کوچک زیر ۲۵۶ جعبه‌های از پیش ساخته‌شده نگه می‌دارد، ولی فقط شمارش‌ها را چک کردم، نه سورس runtime را.

رشد با دو برابر شدن {{< term "amortized-analysis" "سرشکن" >}} O(1) است، همان‌طور که در آرایه‌ی پویا دیدیم. عنصرهایی را که `grow` کپی کرد شمردم:

```
n=10       cap=16       copies=12       copies/n=1.20
n=1000     cap=1024     copies=1020     copies/n=1.02
n=1000000  cap=1048576  copies=1048572  copies/n=1.05
```

تقریباً یک کپی به‌ازای هر push، هر `n` که باشد. (اولین رشد از ۰ به ۴ است، بعد ۴ به ۸ و همین‌طور ادامه، پس شمارش‌ها کمی از `n` بالاتر درمی‌آیند.)

## چهار کاربرد واقعی

stack و queue کوچک‌اند، ولی عجیب است چقدر کار به یکی از آن‌ها برمی‌گردد. چهار نمونه با خروجی واقعی.

**پرانتزهای متوازن** با stack. متن را بپیمایید: هر پرانتز باز را همراه جایش push کنید و برای هر بسته یکی pop کنید و ببینید جور است. اگر بسته‌ای به stack خالی یا بازِ اشتباه برخورد کند، یا آخر کار بازهایی مانده باشند، متن متوازن نیست و جا می‌گوید کجا:

```
"{[()]}"           balanced=true  pos=-1
"f(a[1], {x: 2})"  balanced=true  pos=-1
"(]"               balanced=false pos=1
"((a)"             balanced=false pos=0
"a)"               balanced=false pos=1
```

`pos=-1` یعنی مشکلی نیست. در `"(]"` علامت `]` در جای ۱ به یک `(` می‌خورد، پس گزارش جای ۱ است. در `"((a)"` علامت `)` پرانتز باز دوم را می‌بندد و اولی در جای ۰ هیچ‌وقت بسته نمی‌شود، پس گزارش ۰ است. در `"a)"` علامت `)` در جای ۱ stack را خالی می‌بیند.

**Undo/redo** با دو stack. هر ویرایش متن قبلی را روی stack مربوط به undo می‌گذارد. Undo متن فعلی را به stack مربوط به redo می‌برد و از undo بازمی‌گرداند. ویرایش تازه باید stack مربوط به redo را پاک کند، چون بعد از ویرایش تازه «آینده‌ی قبلی» معنا ندارد:

```
"hello world" undo "hello" undo "" redo "hello" type ! then redo "hello!"
```

از چپ بخوانید: «hello» و « world» را نوشتیم، دو بار undo کردیم و به متن خالی برگشتیم، یک بار redo کردیم و «hello» شد، بعد «!» نوشتیم و redo زدیم. redo چیز تازه‌ای نداد و روی «hello!» ماندیم، چون نوشتن، stack مربوط به redo را پاک کرده بود.

**پیمایش سطح‌به‌سطح** یک درخت کوچک با queue. این ایده‌ی پشت {{< term "bfs" "جست‌وجوی سطح‌اول" >}} (breadth-first search) است: ریشه را ببین، بعد فرزندانش، بعد فرزندان آن‌ها. یک node از جلو بردار، فرزندانش را عقب بگذار. در ابتدای هر دور، `size := q.Len()` دقیقاً تعداد nodeهای سطح فعلی است، پس می‌توانیم گروه‌شان کنیم:

```
levels: [[1] [2 3] [4 5 6] [7]]
```

**عنصر بزرگ‌تر بعدی** با stack یکنواخت (monotonic). برای هر مقدار در یک فهرست، مقدار بزرگ‌تر بعدی در سمت راستش را می‌خواهیم. stack‌ای از اندیس‌هایی نگه می‌داریم که هنوز جوابشان را نمی‌دانیم. برای هر مقدار تازه، همه‌ی اندیس‌های کوچک‌تر را از stack برمی‌داریم و با این مقدار جوابشان را می‌دهیم، بعد اندیس تازه را push می‌کنیم:

```
input: [2 1 5 3 4 9 4] next greater: [5 5 9 4 9 -1 -1] pushes 7 pops 7
n=100000 increasing: pushes 100000 pops 100000
n=100000 decreasing: pushes 100000 pops 100000
```

برای ۲ مقدار بزرگ‌تر بعدی ۵ است، برای ۱ هم ۵، برای ۵ برابر ۹ و همین‌طور؛ `-1` یعنی هیچ (۹ و آخرین ۴). حلقه‌ی داخلی درجه‌ی دو به نظر می‌رسد، ولی هر اندیس یک بار push و حداکثر یک بار pop می‌شود، پس جمع کل حداکثر `2n` عملیات است. دو خط آخر آن را برای دو ورودی حدی نشان می‌دهند، یک فهرست صعودی و یک نزولی از ۱۰۰٬۰۰۰ عدد: در هر دو دقیقاً ۱۰۰٬۰۰۰ push و ۱۰۰٬۰۰۰ pop.

## channel و زبان‌های دیگر

channel بافردار در Go از قبل یک queue FIFO امن برای threadهاست ([goroutine و channel در Go](/fa/posts/go-goroutines-channels/)). بین goroutineها از آن استفاده کنید و از نوع‌های این پست وقتی فقط یک goroutine به داده دست می‌زند. این نوع‌ها برای استفاده‌ی هم‌زمان امن نیستند. طبق مستندات، `std::collections::VecDeque` در Rust یک ring buffer رشدکننده است؛ اینجا اجرایش نکردم.

## باگ‌هایی که در queueها پنهان می‌شوند

- **هنگام pop خانه را پاک کنید،** وگرنه garbage collector نمی‌تواند مقدار را آزاد کند.
- **`q = q[1:]` برای queueهای کوتاه‌عمر خوب است،** نه برای طولانی‌عمر.
- **pop روی ساختار خالی باید `ok == false` برگرداند،** نه panic.
- **باقیمانده‌ی تقسیم در ring buffer جای کلاسیک باگ off-by-one است.** مثل من با یک مدل slice تستش کنید.
- **وقتی اندازه را می‌دانید با `make([]T, 0, n)` از قبل جا بگیرید.**

## تمرین

`Peek` را به `Queue` اضافه کنید، بعد `Deque` را طوری کنید که وقتی یک‌چهارم پر است کوچک شود. با شمارنده‌ی کپی چک کنید که یک الگوی push/pop در مرز کوچک شدن در هر قدم کپی نمی‌کند.
