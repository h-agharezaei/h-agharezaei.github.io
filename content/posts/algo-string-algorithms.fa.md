بعد از [greedy و backtracking](/fa/posts/algo-greedy-backtracking/) از انتخاب‌ها فاصله می‌گیریم و سراغ متن می‌رویم. پیدا کردن یک الگو در یک متن ساده به نظر می‌رسد، ولی روش ساده می‌تواند چهار برابر کار لازم انجام بدهد. دو راه‌حل کلاسیک {{< term "kmp-algorithm" "الگوریتم KMP" >}} و {{< term "rabin-karp" "Rabin–Karp" >}} هستند. هزینه‌ها مثل [Big-O با اندازه‌گیری](/fa/posts/algo-big-o-measured/) شمرده شده‌اند؛ Rabin–Karp به ایده‌هایی از [جدول هش](/fa/posts/algo-hash-tables/) مثل {{< term "hash-collision" "برخورد" >}} تکیه دارد.

> Go 1.26، مثال محلی، تست با `go test -race`. بار ماشین کم نبود، پس شمارش منتشر می‌کنم، نه زمان.

## جست‌وجوی ساده

الگو را روی متن می‌لغزانیم و بایت به بایت مقایسه می‌کنیم. در نسخه‌ی من هر مقایسه‌ی بایت یک شمارنده را زیاد می‌کند. بدترین حالت O(n·m) است: متن `aaaa…ab` (۱۰۰۰۰ تا a و یک b) و الگوی `aaab`.

## KMP: در متن هرگز عقب نرو

وقتی ناهم‌خوانی پیش می‌آید، بخشی که قبلاً تطبیق داده‌ایم می‌گوید تطابق بعدی از کجا می‌تواند شروع شود. **تابع شکست** (failure function) برای هر پیشوند الگو طول بلندترین پیشوندِ سره‌ای را نگه می‌دارد که پسوند همان پیشوند هم هست. برای `ababaca`:

```
i       0 1 2 3 4 5 6
pat    a b a b a c a 
fail   0 0 1 2 3 0 1 
```

`fail[4] = 3` یعنی بعد از تطبیق `ababa`، اگر بایت بعدی جور نشد، `aba` را نگه می‌داریم و از آنجا ادامه می‌دهیم. حلقه‌ی جست‌وجو اندیس متن را هرگز عقب نمی‌برد:

```go
for k > 0 && text[i] != pat[k] {
	k = fail[k-1]
}
if text[i] == pat[k] { k++ }
if k == len(pat) { /* match at i-k+1 */ k = fail[k-1] }
```

ساختن جدول O(m) و جست‌وجو O(n) است. شمارش مقایسه‌ها از اجرای من (`cmp` هر مقایسه‌ی بایت را می‌شمارد):

```
adversarial  n=10001 matches=1 naive=39992 kmp=19998
random abcd  n=10000 matches=32 naive=13290 kmp=12471
```

روی متن بدخواهانه KMP حدود 2n مقایسه می‌کند و روش ساده حدود 4n. روی متن تصادفی با چهار حرف تقریباً برابرند، چون ناهم‌خوانی زود پیش می‌آید. KMP بدترین حالت را تضمین می‌کند؛ روی ورودی معمولی لزوماً برنده نیست.

## Rabin–Karp: اول هش‌ها را مقایسه کن

هش هر پنجره‌ی به طول m را با هش الگو مقایسه می‌کنیم. جابه‌جایی پنجره باید O(1) باشد، برای همین از {{< term "rolling-hash" "هش غلتان" >}} استفاده می‌کنیم:

```go
ht = ((ht - int(text[i])*pow%mod + mod)*base + int(text[i+m])) % mod
```

`pow` برابر base^(m-1) mod `mod` است. هش برابر یعنی رشته‌ی برابر نیست، پس هر برخورد با مقایسه‌ی واقعی تأیید می‌شود. روی ۱۰۰۰۰ بایت تصادفی از `abcd` و الگوی `abcabd`، برخوردها و برخوردهای کاذب (هش برابر، متن متفاوت) را با پیمانه‌ی عمداً کوچک و پیمانه‌ی بزرگ شمردم:

```
RK random mod=101        matches=1 hash-hits=81 spurious=80
RK random mod=1000000007 matches=1 hash-hits=1 spurious=0
```

با ۱۰۱ مقدار ممکن برای هش، یک پنجره حدود یک بار از ۱۰۱ بار اتفاقی جور می‌شود: اینجا ۸۰ هشدار اشتباه، هرکدام با هزینه‌ی یک بررسی. درستی هرگز به پیمانه بستگی ندارد (بررسی همه را می‌گیرد)؛ فقط سرعت بستگی دارد. Rabin–Karp می‌تواند چند الگوی هم‌طول را هم‌زمان جست‌وجو کند: هش آن‌ها را در یک مجموعه بگذار و هر پنجره را در آن جست‌وجو کن.

## بایت، rune و فارسی

KMP بالا روی بایت کار می‌کند. برای تطبیق دقیق روی UTF-8 هم درست است، چون الگوی معتبر UTF-8 فقط در مرز نویسه می‌تواند جور شود. نکته در اندیس است:

```
bytes: [0 20] len bytes 33 runes 18
 byte 0 -> rune 0
 byte 20 -> rune 11
```

جست‌وجوی «سلام» در «سلام دنیا، سلام گو» آفست‌های بایتی ۰ و ۲۰ را می‌دهد؛ تطابق دوم یازدهمین {{< term "rune" "rune" >}} است. حروف فارسی هرکدام دو بایت‌اند. جست‌وجوی بدون حساسیت به حروف و نرمال‌سازی یونیکد (یک حرف با دنباله‌های متفاوتی از نقطه‌های کد) مسئله‌های جدا هستند؛ فقط توضیح می‌دهم و اجرا نکردم: اول هر دو رشته را نرمال کنید، بعد جست‌وجو.

## `strings.Index` چه می‌کند

سورس Go 1.26 را خواندم. طبق آن، `strings.Index` الگوی تک‌بایتی را با `IndexByte` حل می‌کند، برای الگوهای کوتاه روال‌های بهینه دارد، و وقتی `IndexByte` مدام شروع کاذب می‌دهد به یک fallback از نوع Rabin–Karp (`bytealg.IndexRabinKarp`، هش ۳۲ بیتی با سرریز) می‌رود. اینها جزئیات پیاده‌سازی‌اند و ممکن است عوض شوند.

## تست در برابر کتابخانه‌ی استاندارد

یک تست ۵۰۰۰ متن و الگوی تصادفی روی `{a,b}` می‌سازد (seed 7، طول تا ۶۰ و ۵) و بررسی می‌کند KMP و Rabin–Karp (پیمانه‌ی ۱۰۱ برای وادار کردن برخورد) همان تطابق‌های یک پیمایش ساده را بدهند و اولین تطابق با `strings.Index` برابر باشد. `go test -race` سبز است. الفبای کوچک پیشوندهای تکراری زیاد می‌سازد.

## پیچیدگی

| الگوریتم | پیش‌پردازش | جست‌وجو | بدترین حالت |
|---|---|---|---|
| ساده | ندارد | O(n·m) | O(n·m) |
| KMP | O(m) | O(n) | O(n + m) |
| Rabin–Karp | O(m) | O(n) انتظاری | O(n·m) اگر هش‌ها برخورد کنند |

ابزارهای دیگر که فقط نامشان را می‌آورم: الگوریتم Z (همان ایده‌ی تابع شکست با محاسبه‌ای دیگر) و suffix array (متن را یک بار ایندکس کن، بعد به پرسش‌های الگوی زیاد جواب بده).

## چند نکته‌ی مهم

- ببینید زبانتان رشته را با بایت، واحد UTF-16 یا نقطه‌ی کد اندیس می‌کند.
- برخورد هش فقط یک اشاره است؛ همیشه تأیید کنید.
- با الفبای خیلی کوچک تست کنید و با پیاده‌سازی بدیهی مقایسه کنید.

## تمرین

`RabinKarp` را با یک map از هش‌ها برای چند الگوی هم‌طول بنویسید و برخوردهای کاذب را با پیمانه‌ی ۱۰۱ بشمارید. بعد جدول شکست `aabaaab` را اول با دست بنویسید و با `Prefix` بررسی کنید.
