در مقاله‌ی قبلی، [کوتاه‌ترین مسیر و Dijkstra](/fa/posts/algo-shortest-paths-dijkstra/)، یال‌ها هزینه داشتند. اینجا ترتیب دارند: «`log` را پیش از `db` بساز». build، importها و ابزارهای اجرای کار همه به این نیاز دارند و ابزارش همان [پیمایش گراف](/fa/posts/algo-graphs-bfs-dfs/) و یک [صف](/fa/posts/algo-stacks-queues-deques/) است که می‌شناسید.

> Go 1.26، مثال محلی، تست با `go test -race`. میانگین بار ماشین بالای ۴ بود، پس فقط شمارش منتشر می‌کنم، نه زمان.

## چرا باید DAG باشد

یال `u -> v` یعنی u پیش از v. یک {{< term "topological-sort" "ترتیب توپولوژیک" >}} همه‌ی رأس‌ها را طوری فهرست می‌کند که همه‌ی یال‌ها رو به جلو باشند. این فقط برای {{< term "dag" "DAG" >}} ممکن است: در `a -> b -> c -> a` هر کدام باید پیش از بعدی بیاید، پس ترتیبی وجود ندارد. مثال من راه‌اندازی یک سرویس کوچک است با ده یال مثل `log -> config`، `config -> db` و `store -> api`.

## Kahn: صف با in-degree

{{< term "in-degree" "in-degree" >}} یک رأس یعنی چند پیش‌نیاز هنوز مانده است. همه‌ی رأس‌های با in-degree برابر ۰ را در یک {{< term "queue" "صف" >}} می‌گذاریم. یکی را برمی‌داریم، خروجی می‌دهیم، in-degree جانشین‌هایش را کم می‌کنیم و آن‌هایی که به ۰ رسیدند وارد صف می‌شوند. اگر کمتر از V رأس خارج شد، دور وجود داشته است.

## DFS: postorder معکوس

با {{< term "dfs" "DFS" >}} هر رأس را وقتی اضافه می‌کنیم که همه‌ی جانشین‌هایش تمام شده‌اند، و در پایان فهرست را برعکس می‌کنیم. هر دو الگوریتم روی یک گراف:

```
kahn  : [log metrics config db http store api main] {8 20}
dfs   : [metrics log config http db store api main] {8 10}
```

هر دو ترتیب معتبرند و با هم فرق دارند. جفت اعداد `{Visits, EdgeChecks}` است: هر کدام ۸ رأس. شمارنده‌ی Kahn من هر یال را دو بار می‌شمارد (یک بار برای محاسبه‌ی in-degree و یک بار هنگام کم کردن)، پس 20 = 2E؛ DFS هر یال را یک بار می‌بیند، 10 = E. هر دو O(V+E) هستند.

## ترتیب پایدار

ترتیب یکتا نیست و برای buildهای تکرارپذیر آزاردهنده است. صف را با یک {{< term "binary-heap" "min-heap" >}} از نام‌ها عوض می‌کنیم تا کوچک‌ترین نامِ آماده اول برود:

```
stable: [log config db http metrics store api main]
```

ورودی یکسان، خروجی یکسان در هر اجرا، مستقل از ترتیب map.

## دور با مسیر دقیق

سه رنگ: سفید (دیده‌نشده)، خاکستری (روی پشته‌ی فعلی DFS)، سیاه (تمام‌شده). یالی به رأس خاکستری یک دور می‌بندد و پشته مسیرش را دارد. این ورودی را دادم: `app -> lib -> util -> codec -> lib`:

```
error: cycle: lib -> util -> codec -> lib
kahn on cyclic: true
```

Kahn فقط می‌فهمد جایی گیر کرده (خط آخر یعنی `o == nil`)؛ DFS می‌تواند حلقه را نام ببرد.

## تست property

تست ۳۰۰ DAG تصادفی می‌سازد (seed از ۰ تا ۲۹۹، ۲ تا ۴۱ رأس) و فقط یال از رأس زودتر به دیرتر در یک ترتیب پنهان می‌گذارد. برای Kahn، DFS و نسخه‌ی پایدار بررسی می‌کند هر یال `u -> v` شرط `pos[u] < pos[v]` را داشته باشد، همه‌ی رأس‌ها حاضر باشند و شمارنده‌ها دقیقاً V و 2E و غیره باشند. تست دوم پیام دور را بررسی می‌کند. هر دو با `-race` می‌گذرند. این بررسی به سبک {{< term "property-based-testing" "property-based" >}} است: ترتیب درست را نمی‌داند، فقط قانونی را که هر ترتیب باید رعایت کند.

## موج‌ها و مسیر بحرانی

رأس‌ها را به ترتیب توپولوژیک پردازش می‌کنیم و `depth[v] = max(depth[u] + 1)` را روی پیش‌نیازها می‌گذاریم. رأس‌های هم‌عمق به هم وابسته نیستند و می‌توانند موازی اجرا شوند:

```
  0 [log metrics]
  1 [config]
  2 [db http]
  3 [store]
  4 [api]
  5 [main]
critical path length: 6
```

با کارگر نامحدود build در ۶ گام تمام می‌شود، چون `log -> config -> db -> store -> api -> main` یک زنجیره است. این زنجیره {{< term "critical-path" "مسیر بحرانی" >}} است. سریع‌تر کردن `metrics` چیزی را عوض نمی‌کند؛ سریع‌تر کردن `db` عوض می‌کند. اینجا تعداد کارها شمرده شده نه مدتشان؛ با مدت‌ها باید وزن‌ها را روی مسیر جمع کرد.

## یک ابزار واقعی: go list -deps

ماژول کوچکی به نام `tiny` ساختم که `a` پکیج‌های `b` و `c` را import می‌کند و `b` هم `c` را. بعد `go list -deps .` را اجرا کردم:

```
tiny/c
tiny/b
tiny/a
internal/goarch
...
tiny
```

(خط‌های کتابخانه‌ی استاندارد را حذف کردم.) هر پکیج بعد از همه‌ی چیزهایی می‌آید که import می‌کند و خود `tiny` آخر است. این یک ترتیب توپولوژیک است و ابزار Go برای کامپایل به آن نیاز دارد. فقط همین مورد کوچک را با چشم بررسی کردم، نه کل کتابخانه‌ی استاندارد را.

## چند نکته‌ی مهم

- ترتیب یکتا نیست؛ اگر تکرارپذیری می‌خواهید tie-break اضافه کنید.
- دور را بررسی کنید و مسیرش را گزارش دهید، نه فقط «شکست خورد».
- جهت یال مهم است: تصمیم بگیرید `u -> v` یعنی «u پیش از v» یا «u به v نیاز دارد».
- موج‌ها کارگر نامحدود فرض می‌کنند.

## تمرین

به `Waves` مدت کار اضافه کنید و برای هر کار زودترین زمان پایان و مسیر بحرانی وزن‌دار را حساب کنید.
