صبح که لباس می‌پوشید، ترتیبی هست که خودتان نمی‌شناسیدش و فقط رعایت می‌کنید: جوراب پیش از کفش، شلوار پیش از کمربند، پیراهن پیش از کت. بین بعضی کارها ترتیب مهم نیست (جوراب و ساعت)، و بین بعضی دیگر مهم است. برنامه‌ها هم پر از همین‌اند. `go list -deps` هر پکیج را بعد از پکیج‌هایی که import می‌کند چاپ می‌کند، چون کامپایل به همین ترتیب لازم دارد. یک سیستم build یا یک ابزار اجرای کارها هم همین را می‌خواهد: «`log` را پیش از `db` بساز».

در [پست قبل](/fa/posts/algo-shortest-paths-dijkstra/) یال‌های گراف هزینه داشتند. اینجا یال‌ها ترتیب را می‌گویند: `u -> v` یعنی «u باید پیش از v بیاید». ابزارش همان [پیمایش گراف](/fa/posts/algo-graphs-bfs-dfs/) و یک [صف](/fa/posts/algo-stacks-queues-deques/) است که از قبل می‌شناسید. در این پست دو الگوریتم برای پیدا کردن چنین ترتیبی می‌بینیم، بعد می‌بینیم چطور دورها را (که ترتیب را ناممکن می‌کنند) پیدا کنیم و گزارش بدهیم، و در آخر از همین ترتیب برای تقسیم کارها به مرحله‌های موازی استفاده می‌کنیم.

> همه‌ی خروجی‌ها را با Go 1.27 دوباره اجرا کردم. مثال محلی است و تست‌هایش با `go test -race` سبز است. ماشین شلوغ بود، پس زمان منتشر نمی‌کنم؛ فقط شمارش می‌بینید که در هر اجرا یکی است.

## ترتیب توپولوژیک چیست؟

فرض کنید سه کار داریم: `a` پیش از `b` و `b` پیش از `c`. فقط یک ترتیب درست هست: `a, b, c`. حالا فرض کنید `a` پیش از `b` و `a` پیش از `c`، و بین `b` و `c` رابطه‌ای نیست. هر دو `a, b, c` و `a, c, b` درست‌اند. پس ترتیب لزوماً یکتا نیست.

{{< term "topological-sort" "ترتیب توپولوژیک" >}} همه‌ی رأس‌های یک گراف جهت‌دار را طوری در یک فهرست می‌گذارد که هر یال `u -> v` در فهرست رو به جلو باشد، یعنی u پیش از v بیاید. اما همیشه ممکن نیست. اگر `a -> b -> c -> a` باشد، هر کدام باید پیش از بعدی بیاید و این هیچ‌جا تمام نمی‌شود: ترتیبی وجود ندارد. ترتیب توپولوژیک فقط برای گرافی ممکن است که دور نداشته باشد؛ چنین گرافی را {{< term "dag" "DAG" >}} می‌گویند (گراف جهت‌دار بی‌دور).

مثال ما راه‌اندازی یک سرویس کوچک است. هر یال می‌گوید «این باید پیش از آن بالا بیاید»:

```
log -> config    log -> db       log -> http
config -> db     config -> http
db -> store      store -> api    http -> api
metrics -> api   api -> main
```

هشت رأس (`log config db http store api main metrics`) و ده یال.

## الگوریتم Kahn: هر چه پیش‌نیاز ندارد، برود

اولین ایده خیلی طبیعی است. چه کاری را می‌شود همین الان انجام داد؟ کاری که هیچ پیش‌نیاز انجام‌نشده‌ای ندارد. آن را انجام می‌دهیم، از پیش‌نیاز بقیه خط می‌زنیم، و دوباره می‌پرسیم کدام کار حالا آزاد شد.

برای شمردن «پیش‌نیازهای مانده» به هر رأس یک عدد می‌دهیم: {{< term "in-degree" "in-degree" >}}، یعنی تعداد یال‌هایی که به آن رأس وارد می‌شوند. الگوریتم:

1. in-degree همه‌ی رأس‌ها را حساب کن.
2. رأس‌هایی را که in-degree‌شان ۰ است در یک {{< term "queue" "صف" >}} بگذار.
3. تا وقتی صف خالی نشده: اولین رأس را بردار و در خروجی بنویس. برای هر یال خروجی‌اش، in-degree مقصد را یکی کم کن؛ اگر به ۰ رسید، مقصد را به صف اضافه کن.
4. اگر در آخر کمتر از V رأس در خروجی بود، یعنی بعضی رأس‌ها هیچ‌وقت in-degree ۰ نشدند: دور وجود دارد.

روی مثال خودمان: in-degreeها این‌اند: `log` ۰، `metrics` ۰، `config` ۱، `db` ۲، `http` ۲، `store` ۱، `api` ۳، `main` ۱. صف اول `[log, metrics]` است.

| برداشتیم | چه آزاد شد | صف بعد از آن | خروجی تا اینجا |
|---|---|---|---|
| log | config (۰ شد)؛ db و http هنوز یک پیش‌نیاز دارند | [metrics, config] | log |
| metrics | (api هنوز دو پیش‌نیاز دارد) | [config] | log metrics |
| config | db و http هر دو ۰ شدند | [db, http] | log metrics config |
| db | store | [http, store] | log metrics config db |
| http | (api هنوز store را می‌خواهد) | [store] | log metrics config db http |
| store | api | [api] | log metrics config db http store |
| api | main | [main] | log metrics config db http store api |
| main | | [] | log metrics config db http store api main |

خروجی `log metrics config db http store api main` است. هر پیش‌نیازی پیش از وابسته‌اش آمده.

## الگوریتم DFS: آخر از همه تمام شده‌ها، اول از همه

ایده‌ی دوم برعکس به مسئله نگاه می‌کند. مثال ساده‌ی `a -> b -> c` را در نظر بگیرید. اگر با {{< term "dfs" "DFS" >}} از `a` شروع کنیم، اول به `c` می‌رسیم و کارش تمام می‌شود (`c` جایی ندارد که برود)، بعد `b`، بعد `a`. ترتیب «تمام شدن» می‌شود `c, b, a`. یک رأس فقط وقتی تمام می‌شود که همه‌ی چیزهایی که به آن وابسته‌اند تمام شده باشند. پس اگر این ترتیب را برعکس کنیم، `a, b, c` می‌شود که همان ترتیب درست است.

الگوریتم: DFS را از هر رأس دیده‌نشده اجرا کن، هر رأس را وقتی تمام شد (بعد از همه‌ی جانشین‌هایش) به فهرست اضافه کن، و در آخر فهرست را برعکس کن. به این فهرست «postorder معکوس» می‌گویند.

دمو هر دو الگوریتم را روی همین گراف اجرا می‌کند:

```
kahn  : [log metrics config db http store api main] {8 20}
dfs   : [metrics log config http db store api main] {8 10}
```

خط Kahn همان است که با دست به دست آوردیم. هر دو ترتیب معتبرند ولی با هم فرق دارند: برای مثال DFS `http` را پیش از `db` گذاشته، و این اشکالی ندارد چون بین آن دو یالی نیست. جفت `{8 20}` و `{8 10}` شمارنده‌ی `{Visits, EdgeChecks}` است: هر الگوریتم ۸ رأس را دیده. شمارنده‌ی Kahn در کد من هر یال را دو بار می‌شمارد، یک بار هنگام حساب in-degree و یک بار هنگام کم کردنش، پس ۲۰ = 2E. DFS هر یال را یک بار می‌بیند، پس ۱۰ = E. هر دو O(V+E) هستند.

## وقتی ترتیب باید همیشه یکی باشد

دیدیم که ترتیب یکتا نیست. ولی برای build تکرارپذیر یا تست، اینکه هر بار ترتیب دیگری درآید آزاردهنده است. راهش این است که وقتی چند رأس همزمان آماده‌اند، همیشه یک قاعده‌ی ثابت داشته باشیم. در Kahn به‌جای صف از یک {{< term "binary-heap" "min-heap" >}} از نام‌ها استفاده می‌کنیم تا از میان کارهای آماده، کوچک‌ترین نام (به ترتیب الفبا) اول برود:

```
stable: [log config db http metrics store api main]
```

اینجا `metrics` تا لحظه‌ی آخر منتظر می‌ماند، چون `config` و `db` و `http` از نظر الفبایی از آن کوچک‌ترند و وقتی آماده بودند اول رفتند. ورودی یکسان همیشه خروجی یکسان می‌دهد، مستقل از ترتیب درج یا ترتیب پیمایش map.

## دور: فقط «شکست» نه، خود دور را نشان بدهید

اگر ورودی دور داشته باشد، پیام «ترتیبی وجود ندارد» به درد نمی‌خورد؛ کاربر می‌خواهد بداند کدام کارها دور زده‌اند. Kahn فقط می‌فهمد گیر کرده (کمتر از V رأس خارج شد). DFS می‌تواند خود دور را نام ببرد. همان سه رنگ پست قبل: سفید (دیده‌نشده)، خاکستری (روی مسیر فعلی DFS) و سیاه (تمام‌شده). اگر یالی به رأس خاکستری برسد، دور بسته شده و مسیر فعلی DFS (که در یک stack نگه می‌دارم) دقیقاً دور را دارد. ورودی: `app -> lib -> util -> codec -> lib`.

```
error: cycle: lib -> util -> codec -> lib
kahn on cyclic: true
```

خط اول پیام DFS است: `app` در دور نیست، فقط به دور وصل است، و پیام دقیقاً سه رأس دور را نشان می‌دهد. خط دوم یعنی Kahn روی همین ورودی `nil` برگرداند (`o == nil`)؛ می‌داند که ترتیبی نیست ولی نمی‌داند کدام رأس‌ها مقصرند.

## از کجا بدانیم درست است؟

دانستن ترتیب درست از قبل ممکن نیست (یکتا نیست)، ولی قانونی هست که هر ترتیب درستی باید رعایت کند: برای هر یال `u -> v`، موقعیت u در فهرست کوچک‌تر از موقعیت v باشد. تست ۳۰۰ DAG تصادفی می‌سازد (۲ تا ۴۱ رأس)، با این روش که یک ترتیب پنهان تصادفی در نظر می‌گیرد و فقط یال‌هایی از رأس زودتر به دیرتر می‌گذارد (پس دور نمی‌شود). برای Kahn، DFS و نسخه‌ی پایدار بررسی می‌کند که قانون برای هر یال برقرار است، همه‌ی رأس‌ها حاضرند، و شمارنده‌ی Kahn دقیقاً V و 2E است. تست دوم پیام دور را بررسی می‌کند. این بررسی به سبک {{< term "property-based-testing" "property-based" >}} است: جواب درست را نمی‌داند، فقط قانونی را می‌داند که هر جواب درست باید داشته باشد.

## موج‌ها و مسیر بحرانی

ترتیب توپولوژیک چیز دیگری هم می‌دهد. فرض کنید هر کار یک واحد زمان می‌برد و به هر تعداد کارگر دارید. کدام کارها را می‌شود همزمان انجام داد؟ هر رأس را به ترتیب توپولوژیک پردازش می‌کنیم و `depth[v] = max(depth[u] + 1)` را روی پیش‌نیازهایش می‌گذاریم، یعنی طولانی‌ترین زنجیره‌ای که به آن می‌رسد. رأس‌های هم‌عمق به هم وابسته نیستند و می‌توانند موازی اجرا شوند:

```
  0 [log metrics]
  1 [config]
  2 [db http]
  3 [store]
  4 [api]
  5 [main]
critical path length: 6
```

هر خط یک «موج» است. در موج ۰ هم `log` و هم `metrics` می‌توانند شروع شوند، در موج ۲ هم `db` و هم `http`. با کارگر نامحدود کل build در ۶ گام تمام می‌شود، چون `log -> config -> db -> store -> api -> main` یک زنجیره‌ی شش‌رأسی است و هیچ‌کدام از حلقه‌های آن را نمی‌شود موازی کرد. این طولانی‌ترین زنجیره {{< term "critical-path" "مسیر بحرانی" >}} نام دارد. سریع‌تر کردن `metrics` چیزی را عوض نمی‌کند، چون روی مسیر بحرانی نیست؛ سریع‌تر کردن `db` عوض می‌کند. دقت کنید این‌جا فقط تعداد کارها شمرده شده نه مدت‌شان؛ برای مدت‌های واقعی باید به‌جای ۱ مدت هر کار را جمع زد.

## یک ابزار واقعی: go list -deps

برای اینکه ببینیم Go هم همین کار را می‌کند، ماژول کوچکی به نام `tiny` ساختم: پکیج `a` پکیج‌های `b` و `c` را import می‌کند و `b` هم `c` را. بعد `go list -deps .` را اجرا کردم:

```
tiny/c
tiny/b
tiny/a
internal/goarch
...
tiny
```

(بقیه‌ی پکیج‌های کتابخانه‌ی استاندارد را که `main` برای اجرا لازم دارد، حذف کردم؛ در کل ۳۲ خط بود.) `tiny/c` اول است چون کسی را import نمی‌کند، بعد `tiny/b` که `c` را می‌خواهد، بعد `tiny/a` که هر دو را می‌خواهد، و `tiny` که `a` را import می‌کند آخر است. طبق `go help list`، گزینه‌ی `-deps` پکیج‌ها را با پیمایش depth-first و به ترتیب postorder می‌بیند تا هر پکیج پس از همه‌ی وابستگی‌هایش فهرست شود؛ یعنی همان الگوریتم DFS بالا. فقط چون یال‌های اینجا «import می‌کند» هستند، لازم نیست فهرست را معکوس کنیم. من فقط همین مورد کوچک را با چشم بررسی کردم، نه کل کتابخانه‌ی استاندارد را.

## دام‌های ترتیب‌دهی

- **ترتیب یکتا نیست.** اگر خروجی‌تان باید همیشه یکی باشد، مثل ورودی build یا تست، یک tie-break ثابت (مثل مرتب‌سازی نام‌ها) اضافه کنید.
- **دور را فقط «شکست» گزارش نکنید.** مسیر دقیق دور را به کاربر بدهید؛ پیدا کردنش با DFS کم‌هزینه است.
- **جهت یال را از اول تعریف کنید.** `u -> v` یعنی «u پیش از v» یا «u به v نیاز دارد»؟ این دو عکس هم‌اند، و اگر قرارداد را قاطی کنید ترتیب برعکس درمی‌آید.
- **موج‌ها کارگر نامحدود فرض می‌کنند.** با تعداد کارگر محدود، ترتیب واقعی بیشتر طول می‌کشد.

## تمرین

به `Waves` مدت کار اضافه کنید و برای هر کار زودترین زمان پایان و مسیر بحرانی وزن‌دار را حساب کنید. بعد `KahnStable` را طوری تغییر دهید که از میان کارهای آماده، آن را که طولانی‌ترین زنجیره‌ی باقی‌مانده را دارد اول بردارد.
