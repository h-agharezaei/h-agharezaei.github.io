در مقاله‌ی قبلی، [مرتب‌سازی: quick، merge و heap](/fa/posts/algo-sorting/)، یک بار ترتیب را ساختیم. درخت جست‌وجو داده را وقتی عوض می‌شود هم مرتب نگه می‌دارد، پس درج، جست‌وجو و حذف ارزان می‌مانند. این همان ایده‌ی [جست‌وجوی دودویی و invariant](/fa/posts/algo-binary-search-invariants/) است، به شکل پویا، و پسرعمو پهنش همان ایندکسی است که در [ایندکس B-tree و EXPLAIN ANALYZE](/fa/posts/db-indexes-btree-explain/) دیدیم.

> Go 1.26، مثال محلی، تست با `go test -race`. بار این ماشین برای زمان‌گیری زیاد بود (در آخرین بررسی ۳٫۹۷)، پس همه‌چیز قطعی است: ارتفاع و تعداد مقایسه.

## درخت جست‌وجوی دودویی

{{< term "binary-search-tree" "درخت جست‌وجوی دودویی" >}} کلیدهای کوچک‌تر را در زیردرخت چپ و بزرگ‌تر را در راست می‌گذارد. نسخه‌ی جنریک من یک تابع مقایسه می‌گیرد؛ جست‌وجو و درج یک مسیر را می‌روند. `Delete` سه حالت کلاسیک دارد:

```go
switch {
case x.left == nil:  *pp = x.right // بدون فرزند، یا فقط فرزند راست
case x.right == nil: *pp = x.left  // فقط فرزند چپ
default: // دو فرزند: جانشین in-order را جای آن بگذار
	sp := &x.right
	for (*sp).left != nil { sp = &(*sp).left }
	s := *sp
	*sp = s.right
	s.left, s.right = x.left, x.right
	*pp = s
}
```

{{< term "tree-traversal" "پیمایش" >}}های pre-order، post-order، level-order (با queue) و in-order هم هست؛ in-order کلیدها را مرتب برمی‌گرداند. `Range(lo, hi)` زیردرخت‌هایی را که نمی‌توانند جواب بدهند رد می‌کند. یک تست ۲۰٬۰۰۰ درج و حذف تصادفی را با یک oracle (slice مرتب) مقایسه می‌کند: محتوا، جست‌وجو و range. سبز است.

## ورودی مرتب، درخت را می‌کشد

ارتفاع هزینه‌ی هر عملیات است. کلیدهای 0 تا n-1 را مرتب درج کردم و بعد همان‌ها را بُر خورده (seed برابر 42). ارتفاع را با حلقه‌ی غیربازگشتی شمردم تا درخت منحط stack را نترکاند:

```
n=1000   sorted   BST=1000  AVL=10  min=ceil(log2(n+1))=10  max<1.44*log2(n+2)=14.4
n=1000   shuffled BST=20    AVL=12  min=ceil(log2(n+1))=10  max<1.44*log2(n+2)=14.4
n=10000  sorted   BST=10000 AVL=14  min=ceil(log2(n+1))=14  max<1.44*log2(n+2)=19.1
n=10000  shuffled BST=35    AVL=16  min=ceil(log2(n+1))=14  max<1.44*log2(n+2)=19.1
```

ورودی مرتب ارتفاع n می‌دهد: یک لیست پیوندی. ورودی بُرخورده ۲۰ و ۳۵ می‌دهد، نزدیک مقیاس log2 n. داده و کد یکی است، فقط ترتیب فرق دارد.

## AVL: ترمیم با چرخش

{{< term "avl-tree" "درخت AVL" >}} ارتفاع هر node را نگه می‌دارد و بعد از هر درج یا حذف، هر node‌ای را که ارتفاع دو زیردرختش بیش از ۱ فرق دارد با {{< term "tree-rotation" "چرخش (rotation)" >}} درست می‌کند:

```go
func rotR[K any](y *node[K]) *node[K] { // y.left ریشه می‌شود
	x := y.left
	y.left, x.right = x.right, y
	upd(y); upd(x)
	return x
}
```

چهار حالت داریم. LL و RR یک چرخش می‌خواهند و LR و RL دو تا (اول فرزند را بچرخان). در همه‌ی حالت‌ها سه کلید متعادل می‌شوند:

```
LL (3,2,1)   RR (1,2,3)   LR (3,1,2)   RL (1,3,2)
    3            1            3            1
   /              \          /              \
  2                2        1                3
 /                  \        \              /
1                    3        2            2
          همه می‌شوند:  2
                       / \
                      1   3
```

دمو ترتیب level-order هر کدام را چاپ می‌کند: هر چهار حالت `[2 1 3]` می‌دهند، در حالی که BST ساده همان زنجیر را نگه می‌دارد. یک تست ترتیب، ارتفاع‌های ذخیره‌شده و قاعده‌ی تعادل را بعد از هر یک از ۲۰٬۰۰۰ عملیات تصادفی و بعد از ۱۰٬۰۰۰ درج مرتب چک می‌کند. در جدول بالا ارتفاع AVL برای ورودی مرتب ۱۰ و ۱۴ است (کمترین ممکن) و برای بُرخورده ۱۲ و ۱۶، همیشه زیر حد 1.44 log2.

تعداد مقایسه برای ۱۰۰٬۰۰۰ جست‌وجوی تصادفی در درخت ۱۰٬۰۰۰ کلیدی:

```
BST, shuffled input    total=1903183    per search=19.0
BST, sorted input      total=499193738  per search=4991.9
AVL, sorted input      total=1236443    per search=12.4
```

درخت منحط برای هر جست‌وجو حدود ۴٬۹۹۲ مقایسه می‌خواهد، یعنی ۴۰۰ برابر ۱۲٫۴ در AVL.

## چرا دیتابیس درخت پهن می‌خواهد

درخت دودویی از نظر مقایسه کم‌عمق است، اما هر node یک خواندن جدا است. دیسک و دیتابیس کل صفحه می‌خوانند، پس {{< term "b-tree" "B-tree" >}} صدها کلید را در یک node می‌گذارد. ارتفاع حدود لگاریتم n در مبنای {{< term "fan-out" "fan-out" >}} است؛ با کد حساب شده:

```
fanout   n=1e6      n=1e9
2        20         30
16       5          8
128      3          5
512      3          4
```

در [ایندکس B-tree و EXPLAIN ANALYZE](/fa/posts/db-indexes-btree-explain/)، ایندکس `orders.customer_id` (۲۰۰ هزار ردیف) ۲۳۲ صفحه (۱۸۵۶ کیلوبایت) دارد و `bt_metap` سطح ۱ را نشان داد: یک ریشه و برگ‌ها. ایندکس کلید اصلی سطح ۲ داشت، برای همین `WHERE id = 123` فقط ۷ buffer خرج کرد. من اینجا B-tree پیاده نکردم و `github.com/google/btree` را هم امتحان نکردم.

## چند نکته‌ی مهم

- BST ساده برای کلید تصادفی خوب است، برای کلید مرتب مثل timestamp یا ID خطرناک.
- AVL مرتبه‌ی O(log n) را تضمین می‌کند ولی در هر نوشتن هزینه‌ی نگه‌داری ارتفاع دارد.
- درخت‌های اشاره‌گری در حافظه {{< term "cache-locality" "محلیت حافظه" >}}ی بدی دارند؛ node پهن اینجا هم کمک می‌کند.
- در Go وقتی خواندن غالب است، slice مرتب با `slices.BinarySearch` اغلب کافی است.
- درخت را با یک oracle ساده تست کنید و invariant را بعد از هر عملیات چک کنید.

## تمرین

به BST متدهای `Min`، `Max` و `Floor(k)` (بزرگ‌ترین کلید کوچک‌تر یا مساوی k) را اضافه کنید و `Floor` را با oracle مرتب و `slices.BinarySearch` تست کنید.
