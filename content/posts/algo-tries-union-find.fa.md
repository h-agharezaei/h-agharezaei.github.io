در مقاله‌ی قبلی، [درخت جست‌وجو و B-tree](/fa/posts/algo-trees-bst-btree/)، کلیدها با هم مقایسه می‌شدند. دو ساختار این عادت را کنار می‌گذارند. {{< term "trie" "trie" >}} نویسه‌های کلید را قدم‌به‌قدم می‌رود، پس هزینه‌اش به طول کلید بستگی دارد نه به تعداد کلیدها. {{< term "union-find" "union-find" >}} به یک سؤال جواب می‌دهد، «این دو چیز در یک گروه‌اند؟»، آن هم تقریباً در زمان ثابت. هر دو با ایده‌های [hash table از صفر](/fa/posts/algo-hash-tables/) و [تحلیل Big-O با اندازه‌گیری واقعی](/fa/posts/algo-big-o-measured/) هم‌خانواده‌اند.

> Go 1.26، مثال محلی، تست با `go test -race`. موقع اجرا بار این ماشین بالای ۴ بود، پس زمان‌گیری نداریم: فقط شمارش و بایت.

## یک trie

هر گره فرزندهایی دارد که با یک rune کلید خورده‌اند و یک پرچم `end`. `Insert`، `Search` و `HasPrefix` یک مسیر را می‌روند:

```go
type tnode struct {
	next map[rune]*tnode
	end  bool
}
```

`Autocomplete(prefix, limit)` گره‌ی پیشوند را پیدا می‌کند، بعد هرچه زیر آن است را به ترتیب مرتب می‌گردد و در `limit` می‌ایستد. من کلمه‌های کوچک `/usr/share/dict/words` (فهرست کلمه‌ی macOS) را بار کردم و همه را درج کردم:

```
words=210773 chars=2039158 trie nodes=696834 (34.2% of chars)
Search(trie) false Search(tri) true HasPrefix(tri) true HasPrefix(xq) false
Autocomplete("algo", 5): [algocyan algodoncillo algodonite algoesthesiometer algogenic]
Autocomplete("trie", 10): [tried triedly trielaidin triene triennial trienniality triennially triennium triens triental]
```

مجموع نویسه‌های کلمه‌ها ۲٬۰۳۹٬۱۵۸ است ولی trie فقط ۶۹۶٬۸۳۴ گره می‌خواهد: کلمه‌ها پیشوندشان را به اشتراک می‌گذارند و حدود دو سوم نویسه‌ها هزینه‌ای ندارند. (`Search("trie")` نادرست است چون این فهرست «trie» را به‌عنوان کلمه ندارد، ولی «tri» را دارد.) یک تست trie را روی کلمه‌های تصادفی، از جمله متن فارسی، با map و پیمایش مرتب مقایسه می‌کند، پس runeها درست کار می‌کنند.

## گره با map یا با آرایه

گره‌ی map‌دار کوچک تعریف می‌شود ولی خود map جداگانه حافظه می‌گیرد. گره‌ی `[26]*anode` اندیس‌گذاری ثابت دارد و map ندارد، اما حتی برای برگ هم ۲۶ اشاره‌گر دارد. `unsafe.Sizeof` و بایت‌های تخصیص‌یافته هنگام ساخت (اندازه‌گیری همین‌جا با `runtime.MemStats`، پس تقریبی بدانیدشان):

```
Sizeof map node: 16  array node: 216  map header pointer: 8
bytes allocated: map trie=112873376 (162/node), array trie=156090816 (224/node)
```

روی این فهرست، trie آرایه‌ای بزرگ‌تر است، حدود ۲۲۴ بایت در برابر ۱۶۲ برای هر گره، و فقط `a-z` را پوشش می‌دهد. شاید هر قدمش سریع‌تر باشد؛ آن را اندازه نگرفتم. جایی که گره‌ها فرزند کم دارند، و در عمق درخت بیشترشان همین‌طورند، map ارزان‌تر است.

## union-find

یک آرایه‌ی `parent` نگه می‌داریم. هر مجموعه یک درخت است و ریشه نماینده‌اش. `Find` والدها را تا ریشه می‌رود و `Union` یک ریشه را زیر دیگری می‌برد. دو بهینه‌سازی داریم: {{< term "path-compression" "path compression" >}} (در `Find` کل مسیر را به ریشه وصل کن) و {{< term "union-by-size" "union by size" >}} (درخت کوچک‌تر را زیر بزرگ‌تر بگذار). `UF` من برای هر دو پرچم دارد و هر گام والد را می‌شمارد. اول یک زنجیره: `Union(i+1, i)` برای ۲۰٬۰۰۰ عنصر و بعد ۲۰٬۰۰۰ بار `Find(0)`:

```
none              hops(unions)=0      hops(20000 Find(0))=399980000
by size only      hops(unions)=19997  hops(20000 Find(0))=20000
compression only  hops(unions)=0      hops(20000 Find(0))=39998
both              hops(unions)=19997  hops(20000 Find(0))=20000
```

بدون هیچ‌کدام، درخت یک لیست ۲۰٬۰۰۰تایی است و هر `Find` همه‌اش را می‌رود. حالا unionهای تصادفی (seed برابر 7) و بعد `Find` روی همه‌ی عنصرها:

```
100000 random unions on 100000 elements
none                222100465  552463368
compression only       377426     164241
by size only           180584     183368
both                   134293     110884

1000000 random unions on 1000000 elements
none                (not run: too slow)
compression only      4365473    1642501
by size only          1823203    1853238
both                  1344183    1108882
```

ستون‌ها گام‌های حین unionها و گام‌های گذر آخر هستند. نسخه‌ی بدون بهینه‌سازی برای ۱۰۰٬۰۰۰ عنصر ۲۲۲ میلیون گام لازم داشت، پس آن را روی یک میلیون اجرا نکردم. با هر دو بهینه‌سازی، یک میلیون union حدود ۱٫۳ گام برای هر کدام هزینه دارد. طبق منابع، هزینه‌ی {{< term "amortized-analysis" "سرشکن‌شده" >}} تابع معکوس Ackermann است که برای هر ورودی عملی کمتر از ۵ است؛ اثباتش را اینجا نمی‌آورم.

## کاربردها

هر چهار مورد از همان `UF` استفاده می‌کنند و برای هر کدام تست داریم. مؤلفه‌های ۸ گره با یال‌های 0-1، 1-2، 3-4، 5-6، 6-7 و 7-5 خروجی `components: 3` و گروه‌های `[0 1 2]`، `[3 4]` و `[5 6 7]` می‌دهند. اگر یال‌های `[0 1] [1 2] [2 3] [3 1] [4 5]` را به ترتیب اضافه کنیم، `Union` در اندیس ۳ نادرست برمی‌گرداند: این یال دور می‌سازد. برای {{< term "minimum-spanning-tree" "درخت پوشای کمینه" >}} با Kruskal یال‌ها را بر اساس وزن مرتب می‌کنم و هر یالی که `Union`اش موفق شود نگه می‌دارم. روی ۸ گره و ۱۲ یال، ۷ یال با وزن کل ۱۷ می‌ماند:

```
1-2 w=1   6-7 w=1   1-3 w=2   3-4 w=2   0-2 w=3   5-6 w=3   4-6 w=5
```

یک تست این وزن را با brute force روی هر ۴٬۰۹۶ زیرمجموعه‌ی یال‌ها تأیید می‌کند. برای شبکه (grid)، هر `#` را با `#` چپ و بالایش union کنید؛ روی شبکه‌ی ۴ در ۵ تعداد جزیره‌ها ۴ چاپ می‌شود (تست اول ۳ انتظار داشت، چون من با چشم شمرده بودم و اشتباه کرده بودم؛ کد درست بود).

## چند نکته‌ی مهم

- trie حافظه می‌دهد تا پرس‌وجوی پیشوند بگیرد؛ اگر فقط جست‌وجوی دقیق می‌خواهید، map ساده‌تر است.
- طرح گره‌ها را با بایت به‌ازای هر گره مقایسه کنید، نه با حدس.
- union-find بدون بهینه‌سازی به لیست تبدیل می‌شود؛ از اول هر دو را پیاده کنید.
- `Find` را تکراری بنویسید نه بازگشتی، وگرنه درخت عمیق stack را پر می‌کند.
- union-find فقط ادغام می‌کند و نمی‌تواند گروهی را تقسیم کند.

## تمرین

به trie تابع `Delete` اضافه کنید (گره‌هایی که دیگر به کلمه‌ای نمی‌رسند را حذف کند) و تست کنید بعد از درج و حذف یک کلمه تعداد گره‌ها به مقدار قبلی برمی‌گردد.
