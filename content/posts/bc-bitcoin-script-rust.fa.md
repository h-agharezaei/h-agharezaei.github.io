اینکه می‌گوییم «این سکه مال Alice است» دقیقاً یعنی چه؟ در زنجیره‌ی اسباب‌بازی ما جوابش قاعده‌ای است که در کد نود نوشته شده. در [تراکنش و مدل UTXO](/fa/posts/bc-transactions-utxo/) هر {{< term "utxo" "UTXO" >}} یک آدرس نگه می‌دارد. برای خرج کردنش، ورودی باید یک کلید عمومی بیاورد که hashش همان آدرس باشد، و امضایی که آن کلید تأییدش کند. نود هر بار دقیقاً همین را چک می‌کند.

این جواب می‌دهد، تا وقتی همه فقط همین یک نوع مالکیت را بخواهند. ولی اگر سکه‌ای باید با دو امضا از سه امضا خرج شود چه؟ یا فقط بعد از یک تاریخ مشخص قابل خرج باشد؟ با قاعده‌ای که در کد نود نوشته شده، هر نوع تازه‌ی مالکیت یعنی تغییر دادن و به‌روز کردن همه‌ی نودهای شبکه.

جواب بیت‌کوین این است که مالکیت را به داده تبدیل کند. هر خروجی یک برنامه‌ی کوچک با خودش دارد، به اسم **قفل**. کسی که می‌خواهد آن خروجی را خرج کند، یک برنامه‌ی کوچک دیگر می‌آورد، به اسم **بازکننده**. نود این دو را پشت سر هم اجرا می‌کند: اگر نتیجه «درست» بود، سکه می‌تواند جابه‌جا شود. یک جعبه با قفل آویز را در نظر بگیرید. صاحب سکه موقع ساختنش قفل را انتخاب می‌کند، و خرج‌کننده باید چیزی بیاورد که آن را باز کند. نود لازم نیست بداند این چه نوع قفلی است؛ فقط باید بلد باشد امتحانش کند.

زبان این برنامه‌ها {{< term "bitcoin-script" "Bitcoin Script" >}} است. در بیت‌کوین به قفل `scriptPubKey` و به بازکننده `scriptSig` می‌گویند؛ در خروجی‌های جدیدتر SegWit، داده‌ی بازکننده در بخش جدایی به اسم witness می‌رود. در [مقاله‌ی قبل](/fa/posts/bc-mempool-fees/) دیدیم کدام تراکنش‌ها به بلاک می‌رسند؛ این مقاله می‌پرسد چه کسی اجازه دارد یک سکه را خرج کند.

پایین‌تر یک مفسر کوچک برایش با Rust می‌سازم. از همین اول بگویم: این یک **زیرمجموعه‌ی آموزشی است، نه سازگار با consensus بیت‌کوین**. حدود ده opcode دارد، قالب متنی خودش را دارد، و چک امضایش ساده‌شده است. برای فهمیدن ایده خوب است، نه برای چک کردن تراکنش‌های واقعی.

> همه‌ی مثال‌ها را با Rust 1.90 روی macOS (arm64) اجرا کرده‌ام. برای {{< term "ecdsa" "ECDSA" >}} روی منحنی {{< term "secp256k1" "secp256k1" >}} از `k256` 0.13.4، و برای hash از `sha2` 0.10.9 و `ripemd` 0.1.3 استفاده کردم. کلیدها در هر اجرا تازه ساخته می‌شوند، یک‌بارمصرف‌اند و هیچ‌وقت پولی به آن‌ها واریز نشده. کد یک مثال محلی است.

## ماشینی که فقط یک stack دارد

Script روی یک {{< term "stack" "stack" >}} (پشته) اجرا می‌شود، همان ساختار داده‌ی [stack، queue و deque](/fa/posts/algo-stacks-queues-deques/): یک توده که فقط می‌شود چیزی رویش گذاشت یا بالاترینش را برداشت. یک برنامه‌ی Script فهرستی از دستورهاست که از چپ به راست خوانده می‌شود. به هر دستور **opcode** می‌گویند. داده‌ای که در برنامه هست، مثل یک عدد یا یک کلید، فقط روی stack گذاشته می‌شود. هر opcode ورودی‌هایش را از بالای stack برمی‌دارد و نتیجه‌اش را دوباره همان‌جا می‌گذارد.

یک مثال خیلی کوچک قبل از هر کدی: بازکننده `2 3` است و قفل `OP_ADD 5 OP_EQUAL`. ماشین این‌ها را پشت سر هم اجرا می‌کند:

1. `2`: stack می‌شود `[2]`.
2. `3`: stack می‌شود `[2, 3]`.
3. `OP_ADD` دو تای بالا را برمی‌دارد و جمعشان را بالا می‌گذارد: `[5]`.
4. `5`: `[5, 5]`.
5. `OP_EQUAL` دو تای بالا را برمی‌دارد و اگر برابر باشند «درست» می‌گذارد: `[true]`.

برنامه با «درست» در بالا تمام می‌شود، پس خرج معتبر است. به زبان ساده، این قفل می‌گوید: «هر کس دو عدد بیاورد که جمعشان ۵ شود، می‌تواند این سکه را خرج کند». البته قفل خیلی بدی است، چون همه می‌توانند حلش کنند، ولی طرز کار را نشان می‌دهد.

Script عمداً حلقه و پرش به عقب ندارد. طبق ویکی بیت‌کوین، عمداً {{< term "turing-complete" "Turing-complete" >}} نیست، یعنی نمی‌تواند هر محاسبه‌ی ممکنی را بیان کند. این یک ویژگی است، نه کمبود. چون هر opcode حداکثر یک بار اجرا می‌شود، نود قبل از اجرای یک script می‌داند هزینه‌اش حداکثر متناسب با طولش است. هیچ‌کس نمی‌تواند scriptی بفرستد که تا ابد اجرا شود.

## opcodeها به شکل enum

در Rust یک enum که حالت‌هایش می‌توانند داده حمل کنند، مثل [Struct، Enum و Pattern Matching در Rust](/fa/posts/rust-structs-enums-pattern-matching/)، برای opcodeها خیلی مناسب است:

```rust
pub enum Op {
    Push(Vec<u8>),
    Dup, Hash160, Equal, EqualVerify, CheckSig,
    Add, If, Else, EndIf, Return,
}
```

`Push` بایت‌هایی را که روی stack می‌گذارد با خودش دارد؛ بقیه‌ی حالت‌ها خود opcodeها هستند. parser متنی مثل `OP_DUP <89ab..> 5` را می‌خواند: هر اسمی که با `OP_` شروع شود به حالت متناظرش تبدیل می‌شود، `<hex>` گذاشتن همان بایت‌ها روی stack است، یک عدد دهدهی گذاشتن همان عدد با encoding خود Script است (پایین‌تر توضیحش می‌دهم)، و هر چیز دیگری خطاست.

خود stack از نوع `Vec<Vec<u8>>` است: فهرستی از رشته‌های بایت. Script نوع ندارد؛ عدد، کلید و امضا همه فقط بایت‌هایی روی stack‌اند، و هر opcode خودش تصمیم می‌گیرد چطور بخواندشان. خطاها یک enum‌اند، و هر قدم یک `Result` برمی‌گرداند، مثل [مدیریت خطا با Result و Option در Rust](/fa/posts/rust-error-handling-result/). این‌ها opcodeهایی‌اند که برای این مقاله از همه مهم‌ترند:

```rust
Op::Dup => {
    let top = self.stack.last().ok_or(ScriptError::StackUnderflow("OP_DUP"))?;
    self.stack.push(top.clone());
}
Op::Hash160 => {
    let x = self.pop("OP_HASH160")?;
    self.stack.push(hash160(&x).to_vec()); // RIPEMD-160(SHA-256(x))
}
Op::EqualVerify => {
    let (a, b) = (self.pop("OP_EQUALVERIFY")?, self.pop("OP_EQUALVERIFY")?);
    if a != b { return Err(ScriptError::EqualVerifyFailed); }
}
Op::CheckSig => {
    let pubkey = self.pop("OP_CHECKSIG")?;
    let sig = self.pop("OP_CHECKSIG")?;
    let ok = check_sig(&pubkey, &sig, self.sighash);
    self.stack.push(if ok { vec![1] } else { vec![] });
}
Op::Return => return Err(ScriptError::OpReturn),
```

- **`OP_DUP`** بالاترین مورد را کپی می‌کند و کپی را بالا می‌گذارد. اگر stack خالی باشد، خطای `StackUnderflow` است.
- **`OP_HASH160`** بالاترین مورد را برمی‌دارد و HASH160 آن را بالا می‌گذارد: اول SHA-256، بعد RIPEMD-160 نتیجه، که ۲۰ بایت می‌دهد. از crateهای واقعی `sha2` و `ripemd` استفاده می‌کند. یک تست HASH160 ورودی خالی (`b472a266…`) را ثابت نگه می‌دارد، و من همین مقدار را جداگانه با `openssl` هم چک کردم.
- **`OP_EQUALVERIFY`** دو تای بالا را برمی‌دارد. اگر برابر باشند، ادامه می‌دهد و چیزی روی stack نمی‌گذارد. اگر نه، script همان‌جا با خطا متوقف می‌شود.
- **`OP_CHECKSIG`** یک کلید عمومی و یک امضا برمی‌دارد و امضا را چک می‌کند. به این یکی دقت کنید: امضای بد **خطا نیست**. فقط «نادرست» (بایت خالی) روی stack می‌گذارد، و script در آخر شکست می‌خورد، چون «نادرست» بالای stack است.
- **`OP_RETURN`** همیشه فوراً شکست می‌خورد.

`verify` همه را کنار هم می‌گذارد. اول بازکننده را اجرا می‌کند، بعد قفل را روی **همان stack**، و فقط وقتی موفق است که در آخر مورد بالای stack «درست» باشد. یک قاعده‌ی دیگر هم دارد: بازکننده فقط می‌تواند داده روی stack بگذارد. کار بازکننده فقط فراهم کردن داده است، مثل امضا و کلید؛ همه‌ی منطق مال قفلی است که صاحب سکه انتخاب کرده.

## چک امضا ساده‌شده است

قبل از مثال اصلی، یک نکته درباره‌ی چیزی که ساده کرده‌ام. امضا در بیت‌کوین «هر چیزی» را امضا نمی‌کند؛ hash تراکنشی را امضا می‌کند که سکه را خرج می‌کند. به این hash {{< term "sighash" "sighash" >}} می‌گویند. برای همین امضای یک تراکنش برای تراکنش دیگری به درد نمی‌خورد.

`check_sig` من یک کلید عمومی فشرده‌ی ۳۳ بایتی و یک امضای ۶۴ بایتی (`r` و `s` کنار هم) می‌گیرد، و امضا را با یک sighash ۳۲ بایتی که به ماشین داده شده چک می‌کند. در دمو این sighash فقط SHA-256 جمله‌ای مثل "toy tx: alice pays bob 1 coin" است، جانشینی برای یک تراکنش واقعی. طبق ویکی بیت‌کوین، `OP_CHECKSIG` واقعی امضایی با encoding DER می‌گیرد که یک بایت اضافه برای نوع sighash در آخرش دارد، و خودش hash را بر اساس همان نوع از روی تراکنش خرج‌کننده حساب می‌کند. هیچ‌کدام از این‌ها این‌جا نیست.

## خرج یک P2PKH

حالا قفل کلاسیک بیت‌کوین، {{< term "p2pkh" "P2PKH" >}}، کوتاه‌شده‌ی pay to public key hash، یعنی «پرداخت به hash یک کلید عمومی». به زبان ساده می‌گوید: «هر کس کلید عمومی‌ای با این hash بیاورد، و امضای معتبری از همان کلید، می‌تواند این سکه را خرج کند». همان قاعده‌ی زنجیره‌ی اسباب‌بازی ماست، فقط به شکل برنامه نوشته شده:

```
lock:   OP_DUP OP_HASH160 <pubkey hash> OP_EQUALVERIFY OP_CHECKSIG
unlock: <sig> <pubkey>
```

stack را قدم‌به‌قدم دنبال کنیم. اول بازکننده اجرا می‌شود:

1. `<sig>`: `[sig]`
2. `<pubkey>`: `[sig, pubkey]`

بعد قفل، روی همان stack:

3. `OP_DUP` کلید را کپی می‌کند: `[sig, pubkey, pubkey]`
4. `OP_HASH160` کپی را hash می‌کند: `[sig, pubkey, hash(pubkey)]`
5. `<pubkey hash>`، همان hashی که در قفل نوشته شده: `[sig, pubkey, hash(pubkey), pubkey hash]`
6. `OP_EQUALVERIFY` دو تای بالا را مقایسه می‌کند. اگر کلید درست نباشد، script همین‌جا متوقف می‌شود. اگر درست باشد، هر دو برداشته می‌شوند: `[sig, pubkey]`
7. `OP_CHECKSIG` امضا را با کلید چک می‌کند: `[true]`

هفت قدم، و «درست» در بالا. `OP_DUP` به این دلیل هست که کلید دو بار لازم است: یک بار برای مقایسه‌ی hashش، و یک بار برای چک امضا.

`cargo run` یک قفل برای Alice می‌سازد و آن را به چند شکل امتحان می‌کند. چون کلیدها در هر اجرا تازه‌اند، hash خط اول هر بار فرق می‌کند:

```
lock:   OP_DUP OP_HASH160 <9405bb1b..> OP_EQUALVERIFY OP_CHECKSIG
unlock: <sig 64 bytes> <pubkey 33 bytes>

alice spends           ok (7 steps)
mallory's key          error: OP_EQUALVERIFY failed
mallory sig, alice key error: script ended with false on top
tampered sig           error: script ended with false on top
tx changed after sign  error: script ended with false on top
OP_RETURN output       error: OP_RETURN: output is unspendable
unlock with OP_DUP     error: unlock script must only push data
```

دو خط اول قفل (با hash کوتاه‌شده) و شکل بازکننده است: یک امضای ۶۴ بایتی و یک کلید ۳۳ بایتی. بعد هر خط یک تلاش است:

- **`alice spends`:** امضا و کلید Alice. دقیقاً همان هفت قدم بالا، و موفق می‌شود.
- **`mallory's key`:** Mallory با کلید خودش امضا می‌کند و کلید خودش را می‌آورد. hash کلید او همان hash قفل نیست، پس script در `OP_EQUALVERIFY` متوقف می‌شود.
- **`mallory sig, alice key`:** Mallory این بار زرنگ‌تر است: کلید Alice را می‌آورد، که عمومی است، پس چک hash را با موفقیت می‌گذراند. ولی امضا مال خودش است و با کلید Alice تأیید نمی‌شود. `OP_CHECKSIG` «نادرست» می‌گذارد و script با «نادرست» در بالا تمام می‌شود.
- **`tampered sig`:** امضای واقعی Alice، با یک بیت عوض‌شده. باز «نادرست».
- **`tx changed after sign`:** امضای درست Alice، ولی با یک sighash دیگر چک شده، انگار کسی تراکنش را بعد از امضا عوض کرده (مثلاً گیرنده شده Mallory). امضا تراکنش تازه را پوشش نمی‌دهد، پس «نادرست».
- **`OP_RETURN output`:** قفل `OP_RETURN <68656c6c6f>` است (بایت‌های بعدش کلمه‌ی "hello" است). بازکننده هر چه باشد فرقی نمی‌کند: `OP_RETURN` فوراً شکست می‌خورد، پس هیچ‌کس هرگز نمی‌تواند این خروجی را خرج کند. طبق مستندات بیت‌کوین، داده را این‌طوری در تراکنش‌ها جا می‌دهند: چون چنین خروجی‌ای هیچ‌وقت خرج نمی‌شود، نودها لازم نیست آن را بین خروجی‌های خرج‌نشده نگه دارند.
- **`unlock with OP_DUP`:** بازکننده‌ای که به‌جای اینکه فقط داده داشته باشد، یک opcode هم دارد. `verify` قبل از اجرای هر چیزی ردش می‌کند.

سه تا از این شکست‌ها، امضای Mallory، امضای دستکاری‌شده و تراکنش عوض‌شده، به یک شکل تمام می‌شوند: با «نادرست» در بالا. این همان تفاوت `OP_EQUALVERIFY` است، که script را با خطا متوقف می‌کند، با `OP_CHECKSIG`، که فقط یک مقدار تولید می‌کند.

## عددها و شاخه‌ها

همان `cargo run` بعد عددها و شاخه‌ها را امتحان می‌کند:

```
2 + 3 == 5             ok (5 steps)
if/else, true branch   ok (4 steps)
if/else, false branch  error: script ended with false on top
parse OP_LOOP          error: unknown token "OP_LOOP"
```

- **`2 + 3 == 5`:** همان مثال کوچک اول مقاله. پنج قدم: دو push در بازکننده، بعد `OP_ADD`، push عدد `5`، و `OP_EQUAL`.
- **دو خط شاخه** از یک قفل استفاده می‌کنند: `OP_IF 10 OP_ELSE 20 OP_ENDIF 10 OP_EQUAL`. `OP_IF` مورد بالای stack را برمی‌دارد. اگر «درست» باشد، بخش تا `OP_ELSE` اجرا می‌شود؛ اگر نه، بخش بعد از آن. با بازکننده‌ی `1`، شاخه‌ی اول اجرا می‌شود و ۱۰ می‌گذارد، و ۱۰ با ۱۰ برابر است. فقط چهار قدم شمرده می‌شود، چون opcodeهایی که رد شده‌اند، و خود `OP_IF` و `OP_ELSE` و `OP_ENDIF`، شمرده نمی‌شوند. با بازکننده‌ی `0`، شاخه‌ی دوم ۲۰ می‌گذارد، و ۲۰ با ۱۰ برابر نیست.
- **`parse OP_LOOP`:** چنین opcodeی وجود ندارد و parser ردش می‌کند. در این زبان هیچ حلقه‌ای نمی‌شود نوشت.

عددها در Script encoding خودشان را دارند، همانی که ویکی بیت‌کوین توضیح می‌دهد: بایت‌ها به ترتیب little-endian (کم‌ارزش‌ترین بایت اول)، و علامت در بالاترین بیت آخرین بایت. پس ۱ می‌شود `01`، منفی ۱ می‌شود `81`، و ۱۲۸ دو بایت لازم دارد، `80 00`، چون بیت بالای `80` وگرنه علامت منفی خوانده می‌شد. ورودی opcodeهای حسابی حداکثر ۴ بایت می‌توانند باشند. یک نتیجه‌ی عجیب: رشته‌ی بایتی که تنها بیت روشنش بیت علامت است، مثل `80` یا `00 80`، «صفر منفی» است و باید «نادرست» حساب شود. یک تست دقیقاً همین را چک می‌کند. این خروجی `cargo test` است (ترتیب تست‌ها ممکن است از اجرایی به اجرای دیگر فرق کند):

```
test errors ... ok
test numbers_round_trip ... ok
test hash160_known_vector ... ok
test p2pkh_spends_and_rejects_other_sighash ... ok
test result: ok. 4 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s
```

- **`errors`:** کمبود مورد روی stack، `OP_IF` بدون `OP_ENDIF` و `OP_ENDIF` بدون `OP_IF`، عدد بلندتر از ۴ بایت، hex نامعتبر در parser، و یک `OP_RETURN` داخل شاخه‌ای که اجرا نمی‌شود و کاری نمی‌کند.
- **`numbers_round_trip`:** فهرستی از عددها encode و دوباره decode می‌شوند، و صفر منفی «نادرست» است.
- **`hash160_known_vector`:** HASH160 ورودی خالی، همان مقداری که با `openssl` چک کردم.
- **`p2pkh_spends_and_rejects_other_sighash`:** خرج P2PKH با یک کلید ثابت تستی در ۷ قدم موفق می‌شود، و با یک sighash دیگر شکست می‌خورد.

## ظرافت‌های Script

- **امضای بد یک مقدار است، نه خطا.** `OP_CHECKSIG` «نادرست» می‌گذارد و script ادامه می‌دهد. پس «بدون خطا اجرا شد» یعنی «معتبر است» نیست. همیشه چک کنید در آخر چه چیزی بالای stack است، همان کاری که `verify` می‌کند.
- **نبودن حلقه یعنی هزینه‌ی معلوم.** چون هیچ چیز دو بار اجرا نمی‌شود، نود بدترین هزینه‌ی یک script را قبل از اجرایش می‌داند. در شبکه‌ای که هر کسی می‌تواند هر scriptی بفرستد، این خیلی مهم است.
- **این فقط یک زیرمجموعه است.** بیت‌کوین واقعی قاعده‌های خیلی بیشتری دارد که پیاده نکرده‌ام: encoding دقیق امضا، نوع‌های sighash، محدودیت‌های اندازه، opcodeهای غیرفعال‌شده، و چیزهای دیگر. از این مفسر برای چک کردن تراکنش‌های واقعی استفاده نکنید.

## تمرین

۱. `OP_SUB` و `OP_VERIFY` را اضافه کنید، با تست برای کمبود مورد روی stack.
۲. `OP_SWAP` را اضافه کنید، بعد یک قفل ۲ از ۲ با دو `OP_CHECKSIG` و یک `OP_ADD` بنویسید، و نشان دهید یک امضا کافی نیست.
۳. یک سقف برای تعداد قدم‌ها به `Machine` اضافه کنید، و تستی بنویسید که نشان دهد به سقف می‌خورد.
