بیشتر چیزهایی که درباره‌ی بلاکچین می‌شنویم درباره‌ی قیمت و سرمایه‌گذاری است. من می‌خواهم از زاویه‌ی دیگری نگاهش کنم: به‌عنوان یک برنامه‌نویس، بلاکچین دقیقاً چه مسئله‌ای را حل می‌کند که یک دیتابیس معمولی حل نمی‌کند؟ و کجا اصلاً نباید سراغش رفت؟

این اولین قسمت از یک دوره‌ی ۳۲ قسمتی است که فقط درباره‌ی همین‌هاست: ساختار داده، رمزنگاری، شبکه و کد. نه قیمت، نه توصیه‌ی سرمایه‌گذاری. قرار نیست از قبل چیزی درباره‌ی بلاکچین بدانید. اگر خواستید زمینه‌ی بیشتری داشته باشید، این مقاله‌ها کمک می‌کنند: [hash table از صفر](/fa/posts/algo-hash-tables/)، [اشتباه‌های رایج رمزنگاری](/fa/posts/sec-crypto-mistakes/)، [consensus و Raft](/fa/posts/ds-consensus-raft/)، [لاگ، audit و واکنش به حادثه](/fa/posts/sec-logging-audit-incident-response/)، و [هک بایننس از دید فنی](/fa/posts/binance-hack-hot-wallet-2026/) که نشان می‌دهد مشکل گاهی اصلاً بیرون از بلاکچین است.

> دمو را با Go 1.27 روی macOS (arm64) اجرا کرده‌ام و خروجی همان چیزی است که دیدم.

## مسئله در یک جمله

چند طرف که به هم اعتماد ندارند می‌خواهند یک فهرست مشترک را با هم نگه دارند، طوری که فقط بشود به آن اضافه کرد، و هیچ‌کدامشان هم رئیس نباشد.

یک مثال ملموس: چند شرکت با هم معامله می‌کنند و می‌خواهند یک دفتر حساب مشترک داشته باشند. اگر دفتر پیش یکی از آن‌ها باشد، بقیه باید به او اعتماد کنند که چیزی را پاک یا عوض نمی‌کند. بلاکچین تلاشی است برای اینکه این اعتماد لازم نباشد.

به چنین دفتری {{< term "distributed-ledger" "distributed ledger" >}} یا «دفتر کل توزیع‌شده» می‌گویند. این جمله سه شرط دارد که ارزش دارد جدا ببینیمشان:

- **مشترک:** هر طرف یک نسخه‌ی کامل از دفتر را پیش خودش دارد.
- **فقط‌افزودنی (append-only):** گذشته ویرایش یا پاک نمی‌شود. اگر اشتباهی شد، یک ردیف اصلاحی جدید اضافه می‌شود، درست مثل دفتر حساب‌داری.
- **بدون رئیس:** هیچ ادمینی نیست که بتواند مستقیم دستور `UPDATE` بزند. پس طرف‌ها برای اینکه سر ردیف بعدی توافق کنند به یک قاعده‌ی مشترک نیاز دارند. به این قاعده پروتکل {{< term "consensus" "consensus" >}} (اجماع) می‌گویند.

یک نکته‌ی ظریف هم هست. چون طرف‌ها به هم اعتماد ندارند، پروتکل باید با کسی که عمداً دروغ می‌گوید هم کنار بیاید، نه فقط با کامپیوتری که خاموش شده. به این نوع خطا {{< term "byzantine-fault" "Byzantine fault" >}} می‌گویند. همین فرق اصلی بلاکچین با الگوریتمی مثل Raft است: Raft فرض می‌کند همه‌ی نودها صادق‌اند و فقط ممکن است از کار بیفتند.

## چرا یک دیتابیس با audit log کافی نیست؟

اولین سؤالی که هر برنامه‌نویسی می‌پرسد همین است، و جواب صادقانه‌اش این است: خیلی وقت‌ها کافی است. اگر یک شرکت سیستم را اداره می‌کند، یک دیتابیس به‌همراه {{< term "audit-log" "audit log" >}} (لاگی که ثبت می‌کند چه کسی، کی، چه چیزی را تغییر داده) جواب درست است. سریع‌تر، ارزان‌تر و ساده‌تر است.

سؤال اصلی فنی نیست، این است که **به چه کسی اعتماد دارید**:

| | دیتابیس + audit log | بلاکچین |
|---|---|---|
| چه کسی تصمیم می‌گیرد چه نوشته شود | اپراتور سیستم | پروتکلی بین چند طرف |
| چه کسی می‌تواند تاریخچه را بازنویسی کند | اپراتور، یا هر کسی که به سرور دسترسی داشته باشد | هیچ‌کس به‌تنهایی، بدون اینکه بقیه بفهمند |
| اصلاح یک اشتباه | یک `UPDATE` | اضافه کردن یک ردیف اصلاحی |
| سرعت و هزینه | بالا و ارزان | پایین، چون هر نود همه‌ی کار را تکرار می‌کند |

ردیف دوم جدول مهم‌ترین است. audit log شما را در برابر کارمندان خودتان محافظت می‌کند، ولی مشتری‌ها را در برابر خود شما محافظت نمی‌کند، چون هم داده و هم لاگ دست شماست. اگر بخواهید، می‌توانید هر دو را با هم عوض کنید.

## دستکاری را می‌شود دید، ولی نمی‌شود جلویش را گرفت

ابزار اصلی برای اینکه دستکاری دیده شود {{< term "hash-chain" "hash chain" >}} است. ایده‌اش ساده است: برای هر رکورد یک «اثر انگشت» حساب می‌کنیم و اثر انگشت هر رکورد را در رکورد بعدی می‌نویسیم. این اثر انگشت با تابع hash {{< term "sha-256" "SHA-256" >}} ساخته می‌شود: هر ورودی را می‌گیرد و یک رشته‌ی ثابت و به‌ظاهر تصادفی می‌دهد که با کوچک‌ترین تغییر ورودی کاملاً عوض می‌شود (در مقاله‌ی بعد دقیق‌تر سراغش می‌رویم). حالا اگر کسی یک رکورد را عوض کند، اثر انگشتش عوض می‌شود و دیگر با چیزی که در رکورد بعدی نوشته شده نمی‌خواند.

ساده‌ترین نسخه‌اش در Go این است. هر رکورد داده‌ی خودش، hash رکورد قبلی و hash خودش را دارد. `verify` از اول تا آخر می‌رود و برای هر رکورد چک می‌کند که پیوند با قبلی درست باشد و hash خودش هم با محتوایش بخواند:

```go
type Record struct {
	Data     string
	PrevHash string
	Hash     string
}

func hashOf(data, prev string) string {
	sum := sha256.Sum256([]byte(prev + "|" + data))
	return hex.EncodeToString(sum[:])
}

func verify(log []Record) error {
	prev := ""
	for i, r := range log {
		if r.PrevHash != prev {
			return fmt.Errorf("record %d: prev link broken", i)
		}
		if hashOf(r.Data, r.PrevHash) != r.Hash {
			return fmt.Errorf("record %d: hash mismatch", i)
		}
		prev = r.Hash
	}
	return nil
}
```

برنامه‌ی `main` این کارها را به ترتیب انجام می‌دهد:

1. سه رکورد می‌سازد و چاپشان می‌کند.
2. یک «طرف دیگر» (peer) فقط hash آخرین رکورد را پیش خودش نگه می‌دارد.
3. رکورد ۱ بی‌سروصدا ویرایش می‌شود.
4. کسی که ویرایش کرده، همه‌ی hashها را از نو حساب می‌کند (`rehash`) تا رد پایش پاک شود.

```
0 "alice -> bob: 10" prev=-            hash=a09bc3c354a1
1 "bob -> carol: 4"  prev=a09bc3c354a1 hash=e2dcc871b98a
2 "carol -> dave: 1" prev=e2dcc871b98a hash=89e56e1e69d6
verify: <nil>
after edit: record 1: hash mismatch
after rehash: <nil>
head matches peer: false
```

سه خط اول زنجیره‌ی سالم است: `prev` هر رکورد همان `hash` رکورد بالایی است. `verify: <nil>` یعنی مشکلی نیست. بعد از ویرایش، `verify` فوراً می‌گوید hash رکورد ۱ نمی‌خواند.

ولی دو خط آخر درس اصلی این مقاله است. کسی که کل فایل دستش است، می‌تواند بعد از ویرایش همه‌ی hashها را از نو حساب کند، و `verify` دیگر هیچ خطایی نمی‌دهد (`after rehash: <nil>`). یعنی زنجیره‌ی hash به‌تنهایی جلوی دستکاری را نمی‌گیرد. تنها چیزی که لو می‌دهد خط آخر است: hash آخر دیگر با چیزی که peer نگه داشته یکی نیست.

پس زنجیره فقط وقتی دستکاری را نشان می‌دهد (به انگلیسی *tamper-evident*) که **کس دیگری** hash آخر را نگه داشته باشد، کسی که شما نمی‌توانید نسخه‌اش را عوض کنید. در بلاکچین تعداد زیادی نود مستقل hash آخر را دارند، پس بازنویسی تاریخچه دیده می‌شود. اینکه بازنویسی را علاوه بر دیده‌شدن **گران** هم کنیم، کار proof of work و proof of stake است که بعداً به آن می‌رسیم.

یک تکه هنوز کم است: هویت. در این دمو هر کسی می‌تواند رکورد «bob -> carol» را اضافه کند، حتی اگر bob نباشد. برای اینکه فقط خود bob بتواند پولش را خرج کند، به {{< term "digital-signature" "امضای دیجیتال" >}} او نیاز داریم، که آن هم در قسمت‌های بعد می‌آید.

## جاهایی که بلاکچین ابزار اشتباهی است

بلاکچین ابزار گرانی است، پس باید بدانیم کجا جایش نیست:

- **همه‌ی کسانی که می‌نویسند زیر نظر یک سازمان‌اند.** یک دیتابیس کافی است. اگر مدرک ضددستکاری لازم دارید، audit log با hash chain بسازید.
- **باید بتوانید داده را پاک کنید.** مثلاً به خاطر قانون حریم خصوصی یا یک اشتباه. دفتری که فقط‌افزودنی است و نسخه‌اش پیش همه است، این کار را خیلی سخت می‌کند.
- **داده از دنیای بیرون می‌آید.** زنجیره فقط ثابت می‌کند *چه چیزی ثبت شده*، نه اینکه آن چیز *درست* است. اگر کسی دمای غلط یک انبار را ثبت کند، بلاکچین فقط همان دمای غلط را با دقت نگه می‌دارد.
- **سرعت بالا یا تأخیر کم لازم دارید.** هر نود همه‌چیز را خودش چک می‌کند، پس سیستم کند است.
- **همه از قبل به یک طرف بی‌طرف اعتماد دارند.** مثل یک بانک یا اداره‌ی ثبت. همان طرف ساده‌تر و ارزان‌تر است.

خلاصه اینکه اگر شرط «بدون رئیس» را برداریم، داریم فقط یک دیتابیس کند می‌سازیم.

## نقشه‌ی دوره

دوره چهار بخش دارد:

۱. **مبانی** (با Go و یک قسمت با Rust): hash، Merkle tree، کلید، تراکنش، proof of work، شبکه‌ی P2P، fork، و آخر سر یک نود کامل کوچک.
۲. **اتریوم** (Solidity، Go، Rust): ماشین مجازی اتریوم (EVM)، نوشتن قرارداد با Foundry، توکن، کلاینت، indexer و کیف‌پول.
۳. **DeFi و امنیت** (Solidity، Go): صرافی خودکار (AMM)، وام‌دهی، oracle، امنیت قرارداد و MEV.
۴. **پیشرفته**: proof of stake، rollup، bridge، zero-knowledge، مهندسی صرافی، و یک پروژه‌ی پایانی.

همه‌چیز روی کامپیوتر خودتان اجرا می‌شود، بدون کلید یا پول واقعی.

## آنچه hash chain ثابت نمی‌کند

قبل از اینکه جلو برویم، حد این ابزار را یک بار مرور کنیم:

- hash chain ثابت می‌کند ترتیب رکوردها و محتوایشان دست نخورده است. ثابت نمی‌کند محتوا درست است یا چه کسی آن را نوشته.
- دیده‌شدن دستکاری فقط وقتی ممکن است که نسخه‌ی مستقلی از hash آخر جای دیگری باشد.
- بایت‌هایی که hash می‌کنید باید دقیق و بی‌ابهام تعریف شوند. جداکننده‌ی `"|"` در این دمو فقط به این دلیل جواب می‌دهد که `PrevHash` همیشه یا خالی است یا دقیقاً ۶۴ کاراکتر. اگر چند فیلد متنی آزاد را این‌طوری پشت هم بچسبانید، مرز بین فیلدها مبهم می‌شود و دو داده‌ی متفاوت می‌توانند یک hash بدهند. در مقاله‌ی بعد این را درست حل می‌کنیم.

## تمرین

۱. دمو را اجرا کنید و این بار به‌جای ویرایش، رکورد ۱ را کلاً حذف کنید. چه خطایی می‌گیرید؟
۲. جای رکورد ۱ و ۲ را عوض کنید. کدام چک آن را می‌گیرد؟
۳. `peerHead` را در یک فایل جدا ذخیره کنید و یک دستور `check` بنویسید که آن را با لاگ مقایسه کند.
