این اولین پست از یک دوره‌ی ۳۲ قسمتی درباره‌ی بلاکچین از دید برنامه‌نویس است: نه قیمت، نه سرمایه‌گذاری؛ فقط ساختار داده، رمزنگاری، شبکه و کد. اول خود مسئله، چون بیشتر سردرگمی‌ها از جا انداختن همین قدم است. پیش‌زمینه: [hash table از صفر](/fa/posts/algo-hash-tables/)، [اشتباه‌های رایج رمزنگاری](/fa/posts/sec-crypto-mistakes/)، [consensus و Raft](/fa/posts/ds-consensus-raft/)، [لاگ، audit و واکنش به حادثه](/fa/posts/sec-logging-audit-incident-response/) و [هک بایننس از دید فنی](/fa/posts/binance-hack-hot-wallet-2026/) که مشکلش بیرون از زنجیره بود.

> دمو را با Go 1.27 روی macOS (arm64) اجرا کرده‌ام.

## مسئله در یک جمله

چند طرف که به هم اعتماد ندارند می‌خواهند یک فهرست مشترک و فقط‌افزودنی نگه دارند، بدون این‌که یکی‌شان اپراتورِ تصمیم‌گیرنده باشد.

این یعنی یک {{< term "distributed-ledger" "distributed ledger" >}}. *مشترک*: هر کس یک کپی کامل دارد. *append-only*: تاریخچه ویرایش نمی‌شود، فقط ادامه پیدا می‌کند. *بدون اپراتور*: ادمینی با دسترسی `UPDATE` وجود ندارد، پس طرف‌ها برای توافق روی entry بعدی به یک قاعده نیاز دارند، یعنی پروتکل {{< term "consensus" "consensus" >}}. چون اعتمادی در کار نیست، پروتکل باید {{< term "byzantine-fault" "Byzantine fault" >}} را تحمل کند: شرکت‌کننده‌ای که دروغ می‌گوید، نه فقط کسی که crash می‌کند. Raft فرض می‌کند nodeها صادق‌اند؛ تفاوت اصلی همین است.

## چرا یک دیتابیس با audit log کافی نیست؟

اگر یک شرکت سیستم را اجرا می‌کند، دیتابیس به‌همراه {{< term "audit-log" "audit log" >}} جواب درست است: سریع‌تر، ارزان‌تر و ساده‌تر. سؤال این است که به چه کسی اعتماد دارید:

| | دیتابیس + audit log | بلاکچین |
|---|---|---|
| چه کسی تصمیم می‌گیرد چه نوشته شود | اپراتور | پروتکلی بین چند طرف |
| چه کسی می‌تواند تاریخچه را بازنویسی کند | اپراتور (یا هر کس سرور دستش باشد) | هیچ‌کس به‌تنهایی، بدون این‌که بقیه بفهمند |
| اصلاح یک اشتباه | `UPDATE` | اضافه کردن entry اصلاحی |
| throughput و هزینه | بالا، ارزان | پایین، هر node همه‌ی کار را تکرار می‌کند |

audit log شما را در برابر کارمندان خودتان محافظت می‌کند، نه مشتری‌ها را در برابر شما: کلید هم داده و هم لاگ دست شماست.

## tamper-evident، نه tamper-proof

ابزار پایه {{< term "hash-chain" "hash chain" >}} است: هر رکورد hash {{< term "sha-256" "SHA-256" >}} رکورد قبلی را نگه می‌دارد. یک رکورد را عوض کنید، پیوند بعدی می‌شکند. نسخه‌ی حداقلی در Go (بلاک واقعی در پست بعد):

```go
type Record struct {
	Data     string
	PrevHash string
	Hash     string
}

func hashOf(data, prev string) string {
	sum := sha256.Sum256([]byte(prev + "|" + data))
	return hex.EncodeToString(sum[:])
}

func verify(log []Record) error {
	prev := ""
	for i, r := range log {
		if r.PrevHash != prev {
			return fmt.Errorf("record %d: prev link broken", i)
		}
		if hashOf(r.Data, r.PrevHash) != r.Hash {
			return fmt.Errorf("record %d: hash mismatch", i)
		}
		prev = r.Hash
	}
	return nil
}
```

`main` سه رکورد می‌سازد، یک «peer» hash آخر را نگه می‌دارد، رکورد ۱ ویرایش می‌شود و بعد همه‌ی hashها دوباره حساب می‌شوند (`rehash`):

```
0 "alice -> bob: 10" prev=-            hash=a09bc3c354a1
1 "bob -> carol: 4"  prev=a09bc3c354a1 hash=e2dcc871b98a
2 "carol -> dave: 1" prev=e2dcc871b98a hash=89e56e1e69d6
verify: <nil>
after edit: record 1: hash mismatch
after rehash: <nil>
head matches peer: false
```

درس اصلی دو خط آخر است: کسی که کل فایل دستش است زنجیره را دوباره حساب می‌کند و verify محلی رد نمی‌شود. زنجیره فقط وقتی *tamper-evident* است که کس دیگری hashی را نگه دارد که شما نمی‌توانید عوضش کنید. در بلاکچین nodeهای مستقل زیادی hash آخر را دارند، پس بازنویسی دیده می‌شود. *گران* کردن بازنویسی (proof of work، stake) بعداً می‌آید.

تکه‌ی گمشده هویت است: چه کسی اجازه دارد «bob -> carol» را اضافه کند؟ این {{< term "digital-signature" "امضای دیجیتال" >}} با کلید Bob را لازم دارد که بعداً می‌آید.

## جاهایی که بلاکچین ابزار اشتباهی است

- همه‌ی نویسنده‌ها زیر دست یک سازمان‌اند: دیتابیس، و اگر مدرک لازم است audit log با hash chain.
- باید داده را حذف کنید (قانون حریم خصوصی، اشتباه): append-only و کپی‌شده روی همه‌جا این کار را خیلی سخت می‌کند.
- داده از دنیای بیرون می‌آید: زنجیره ثابت می‌کند *چه چیزی نوشته شده*، نه این‌که *درست* است.
- throughput بالا یا latency کم لازم دارید: هر node همه‌چیز را validate می‌کند.
- طرف‌ها از قبل به یک اپراتور بی‌طرف (بانک، اداره‌ی ثبت) اعتماد دارند: همان اپراتور ساده‌تر است.

## نقشه‌ی دوره

۱. مبانی (Go، یک پست Rust): hash، Merkle tree، کلید، تراکنش، proof of work، P2P، fork و یک نود کامل کوچک.
۲. اتریوم (Solidity، Go، Rust): EVM، قرارداد با Foundry، توکن، کلاینت، indexer و کیف‌پول.
۳. DeFi و امنیت (Solidity، Go): AMM، وام‌دهی، oracle، امنیت قرارداد و MEV.
۴. پیشرفته: proof of stake، rollup، bridge، zero-knowledge، مهندسی صرافی و پروژه‌ی پایانی.

همه‌چیز محلی اجرا می‌شود، بدون کلید واقعی.

## چند نکته‌ی مهم

- hash chain ترتیب و یکپارچگی را ثابت می‌کند، نه درستی یا نویسنده را.
- tamper-evident بودن به کپی مستقلی از hash آخر نیاز دارد.
- اگر شرط «بدون اپراتور مرکزی» را ندارید، دارید یک دیتابیس کُند می‌سازید.
- یک encoding دقیق را hash کنید. جداکننده‌ی `"|"` این‌جا اسباب‌بازی است؛ فرمت واقعی به چیدمان بایتی بی‌ابهام نیاز دارد.
