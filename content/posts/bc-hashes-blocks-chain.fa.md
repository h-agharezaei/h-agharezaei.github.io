فرض کنید یک دفتر حساب دارید و چند نفر دیگر هم هرکدام یک نسخه‌ی کامل از همین دفتر را پیش خودشان نگه داشته‌اند. یک نفر شب، بی‌سروصدا، یک رقم را در صفحه‌ی سوم عوض می‌کند: «۱۰ تومان» می‌شود «۱۰۰۰ تومان». چطور می‌شود فوراً فهمید که دفتر دستکاری شده، آن هم بدون اینکه کلمه‌به‌کلمه با نسخه‌ی بقیه مقایسه‌اش کنیم؟

جواب بلاکچین به این سؤال خیلی ساده است: به هر صفحه یک «اثر انگشت» بده و اثر انگشت هر صفحه را در صفحه‌ی بعدی بنویس. حالا اگر کسی صفحه‌ی سوم را عوض کند، اثر انگشتش عوض می‌شود و دیگر با چیزی که در صفحه‌ی چهارم نوشته شده نمی‌خواند. در [مقاله‌ی قبل](/fa/posts/bc-blockchain-for-programmers/) نسخه‌ی خیلی ساده‌ای از این ایده را با چند رکورد دیدیم؛ این‌جا می‌خواهم از آن یک زنجیره‌ی واقعی بسازم و ببینم کجاها ساده‌تر از چیزی است که فکر می‌کنیم و کجاها سخت‌تر.

این ترفند فقط مال بلاکچین نیست. در [لاگ، audit و واکنش به حادثه](/fa/posts/sec-logging-audit-incident-response/) همین را برای ضددستکاری‌کردن لاگ‌ها به کار بردیم، و گیت هم دقیقاً همین‌طور هر commit را به commit قبلی وصل می‌کند ([گیت چطور فکر می‌کند: object و hash](/fa/posts/git-how-git-thinks/)).

> همه‌ی مثال‌ها را با Go 1.27 روی macOS (arm64) اجرا کرده‌ام و خروجی‌ها همان چیزی است که دیدم. کد یک مثال محلی است، نه repo منتشرشده.

## اثر انگشت: تابع hash

آن «اثر انگشت» در دنیای واقعی یک **تابع hash** است. تابع hash هر ورودی‌ای را، چه یک کلمه باشد چه یک فایل چندگیگابایتی، می‌گیرد و یک عدد با اندازه‌ی ثابت تحویل می‌دهد. به این عدد **digest** یا خود hash می‌گویند. ما از {{< term "sha-256" "SHA-256" >}} استفاده می‌کنیم که خروجی‌اش همیشه ۳۲ بایت است، یعنی ۲۵۶ بیت.

برای کار ما سه ویژگی مهم است:

- **قطعی است.** ورودی یکسان همیشه hash یکسان می‌دهد، روی هر کامپیوتری.
- **حساس است.** کوچک‌ترین تغییر در ورودی، hash را کاملاً عوض می‌کند. اسم این ویژگی {{< term "avalanche-effect" "اثر بهمنی" >}} است: یک سنگ‌ریزه، یک بهمن.
- **نمی‌شود دو ورودی با hash یکسان پیدا کرد.** این را نمی‌توانم با تست نشانتان بدهم؛ تکیه‌اش به سال‌ها تلاش رمزنگارها برای شکستن SHA-256 است که تا امروز موفق نشده‌اند.

در Go کد ما فقط یک تایپ و یک تابع کوچک است:

```go
type Hash [32]byte

func Sum(b []byte) Hash { return sha256.Sum256(b) }
```

برای اینکه دو ویژگی اول را با چشم ببینیم، `go run ./cmd/toychain sha` اول یک پیام را دو بار hash می‌کند. بعد فقط یک بیت از آن را عوض می‌کند (`10` می‌شود `11`) و تعداد بیت‌های متفاوت خروجی را می‌شمارد. آخر سر همین آزمایش را روی ۱۰٬۰۰۰ ورودی تصادفی ۶۴ بایتی تکرار می‌کند:

```
same input twice:
  91eff314c1e123de34a8347604128c113a48f9fc48d0a854a8fd4babc12c19ea
  91eff314c1e123de34a8347604128c113a48f9fc48d0a854a8fd4babc12c19ea
one bit flipped: "alice -> bob: 11"
  e15286f848d3de8b06620811c49d4e31160f86ce4992e11f8833f77851a375ac
differing bits: 120 of 256
10000 trials: min 98, avg 128.1, max 161 differing bits
```

دو خط اول یکسان‌اند: همان قطعی‌بودن. خط بعد، با فقط یک بیت تغییر، هیچ شباهتی به قبلی ندارد: ۱۲۰ بیت از ۲۵۶ بیت عوض شده. در ۱۰٬۰۰۰ آزمایش میانگین ۱۲۸٫۱ بیت است، یعنی تقریباً دقیقاً نصف. این همان چیزی است که از یک تابع hash خوب انتظار داریم: خروجی آن‌قدر به هم ریخته است که انگار هر بیت را با سکه انداختن تعیین کرده‌ایم، پس از روی hash نمی‌شود هیچ حدسی درباره‌ی ورودی زد.

## بلاک: یک صفحه از دفتر

حالا که اثر انگشت داریم، صفحه‌های دفتر را می‌سازیم. هر صفحه یک **بلاک** است و دو بخش دارد:

- **داده** (`Data`): محتوای اصلی، مثلاً «alice به bob ده تومان داد».
- **{{< term "block-header" "header" >}}**: یک برچسب کوچک با چهار فیلد که شماره‌ی صفحه، زمان، و دو hash را نگه می‌دارد.

```go
type Header struct {
	Height    uint64 // 0 for genesis
	Timestamp int64  // unix seconds
	PrevHash  Hash   // hash of the previous block header, zero for genesis
	DataHash  Hash   // SHA-256 of the block data
}

type Block struct {
	Header Header
	Hash   Hash
	Data   []byte
}
```

`Height` شماره‌ی بلاک است و `Timestamp` زمان ساختنش. دو فیلد آخر کار اصلی را می‌کنند:

- `DataHash` اثر انگشت داده است. خود داده داخل header نمی‌رود، فقط hash آن. پس اگر داده عوض شود، دیگر با `DataHash` نمی‌خواند.
- `PrevHash` اثر انگشت بلاک قبلی است. این همان «نوشتن اثر انگشت صفحه‌ی قبل در صفحه‌ی بعد» است.

در آخر خود بلاک یک `Hash` دارد که فقط از روی header حساب می‌شود. چون `DataHash` داخل header است، این hash به‌طور غیرمستقیم داده را هم پوشش می‌دهد.

نتیجه‌ی این طراحی را ارزش دارد یک بار آرام مرور کنیم. hash بلاک ۳ به `PrevHash` آن بستگی دارد، که همان hash بلاک ۲ است، که خودش به hash بلاک ۱ بستگی دارد، و همین‌طور تا اولین بلاک. پس **hash آخرین بلاک به کل تاریخچه بستگی دارد**: هر چیزی در هر بلاکی عوض شود، hash آخر هم عوض می‌شود. به چنین ساختاری {{< term "hash-chain" "زنجیره‌ی hash" >}} می‌گویند.

## یک دام پنهان: کدام بایت‌ها را hash کنیم؟

تا این‌جا گفتم «header را hash می‌کنیم». ولی تابع hash روی بایت کار می‌کند، نه روی struct در Go. پس اول باید header را به یک رشته بایت تبدیل کنیم (به این کار **serialize** کردن می‌گویند). این‌جا جایی است که خیلی راحت می‌شود اشتباه کرد.

در بلاکچین چند کامپیوتر (به هر کدام **نود** می‌گویند) هر کدام جداگانه hash بلاک‌ها را حساب می‌کنند و باید به جواب یکسان برسند. اگر دو نود یک header را کمی متفاوت به بایت تبدیل کنند، به دو hash متفاوت می‌رسند و دیگر سر اینکه زنجیره‌ی درست کدام است توافق نمی‌کنند. اولین راهی که به ذهن می‌رسد JSON است؛ ببینیم چه می‌شود. خروجی `go run ./cmd/toychain encoding`:

```
json.Marshal:        {"from":"alice","to":"bob","amount":10,"memo":"rent<may>"}
  9ad464a5d059
Encoder, no escape:  {"from":"alice","to":"bob","amount":10,"memo":"rent<may>"}
  1e65ec03e3fb
map via json.Marshal: {"amount":10,"from":"alice","to":"bob"}
"ab"+"c" vs "a"+"bc" same hash: true
header bytes (80): 0000000000000001000000006553f13c...
```

این خروجی را خط‌به‌خط بخوانیم:

- **دو خط اول:** یک پرداخت واحد را با دو روش استاندارد خود Go به JSON تبدیل کرده‌ام. `json.Marshal` به‌طور پیش‌فرض علامت‌های `<` و `>` را به شکل `<` و `>` می‌نویسد (برای امنیت در HTML)، ولی `Encoder` با تنظیم `SetEscapeHTML(false)` همان `<` را می‌نویسد. معنی یکی است، بایت‌ها فرق دارند، پس hashها هم فرق دارند (`9ad4…` در برابر `1e65…`). یعنی حتی دو برنامه‌ی Go هم ممکن است سر یک داده توافق نکنند.
- **خط map:** Go کلیدهای map را موقع تبدیل به JSON مرتب می‌کند، پس در Go این خروجی همیشه یکسان است. ولی زبان‌های دیگر لزوماً این کار را نمی‌کنند؛ مثلاً `JSON.stringify` در JavaScript کلیدها را به همان ترتیبی که اضافه شده‌اند می‌نویسد. فاصله‌ها، شکل نوشتن عددها و escape کاراکترهای یونیکد هم از کتاب‌خانه‌ای به کتاب‌خانه‌ی دیگر فرق می‌کند.
- **خط چهارم:** اگر به‌جای JSON فیلدها را ساده پشت هم بچسبانیم، مشکل دیگری پیش می‌آید. `"ab"` و `"c"` چسبیده می‌شود `"abc"`؛ `"a"` و `"bc"` هم می‌شود `"abc"`. دو داده‌ی متفاوت، یک hash. مرز بین فیلدها گم شده است.

پس به یک روش تبدیل نیاز داریم که هیچ جای تفسیر نداشته باشد: هر داده‌ی یکسان، در هر زبانی، دقیقاً همان بایت‌ها. به این می‌گویند {{< term "canonical-encoding" "encoding یکتا" >}}. برای header ما کار ساده است، چون همه‌ی فیلدهایش طول ثابت دارند. فیلدها را همیشه با همین ترتیب پشت هم می‌گذاریم، و عددها را هم همیشه با یک ترتیب بایت مشخص (**big-endian**، یعنی بایت پرارزش‌تر اول) می‌نویسیم:

```go
func (h Header) Encode() []byte {
	buf := make([]byte, 0, HeaderSize)
	buf = binary.BigEndian.AppendUint64(buf, h.Height)
	buf = binary.BigEndian.AppendUint64(buf, uint64(h.Timestamp))
	buf = append(buf, h.PrevHash[:]...)
	buf = append(buf, h.DataHash[:]...)
	return buf
}

func (h Header) Hash() Hash { return Sum(h.Encode()) }
```

۸ بایت برای ارتفاع، ۸ بایت برای زمان، ۳۲ بایت برای هر hash: همیشه دقیقاً ۸۰ بایت. چون طول و جای هر فیلد معلوم است، ابهام چسباندن هم پیش نمی‌آید. خط آخر خروجی بالا همین ۸۰ بایت است: `0000000000000001` همان ارتفاع ۱ است و `000000006553f13c` زمان.

## ساختن زنجیره و چک کردنش

اولین بلاک زنجیره قبلی ندارد که به آن اشاره کند. به آن {{< term "genesis-block" "بلاک genesis" >}} می‌گویند: ارتفاعش ۰ است و `PrevHash`ش تمام صفر. هر بلاک بعدی را `Append` روی آخرین بلاک زنجیره می‌سازد. شماره را یکی زیاد می‌کند و hash آخرین بلاک را به‌عنوان `PrevHash` بلاک جدید می‌گذارد:

```go
func (c *Chain) Append(ts int64, data []byte) Block {
	tip := c.Tip()
	b := NewBlock(tip.Header.Height+1, tip.Hash, ts, data)
	c.blocks = append(c.blocks, b)
	return b
}
```

برای چک کردن زنجیره، `ValidateBlocks` به هیچ hash ذخیره‌شده‌ای اعتماد نمی‌کند و همه را از نو حساب می‌کند. برای هر بلاک می‌پرسد:

1. آیا شماره‌اش درست است؟
2. آیا hash داده‌اش با `DataHash` می‌خواند؟
3. آیا hash header با `Hash` ذخیره‌شده می‌خواند؟
4. آیا `PrevHash`ش با hash بلاک قبلی یکی است؟

به اولین «نه» که برسد، می‌ایستد و می‌گوید کدام بلاک و چه مشکلی.

## امتحانش کنیم: دستکاری دفتر

حالا برگردیم به سؤال اول. `go run ./cmd/toychain chain` یک زنجیره‌ی چهاربلاکی می‌سازد، بعد یک نسخه از آن را برمی‌دارد و نقش آدمی را بازی می‌کند که می‌خواهد در بلاک ۱ عدد `10` را به `1000` تبدیل کند، و هر بار کمی زرنگ‌تر:

```
  #0 prev=-            hash=4d7f75130edb data="genesis"
  #1 prev=4d7f75130edb hash=056ffcc052ff data="alice -> bob: 10"
  #2 prev=056ffcc052ff hash=75a7ae117b39 data="bob -> carol: 4"
  #3 prev=75a7ae117b39 hash=5be1abf7508b data="carol -> dave: 1"
validate: <nil>
edit data:       block 1: data hash does not match data
rehash block 1:  block 2: previous hash does not match
rebuild rest:    <nil>
tip before: 5be1abf7508b tip after: a571aac4dcd0
```

چهار خط اول زنجیره‌ی سالم است. ببینید `prev` هر بلاک دقیقاً همان `hash` بلاک بالایی است؛ این همان زنجیر است. `validate: <nil>` یعنی هیچ مشکلی پیدا نشد. بعد سه تلاش برای دستکاری:

- **تلاش اول (`edit data`):** فقط داده‌ی بلاک ۱ عوض می‌شود. اعتبارسنجی فوراً می‌گیردش: hash داده‌ی جدید با `DataHash` که در header مانده نمی‌خواند.
- **تلاش دوم (`rehash block 1`):** دستکاری‌کننده زرنگ‌تر است و `DataHash` و `Hash` بلاک ۱ را هم از نو حساب می‌کند. حالا بلاک ۱ به‌تنهایی سالم به نظر می‌رسد، ولی مشکل به بلاک ۲ منتقل شده: `PrevHash` بلاک ۲ هنوز hash قدیمی بلاک ۱ را دارد.
- **تلاش سوم (`rebuild rest`):** دستکاری‌کننده همه‌ی بلاک‌های بعدی را هم بازسازی می‌کند. حالا اعتبارسنجی چیزی پیدا نمی‌کند.

پس دستکاری موفق شد؟ نه کاملاً، و این مهم‌ترین نکته‌ی این مقاله است. خط آخر را ببینید: hash آخرین بلاک از `5be1abf7508b` شده `a571aac4dcd0`. زنجیره‌ی جعلی از درون سالم است، ولی **اثر انگشت آخرش فرق دارد**. اعتبارسنجی به‌تنهایی نمی‌تواند بگوید کدام نسخه اصل است. چیزی که از نسخه‌ی اصل محافظت می‌کند این است که بقیه‌ی نودها hash آخر نسخه‌ی اصل را از قبل دارند و نسخه‌ی جعلی را فوراً تشخیص می‌دهند. در مقاله‌های بعدی، با proof of work، یک لایه‌ی دیگر هم اضافه می‌شود: بازسازی بلاک‌ها دیگر مثل این‌جا مجانی نیست و هزینه‌ی واقعی دارد.

`go test ./...` هم همین سناریوها را به شکل تست تکرار می‌کند.

## کجاها راحت می‌شود خراب کرد

- **خروجی پیش‌فرض کتاب‌خانه‌ها را hash نکنید.** نه خروجی `json.Marshal`، نه `fmt.Sprintf("%v")`. همان‌طور که دیدیم، این‌ها ممکن است بی‌خبر از شما عوض شوند یا در زبان دیگری فرق کنند. روش تبدیل به بایت را خودتان تعریف کنید و ثابت نگهش دارید.
- **فیلدهای با طول متغیر را بی‌مرز نچسبانید.** اگر فیلدی مثل متن یا لیست دارید که طولش ثابت نیست، قبل از آن طولش را بنویسید، تا معلوم باشد کجا تمام می‌شود. وگرنه به همان مشکل `"ab"+"c"` می‌خورید.
- **به hash ذخیره‌شده اعتماد نکنید.** نگه‌داشتن hash برای سرعت خوب است، ولی موقع اعتبارسنجی همیشه از نو حسابش کنید. hash ذخیره‌شده را هم مثل داده می‌شود دستکاری کرد، همان‌طور که در تلاش دوم دیدیم.
- **hash فقط تغییر را نشان می‌دهد، نه اینکه چه کسی تغییر داده.** زنجیره‌ی ما نمی‌داند بلاک را چه کسی ساخته است. این کار امضای دیجیتال است که بعداً به آن می‌رسیم.

## تمرین

۱. یک فیلد `Version uint32` به header اضافه کنید و `Encode` و `HeaderSize` را به‌روز کنید. اگر یادتان برود `HeaderSize` را عوض کنید، کدام تست می‌گیردش؟
۲. کاری کنید `ValidateBlocks` بلاکی را که زمانش از بلاک قبلی قدیمی‌تر است رد کند.
۳. تابع `Decode([]byte) (Header, error)` را بنویسید که کار `Encode` را برعکس کند، و تستی که نشان دهد `Decode(h.Encode())` دقیقاً همان `h` را برمی‌گرداند.
