فرض کنید یک کیف پول روی گوشی دارید و دیروز به کسی پول فرستاده‌اید. حالا می‌خواهید مطمئن شوید که پرداختتان واقعاً در بلاک شماره‌ی ۱۰۰۰ ثبت شده است. گوشی شما جا و اینترنت کافی ندارد که کل بلاک را دانلود کند، چون یک بلاک واقعی ممکن است هزاران تراکنش داشته باشد. آیا راهی هست که فقط چند صد بایت بگیرید و با اطمینان بگویید «بله، پرداخت من در این بلاک هست»؟

با طراحی [مقاله‌ی قبل](/fa/posts/bc-hashes-blocks-chain/) چنین راهی نداریم. آن‌جا header هر بلاک یک `DataHash` داشت، یعنی hash کل داده‌ی بلاک. برای اینکه این hash را از نو حساب کنید و ببینید با header می‌خواند، باید **همه‌ی** داده را داشته باشید. hash یکجا یا همه را تأیید می‌کند یا هیچ را.

{{< term "merkle-tree" "Merkle tree" >}} همین مشکل را حل می‌کند. header هنوز فقط یک hash سی‌ودوبایتی نگه می‌دارد، ولی حالا هر کسی می‌تواند با چند hash ثابت کند یک تراکنش مشخص در بلاک هست. این ساختار فقط مال بلاکچین نیست: در [replication و quorum](/fa/posts/ds-replication-quorum/) از آن برای مقایسه‌ی سریع replicaها استفاده کردیم. اگر خود درخت‌ها برایتان تازه است، [درخت جست‌وجو و B-tree](/fa/posts/algo-trees-bst-btree/) زمینه‌ی خوبی است.

کد این مقاله ادامه‌ی همان ماژول `toychain` مقاله‌ی قبل است. یک نسخه از آن برداشتم و دو چیز را عوض کردم: در header، فیلد `DataHash` جایش را به `MerkleRoot` داد، و در بلاک، `Data []byte` شد `Txs [][]byte`، یعنی یک لیست تراکنش به‌جای یک تکه داده. تراکنش‌ها هنوز فقط چند بایت خام‌اند، مثل `"alice -> bob: 10"`. تراکنش امضاشده‌ی واقعی دو مقاله‌ی بعد می‌آید.

> همه‌ی مثال‌ها را با Go 1.27 روی macOS (arm64) اجرا کرده‌ام و خروجی‌ها همان چیزی است که دیدم. کد یک مثال محلی است، نه repo منتشرشده.

## ایده با چهار تراکنش

قبل از کد، بیایید ایده را با یک مثال کوچک ببینیم. فرض کنید بلاک چهار تراکنش دارد: `a`، `b`، `c` و `d`.

اول هر تراکنش را جدا hash می‌کنیم. به هر کدام از این hashها یک **برگ** درخت می‌گوییم. بعد برگ‌ها را دوتادوتا جفت می‌کنیم و hash هر جفت را حساب می‌کنیم. این‌ها **گره‌های میانی**‌اند. همین کار را آن‌قدر تکرار می‌کنیم تا فقط یک hash بماند. به این آخری **ریشه** یا {{< term "merkle-root" "Merkle root" >}} می‌گویند، و همین است که در {{< term "block-header" "header" >}} بلاک می‌نشیند:

```
            root = H(ab, cd)
           /                \
     ab = H(a, b)       cd = H(c, d)
      /       \          /       \
   H(a)      H(b)     H(c)      H(d)
```

ریشه هنوز به همه‌ی تراکنش‌ها بستگی دارد. اگر `c` حتی یک بیت عوض شود، `H(c)` عوض می‌شود، پس `cd` عوض می‌شود، پس ریشه هم عوض می‌شود. از این نظر هیچ چیزی نسبت به `DataHash` از دست نداده‌ایم.

ولی حالا یک چیز تازه به دست آورده‌ایم. فرض کنید می‌خواهم به شما ثابت کنم `c` در بلاک هست، و شما فقط ریشه را از header دارید. لازم نیست هر چهار تراکنش را بفرستم. کافی است دو hash بفرستم: `H(d)` و `ab`. شما خودتان این کارها را می‌کنید:

1. `H(c)` را حساب می‌کنید.
2. آن را با `H(d)` ترکیب می‌کنید و به `cd` می‌رسید.
3. `ab` را با `cd` ترکیب می‌کنید و به یک ریشه می‌رسید.
4. اگر این ریشه با ریشه‌ی header یکی بود، `c` حتماً در بلاک هست.

به این دو hash که فرستادم {{< term "inclusion-proof" "اثبات عضویت" >}} می‌گویند. هر کدامشان «جفت» (sibling) یک گره روی مسیر `c` تا ریشه است، یعنی گره‌ی دیگری که همان پدر را دارد. برای چهار تراکنش، اثبات دو hash است. هر بار که تعداد تراکنش‌ها دو برابر شود، درخت فقط یک طبقه بلندتر می‌شود و اثبات فقط یک hash بزرگ‌تر. کمی پایین‌تر عدد واقعی‌اش را می‌بینیم.

## ساختن درخت در Go

حالا همین را به کد تبدیل کنیم. دو تابع داریم: یکی hash برگ را حساب می‌کند و یکی hash گره‌ی میانی را. دو ثابت `leafPrefix` و `nodePrefix` را فعلاً نادیده بگیرید؛ در بخش بعد می‌گویم چرا وجود دارند.

```go
const (
	leafPrefix = 0x00
	nodePrefix = 0x01
)

// LeafHash is SHA-256(0x00 || tx).
func LeafHash(tx []byte) Hash {
	return Sum(append([]byte{leafPrefix}, tx...))
}

// NodeHash is SHA-256(0x01 || left || right).
func NodeHash(left, right Hash) Hash { /* ... */ }

func nextLevel(level []Hash) []Hash {
	next := make([]Hash, 0, (len(level)+1)/2)
	for i := 0; i < len(level); i += 2 {
		if i+1 == len(level) {
			next = append(next, level[i]) // lone node: promoted as is
			break
		}
		next = append(next, NodeHash(level[i], level[i+1]))
	}
	return next
}
```

`nextLevel` یک طبقه از درخت را می‌گیرد و طبقه‌ی بالایی را می‌سازد: گره‌ها را دوتادوتا برمی‌دارد و `NodeHash` هر جفت را حساب می‌کند. `MerkleRoot` اول همه‌ی برگ‌ها را می‌سازد و بعد آن‌قدر `nextLevel` را صدا می‌زند تا فقط یک hash بماند.

مثال چهارتایی ما مرتب بود. ولی اگر تعداد گره‌ها فرد باشد چه؟ مثلاً با سه تراکنش، `c` در طبقه‌ی اول جفتی ندارد. این‌جا باید یک قاعده انتخاب کنیم، و هر قاعده‌ای ریشه‌ی متفاوتی می‌دهد:

- **بالا بردن:** گره‌ی تنها را بدون تغییر به طبقه‌ی بعد می‌بریم. کد من همین کار را می‌کند (خط `promoted as is`).
- **تکرار کردن:** گره‌ی تنها را با خودش جفت می‌کنیم، یعنی `H(c, c)`. بیت‌کوین این کار را می‌کند.

با قاعده‌ی بالا بردن، درخت ما همان شکلی را دارد که RFC 6962 تعریف کرده است. این RFC استاندارد Certificate Transparency است، سیستمی که گواهی‌های HTTPS را در یک لاگ عمومی ثبت می‌کند. برای اینکه مطمئن شوم، یک تست نوشتم که ریشه‌ی کد من را با یک پیاده‌سازی مستقیم از تعریف بازگشتی RFC مقایسه می‌کند. برای ۰ تا ۳۰۰ تراکنش همه یکی‌اند.

## چرا برگ و گره پیشوند متفاوت دارند

حالا برگردیم به آن دو ثابت. `LeafHash` قبل از تراکنش یک بایت `0x00` می‌گذارد و `NodeHash` قبل از دو hash فرزند یک بایت `0x01`. چرا؟

فرض کنید این پیشوندها نبودند. آن‌وقت hash برگ می‌شد `SHA-256(tx)` و hash گره‌ی میانی می‌شد `SHA-256(left || right)`، یعنی hash دو فرزند که پشت هم چسبیده‌اند. هر hash سی‌ودو بایت است، پس ورودی گره‌ی میانی همیشه دقیقاً ۶۴ بایت است.

مشکل این است که درخت نمی‌تواند بفهمد این ۶۴ بایت «دو hash چسبیده» است یا «یک تراکنش ۶۴ بایتی». تابع hash فقط بایت می‌بیند. پس کسی می‌تواند یک «تراکنش» جعلی بسازد که دقیقاً همان ۶۴ بایت باشد. hash این برگ جعلی با hash آن گره‌ی میانی یکی می‌شود. نتیجه: یک لیست تراکنش کاملاً متفاوت که همان ریشه را می‌دهد.

به این حمله {{< term "second-preimage-attack" "second preimage" >}} می‌گویند: پیدا کردن ورودی دومی که همان hash ورودی اول را بدهد. نکته‌ی مهم این است که این‌جا SHA-256 نشکسته است. درخت ما به‌خاطر طراحی‌اش دو چیز متفاوت را با یک شکل hash می‌کند.

`go run ./cmd/toychain naive` این را نشان می‌دهد. اول یک درخت بدون پیشوند روی چهار تراکنش واقعی می‌سازد. بعد دو «تراکنش» جعلی ۶۴ بایتی درست می‌کند: اولی hash تراکنش ۰ و ۱ است که پشت هم چسبیده‌اند، دومی hash تراکنش ۲ و ۳. روی این دو تا هم درخت بدون پیشوند می‌سازد. آخر سر همین دو لیست را با درخت واقعی خودمان، که پیشوند دارد، امتحان می‌کند:

```
naive root, 4 real txs:  472c9838ed30
naive root, 2 fake txs:  472c9838ed30
prefixed root, real:     8e904c88352a
prefixed root, fake:     e0b533a65e8d
```

(برای خوانایی، دمو فقط شش بایت اول هر hash را چاپ می‌کند.)

- **دو خط اول:** درخت بدون پیشوند برای چهار تراکنش واقعی و دو تراکنش جعلی **یک ریشه** داده است. یعنی یک header، دو محتوای متفاوت. کسی که فقط ریشه را دارد نمی‌تواند بگوید کدام درست است.
- **دو خط آخر:** با پیشوند، ریشه‌ها دوباره فرق دارند. حالا hash برگ همیشه با `0x00` شروع می‌شود و hash گره‌ی میانی با `0x01`، پس هیچ برگی نمی‌تواند خودش را جای گره‌ی میانی جا بزند.

به این کار، یعنی جدا کردن دو نوع hash با یک برچسب ثابت، {{< term "domain-separation" "domain separation" >}} می‌گویند. RFC 6962 هم دقیقاً همین دو پیشوند را دارد.

## تله‌ی تکرار گره‌ی آخر

گفتم بیت‌کوین گره‌ی تنها را تکرار می‌کند. این قاعده هم یک تله‌ی شناخته‌شده دارد، و این بار مشکل از پیشوند نیست. `go run ./cmd/toychain dup` یک نسخه‌ی ساده‌شده از قاعده‌ی بیت‌کوین را اجرا می‌کند. ساده‌شده یعنی یک بار SHA-256 به‌جای دو بار، و بدون پیشوند. این نسخه را روی دو لیست `[a b c]` و `[a b c c]` امتحان می‌کند، و بعد همین دو لیست را با قاعده‌ی بالا بردن خودمان:

```
duplicate-last [a b c]:   d31a37ef6ac1
duplicate-last [a b c c]: d31a37ef6ac1
promote-last   [a b c]:   36642e73c254
promote-last   [a b c c]: e9636069c740
```

دو خط اول یکی‌اند، و دلیلش ساده است. در `[a b c]`، گره‌ی `c` تنهاست و با خودش جفت می‌شود: `H(c, c)`. در `[a b c c]`، دو `c` واقعی کنار هم‌اند و باز می‌شود `H(c, c)`. از آن به بعد هر دو درخت عین هم‌اند. پس یک header با دو لیست تراکنش متفاوت جور درمی‌آید.

دو خط آخر نشان می‌دهد قاعده‌ی بالا بردن این مشکل را ندارد: `[a b c]` و `[a b c c]` ریشه‌ی متفاوت دارند.

تا جایی که می‌دانم، این مشکل در بیت‌کوین با شناسه‌ی CVE-2012-2459 گزارش شد: می‌شد نود را فریب داد که یک بلاک معتبر را نامعتبر علامت بزند. من چیزی را روی خود بیت‌کوین بازتولید نکردم؛ دمو فقط شکل مسئله را نشان می‌دهد.

## اثبات عضویت در کد

حالا که درخت درست ساخته می‌شود، برگردیم به هدف اصلی: ثابت کردن اینکه یک تراکنش در بلاک هست. اثبات سه چیز دارد:

```go
type Proof struct {
	Index    int    // position of the transaction
	TxCount  int    // number of transactions in the tree
	Siblings []Hash // bottom to top; promoted levels have no sibling
}
```

`Siblings` همان hashهای «جفت» است که در مثال چهارتایی فرستادم، از پایین به بالا. `Index` جای تراکنش در لیست است و `TxCount` تعداد کل تراکنش‌ها.

`VerifyProof(root, tx, p)` همان چهار قدمی را انجام می‌دهد که بالاتر دستی انجام دادیم. از `LeafHash(tx)` شروع می‌کند و طبقه‌به‌طبقه آن را با جفتش ترکیب می‌کند تا به ریشه برسد. در هر طبقه باید بداند جفت سمت چپ است یا سمت راست، چون `H(x, y)` با `H(y, x)` فرق دارد. این را از `Index` و `TxCount` حساب می‌کند، نه اینکه از فرستنده‌ی اثبات بپرسد. اگر فرستنده می‌توانست بگوید «این‌جا سمت چپ است»، اثبات فقط عضویت را نشان می‌داد و درباره‌ی جای تراکنش چیزی نمی‌گفت. با این کار، `Index` هم بخشی از چیزی است که چک می‌شود. یک شرط دیگر هم دارد: همه‌ی hashهای `Siblings` باید مصرف شوند، تا کسی نتواند hash اضافه در اثبات بگذارد.

`go run ./cmd/toychain merkle` یک درخت با پنج تراکنش می‌سازد، برای تراکنش ۲ اثبات می‌سازد و آن را یک بار با تراکنش درست و یک بار با تراکنش دستکاری‌شده چک می‌کند. آخر سر همین کار را برای تراکنش ۴ انجام می‌دهد:

```
root of 5 txs: d9f7ce89020c
proof for tx 2 of 5: 3 siblings, 96 bytes
  sibling 0: 5850eb6c9ec8
  sibling 1: 408cc2b42814
  sibling 2: b0bdb971b6f9
verify real tx:    true
verify edited tx:  false
proof for tx 4 (promoted twice): 1 siblings
verify: true
```

برای اینکه این خروجی معنی پیدا کند، شکل درخت پنج‌تایی را ببینید. اسم تراکنش‌ها را ۰ تا ۴ گذاشته‌ام:

```
                  root
                /      \
           N0123         4
          /     \        |
       N01       N23     4
      /   \     /   \    |
     0     1   2     3   4
```

تراکنش ۴ در طبقه‌ی اول جفتی ندارد و بالا می‌رود، در طبقه‌ی دوم هم همین‌طور، و فقط در طبقه‌ی آخر با `N0123` جفت می‌شود.

حالا خروجی را بخوانیم:

- **اثبات تراکنش ۲** سه hash دارد، یعنی ۹۶ بایت. از پایین به بالا: `sibling 0` برگ تراکنش ۳ است، `sibling 1` گره‌ی `N01` است، و `sibling 2` برگ تراکنش ۴ است که تا طبقه‌ی آخر بالا آمده.
- **`verify real tx: true`:** با این سه hash، ریشه‌ی حساب‌شده با ریشه‌ی درخت یکی شد.
- **`verify edited tx: false`:** همان اثبات را با تراکنش `"carol -> dave: 100"` به‌جای `"carol -> dave: 1"` امتحان کردیم. hash برگ فرق کرد، پس ریشه هم فرق کرد و اثبات رد شد.
- **اثبات تراکنش ۴** فقط یک hash دارد، یعنی `N0123`. دلیلش همان است که در شکل دیدیم: در دو طبقه‌ی اول جفتی ندارد، پس آن‌جا چیزی برای فرستادن نیست.

تست‌ها هم برای ۱ تا ۷۰ تراکنش همه‌ی جایگاه‌ها را امتحان می‌کنند: اثبات درست باید قبول شود، و همان اثبات با یک تراکنش جعلی یا با `Index` اشتباه باید رد شود.

## اثبات چقدر بزرگ است؟

گفتم اندازه‌ی اثبات خیلی کند رشد می‌کند. `go run ./cmd/toychain sizes` درخت‌هایی با اندازه‌های مختلف می‌سازد و هر بار برای تراکنش ۰ اثبات می‌گیرد:

```
      txs siblings  proof bytes all leaf hashes
        1        0            0             32
        2        1           32             64
        3        2           64             96
        4        2           64            128
        5        3           96            160
        8        3           96            256
      100        7          224           3200
     1000       10          320          32000
     4096       12          384         131072
  1000000       20          640       32000000
```

ستون‌ها به این معنی‌اند: تعداد تراکنش‌ها، تعداد hashهای اثبات، اندازه‌ی اثبات به بایت، و در ستون آخر اندازه‌ی همه‌ی hashهای برگ کنار هم. ستون آخر حداقل چیزی است که بدون درخت لازم داشتید، تازه بدون حساب کردن خود تراکنش‌ها.

مقایسه‌ی دو ستون آخر همه‌چیز را می‌گوید. برای هزار تراکنش، اثبات ۳۲۰ بایت است در برابر ۳۲ هزار بایت. برای یک میلیون تراکنش، اثبات ۲۰ hash است، یعنی ۶۴۰ بایت، در برابر ۳۲ میلیون بایت. تعداد hashهای اثبات تقریباً برابر log2 تعداد تراکنش‌هاست: ۲ به توان ۲۰ کمی بیشتر از یک میلیون است، پس ۲۰ طبقه کافی است.

این همان جواب سؤال اول مقاله است. whitepaper بیت‌کوین به این روش {{< term "spv" "simplified payment verification" >}} می‌گوید: یک کلاینت سبک، مثل کیف پول روی گوشی، فقط headerها را نگه می‌دارد. هر وقت خواست بداند تراکنشی در بلاکی هست، اثبات عضویتش را می‌خواهد و خودش چکش می‌کند.

## برگشت به زنجیره

حالا Merkle tree را به زنجیره‌ی مقاله‌ی قبل وصل کنیم. `ValidateBlocks` قبلاً hash داده را از نو حساب می‌کرد و با `DataHash` مقایسه می‌کرد. حالا ریشه را از روی `Txs` از نو می‌سازد و با `MerkleRoot` در header مقایسه می‌کند. `go run ./cmd/toychain chain` یک زنجیره‌ی سه‌بلاکی می‌سازد، آن را چک می‌کند، بعد فقط یک تراکنش در بلاک ۱ را عوض می‌کند (`10` می‌شود `1000`) و دوباره چک می‌کند:

```
  #0 prev=-            root=7b5eabeb1bbd hash=759fc6cff9c0 txs=1
  #1 prev=759fc6cff9c0 root=63a5466f1041 hash=cedaf9a6150d txs=3
  #2 prev=cedaf9a6150d root=5850eb6c9ec8 hash=a07354280ad9 txs=1
validate: <nil>
edit one tx: block 1: merkle root does not match transactions
```

سه خط اول زنجیره است. مثل قبل، `prev` هر بلاک همان `hash` بلاک قبلی است، و حالا هر بلاک یک `root` و تعداد تراکنش‌هایش (`txs`) را هم نشان می‌دهد. `validate: <nil>` یعنی زنجیره‌ی سالم مشکلی ندارد. خط آخر دستکاری را می‌گیرد: ریشه‌ای که از تراکنش‌های تازه ساخته شد با ریشه‌ی header بلاک ۱ نمی‌خواند.

یک جزئیات کوچک هم در این خروجی هست. ریشه‌ی بلاک ۲، یعنی `5850eb6c9ec8`، با `sibling 0` در دموی قبل یکی است. دلیلش این است که بلاک ۲ فقط یک تراکنش دارد، `"dave -> erin: 2"`، و ریشه‌ی درختی که یک برگ دارد همان hash آن برگ است. در دموی قبل هم `sibling 0` برگ همین تراکنش بود.

## یک اثبات چه چیزی را ثابت نمی‌کند

اثبات عضویت ابزار قدرتمندی است، ولی راحت می‌شود بیشتر از آنچه هست از آن انتظار داشت:

- **اثبات فقط به اندازه‌ی ریشه‌اش ارزش دارد.** اگر ریشه را از همان کسی بگیرید که اثبات را می‌فرستد، او می‌تواند هر درختی که بخواهد بسازد و اثبات معتبر هم برایش درست کند. ریشه را باید از headerی بگیرید که خودتان اعتبارسنجی کرده‌اید.
- **قاعده‌ی تعداد فرد را بنویسید و ثابت نگهش دارید.** بالا بردن و تکرار کردن ریشه‌ی متفاوت می‌دهند. اگر دو پیاده‌سازی سر این قاعده توافق نداشته باشند، روی هیچ بلاکی با تعداد فرد تراکنش توافق نمی‌کنند.
- **hash برگ و گره را از هم جدا کنید.** همان‌طور که در دموی `naive` دیدیم، بدون پیشوند درخت می‌شکند، حتی وقتی SHA-256 کاملاً سالم است.
- **header ما تعداد تراکنش‌ها را ثابت نمی‌کند.** `TxCount` داخل اثبات است، نه داخل header. امتحان کردم: اثبات تراکنش ۰ از ۵ اگر ادعا کند ۶، ۷ یا ۸ تراکنش هست هم قبول می‌شود. دلیلش این است که مسیر تراکنش ۰ در همه‌ی این درخت‌ها همان سه جفت را دارد. پس عضویت درست ثابت می‌شود، ولی تعداد نه.
- **عضویت یعنی فقط «این تراکنش در این بلاک هست».** اثبات نمی‌گوید تراکنش معتبر است، امضای درستی دارد، یا پولی که خرج کرده قبلاً خرج نشده بود. این‌ها کار قواعد دیگری است که در مقاله‌های بعدی می‌سازیم.

## تمرین

۱. تستی بنویسید که نشان دهد `[a b c]` و `[a b c c]` با `MerkleRoot` ریشه‌ی متفاوت دارند.
۲. `TxCount` را به header اضافه کنید و کاری کنید verifier تعداد را از header بگیرد، نه از اثبات. بعد دوباره امتحان کنید که اثبات با ادعای ۶ تراکنش هنوز قبول می‌شود یا نه.
۳. اثباتی برای دو تراکنش هم‌زمان بنویسید که hashهای جفت مشترکشان را فقط یک بار بفرستد.

## قدم بعدی

مقاله‌ی بعد «کلید، امضای ECDSA و آدرس روی secp256k1» است. تا این‌جا هر کسی می‌تواند بنویسد `"alice -> bob: 10"`؛ آن‌جا می‌بینیم چطور فقط خود alice می‌تواند تراکنشی به اسم خودش بسازد.
