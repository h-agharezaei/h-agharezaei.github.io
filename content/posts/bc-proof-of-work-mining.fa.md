یادتان هست در [هش، بلاک و زنجیره](/fa/posts/bc-hashes-blocks-chain/) کسی که می‌خواست دفتر را دستکاری کند چه کرد؟ عددی را در بلاک ۱ عوض کرد و بعد همه‌ی بلاک‌های بعدی را از نو ساخت. زنجیره‌ی جعلی از درون کاملاً سالم بود، و تنها چیزی که لوش داد این بود که بقیه hash آخر نسخه‌ی اصل را داشتند. ولی حالا یک سؤال سخت‌تر: اگر دو نسخه‌ی سالم از زنجیره در شبکه دست‌به‌دست شود، نودها کدام را قبول کنند؟

با کدی که تا این‌جا داریم، این سؤال جواب خوبی ندارد، چون ساختن یک بلاک معتبر فقط چند میکروثانیه طول می‌کشد. هر کسی می‌تواند در یک چشم به هم زدن یک زنجیره‌ی کامل و معتبر بسازد. در [بلاکچین از دید برنامه‌نویس](/fa/posts/bc-blockchain-for-programmers/) گفتم زنجیره‌ی hash فقط دستکاری را آشکار می‌کند، و اینکه بازنویسی را **گران** هم کنیم بعداً می‌آید. این همان مقاله است. بعد از مقایسه‌ی مدل حساب و UTXO در [مقاله‌ی قبل](/fa/posts/bc-account-model-nonce/)، حالا وقت این است که ساختن بلاک هزینه داشته باشد.

راه‌حل اول که به ذهن می‌رسد رأی‌گیری است: هر نود یک رأی، و زنجیره‌ای برنده است که بیشتر نودها قبولش دارند. در [consensus و Raft](/fa/posts/ds-consensus-raft/) دقیقاً همین کار را کردیم، و آن‌جا جواب می‌داد، چون فهرست سرورها از قبل معلوم بود. ولی یک شبکه‌ی باز فهرست ندارد. هر کسی می‌تواند هزار نود بالا بیاورد و هزار رأی داشته باشد. {{< term "proof-of-work" "Proof of Work" >}} این را عوض می‌کند: به‌جای «هر نود یک رأی»، «هر واحد محاسبه یک رأی». نود ساختن مجانی است، ولی محاسبه برق و سخت‌افزار می‌خواهد.

کد این مقاله ادامه‌ی ماژول `toychain` مقاله‌ی قبل است. یک نسخه از آن برداشتم و پکیج `chain` را گسترش دادم. بلاک‌ها هنوز تراکنش UTXO دارند.

> همه‌ی مثال‌ها را با Go 1.27 روی macOS (arm64) اجرا کرده‌ام و خروجی‌ها همان چیزی است که دیدم. کد یک مثال محلی است. load average ماشین موقع اجرا حدود ۳ بود، برای همین به‌جای زمان اجرا، تعداد hashها را نشان می‌دهم که به بار ماشین بستگی ندارد.

## یک معما: سخت برای حل، آسان برای چک

ایده‌ی Proof of Work این است: برای اینکه بلاکی قبول شود، سازنده‌اش باید یک معما را حل کند. این معما دو ویژگی دارد. حل کردنش زمان‌بر است و هیچ میان‌بُری ندارد، ولی چک کردن جوابش فوری است.

معما از همان تابع hash ساخته می‌شود. از مقاله‌ی hash یادمان هست که خروجی SHA-256 مثل یک رشته‌ی تصادفی از بیت‌هاست؛ انگار هر بیت را با انداختن سکه تعیین کرده باشیم. حالا شرط می‌گذاریم: hash header بلاک باید با مثلاً ۸ بیت صفر شروع شود. این مثل این است که ۸ سکه بیندازید و بخواهید همه شیر بیاید. احتمالش ۱ در ۲۵۶ است. پس به‌طور متوسط باید حدود ۲۵۶ بار امتحان کنید. اگر شرط ۹ بیت باشد، ۵۱۲ بار. هر بیت اضافه، کار را دو برابر می‌کند.

ولی اگر header ثابت باشد، hashش هم ثابت است. چطور «دوباره امتحان» کنیم؟ با یک فیلد تازه در header که هیچ معنایی ندارد جز اینکه سازنده‌ی بلاک بتواند عوضش کند. هر بار عوضش کنید، hash کاملاً تازه‌ای می‌گیرید؛ یعنی یک بار دیگر سکه‌ها را انداخته‌اید. به این حدس زدن پشت سر هم {{< term "mining" "mining" >}} یا «استخراج» می‌گویند، و به کسی که این کار را می‌کند ماینر.

## دو فیلد تازه در header

```go
type Header struct {
	Height     uint64
	Timestamp  int64
	PrevHash   Hash
	MerkleRoot Hash
	TxCount    uint32
	Bits       uint32 // the hash must start with this many zero bits
	Nonce      uint64 // changed by the miner until it does
}
```

دو فیلد آخر تازه‌اند:

- **`Bits`** سختی معماست، یا difficulty: hash باید حداقل با این تعداد بیت صفر شروع شود. اگر hash را یک عدد ۲۵۶ بیتی در نظر بگیریم، این یعنی hash باید از `2^(256-Bits)` کوچک‌تر باشد.
- **`Nonce`** همان فیلدی است که ماینر عوضش می‌کند. این سومین بار است که در این مجموعه به کلمه‌ی {{< term "nonce" "nonce" >}} می‌رسیم، و هر بار معنی‌اش فرق کرده. در مقاله‌ی کلیدها یک عدد مخفی در امضا بود، در مقاله‌ی قبل یک شماره‌ی ترتیب. این‌جا فقط عددی است که ماینر آن‌قدر زیادش می‌کند تا hash شرط را برآورده کند. وجه مشترک هر سه این است که عددی است که «برای یک بار» استفاده می‌شود.

{{< term "block-header" "header" >}} حالا ۹۶ بایت است. چون `Bits` داخل header است، hash هم آن را پوشش می‌دهد؛ ماینر نمی‌تواند بعد از ماین کردن ادعا کند که سختی بیشتری را حل کرده.

خود ماین کردن یک حلقه‌ی ساده است:

```go
func Mine(h Header, maxTries uint64) (Header, uint64, bool) {
	for tries := uint64(1); tries <= maxTries; tries++ {
		if h.MeetsTarget() {
			return h, tries, true
		}
		if tries == maxTries || h.Nonce == math.MaxUint64 {
			return h, tries, false
		}
		h.Nonce++
	}
	return h, 0, false
}
```

`MeetsTarget` header را hash می‌کند و بیت‌های صفر اولش را می‌شمارد. اگر کافی بود، کار تمام است. اگر نه، `Nonce` یکی زیاد می‌شود و دوباره امتحان می‌کنیم. هیچ راه زیرکانه‌تری وجود ندارد؛ از روی یک hash نمی‌شود فهمید کدام nonce به hash بهتر نزدیک‌تر است. `maxTries` فقط برای این است که بشود حلقه را بعد از تعداد مشخصی امتحان قطع کرد؛ بعداً در شبیه‌سازی به کارمان می‌آید.

یک نکته درباره‌ی بیت‌کوین: طبق مستندات بیت‌کوین، header آن به‌جای تعداد بیت صفر یک **{{< term "difficulty-target" "target" >}}** کامل ۲۵۶ بیتی را به شکلی فشرده نگه می‌دارد، و hash باید از آن کوچک‌تر باشد. این‌طوری سختی می‌تواند با هر ضریبی بالا و پایین برود. شمردن بیت‌های صفر خواناتر است، ولی هزینه دارد: سختی فقط می‌تواند دو برابر یا نصف شود. این هزینه را در جدول retarget می‌بینیم.

## ماین کردن یک بلاک

`go run ./cmd/toychain mine` یک بلاک genesis را سه بار، با سه سختی مختلف، ماین می‌کند. بعد یک بار دیگر آن را با سختی ۲۰ ماین می‌کند، و بعد از پیدا شدن جواب، فقط `Timestamp` را یک ثانیه جلو می‌برد:

```
bits  8: nonce      28,      29 hashes, hash 002acbe8e52ec14be233...
bits 16: nonce   49014,   49015 hashes, hash 0000af50878911463738...
bits 20: nonce 1908273, 1908274 hashes, hash 0000084c8f5cc05e63b2...
timestamp +1 after mining: 3c89edab33b4024d79b0..., meets target: false
```

برای خواندن hashها کمک می‌کند بدانید هر رقم hex چهار بیت است:

- **سختی ۸:** nonce ۲۸ جواب داد. چون از صفر شروع کردیم، این ۲۹ امتحان شد. hash با `00` شروع می‌شود، یعنی دو رقم hex صفر، یعنی ۸ بیت. این بار شانس آوردیم؛ متوسط ۲۵۶ است.
- **سختی ۱۶:** ۴۹٬۰۱۵ امتحان، و hash با `0000` شروع می‌شود: ۱۶ بیت.
- **سختی ۲۰:** نزدیک ۱٫۹ میلیون امتحان. hash با `00000` شروع می‌شود، پنج رقم صفر، یعنی ۲۰ بیت.
- **خط آخر:** بلاک ماین‌شده‌ی سختی ۲۰ را برداشتیم و فقط زمانش را یک ثانیه عوض کردیم. hash کاملاً تازه است و با `3c` شروع می‌شود، که فقط دو بیت صفر دارد، نه بیست. همه‌ی آن ۱٫۹ میلیون امتحان دود شد.

همین عدم تقارن قلب ماجراست. پیدا کردن جواب ۱٫۹ میلیون hash طول کشید، ولی هر کسی با **یک** hash می‌تواند چک کند که جواب درست است. و هر تغییری در بلاک، حتی یک ثانیه در زمان، کار را باطل می‌کند.

## هر بیت، دو برابر کار

یک بلاک به‌تنهایی به شانس بستگی دارد؛ دیدیم که سختی ۸ به‌جای ۲۵۶ امتحان با ۲۹ امتحان حل شد. برای اینکه قاعده‌ی کلی را ببینیم، باید میانگین بگیریم. `go run ./cmd/toychain tries` برای هر سختی از ۸ تا ۱۸ بیت، ۲۵۶ header متفاوت را ماین می‌کند و میانگین تعداد امتحان‌ها را حساب می‌کند:

```
bits   avg hashes     2^bits    vs prev
   8          245        256          -
   9          506        512      2.07x
  10         1178       1024      2.33x
  11         2044       2048      1.73x
  12         4071       4096      1.99x
  13         8113       8192      1.99x
  14        17520      16384      2.16x
  15        29389      32768      1.68x
  16        66541      65536      2.26x
  17       145265     131072      2.18x
  18       290333     262144      2.00x
```

ستون‌ها: سختی، میانگین تعداد hash که واقعاً لازم شد، عدد مورد انتظار یعنی `2^bits`، و نسبت میانگین هر ردیف به ردیف قبلی.

ستون دوم و سوم خیلی نزدیک هم‌اند: میانگین واقعی تقریباً همان `2^bits` است. ستون آخر نشان می‌دهد هر بیت اضافه کار را تقریباً دو برابر می‌کند. تک‌تک قدم‌ها نویز دارند، از ۱٫۶۸ تا ۲٫۳۳ برابر، چون ۲۵۶ نمونه هنوز کاملاً شانس را صاف نمی‌کند. ولی روند کلی روشن است: از ۸ تا ۱۸ بیت، ده بیت اضافه، و کار حدود هزار برابر شده، یعنی ۲ به توان ۱۰.

## اعتبارسنجی

ماین کردن به‌تنهایی کافی نیست؛ نودها باید سختی را هم چک کنند. `AddBlock` حالا این‌ها را به ترتیب چک می‌کند: بلاک درست به بلاک قبلی وصل است، زمانش بعد از زمان بلاک قبلی است، `Bits` همان چیزی است که قواعد زنجیره می‌خواهد، hash شرط سختی را برآورده می‌کند، و بعد Merkle root و همه‌ی تراکنش‌ها.

`go run ./cmd/toychain powcheck` چهار بلاک مختلف را به زنجیره می‌دهد:

```
required bits: 8
unmined block:         block 1: hash does not meet the difficulty target
own bits 2 (21 hashes): block 1: wrong difficulty bits
mined, then tx edited: block 1: merkle root does not match transactions
mined (87 hashes):    <nil>
chainwork: genesis 256, tip 512
```

- **`required bits: 8`:** قواعد زنجیره برای بلاک بعدی ۸ بیت سختی می‌خواهند.
- **`unmined block`:** بلاکی که اصلاً ماین نشده رد می‌شود: hashش با ۸ بیت صفر شروع نمی‌شود.
- **`own bits 2`:** یک ماین تنبل سختی را خودش ۲ گذاشته و با ۲۱ امتحان ماینش کرده. hash شرط ۲ بیت را برآورده می‌کند، ولی بلاک رد می‌شود: سختی را قواعد زنجیره تعیین می‌کنند، نه سازنده‌ی بلاک.
- **`mined, then tx edited`:** بلاک درست ماین شده، ولی بعدش کسی گیرنده‌ی یک تراکنش را عوض کرده. header دست‌نخورده است، پس proof of work هنوز درست است، ولی Merkle root دیگر با تراکنش‌ها نمی‌خواند. برای دستکاری تراکنش باید Merkle root عوض شود، و آن‌وقت باید دوباره ماین کرد.
- **`mined (87 hashes)`:** همان بلاک با تراکنش اصلی، که با ۸۷ امتحان ماین شده بود، قبول می‌شود.
- **خط آخر** chainwork است، که چند بخش پایین‌تر توضیحش می‌دهم.

## Retarget: ثابت نگه داشتن سرعت بلاک‌ها

تا این‌جا سختی ثابت بود. ولی قدرت محاسبه‌ی شبکه ثابت نیست. ماینرهای تازه می‌آیند، بعضی می‌روند، سخت‌افزار سریع‌تر می‌شود. اگر سختی ثابت بماند و قدرت شبکه چهار برابر شود، بلاک‌ها هم چهار برابر سریع‌تر ساخته می‌شوند. ما می‌خواهیم سرعت ساخت بلاک ثابت بماند، مثلاً هر ۱۰ ثانیه یک بلاک، هر چقدر هم قدرت شبکه باشد.

راه‌حل این است که سختی هر چند وقت یک بار خودش را تنظیم کند. به این کار {{< term "difficulty-adjustment" "retarget" >}} می‌گویند. هر `RetargetInterval` بلاک، `NextBits` نگاه می‌کند دوره‌ی گذشته چقدر طول کشیده و چقدر **باید** طول می‌کشید. اگر بلاک‌ها خیلی سریع آمده بودند، سختی را بالا می‌برد؛ اگر خیلی کند، پایین. چون سختی ما فقط می‌تواند دو برابر یا نصف شود، `NextBits` نسبت را به نزدیک‌ترین توان دو گرد می‌کند. و برای اینکه سختی یک‌باره خیلی بالا و پایین نپرد، تغییر در هر دوره حداکثر ۲ بیت است، یعنی چهار برابر در هر جهت.

یک شرط مهم دیگر هم هست: همه‌ی نودها باید دقیقاً به یک جواب برسند. اگر یک نود بگوید سختی بلاک بعدی ۱۳ است و نود دیگر بگوید ۱۴، سر اعتبار بلاک‌ها توافق نمی‌کنند و زنجیره دو تکه می‌شود. برای همین این کد فقط با عدد صحیح کار می‌کند، نه عدد اعشاری:

```go
w2, a2 := want*want, actual*actual
switch {
case w2 >= 8*a2: // at least 2^1.5 times too fast
	delta = 2
case w2 >= 2*a2:
	delta = 1
case a2 >= 8*w2:
	delta = -2
case a2 >= 2*w2:
	delta = -1
}
```

`want` زمانی است که دوره باید طول می‌کشید و `actual` زمانی که واقعاً طول کشید. سؤال این است: نسبت این دو به کدام توان دو نزدیک‌تر است؟ مرز بین «یک برابر» و «دو برابر» در مقیاس توان‌های دو، `2^0.5` است، یعنی رادیکال ۲. مرز بین «دو برابر» و «چهار برابر» هم `2^1.5`، یعنی رادیکال ۸. کد برای اینکه به رادیکال و عدد اعشاری نیاز نداشته باشد، دو طرف را به توان دو می‌رساند. مثلاً «`want/actual` حداقل رادیکال ۸ است» همان «`want²` حداقل ۸ برابر `actual²` است». پس اگر بلاک‌ها حداقل ۲٫۸۳ برابر سریع‌تر از قرار آمده باشند، ۲ بیت به سختی اضافه می‌شود؛ اگر حداقل ۱٫۴۱ برابر، ۱ بیت. دو حالت آخر همین قاعده برای کندی است.

تا جایی که می‌دانم، بیت‌کوین همین کار را هر ۲۰۱۶ بلاک انجام می‌دهد، با همین سقف چهار برابر. پیش‌فرض کد من ۸ بلاک است تا دموهای مقاله‌های بعد کوتاه بمانند.

برای دیدن retarget در عمل، `go run ./cmd/toychain retarget` یک ماینر را شبیه‌سازی می‌کند. در هر «ثانیه‌ی شبیه‌سازی‌شده»، ماینر به تعداد `hashrate` nonce امتحان می‌کند. اگر جواب پیدا نشد، زمان header را یک ثانیه جلو می‌برد و از nonce صفر دوباره شروع می‌کند. hashها واقعی‌اند؛ فقط ساعت شبیه‌سازی شده است. وسط کار، قدرت ماینر را عوض می‌کنیم: اول ۴۰۰ hash در ثانیه، بعد چهار برابر، و بعد یک‌هشتم آن. با دوره‌های ۸ بلاکی نویز آن‌قدر زیاد بود که جدول خوانا نبود، برای همین این دمو دوره را ۳۲ بلاک گذاشته است:

```
retarget every 32 blocks, target 10s per block, genesis bits 12
  heights   hashrate  bits  avg spacing     hashes    chainwork
   1-31        400/s    12        10.8s     127388       131072
  32-63        400/s    12        10.4s     127554       262144
  64-95       1600/s    12         3.6s     156288       393216
  96-127      1600/s    13         6.2s     295686       655360
 128-159      1600/s    14         9.8s     476788      1179648
```

هر ردیف یک دوره است: بازه‌ی ارتفاع بلاک‌ها، قدرت ماینر، سختی آن دوره، فاصله‌ی متوسط بین بلاک‌ها، تعداد کل hashهای آن دوره، و chainwork تا آخر دوره. هدف ۱۰ ثانیه است. بیایید داستان را دنبال کنیم:

- **دو دوره‌ی اول (۴۰۰ در ثانیه):** با سختی ۱۲، یعنی حدود ۴۰۹۶ hash برای هر بلاک، ماینر ۴۰۰تایی به‌طور متوسط حدود ۱۰ ثانیه لازم دارد. فاصله‌ها ۱۰٫۸ و ۱۰٫۴ ثانیه است، نزدیک هدف. سختی عوض نمی‌شود.
- **دوره‌ی سوم (۱۶۰۰ در ثانیه):** قدرت چهار برابر شد، ولی سختی هنوز همان ۱۲ است، چون retarget فقط در آخر دوره اتفاق می‌افتد. بلاک‌ها هر ۳٫۶ ثانیه می‌آیند.
- **دوره‌ی چهارم:** آخر دوره‌ی قبل، retarget دید بلاک‌ها ۱۰ تقسیم بر ۳٫۶، یعنی حدود ۲٫۸ برابر، سریع‌تر بوده‌اند. این کمی کمتر از مرز ۲٫۸۳ است، پس فقط **یک** بیت اضافه شد: سختی ۱۳. فاصله به ۶٫۲ ثانیه رسید، هنوز سریع.
- **دوره‌ی پنجم:** یک بیت دیگر، سختی ۱۴، و فاصله ۹٫۸ ثانیه. دوباره روی هدف‌ایم. دو دوره طول کشید تا سختی به قدرت تازه برسد.
- **دوره‌ی ششم (۲۰۰ در ثانیه):** قدرت هشت برابر کم شد و سختی هنوز ۱۴ است. هر بلاک ۶۷٫۳ ثانیه طول می‌کشد.
- **دوره‌ی هفتم:** کندی بیش از ۲٫۸۳ برابر بود، ولی سقف اجازه‌ی بیش از ۲ بیت کاهش نمی‌دهد: سختی ۱۲. فاصله ۲۴٫۳ ثانیه است، هنوز کند.
- **دوره‌ی هشتم:** یک بیت دیگر کم شد، سختی ۱۱، و فاصله ۹٫۹ ثانیه.
- **`validate: <nil>`:** کل زنجیره، با همه‌ی تغییرهای سختی، از اول دوباره چک شد و درست بود.

این جدول هر دو طرف سقف را نشان می‌دهد. سقف جلوی پرش‌های ناگهانی سختی را می‌گیرد، ولی وقتی قدرت شبکه ناگهان خیلی عوض شود، سیستم چند دوره طول می‌کشد تا خودش را برساند.

## Chainwork: کار پشت زنجیره

ستون آخر جدول {{< term "chainwork" "chainwork" >}} است: جمع `2^Bits` روی همه‌ی بلاک‌های زنجیره. چون `2^Bits` تعداد متوسط hashهای لازم برای یک بلاک است، chainwork یعنی «به‌طور متوسط چند hash پشت این زنجیره است». در خروجی `powcheck` هم دیدیم: genesis با سختی ۸ کار ۲۵۶ دارد، و با اضافه شدن یک بلاک دیگر با همان سختی، کار به ۵۱۲ رسید.

ستون hashes و ستون chainwork را در جدول مقایسه کنید. hashes تعداد واقعی hashهایی است که ماینر زده، که به شانس بستگی دارد. chainwork عدد مورد انتظار است، که فقط از روی سختی‌ها حساب می‌شود و هر نودی بدون اعتماد به کس دیگر می‌تواند حسابش کند.

chainwork جواب سؤال اول مقاله است. دو مقاله‌ی بعد می‌بینیم که وقتی دو نسخه از زنجیره داریم، نودها نسخه‌ای را انتخاب می‌کنند که chainwork بیشتری دارد، نه لزوماً بلاک بیشتر. زنجیره‌ای با بلاک‌های بیشتر ولی سختی کمتر، کار کمتری پشتش است.

## چرا این جلوی Sybil را می‌گیرد

برگردیم به مشکل رأی‌گیری. در یک {{< term "sybil-attack" "حمله‌ی Sybil" >}} یک نفر خودش را جای خیلی‌ها جا می‌زند. اگر هر نود یک رأی داشت، کسی که هزار نود جعلی بالا بیاورد برنده می‌شد، چون نود ساختن مجانی است.

با Proof of Work، هویت جعلی نه هزینه‌ای دارد و نه فایده‌ای. تعداد نودها مهم نیست؛ فقط تعداد hashها حساب می‌شود، و hash زدن برق و سخت‌افزار می‌خواهد. هزار نود روی یک لپ‌تاپ همان قدرت یک لپ‌تاپ را دارد.

و حالا بازنویسی تاریخچه هم گران شده است. کسی که بخواهد بلاکی را عوض کند، باید کار همان بلاک و همه‌ی بلاک‌های بعدی را از نو انجام دهد، و این کار را باید سریع‌تر از کل بقیه‌ی شبکه انجام دهد، که در همین مدت دارد زنجیره‌ی اصلی را جلو می‌برد.

## دام‌های کد consensus

- **proof of work را قبل از چک‌های گران چک کنید، و `Bits` را با قاعده‌ی خودتان مقایسه کنید.** چک کردن hash فقط یک hash است، ولی چک کردن همه‌ی امضاهای یک بلاک خیلی گران‌تر است. اگر اول امضاها را چک کنید، هر کسی می‌تواند با بلاک‌های ماین‌نشده‌ی پر از تراکنش نودتان را مشغول کند. و هرگز سختی را از خود بلاک قبول نکنید؛ همان‌طور که در `own bits 2` دیدیم، سازنده‌ی بلاک هر عددی که راحتش باشد می‌نویسد.
- **در کد consensus فقط با عدد صحیح کار کنید.** محاسبه با عدد اعشاری ممکن است روی پردازنده‌ها، کامپایلرها یا زبان‌های مختلف کمی متفاوت گرد شود. در بیشتر برنامه‌ها این تفاوت اهمیتی ندارد، ولی این‌جا یعنی دو نود سر سختی بلاک بعدی توافق نمی‌کنند.
- **زمان بلاک‌ها روی retarget اثر می‌گذارد.** ماینر خودش `Timestamp` را می‌نویسد. اگر بتواند زمان‌های غلط بنویسد، می‌تواند retarget را فریب دهد و سختی را پایین بیاورد. من فقط چک می‌کنم که زمان هر بلاک از قبلی بیشتر باشد. تا جایی که می‌دانم، بیت‌کوین سخت‌گیرتر است: زمان باید از میانه‌ی زمان ۱۱ بلاک قبلی بیشتر باشد، و نباید زیادی در آینده باشد.

## تمرین

۱. `Bits` را با یک target کامل ۲۵۶ بیتی (با `math/big`) عوض کنید و retarget را با نسبت دقیق انجام دهید، هنوز با سقف چهار برابر.
۲. یک قاعده اضافه کنید که زمان بلاک بیش از ۲ ساعت جلوتر از ساعت نود نباشد، و برایش تست بنویسید.
۳. شبیه‌سازی retarget را با دوره‌های ۸، ۳۲ و ۱۲۸ بلاکی اجرا کنید و ببینید پراکندگی فاصله‌ی بلاک‌ها چطور عوض می‌شود.
