همه‌ی نودهایی که تا این‌جا ساختیم یک ضعف مشترک داشتند: داخل یک برنامه‌ی دمو زندگی می‌کردند و وقتی برنامه تمام می‌شد، نود همه‌چیز را فراموش می‌کرد. بلاک‌ها، مجموعه‌ی UTXO، mempool، همه در حافظه بودند. نود واقعی یک برنامه‌ی همیشه‌روشن است. متوقف می‌شود و دوباره راه می‌افتد، گاهی crash می‌کند، و هر بار باید با زنجیره‌ی سالمش برگردد.

این مقاله بخش اول مجموعه را با حل همین مشکل می‌بندد. نتیجه یک {{< term "full-node" "نود کامل" >}} (full node) کوچک است: برنامه‌ای که کل زنجیره را خودش نگه می‌دارد، هر بلاک را خودش چک می‌کند، و به هیچ‌کس اعتماد نمی‌کند. یک باینری جدا به اسم `toynode` است که بلاک‌هایش را روی دیسک نگه می‌دارد، از طریق یک API به سؤال‌ها جواب می‌دهد، و یک کیف‌پول خط فرمان جدا هم کنارش هست.

کد Go از [Mempool، کارمزد و انتخاب تراکنش](/fa/posts/bc-mempool-fees/) ادامه پیدا می‌کند؛ [مفسر Script](/fa/posts/bc-bitcoin-script-rust/) در مقاله‌ی قبل یک گریز کوتاه به Rust بود و بخشی از این نود نیست. تکه‌های تازه از مقاله‌های قبلی بیرون از این مجموعه می‌آیند: [ساخت ابزار خط فرمان با Go](/fa/posts/go-cli-tool/)، [ساخت API با net/http در Go](/fa/posts/go-http-api-stdlib/) و [خاموشی تمیز Workerها در Go](/fa/posts/go-graceful-shutdown-workers/).

> همه‌ی مثال‌ها را با Go 1.27 روی macOS (arm64) اجرا کرده‌ام و خروجی‌ها همان چیزی است که دیدم. کد یک مثال محلی است و فقط از loopback استفاده می‌کند. کلیدها از کلمه‌هایی مثل "miner" ساخته شده‌اند، پس عمومی‌اند و فقط به درد دمو می‌خورند. مسیرهای موقت به شکل `<tmp>` نوشته شده‌اند.

## هر نود یک پروسه

تا این‌جا همه‌ی نودها در یک پروسه بودند و با فراخوانی تابع‌های Go و socketهای loopback با هم حرف می‌زدند. حالا هر نود یک پروسه‌ی جدای سیستم‌عامل است که از خط فرمان و با چند flag راه می‌افتد:

```
$ toynode -h
Usage of <tmp>/bin/toynode:
  -data string
    	directory for blocks.dat (required)
  -interval duration
    	time between mined blocks (default 2s)
  -listen string
    	P2P address (default "127.0.0.1:19001")
  -mine
    	mine blocks
  -miner string
    	demo key name that receives block rewards (default "miner")
  -name string
    	name used in logs and the handshake (default "node")
  -peers string
    	comma-separated P2P addresses to keep connected to
  -rpc string
    	JSON-RPC address (loopback only) (default "127.0.0.1:18001")
```

- `-data` پوشه‌ای است که نود بلاک‌هایش را در آن نگه می‌دارد. اجباری است، چون نود بدون دیسک دقیقاً همان چیزی است که می‌خواهیم از شرش خلاص شویم.
- `-listen` آدرس اتصال‌های P2P با نودهای دیگر است، و `-rpc` آدرس API، که بعداً می‌آید.
- `-peers` فهرست نودهایی است که این نود باید به آن‌ها وصل بماند.
- `-mine` ماین کردن را روشن می‌کند؛ `-interval` تعیین می‌کند هر چند وقت یک بلاک ماین شود، و `-miner` پاداش به کلید دموی چه کسی برسد.

یک تکه‌ی کوچک ولی مهم: یک goroutine هر ثانیه همه‌ی آدرس‌های `-peers` را مرور می‌کند و به هر کدام که وصل نیست دوباره وصل می‌شود. پس اگر یک peer ری‌استارت شود، اتصال خودبه‌خود برمی‌گردد، بدون اینکه کسی کاری بکند.

## بلاک روی دیسک

بلاک‌ها را چطور روی دیسک نگه داریم؟ با ساده‌ترین راه ممکن: یک فایل، `blocks.dat`، که فقط به تهش اضافه می‌کنیم. هر رکورد همان framingی است که در شبکه داشتیم: یک طول ۴ بایتی، بعد بلاک به شکل JSON. بعد از هر نوشتن، نود `fsync` را صدا می‌زند، که به سیستم‌عامل می‌گوید داده را واقعاً روی دیسک بنویسد، نه اینکه فقط در حافظه‌ی خودش نگه دارد. فقط بعد از آن نود بلاک را ذخیره‌شده حساب می‌کند.

هر بلاکی که نود به درختش اضافه می‌کند نوشته می‌شود، شاخه‌های فرعی هم. چون بلاک فقط بعد از والدش می‌تواند وارد درخت شود، در فایل هم والد همیشه قبل از فرزند می‌آید.

وقتی نود راه می‌افتد، دو اتفاق می‌افتد:

1. **رکورد نیمه‌کاره بریده می‌شود.** اگر نود وسط نوشتن یک بلاک crash کرده باشد، آخرین رکورد فایل ناقص است. `store.Open` همه‌ی رکوردهای کامل را می‌خواند، و اگر آخری ناقص باشد، فایل را تا ته آخرین رکورد کامل کوتاه می‌کند.
2. **همه‌چیز دوباره چک می‌شود.** هر بلاکی که از دیسک خوانده می‌شود از همان `AddBlock` رد می‌شود که بلاک‌های شبکه رد می‌شوند: header و proof of work برای همه‌ی بلاک‌ها، تراکنش و امضا برای زنجیره‌ی فعال، و انتخاب شاخه با chainwork.

```go
for _, b := range blocks {
	if b.Header.Height == 0 {
		continue // genesis is built in
	}
	if _, err := n.chain.AddBlock(b); err != nil {
		return err
	}
}
```

بلاک genesis در خود کد ساخته شده، پس از آن می‌گذریم. بقیه همه دوباره از `AddBlock` رد می‌شوند.

چرا چیزی را که خودمان نوشته‌ایم دوباره چک کنیم؟ چون دیسک هم یک ورودی است. ممکن است فایل خراب شده باشد، یک باگ چیز غلطی نوشته باشد، یا کسی دستی ویرایشش کرده باشد. اعتبارسنجی دوباره برای یک زنجیره‌ی بزرگ کند است، ولی نود به هیچ چیزی که خودش چک نکرده اعتماد نمی‌کند. یک تست ۵ بایت از ته فایل می‌بُرد، انگار وسط نوشتن crash شده، و چک می‌کند که بلاک‌های قبلی هنوز بار می‌شوند و نوشتن می‌تواند بعد از آن‌ها ادامه پیدا کند.

mempool ذخیره نمی‌شود؛ بعد از ری‌استارت خالی است. تا جایی که می‌دانم، Bitcoin Core موقع خاموش شدن mempoolش را روی دیسک می‌نویسد و موقع شروع دوباره می‌خواندش.

## یک API از نوع JSON-RPC روی loopback

یک نود به‌تنهایی به درد زیادی نمی‌خورد؛ برنامه‌های دیگر باید بتوانند از آن سؤال کنند. برای این کار یک API از نوع {{< term "json-rpc" "JSON-RPC" >}} 2.0 روی HTTP دارد. JSON-RPC یک قرارداد ساده است: هر درخواست یک شیء JSON با اسم یک متد و پارامترهایش است، و هر جواب یک شیء JSON با `result` یا `error`. متدها این‌ها هستند:

- `getblockcount`: ارتفاع آخرین بلاک.
- `getblock`: بلاکی در یک ارتفاع مشخص.
- `getbalance` و `listunspent`: موجودی و خروجی‌های خرج‌نشده‌ی یک آدرس.
- `sendtx`: دادن یک تراکنش امضاشده به نود.
- `getmempoolinfo`: وضعیت mempool.

این API احراز هویت ندارد. هر کس به آن دسترسی داشته باشد می‌تواند، مثلاً، برای نود تراکنش بفرستد. برای همین نود قبول نمی‌کند روی هیچ آدرسی جز loopback گوش بدهد:

```
$ toynode -data <tmp>/x -rpc 0.0.0.0:18109
rpc address 0.0.0.0:18109 is not a loopback IP
```

تا جایی که می‌دانم، bitcoind از RPCش با یک فایل cookie یا با اعتبارنامه‌ای که در تنظیماتش تعریف شده محافظت می‌کند.

کلید خصوصی در نود نیست؛ در برنامه‌ی جدایی به اسم `toywallet` است. دستور `send` آن این کارها را می‌کند:

1. خروجی‌های تأییدشده‌ی فرستنده را از نود می‌پرسد (`listunspent`).
2. آن‌ها را از بزرگ‌ترین به پایین برمی‌دارد، تا مبلغ به‌علاوه‌ی کارمزد پوشش داده شود.
3. هر چه اضافه بماند، به شکل یک خروجی تازه به خود فرستنده برمی‌گردد، که به آن **باقی‌مانده** (change) می‌گویند.
4. تراکنش را امضا می‌کند و با `sendtx` به نود می‌دهد.

نود فقط تراکنش امضاشده را می‌بیند. هیچ‌وقت کلید خصوصی را نمی‌بیند.

## سه نود و یک ری‌استارت

`demo.sh` همه‌ی این‌ها را کنار هم می‌گذارد. سه پروسه روی loopback راه می‌اندازد:

- **n1** هر ۲ ثانیه یک بلاک ماین می‌کند.
- **n2** به n1 وصل می‌شود.
- **n3** به هر دو وصل می‌شود.

بعد ماینر بیست سکه به Bob می‌دهد، n2 با `SIGTERM` (سیگنال عادی «لطفاً خاموش شو») متوقف می‌شود، شبکه مدتی بدون آن جلو می‌رود، و بعد n2 دوباره راه می‌افتد. hash بلاک‌ها، زمان‌ها و ارتفاع‌های دقیق به زمان‌بندی بستگی دارند، پس در هر اجرا فرق می‌کنند:

```
== heights
{"jsonrpc":"2.0","id":1,"result":3}
{"jsonrpc":"2.0","id":1,"result":3}
{"jsonrpc":"2.0","id":1,"result":3}
== wallet
miner 0xb7885750: 150
sent a1ee6a59dee4: 1 inputs, 20 to 0xd94f176c, fee 1, 233 bytes
bob 0xd94f176c: 20
bob 0xd94f176c: 20
{"jsonrpc":"2.0","id":2,"result":{"height":4,"hash":"0000359c9480ba929389cca89523c1967ec04f8a1ac2e78190ad31f398cefd25","prev":"0003f6b32dc59ccac63d9416036d5b5de9c241b3d48b71f8b1f6cb946ea2ef07","time":1793564462,"bits":12,"txids":["3f4cb1ba34d5822b628abfb47aad11a6b376e22600327143c0d1b1ed43d2b2bf","a1ee6a59dee410ccacc13ce9482db04bf2d46a2276b85fd227564a89e95df997"]}}
== stop n2 (SIGTERM)
== heights while n2 is down
{"jsonrpc":"2.0","id":1,"result":7}
{"jsonrpc":"2.0","id":1,"result":7}
== restart n2
== heights
{"jsonrpc":"2.0","id":1,"result":9}
{"jsonrpc":"2.0","id":1,"result":9}
{"jsonrpc":"2.0","id":1,"result":9}
bob 0xd94f176c: 20
```

- **`== heights`:** بعد از ۷ ثانیه هر سه نود در ارتفاع ۳ هستند. هر خط جواب خام JSON-RPC به `getblockcount` است.
- **`== wallet`:** کیف‌پول موجودی ماینر را از n2 می‌پرسد: ۱۵۰، یعنی پاداش ۳ بلاک. بعد پرداخت را از طریق **n3** می‌فرستد: یک ورودی، ۲۰ سکه به Bob، کارمزد ۱، ۲۳۳ بایت. سه ثانیه بعد هم n1 و هم n2 می‌گویند Bob بیست سکه دارد. پرداخت وارد n3 شد، gossip آن را به n1 رساند، n1 آن را در یک بلاک گذاشت، و بلاک به n2 رسید.
- **خط `getblock`:** بلاک ۴، از دید n2. دو شناسه‌ی تراکنش دارد: coinbase، و پرداخت ماینر به Bob، که شناسه‌اش با `a1ee6a59dee4` شروع می‌شود، همانی که در خط کیف‌پول بود.
- **`== heights while n2 is down`:** n2 متوقف شده و فقط n1 و n3 جواب می‌دهند. زنجیره تا ارتفاع ۷ جلو رفته است.
- **بعد از ری‌استارت:** هر سه دوباره در یک ارتفاع‌اند، و n2 هنوز می‌داند که Bob بیست سکه دارد.

بخش جالب‌تر لاگ خود n2 است، اطراف توقف و ری‌استارت:

```
[n2] block 4 0000359c9480 from n1: extended, 2 txs, relayed to 1
[n2] signal received, shutting down
[n2] block 5 000a8de373da from n1: extended, 1 txs, relayed to 1
[n2] stopped at height 5
[n2] loaded 5 blocks from disk, re-validated, tip 5 000a8de373da
[n2] p2p 127.0.0.1:19102, rpc 127.0.0.1:18102, mining false
[n2] connected to n1 (its height 7 work 32768, mine 5 work 24576)
[n2] block 6 00015ccd8617 from n1: extended, 1 txs, relayed to 0
[n2] block 7 00087e9fdc04 from n1: extended, 1 txs, relayed to 0
```

- **`signal received, shutting down`:** n2 سیگنال `SIGTERM` را گرفت.
- **`block 5 ... extended`:** بلاک ۵ **بعد از** سیگنال رسید، و باز اضافه و ذخیره شد. این باگ نیست؛ شکل یک خاموشی مرتب همین است، که پایین‌تر توضیحش می‌دهم.
- **`stopped at height 5`:** n2 تمیز بیرون رفت، با بلاک ۵ روی دیسک.
- **`loaded 5 blocks from disk, re-validated`:** موقع ری‌استارت، n2 پنج بلاکش را از فایل خواند و تک‌تکشان را دوباره چک کرد.
- **`connected to n1 (its height 7 ..., mine 5 ...)`:** در handshake، n1 می‌گوید کار بیشتری دارد، پس n2 block locator خودش را می‌فرستد، مثل مقاله‌ی reorg.
- **بلاک‌های ۶ و ۷:** n2 چیزی را که در مدت خاموشی از دست داده بود می‌گیرد و دوباره هماهنگ می‌شود.

چرا بلاک ۵ هنوز توانست وارد شود؟ چون یک {{< term "graceful-shutdown" "خاموشی تمیز" >}} با یک ترتیب حساب‌شده پیش می‌رود:

1. سرور HTTP را متوقف کن. درخواست‌هایی که در جریان‌اند اجازه دارند تمام شوند.
2. ماینر و dialer را متوقف کن و منتظرشان بمان، تا دیگر بلاک تازه‌ای از طرف ما ساخته نشود.
3. نود را ببند: peerها را قطع کن و منتظر بمان goroutineهایشان تمام شوند.
4. فقط در آخر، فایل را sync کن و ببند.

بین سیگنال و قدم ۳، نود هنوز به peerهایش وصل است، پس بلاک ۵ توانست برسد و ذخیره شود. قاعده‌ی پشت این ترتیب این است: اول ورودی‌ها را ببند، و انبار را آخر از همه. اگر ترتیب برعکس بود، ممکن بود بلاکی بعد از بسته شدن فایل برسد و گم شود.

خود ری‌استارت یک {{< term "initial-block-download" "initial block download" >}} کوچک است، یعنی فرایندی که نودی که عقب افتاده، یا تازه راه افتاده، زنجیره را از peerهایش می‌گیرد و چک می‌کند. این‌جا فقط دو بلاک بود، ولی سازوکار همان است.

## چیزهایی که نود واقعی دارد و این ندارد

این فهرست کامل نیست، ولی نشان می‌دهد نود واقعی چقدر با این فاصله دارد:

- **همگام‌سازی سریع‌تر.** یک نود واقعی بیت‌کوین اول headerها را همگام می‌کند و بعد بدنه‌ی بلاک‌ها را هم‌زمان از چند peer می‌گیرد. نود من کل بلاک‌ها را از یک peer می‌گیرد.
- **دفاع در برابر {{< term "denial-of-service" "denial of service" >}}:** سقف تعداد اتصال‌ها، قطع کردن peerهایی که بدرفتاری می‌کنند، و حافظه‌ی محدود برای هر peer.
- **Script.** خروجی‌های این‌جا هنوز فقط یک آدرس را نام می‌برند؛ مفسر مقاله‌ی Script به این نود وصل نشده است.
- **پخش فشرده‌ی بلاک** (compact block relay، BIP-152)، تا بلاک تازه بتواند با استفاده از تراکنش‌هایی فرستاده شود که peer از قبل در mempoolش دارد، به‌جای اینکه همه دوباره فرستاده شوند.
- **قاعده‌های consensus بیشتر:** بلوغ coinbase، قاعده‌ی median-time-past، و محدودیت زمان‌های آینده.
- **یک پایگاه داده‌ی واقعی** برای مجموعه‌ی UTXO، هرس کردن (pruning) بلاک‌های قدیمی، peer discovery، و تخمین کارمزد.

## درس‌های عملیاتی

- **چیزی را که بار می‌کنید دوباره چک کنید.** دیسک هم مثل شبکه یک ورودی است. نودی که به فایل خودش اعتماد کند، به هر کسی، یا هر باگی، که آن را نوشته اعتماد کرده است.
- **قبل از اینکه بگویید بلاک ذخیره شد `fsync` کنید، و رکوردهای نیمه‌کاره را موقع شروع ببرید.** تا `fsync` برنگشته، ممکن است داده فقط در حافظه‌ی سیستم‌عامل باشد و با قطع برق از دست برود. crash وسط نوشتن نصف یک رکورد را جا می‌گذارد، و نود باید تشخیصش دهد و حذفش کند.
- **API بدون احراز هویت جایش روی loopback است.** حتی در یک شبکه‌ی خانگی، یک پورت RPC باز یعنی هر کسی در آن شبکه می‌تواند به نودتان دستور بدهد.
- **به ترتیب خاموش کنید: اول ورودی‌ها، آخر انبار.** برای همین بلاک ۵ در دمو گم نشد.

## تمرین

۱. mempool را موقع خاموش شدن ذخیره کنید و موقع شروع دوباره اضافه‌اش کنید.
۲. یک فایل `-rpccookie` با یک توکن تصادفی اضافه کنید، و آن توکن را در هر فراخوانی چک کنید.
۳. ماینر را در یک حلقه با `SIGKILL` بکشید، و چک کنید که هر ری‌استارت یک زنجیره‌ی معتبر بار می‌کند.

## قدم بعدی

بخش دوم مجموعه یک لایه زیر Solidity می‌رود و با «EVM از درون: stack، memory، storage و gas با یک مفسر کوچک Rust» شروع می‌شود. بعد از زنجیره‌ای که فقط سکه جابه‌جا می‌کند، سراغ زنجیره‌ای می‌رویم که برنامه اجرا می‌کند.
