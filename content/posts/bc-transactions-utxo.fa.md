کیف پولتان را باز کنید. یک اسکناس پنجاه‌هزارتومانی دارید و می‌خواهید سی هزار تومان بدهید. اسکناس را از وسط پاره نمی‌کنید؛ کل اسکناس را می‌دهید و بیست هزار تومان پس می‌گیرید. حالا یک سؤال: «موجودی» شما کجا نوشته شده است؟ هیچ‌جا. موجودی شما فقط جمع اسکناس‌هایی است که الان در کیفتان دارید.

بیت‌کوین دقیقاً همین‌طور کار می‌کند، و این مقاله درباره‌ی همین مدل است. بلاک‌هایی که در [Merkle tree و اثبات عضویت](/fa/posts/bc-merkle-trees-proofs/) ساختیم هنوز رشته‌های ساده‌ای مثل `"alice -> bob: 10"` دارند که هر کسی می‌تواند بنویسد. در [مقاله‌ی قبل](/fa/posts/bc-keys-ecdsa-addresses/) پکیج `wallet` را ساختیم که یک hash سی‌ودوبایتی را امضا می‌کند. حالا وقتش است این دو را کنار هم بگذاریم و آن رشته‌ها را با تراکنش واقعی عوض کنیم. می‌خواهیم به سه سؤال جواب بدهیم: هر سکه مال کیست، چه کسی اجازه‌ی خرجش را دارد، و یک نود قبل از قبول کردن تراکنش چه چیزهایی را چک می‌کند.

اسم این مدل {{< term "utxo" "UTXO" >}} است، کوتاه‌شده‌ی Unspent Transaction Output، یعنی «خروجی خرج‌نشده‌ی تراکنش». معنی‌اش چند بخش پایین‌تر روشن می‌شود. یک نکته هم درباره‌ی اسم: «تراکنش» در دیتابیس، که در [تراکنش و ACID](/fa/posts/db-transactions-acid/) دیدیم، چیز کاملاً دیگری است و فقط اسمشان یکی است.

کد این مقاله ادامه‌ی همان ماژول `toychain` مقاله‌ی Merkle است. یک نسخه از آن برداشتم و پکیج `wallet` را هم داخلش، در پوشه‌ی `wallet/`، کپی کردم تا همه یک ماژول باشد. یک تابع کمکی هم به `wallet` اضافه کردم: `AddressBytes`، که آدرس را به شکل خام ۲۰ بایتی برمی‌گرداند.

> همه‌ی مثال‌ها را با Go 1.27 روی macOS (arm64) اجرا کرده‌ام و خروجی‌ها همان چیزی است که دیدم. کد یک مثال محلی است. کلیدها از روی کلمه‌هایی مثل "alice" ساخته شده‌اند، پس عمومی‌اند؛ هرگز پولی نگرفته‌اند و فقط برای این دمو هستند.

## اسکناس به‌جای موجودی

در مدل UTXO هیچ جدولی به اسم «موجودی حساب‌ها» وجود ندارد. چیزی که وجود دارد **خروجی** است. هر خروجی مثل یک اسکناس است: یک مبلغ و یک صاحب. مثلاً «۵۰ سکه، متعلق به این آدرس».

یک تراکنش دو کار می‌کند:

- چند خروجی قبلی را **خرج می‌کند**. به این‌ها **ورودی**‌های تراکنش می‌گوییم. هر ورودی می‌گوید «آن خروجی شماره‌ی فلان از آن تراکنش قبلی را خرج می‌کنم».
- چند خروجی **تازه** می‌سازد که مال صاحبان جدید است.

یک خروجی تا وقتی خرج نشده، «خرج‌نشده» است؛ همان UTXO. وقتی خرج شد، از بازی بیرون می‌رود و دیگر هیچ‌وقت نمی‌شود دوباره خرجش کرد. موجودی alice هم یعنی جمع همه‌ی خروجی‌های خرج‌نشده‌ای که صاحبشان alice است.

در Go این‌طور شکل می‌گیرد:

```go
type OutPoint struct {
	TxID  Hash
	Index uint32
}

type TxIn struct {
	Prev   OutPoint
	PubKey []byte // must hash to the owner of Prev
	Sig    []byte // 64 bytes, r || s
}

type TxOut struct {
	Value uint64
	Owner Address // 20 bytes
}

type Tx struct {
	Inputs  []TxIn
	Outputs []TxOut
}
```

از پایین بخوانیم:

- `TxOut` همان اسکناس است: مبلغ (`Value`) و آدرس ۲۰ بایتی صاحب (`Owner`).
- `OutPoint` نشانی یک خروجی است: شناسه‌ی تراکنشی که آن را ساخته (`TxID`) و شماره‌اش در لیست خروجی‌های آن تراکنش (`Index`).
- `TxIn` یک ورودی است. `Prev` می‌گوید کدام خروجی را خرج می‌کند. `PubKey` کلید عمومی کسی است که خرج می‌کند، و hash آن باید همان آدرس صاحب خروجی باشد. `Sig` امضای او است. از مقاله‌ی قبل یادمان هست که از روی آدرس نمی‌شود کلید عمومی را به دست آورد، برای همین کلید عمومی همراه خود ورودی می‌آید.

مثل اسکناس، یک خروجی همیشه **کامل** خرج می‌شود. فرض کنید alice یک خروجی ۵۰ سکه‌ای دارد و می‌خواهد ۳۰ سکه به bob بدهد. تراکنشش یک ورودی دارد (همان ۵۰ سکه) و دو خروجی: ۳۰ سکه برای bob و ۱۵ سکه برای خودش. به این خروجی دوم **باقی‌مانده** یا change می‌گویند، همان بقیه‌ی پولی که از فروشنده پس می‌گیرید.

ولی ۳۰ و ۱۵ می‌شود ۴۵، نه ۵۰. آن ۵ سکه کجا رفت؟ آن **کارمزد** است و به کسی می‌رسد که بلاک را می‌سازد. نکته‌ی جالب این است که کارمزد هیچ‌جا در تراکنش نوشته نشده. فقط از تفاوت حساب می‌شود:

```
fee = sum(inputs) - sum(outputs)
```

این نکته بعداً، وقتی می‌خواهیم دستکاری را بگیریم، مهم می‌شود.

## چه چیزی امضا می‌شود، و شناسه‌ی تراکنش چیست

برای امضا کردن و برای ساختن شناسه، اول باید تراکنش را به بایت تبدیل کنیم. همان‌طور که در [هش، بلاک و زنجیره](/fa/posts/bc-hashes-blocks-chain/) دیدیم، این تبدیل باید یکتا باشد، یعنی یک تراکنش همیشه دقیقاً همان بایت‌ها را بدهد. روشش هم همان است: اول تعداد ورودی‌ها، بعد هر ورودی با فیلدهایش به ترتیب ثابت، بعد تعداد خروجی‌ها و خود خروجی‌ها. کلید عمومی و امضا طول ثابت ندارند، پس قبل از هر کدام طولش را می‌نویسیم تا معلوم باشد کجا تمام می‌شود.

از این بایت‌ها دو hash متفاوت درمی‌آید:

```go
func (tx Tx) ID() Hash { return Sum(tx.Encode()) }

func (tx Tx) SigHash() Hash {
	return Sum(append([]byte{0x02}, tx.encode(false)...))
}
```

- **`ID`** یا **txid** شناسه‌ی تراکنش است، و از روی **همه‌ی** بایت‌ها ساخته می‌شود، امضاها هم جزوش‌اند. ورودی‌های تراکنش‌های بعدی با همین شناسه به خروجی‌های این تراکنش اشاره می‌کنند.
- **`SigHash`** چیزی است که امضا می‌شود. به آن {{< term "sighash" "sighash" >}} می‌گویند. همه‌ی ورودی‌ها و خروجی‌ها را پوشش می‌دهد، ولی جای امضاها را خالی می‌نویسد (`encode(false)`). دلیلش ساده است: امضا نمی‌تواند خودش را امضا کند، چون تا امضا را نسازید نمی‌دانید چه بایت‌هایی است.

یک جزئیات ظریف این‌جا هست. txid امضاها را هم پوشش می‌دهد. در مقاله‌ی قبل دیدیم که هر امضای ECDSA یک شکل دوم معتبر هم دارد. اگر آن شکل دوم قبول می‌شد، هر کسی می‌توانست امضا را عوض کند و txid را تغییر دهد، بدون اینکه چیز دیگری در تراکنش عوض شود. این همان {{< term "signature-malleability" "malleability" >}} است. این طراحی فقط به این دلیل امن است که `wallet.Verify` امضای با `s` بزرگ را رد می‌کند.

پیشوند `0x02` هم همان domain separation مقاله‌ی Merkle است: برگ‌های درخت با `0x00` شروع می‌شوند، گره‌های میانی با `0x01`، و sighash با `0x02`. این‌طوری هیچ‌کدام از این سه نوع hash با دیگری قاطی نمی‌شود.

## سکه‌ی تازه از کجا می‌آید

تا این‌جا هر تراکنش فقط سکه‌های قبلی را جابه‌جا می‌کند. ولی اولین سکه‌ها از کجا آمده‌اند؟ جوابش {{< term "coinbase-transaction" "تراکنش coinbase" >}} است. این تراکنش ویژه همیشه اولین تراکنش هر بلاک است و سکه‌ی تازه می‌سازد. سازنده‌ی بلاک آن را به خودش پرداخت می‌کند؛ این پاداش ساختن بلاک است.

coinbase خروجی قبلی‌ای برای خرج کردن ندارد. در طراحی ما یک ورودی ساختگی دارد: `TxID` تمام صفر، و ارتفاع بلاک به‌جای `Index`. چرا ارتفاع؟ چون اگر دو بلاک coinbaseای با مبلغ یکسان به یک آدرس داشته باشند، بدون این عدد بایت‌هایشان یکی می‌شد و شناسه‌ی یکسان می‌گرفتند. با ارتفاع، هر coinbase شناسه‌ی خودش را دارد.

coinbase هم سقف دارد: حداکثر می‌تواند `BlockReward` (در این‌جا ۵۰ سکه) به‌علاوه‌ی جمع کارمزدهای تراکنش‌های همان بلاک را بپردازد.

## مجموعه‌ی UTXO و چک کردن بلاک

حالا کل وضعیت دفتر چیست؟ فقط یک map از همه‌ی خروجی‌های خرج‌نشده:

```go
type UTXOSet map[OutPoint]TxOut
```

کلید map نشانی خروجی است و مقدارش خود خروجی. موجودی هر آدرس جمع مقدار خروجی‌هایی است که صاحبشان آن آدرس است.

وقتی بلاک تازه‌ای می‌رسد، `ApplyBlock` آن را چک می‌کند. برای هر تراکنش غیر coinbase، به این ترتیب می‌پرسد:

1. آیا هر ورودی به خروجی‌ای اشاره می‌کند که در مجموعه هست؟ اگر نه، یا وجود ندارد یا قبلاً خرج شده.
2. آیا این خروجی قبلاً در **همین بلاک** خرج نشده است؟
3. آیا hash کلید عمومی ورودی همان صاحب خروجی است؟
4. آیا {{< term "digital-signature" "امضا" >}} روی sighash با این کلید درست است؟
5. آیا جمع ورودی‌ها حداقل به اندازه‌ی جمع خروجی‌هاست؟ (و هیچ جمعی از سقف `uint64` رد نمی‌شود.)

اگر همه درست بود، خروجی‌های خرج‌شده را از مجموعه حذف و خروجی‌های تازه را اضافه می‌کند. یک نکته‌ی مهم: `ApplyBlock` همه‌ی این کارها را روی یک **کپی** از مجموعه انجام می‌دهد. اگر وسط کار حتی یک تراکنش خطا داشت، کپی دور ریخته می‌شود و مجموعه‌ی اصلی دست‌نخورده می‌ماند. یعنی یا کل بلاک قبول می‌شود، یا هیچ‌چیزش.

## یک پرداخت با باقی‌مانده

حالا همان مثال اسکناس را اجرا کنیم. `go run ./cmd/toychain pay` یک زنجیره می‌سازد که coinbase بلاک genesis پنجاه سکه به alice می‌دهد. بعد alice سی سکه به bob می‌دهد و پانزده سکه باقی‌مانده برای خودش برمی‌دارد. سازنده‌ی بلاک بعدی را `miner` صدا می‌زنیم:

```
after genesis:
  197a84d5374b:0   50  alice
tx ef4d0ece5dfd: 233 bytes, sighash 74a059145008, fee 5, err <nil>
block 1: 2 txs, err <nil>
after block 1:
  569759b941f7:0   55  miner
  ef4d0ece5dfd:0   30  bob
  ef4d0ece5dfd:1   15  alice
balances: alice 15, bob 30, miner 55
validate: <nil>
```

هر ردیف مجموعه‌ی UTXO به شکل `txid:index  مبلغ  صاحب` است. خط به خط:

- **`after genesis`:** فقط یک خروجی وجود دارد: خروجی شماره‌ی ۰ از coinbase بلاک genesis، پنجاه سکه، مال alice.
- **خط `tx`:** تراکنش alice. ۲۳۳ بایت است: ۴ بایت تعداد ورودی‌ها، ۱۶۹ بایت برای تنها ورودی (۳۲ بایت txid، ۴ بایت index، و کلید عمومی ۶۵ بایتی و امضای ۶۴ بایتی که هر کدام ۲ بایت طول هم جلویشان دارند)، ۴ بایت تعداد خروجی‌ها، و دو خروجی ۲۸ بایتی (۸ بایت مبلغ و ۲۰ بایت آدرس). کارمزد `5` است و `err <nil>` یعنی تراکنش معتبر است.
- **`block 1: 2 txs`:** بلاک ۱ دو تراکنش دارد: coinbase سازنده‌ی بلاک و تراکنش alice.
- **`after block 1`:** خروجی پنجاه‌سکه‌ای genesis دیگر نیست؛ خرج شده است. به‌جایش سه خروجی تازه داریم. ۳۰ سکه‌ی bob و ۱۵ سکه‌ی alice هر دو با txid تراکنش alice (`ef4d…`) شروع می‌شوند و شماره‌هایشان ۰ و ۱ است. miner هم ۵۵ سکه گرفته: ۵۰ پاداش بلاک به‌علاوه‌ی ۵ کارمزد.
- **`balances`:** موجودی‌ها فقط جمع همین خروجی‌هاست.
- **`validate: <nil>`:** کل زنجیره از اول دوباره چک شد و مشکلی نداشت.

## Double spend: یک سکه، دو بار

حالا اولین حمله. مشکل اصلی هر پول دیجیتال این است که داده را می‌شود کپی کرد. چه چیزی جلوی alice را می‌گیرد که یک سکه را دو بار، به دو نفر، خرج کند؟ به این کار {{< term "double-spend" "double spend" >}} یا «دو بار خرج کردن» می‌گویند.

`go run ./cmd/toychain double` دو تراکنش می‌سازد که هر دو همان ۵۰ سکه‌ی alice را خرج می‌کنند: یکی همه را به bob می‌دهد، یکی همه را به miner. هر دو امضای درست alice را دارند. بعد آن‌ها را به چند شکل به زنجیره می‌دهد:

```
both valid alone: <nil> <nil>
same block: block 1: tx 2: input 0: output spent twice in one block
block 1 with one of them: <nil>
the other in block 2: block 2: tx 1: input 0: input is unknown or already spent
replay toBob in block 2: block 2: tx 1: input 0: input is unknown or already spent
chain length: 2
```

- **خط اول:** هر تراکنش به‌تنهایی کاملاً معتبر است. هیچ‌کدام امضای جعلی یا مبلغ اشتباه ندارد.
- **`same block`:** وقتی هر دو در یک بلاک باشند، تراکنش دوم (`tx 2`؛ تراکنش ۰ همان coinbase است) رد می‌شود، چون همان خروجی در همان بلاک قبلاً خرج شده. کل بلاک رد می‌شود.
- **`block 1 with one of them`:** بلاک ۱ فقط با پرداخت به bob قبول می‌شود.
- **`the other in block 2`:** حالا پرداخت به miner در بلاک ۲ رد می‌شود، چون خروجی دیگر در مجموعه‌ی UTXO نیست.
- **`replay toBob`:** حتی فرستادن دوباره‌ی **همان** تراکنش تأییدشده هم رد می‌شود، به همان دلیل. خروجی‌ای که یک بار خرج شد، برای همیشه رفته است.
- **`chain length: 2`:** زنجیره فقط genesis و بلاک ۱ را دارد.

پس مدل UTXO دو بار خرج کردن را خودبه‌خود می‌گیرد. ولی یک سؤال باز می‌ماند: اگر دو نود هم‌زمان دو تراکنش متضاد ببینند، کدام برنده می‌شود؟ این دیگر کار اعتبارسنجی نیست، کار consensus است، که در مقاله‌های بعدی می‌آید.

## امضای جعلی

حمله‌ی بعدی: mallory می‌خواهد سکه‌ی alice را خرج کند. `go run ./cmd/toychain forge` چهار تلاش او را امتحان می‌کند:

```
alice's key, mallory's signature: input 0: bad signature
mallory's key on alice's coin:   input 0: public key does not match the output owner
output rewritten after signing:  input 0: bad signature
change lowered after signing:    input 0: bad signature
```

- **تلاش اول:** mallory کلید عمومی alice را در ورودی می‌گذارد تا چک صاحب خروجی رد نشود، ولی با کلید خودش امضا می‌کند. امضا با کلید alice نمی‌خواند.
- **تلاش دوم:** mallory کلید عمومی خودش را می‌گذارد و درست امضا می‌کند. امضا سالم است، ولی hash کلید او آدرس صاحب سکه نیست.
- **تلاش سوم:** alice یک پرداخت درست ۱۰ سکه‌ای به bob امضا می‌کند، و کسی در راه آدرس bob را با آدرس mallory عوض می‌کند. چون خروجی‌ها جزو sighash هستند، sighash عوض می‌شود و امضای alice دیگر برایش معتبر نیست.
- **تلاش چهارم:** این بار کسی آدرس‌ها را دست نمی‌زند، فقط باقی‌مانده‌ی alice را از ۴۰ به ۱ کم می‌کند.

خط آخر از همه جالب‌تر است. یادتان هست کارمزد هیچ‌جا نوشته نشده و فقط از تفاوت ورودی و خروجی حساب می‌شود؟ پس کم کردن باقی‌مانده، کارمزد را از صفر به ۳۹ سکه می‌رساند، و این پول به سازنده‌ی بلاک می‌رسد. اگر کارمزد یک فیلد جدا بود که امضا نمی‌شد، این حمله ممکن بود. ولی چون همه‌ی خروجی‌ها امضا شده‌اند، تغییر باقی‌مانده هم امضا را خراب می‌کند و گیر می‌افتد.

## خرج بیش از موجودی و کارمزد

آخرین دسته، مبلغ‌ها را چک می‌کند. `go run ./cmd/toychain overspend`:

```
50 in, 60 out: outputs exceed inputs: in 50, out 60
50 in, 50 out: fee 0, err <nil>
50 in, 1 out:  fee 49, err <nil> (forgot the change)
coinbase takes 51 with 0 fees: block 1: tx 0: coinbase pays more than reward + fees or has the wrong height
```

- **خط اول:** با ۵۰ سکه ورودی نمی‌شود ۶۰ سکه خروجی ساخت. رد می‌شود.
- **خط دوم:** ورودی و خروجی برابرند، کارمزد صفر است، و تراکنش معتبر است.
- **خط سوم:** alice می‌خواست یک سکه به bob بدهد و یادش رفت خروجی باقی‌مانده را بسازد. این تراکنش **معتبر** است، و ۴۹ سکه کارمزد به سازنده‌ی بلاک می‌رسد. سیستم نمی‌تواند بفهمد این اشتباه است یا یک کارمزد خیلی سخاوتمندانه.
- **خط آخر:** سازنده‌ی بلاک در coinbase ۵۱ سکه به خودش داده، در حالی که پاداش ۵۰ است و کارمزدی هم نیست. بلاک رد می‌شود.

تست‌ها دو حالت دیگر را هم پوشش می‌دهند: خرج کردن خروجی‌ای که در همان بلاک ساخته شده (که مجاز است)، و دستکاری یک تراکنش تأییدشده. همه پاس شدند:

```
ok  	toychain/chain	0.413s
?   	toychain/cmd/toychain	[no test files]
ok  	toychain/wallet	(cached)
```

یک چیز دیگر هم در این مرحله درست کردم. در مقاله‌ی Merkle دیدیم که header تعداد تراکنش‌ها را ثابت نمی‌کرد و اثبات می‌توانست درباره‌ی تعداد دروغ بگوید. حالا {{< term "block-header" "header" >}} یک فیلد `TxCount` دارد، و `VerifyInclusion` تعداد را از header برمی‌دارد، نه از کسی که اثبات را می‌فرستد.

## دام‌های اعتبارسنجی

- **هر چیزی را که مهم است امضا کنید.** هر چیزی که بیرون از sighash بماند را هر کسی در راه می‌تواند عوض کند، و امضا هنوز معتبر به نظر می‌رسد. تلاش سوم و چهارم mallory فقط به این دلیل شکست خوردند که خروجی‌ها امضا شده بودند.
- **کارمزد را از تفاوت حساب کنید و سرریز را چک کنید.** جمع چند `uint64` بزرگ می‌تواند از سقف رد شود و به یک عدد کوچک برگردد. آن‌وقت تراکنشی که خیلی بیشتر از ورودی‌اش خرج می‌کند ممکن است معتبر به نظر برسد. برای همین کد ما هر جمع را با `bits.Add64` انجام می‌دهد و سرریز را رد می‌کند.
- **کل بلاک را روی یک کپی از وضعیت چک کنید، نه درجا.** اگر تراکنش پنجم یک بلاک خراب باشد و شما چهار تراکنش اول را مستقیم روی وضعیت اصلی اعمال کرده باشید، دفترتان حالا نیمه‌کاره است و با بقیه‌ی نودها نمی‌خواند.
- **بیت‌کوین واقعی پیچیده‌تر است.** تا جایی که می‌دانم، بیت‌کوین خروجی‌ها را با یک script کوچک قفل می‌کند، نه فقط با یک آدرس، و برای هر ورودی یک sighash جداگانه امضا می‌کند. هیچ‌کدام از این‌ها را این‌جا پیاده نکردم.

## تمرین

۱. اجازه دهید coinbase چند خروجی داشته باشد، و تستی بنویسید که نشان دهد جمع آن‌ها هنوز سقف دارد.
۲. یک فیلد `Locktime` اضافه کنید: تراکنش قبل از آن ارتفاع نامعتبر است. مطمئن شوید این فیلد امضا می‌شود؛ وگرنه چه کسی می‌تواند عوضش کند؟
۳. تابع `Select(utxo, owner, amount)` را بنویسید که از خروجی‌های یک نفر به اندازه‌ی کافی انتخاب کند و خروجی باقی‌مانده را بسازد.

## قدم بعدی

مقاله‌ی بعد «مدل حساب، nonce و جلوگیری از replay» است. اتریوم به‌جای اسکناس، برای هر آدرس یک موجودی نگه می‌دارد. آن‌جا دیگر خروجی‌ای نیست که خرج شود و برود، پس برای جلوگیری از فرستادن دوباره‌ی یک تراکنش به روش دیگری نیاز داریم.
