You have a colour-blind friend. You hold two balls, one red and one green, and you want to prove the colours differ without telling him which is which. He puts the balls behind his back, either swaps them or not, shows them again and asks: "Did I swap?" You can see the colours, so you always answer correctly. If the balls were really the same colour, you would be right only half the time. After 20 correct answers he is sure the colours differ, yet he still does not know which ball is red.

This is what a {{< term "zero-knowledge-proof" "zero-knowledge proof" >}} does: it convinces someone that a statement is true without showing why. In [Bridges and cross-chain messaging](/posts/bc-bridges-cross-chain/) one chain had to trust a claim about another chain, and trusting a few signers became the weak point. Mathematical proofs are a way to remove that trust. Two things from earlier posts come back here as well: in [Merkle trees and inclusion proofs](/posts/bc-merkle-trees-proofs/) the proof revealed the leaf, and in [Keys, ECDSA signatures and addresses on secp256k1](/posts/bc-keys-ecdsa-addresses/) a reused nonce leaked a private key.

> Toy code for learning, not production. Every secret is a fresh random scalar and is never printed. Rust 1.90, `k256` 0.13.4 (feature `arithmetic`), `sha2` 0.10.9, `rand_core` 0.6.4, macOS (arm64). The demo is a local Cargo project.

## What a proof promises

A proof runs between two parties: a prover and a verifier. It makes three promises:

- **Completeness**: an honest prover who has the secret always convinces the verifier.
- **Soundness**: a prover without the secret fails, except with negligible probability.
- **Zero-knowledge**: the verifier learns only that the statement is true. Everything it saw, it could have generated by itself without the prover, so it learned nothing new about the secret.

The statement we prove is: "I know `x` such that `X = x·G`", on the secp256k1 curve. This is the relation between a private and a public key: `x` is the private key, `G` is the curve's base point and `X` is the public key. Computing `X` from `x` is easy. Finding `x` from `X` is the {{< term "discrete-logarithm" "discrete logarithm" >}} problem, believed infeasible on this curve.

## The interactive Schnorr protocol

The {{< term "schnorr" "Schnorr protocol" >}} has three messages, like the ball game:

1. The prover picks a random number `r` and sends `R = r·G`. This is the commitment.
2. The verifier sends a random number `c`. This is the challenge.
3. The prover answers `s = r + c·x`.

The verifier checks one thing: `s·G` must equal `R + c·X`. Why? Because `s·G = (r + c·x)·G = r·G + c·(x·G) = R + c·X`.

A small example with hand-made numbers (this is an illustration, not demo output). Instead of the curve, take a simple group in which 4 has order 11 modulo 23. In this group "multiplying by G" is raising to a power, `4^x`. Say our secret is `x = 3`, so `X = 4^3 mod 23 = 18`. Now:

- The prover picks `r = 5` and sends `R = 4^5 mod 23 = 12`.
- The verifier sends the challenge `c = 7`.
- The prover answers `s = (5 + 7·3) mod 11 = 4`. (The group order is 11, so the exponents add modulo 11.)
- The verifier checks: `4^4 mod 23 = 3` and `R · X^7 mod 23 = 12 · 6 mod 23 = 3`. They are equal, so it accepts.

The verifier never saw `x = 3`. The number `r` works like a mask that hides `x` inside `s`. In this role `r` is called a {{< term "nonce" "nonce" >}}: a random number used once.

These are the same three functions in the Rust code on secp256k1:

```rust
fn commit() -> (Scalar, Point) {
    let r = Scalar::random(&mut OsRng);
    (r, G * r)
}
fn respond(x: Scalar, r: Scalar, c: Scalar) -> Scalar {
    r + c * x
}
fn verify(pub_x: Point, big_r: Point, c: Scalar, s: Scalar) -> bool {
    G * s == big_r + pub_x * c
}
```

The program ran an honest prover 1000 times (with a fresh `x` each run). The verifier accepted all 1000 times, so completeness holds:

```
== interactive, honest prover ==
accepted 1000/1000
```

## Soundness: a cheater and an extractor

Now let us see what chance someone without `x` has. A cheater can guess the challenge (`c_guess`), pick any `s`, and build the commitment backwards: `R = s·G - c_guess·X`. If the verifier happens to send exactly `c_guess`, the answer is valid. Otherwise it is rejected. So the success probability is `1/q`, where q is the group order.

On secp256k1 that is about 2^-256, which is nothing. To see something with our own eyes, I also put the small group in the code (4 has order 11 modulo 23). There the probability should be about `1/11`, which is 0.0909:

```
== cheating prover (does not know x) ==
toy group q=11: 8837/100000 = 0.0884 (1/q = 0.0909)
secp256k1:      0/10000
```

Out of 100,000 attempts in the small group the cheater succeeded 8837 times, about 8.8 percent, close to 1/11. On secp256k1 it succeeded 0 times in 10,000. These numbers are random and differ a little on every run. In five other runs the rate was 0.0905, 0.0923, 0.0901, 0.0905 and 0.0914.

Does the cheater have a better strategy? No, and the reason is interesting. Suppose a prover can answer two different challenges for the same `R`. From the two answers you can compute `x`: `x = (s1 - s2) / (c1 - c2)`. So someone who can answer any challenge in practice knows `x`. With the hand example: the same `r = 5` and a second challenge `c = 2` gives `s = 0`, and `x = (4 - 0) / (7 - 2) = 3` (modulo 11). The code does the same on secp256k1:

```
== extractor: same R, two challenges ==
both transcripts valid: true, extracted x == x: true
```

Both transcripts (the record of one run of the protocol) were valid, and the extracted `x` equals the real `x`.

## Zero-knowledge: a simulator

Now the third promise. We want to show that a transcript leaks nothing about `x`. The way is to show that a valid transcript can be made without `x`. Turn the order around: pick `c` and `s` first, then compute `R = s·G - c·X`.

```
== simulator: valid transcript without x ==
simulated (R, c, s) verifies: true
```

This transcript looks like a real one, yet `x` played no part in building it. So if the verifier sees a real transcript, it learns nothing it could not have faked itself. The argument assumes `c` is truly random (this is called honest-verifier zero-knowledge).

## Fiat-Shamir: no verifier needed

So far the verifier has to be online and send the challenge. The {{< term "fiat-shamir" "Fiat-Shamir transform" >}} removes that: the challenge is the hash of everything seen so far. Anyone can check the proof later, like a {{< term "digital-signature" "signature" >}}. Here the message (`msg`) goes into the hash too, so the proof is tied to that message:

```rust
fn challenge(pub_x: Point, big_r: Point, msg: &[u8]) -> Scalar {
    hash_to_scalar(&[b"bc30/schnorr/v1", &enc(G), &enc(pub_x), &enc(big_r), msg])
}
```

The program makes a proof for the message "login to toy-service, session 42" and checks three things:

```
== Fiat-Shamir ==
proof: R=02010fea30003cab.. s=5be1affab357361e..
check: true
check other msg: false
check other key: false
```

The first is the proof with the right message and key: `true`. The second checks it against the message "session 43" and it is rejected. The third checks it against a different public key and is rejected again. (The values of `R` and `s` differ on every run, because `x` and `r` are fresh each time.)

A classic bug is leaving something out of the hash. My function `challenge_no_r` deliberately leaves out `R`. Then the attacker knows `c` before choosing `R`, which is exactly the simulator's trick:

```rust
let c = challenge_no_r(pub_x, msg);
let s = Scalar::random(&mut OsRng);
let forged = Proof { big_r: G * s - pub_x * c, s };
```

```
== bug: R not hashed -> forgery ==
forged, buggy verifier: true
forged, correct verifier: false
```

The attacker had only `pub_x`, but the buggy verifier accepted the forged proof. The correct verifier (which hashes `R`) rejected it. So a valid proof was made for a key whose secret the attacker never had. It is said that leaving out the public key breaks things in a similar way; I did not demonstrate that.

## Nonce reuse leaks the secret

The extractor above is also an attack. If two proofs are made with the same `r`, their challenges differ and the same formula gives `x`:

```
== nonce reuse leaks x ==
both valid: true, same R: true
recovered x == x: true
```

Two proofs for two messages ("message one" and "message two") were made with the same `r`. Both are valid, `R` is the same, and `x` was fully recovered from them. The algebra is the same as the {{< term "ecdsa" "ECDSA" >}} leak in the keys post. According to BIP-340, Bitcoin's Schnorr signatures are this construction on secp256k1, with tagged hashes and a recommended way to derive the nonce.

## Zooming out (no code)

Schnorr proves one fixed statement. More general systems prove "this program ran correctly on secret inputs":

- **Circuits**: the computation becomes arithmetic constraints over a finite field (arithmetization). The prover shows that an assignment satisfying all constraints exists.
- A {{< term "zk-snark" "zk-SNARK" >}} has tiny proofs (Groth16: three group elements, according to its paper) and fast verification. Many SNARKs need a {{< term "trusted-setup" "trusted setup" >}}, and whoever keeps its secret randomness can forge proofs.
- A {{< term "zk-stark" "zk-STARK" >}} is transparent (only hash functions, no setup). As far as I know its proofs are much larger, tens of kilobytes or more.
- **ZK rollups** post a validity proof with each batch, and an L1 contract verifies it before accepting the new state root (we saw this in [Layer 2 and rollups: optimistic and ZK](/posts/bc-layer2-rollups/)).
- **Privacy**: prove membership in a Merkle tree without revealing the leaf. Zcash's shielded transactions use zk-SNARKs.

Real systems use libraries such as arkworks, halo2 or RISC Zero. I did not use any of them here.

## Where proofs break

- Hash everything into the challenge: domain tag, generator, public key, commitment and message.
- Never reuse or bias a nonce. One repeat gives the secret away.
- Use audited libraries. This code is neither constant-time nor reviewed.
- Ask what a trusted setup trusts and who destroyed its secrets.
