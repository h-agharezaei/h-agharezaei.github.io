دوستی دارید که رنگ‌کور است. دو توپ دارید، یکی قرمز و یکی سبز، و می‌خواهید ثابت کنید رنگشان فرق دارد، بدون اینکه بگویید کدام کدام است. او توپ‌ها را پشت سرش می‌برد، یا جایشان را عوض می‌کند یا نه، دوباره نشانتان می‌دهد و می‌پرسد: «جابه‌جا کردم؟» شما رنگ‌ها را می‌بینید و همیشه درست جواب می‌دهید. اگر توپ‌ها واقعاً یک رنگ بودند، هر بار فقط نصف شانس داشتید. بعد از ۲۰ بار درست‌گفتن، او مطمئن می‌شود که رنگ‌ها فرق دارند، ولی هنوز نمی‌داند کدام توپ قرمز است.

این همان کاری است که یک {{< term "zero-knowledge-proof" "zero-knowledge proof" >}} (اثبات دانش‌صفر) می‌کند: کسی را قانع می‌کند که یک جمله درست است، بدون اینکه دلیلش را نشان بدهد. در [Bridge و ارتباط بین زنجیره‌ها](/fa/posts/bc-bridges-cross-chain/) یک زنجیره باید به ادعایی درباره‌ی زنجیره‌ی دیگر اعتماد می‌کرد، و اعتماد به چند امضاکننده نقطه‌ی ضعف شد. اثبات‌های ریاضی راهی هستند که این اعتماد را بردارند. دو چیز از مقاله‌های قبل هم این‌جا برمی‌گردد: در [Merkle tree و اثبات عضویت](/fa/posts/bc-merkle-trees-proofs/) اثبات خود برگ را نشان می‌داد، و در [کلید، امضای ECDSA و آدرس روی secp256k1](/fa/posts/bc-keys-ecdsa-addresses/) یک nonce تکراری کلید خصوصی را لو می‌داد.

> کد اسباب‌بازی برای یادگیری است، نه production. هر secret یک scalar تصادفی تازه است و هیچ‌وقت چاپ نمی‌شود. Rust 1.90، `k256` نسخه‌ی 0.13.4 (با feature به نام `arithmetic`)، `sha2` نسخه‌ی 0.10.9، `rand_core` نسخه‌ی 0.6.4 روی macOS (arm64). دمو یک پروژه‌ی Cargo محلی است.

## یک اثبات چه قولی می‌دهد

اثبات بین دو طرف انجام می‌شود: prover (اثبات‌کننده) و verifier (بررسی‌کننده). سه قول دارد:

- **Completeness (کامل‌بودن):** prover درستکار که secret را دارد، همیشه verifier را قانع می‌کند.
- **Soundness (استواری):** prover‌ای که secret را ندارد، شکست می‌خورد؛ مگر با احتمالی ناچیز.
- **Zero-knowledge (دانش‌صفر):** verifier فقط یاد می‌گیرد که حرف درست است. هر چه دیده، خودش هم می‌توانست بدون کمک prover بسازد، پس چیز تازه‌ای از secret نفهمیده.

جمله‌ای که ما اثبات می‌کنیم این است: «من `x` را می‌دانم که `X = x·G`»، روی منحنی secp256k1. این همان رابطه‌ی کلید خصوصی و عمومی است: `x` کلید خصوصی، `G` نقطه‌ی پایه‌ی منحنی، و `X` کلید عمومی. محاسبه‌ی `X` از `x` آسان است. پیداکردن `x` از `X` همان مسئله‌ی {{< term "discrete-logarithm" "لگاریتم گسسته" >}} است، که تا جایی که می‌دانیم روی این منحنی شدنی نیست.

## پروتکل تعاملی Schnorr

{{< term "schnorr" "پروتکل Schnorr" >}} سه پیام دارد، مثل بازی توپ‌ها:

1. prover یک عدد تصادفی `r` انتخاب می‌کند و `R = r·G` را می‌فرستد. این تعهد (commitment) است.
2. verifier یک عدد تصادفی `c` می‌فرستد. این چالش است.
3. prover جواب می‌دهد: `s = r + c·x`.

verifier فقط یک چیز را چک می‌کند: `s·G` باید با `R + c·X` برابر باشد. چرا؟ چون `s·G = (r + c·x)·G = r·G + c·(x·G) = R + c·X`.

یک مثال کوچک با عددهای دستی (این مثال ساختگی است و خروجی دمو نیست). به‌جای منحنی، گروه ساده‌ای را در نظر بگیرید که ۴ در پیمانه‌ی ۲۳ مرتبه‌ی ۱۱ دارد. در این گروه «ضرب‌کردن در G» همان توان‌رساندن `4^x` است. فرض کنید secret ما `x = 3` باشد. پس `X = 4^3 mod 23 = 18`. حالا:

- prover `r = 5` را انتخاب می‌کند و `R = 4^5 mod 23 = 12` را می‌فرستد.
- verifier چالش `c = 7` را می‌فرستد.
- prover جواب می‌دهد `s = (5 + 7·3) mod 11 = 4`. (مرتبه‌ی گروه ۱۱ است، پس عددها پیمانه‌ی ۱۱ جمع می‌شوند.)
- verifier چک می‌کند: `4^4 mod 23 = 3` و `R · X^7 mod 23 = 12 · 6 mod 23 = 3`. برابرند، پس قبول.

verifier هیچ‌وقت `x = 3` را ندید. `r` مثل یک نقاب است که `x` را داخل `s` پنهان می‌کند. اسم `r` در این‌جا {{< term "nonce" "nonce" >}} است: عدد تصادفی یک‌بارمصرف.

این‌ها همان سه تابع در کد Rust روی secp256k1 هستند:

```rust
fn commit() -> (Scalar, Point) {
    let r = Scalar::random(&mut OsRng);
    (r, G * r)
}
fn respond(x: Scalar, r: Scalar, c: Scalar) -> Scalar {
    r + c * x
}
fn verify(pub_x: Point, big_r: Point, c: Scalar, s: Scalar) -> bool {
    G * s == big_r + pub_x * c
}
```

برنامه را ۱۰۰۰ بار با prover درستکار اجرا کردم (`x` در هر اجرا تازه است). هر ۱۰۰۰ بار verifier قبول کرد، یعنی completeness برقرار است:

```
== interactive, honest prover ==
accepted 1000/1000
```

## Soundness: متقلب و استخراج‌کننده

حالا ببینیم کسی که `x` را ندارد چه شانسی دارد. متقلب می‌تواند چالش را حدس بزند (`c_guess`)، هر `s` دلخواه بردارد و تعهد را برعکس بسازد: `R = s·G - c_guess·X`. اگر verifier دقیقاً همان `c_guess` را بفرستد، جواب درست می‌شود. وگرنه رد می‌شود. پس احتمال موفقیتش `1/q` است، که q مرتبه‌ی گروه است.

روی secp256k1 این احتمال حدود 2^-256 است، یعنی عملاً هیچ. پس برای دیدن چیزی با چشم، همان گروه کوچک (۴ در پیمانه‌ی ۲۳ با مرتبه‌ی ۱۱) را هم در کد گذاشتم. این‌جا احتمال باید حدود `1/11` باشد، یعنی ۰٫۰۹۰۹:

```
== cheating prover (does not know x) ==
toy group q=11: 8837/100000 = 0.0884 (1/q = 0.0909)
secp256k1:      0/10000
```

از ۱۰۰٬۰۰۰ تلاش در گروه کوچک، متقلب ۸۸۳۷ بار موفق شد، یعنی حدود ۸٫۸ درصد، نزدیک به ۱/۱۱. روی secp256k1 از ۱۰٬۰۰۰ تلاش هیچ‌بار. این اعداد تصادفی‌اند و در هر اجرا کمی فرق می‌کنند. در پنج اجرای دیگر نرخ ۰٫۰۹۰۵ و ۰٫۰۹۲۳ و ۰٫۰۹۰۱ و ۰٫۰۹۰۵ و ۰٫۰۹۱۴ درآمد.

آیا متقلب راه بهتری هم دارد؟ نه، و دلیلش جالب است. فرض کنید prover برای یک `R` به دو چالش مختلف جواب درست بدهد. از دو جواب می‌شود `x` را حساب کرد: `x = (s1 - s2) / (c1 - c2)`. پس کسی که برای هر چالشی جواب می‌دهد، در عمل `x` را می‌داند. با مثال دستی: همان `r = 5`، چالش دوم `c = 2` جواب `s = 0` می‌دهد، و `x = (4 - 0) / (7 - 2) = 3` درمی‌آید (پیمانه‌ی ۱۱). کد همین را روی secp256k1 انجام می‌دهد:

```
== extractor: same R, two challenges ==
both transcripts valid: true, extracted x == x: true
```

دو برگه‌ی گفتگو (transcript) معتبر بودند و `x` استخراج‌شده با `x` واقعی برابر است.

## Zero-knowledge: یک شبیه‌ساز

حالا قول سوم. می‌خواهیم نشان دهیم یک transcript چیزی از `x` لو نمی‌دهد. راهش این است که نشان بدهیم می‌شود transcript معتبر را بدون `x` ساخت. ترتیب را برعکس کنیم: اول `c` و `s` را انتخاب کن، بعد `R = s·G - c·X` را حساب کن.

```
== simulator: valid transcript without x ==
simulated (R, c, s) verifies: true
```

این transcript شبیه transcript واقعی است ولی `x` در ساختنش دخالتی نداشت. پس اگر verifier یک transcript واقعی ببیند، چیزی نمی‌فهمد که خودش نمی‌توانست جعل کند. این استدلال فرض می‌کند `c` واقعاً تصادفی است (به آن honest-verifier zero-knowledge می‌گویند).

## Fiat-Shamir: بدون verifier

تا این‌جا verifier باید زنده باشد و چالش بفرستد. {{< term "fiat-shamir" "تبدیل Fiat-Shamir" >}} این را حذف می‌کند: چالش را hash همه‌ی چیزهایی می‌گیریم که تا این‌جا دیده شده. هر کسی می‌تواند بعداً اثبات را بررسی کند، درست مثل یک {{< term "digital-signature" "امضا" >}}. در این حالت پیام (`msg`) هم داخل hash می‌رود و اثبات به آن پیام بسته می‌شود:

```rust
fn challenge(pub_x: Point, big_r: Point, msg: &[u8]) -> Scalar {
    hash_to_scalar(&[b"bc30/schnorr/v1", &enc(G), &enc(pub_x), &enc(big_r), msg])
}
```

برنامه یک اثبات برای پیام «login to toy-service, session 42» می‌سازد و سه چیز را چک می‌کند:

```
== Fiat-Shamir ==
proof: R=02010fea30003cab.. s=5be1affab357361e..
check: true
check other msg: false
check other key: false
```

اولی همان اثبات با پیام و کلید درست است: `true`. دومی را با پیام «session 43» چک می‌کنیم و رد می‌شود. سومی را با یک کلید عمومی دیگر چک می‌کنیم و باز رد می‌شود. (مقدار `R` و `s` در هر اجرا فرق می‌کند، چون `x` و `r` هر بار تازه‌اند.)

یک خطای کلاسیک این است که چیزی را از hash جا بیندازند. تابع `challenge_no_r` در کد من عمداً `R` را نمی‌گذارد. در این صورت مهاجم `c` را پیش از انتخاب `R` می‌داند، و این دقیقاً ترفند شبیه‌ساز است:

```rust
let c = challenge_no_r(pub_x, msg);
let s = Scalar::random(&mut OsRng);
let forged = Proof { big_r: G * s - pub_x * c, s };
```

```
== bug: R not hashed -> forgery ==
forged, buggy verifier: true
forged, correct verifier: false
```

مهاجم فقط `pub_x` را داشت، ولی verifier معیوب اثبات جعلی را قبول کرد. verifier درست (که `R` در hashش هست) رد کرد. یعنی یک اثبات معتبر برای کلیدی ساخته شد که secretش دست مهاجم نبود. گفته می‌شود اگر کلید عمومی را هم از hash بیندازیم مشکل مشابهی پیش می‌آید؛ آن را نشان ندادم.

## nonce تکراری، secret را لو می‌دهد

استخراج‌کننده‌ی بالا یک حمله هم هست. اگر دو اثبات با همان `r` ساخته شوند، چالش‌هایشان فرق دارد و همان فرمول `x` را بیرون می‌دهد:

```
== nonce reuse leaks x ==
both valid: true, same R: true
recovered x == x: true
```

دو اثبات برای دو پیام ("message one" و "message two") با همان `r` ساخته شد. هر دو معتبرند، `R` یکی است، و از روی آن‌ها `x` کامل بازیابی شد. جبرش همان جبر نشت {{< term "ecdsa" "ECDSA" >}} در مقاله‌ی کلیدهاست. طبق BIP-340، امضای Schnorr بیت‌کوین همین ساختار روی secp256k1 است، با tagged hash و روش پیشنهادی برای ساختن nonce.

## نگاه از بالا (بدون کد)

Schnorr فقط یک جمله‌ی ثابت را اثبات می‌کند. سیستم‌های عمومی‌تر اثبات می‌کنند که «این برنامه روی ورودی‌های محرمانه درست اجرا شد»:

- **مدار (circuit):** محاسبه به قیدهای حسابی روی یک میدان متناهی تبدیل می‌شود (arithmetization). prover نشان می‌دهد مقداردهی‌ای هست که همه‌ی قیدها را برآورده می‌کند.
- {{< term "zk-snark" "zk-SNARK" >}} اثبات‌های خیلی کوچک و بررسی سریع دارد (Groth16 طبق مقاله‌اش سه عضو گروه است). خیلی از SNARKها به {{< term "trusted-setup" "trusted setup" >}} نیاز دارند، و کسی که randomness محرمانه‌ی آن را نگه دارد می‌تواند اثبات جعلی بسازد.
- {{< term "zk-stark" "zk-STARK" >}} شفاف است (فقط تابع hash، بدون setup). تا جایی که می‌دانم اثبات‌هایش خیلی بزرگ‌ترند، در حد ده‌ها کیلوبایت یا بیشتر.
- **ZK rollupها** برای هر دسته یک اثبات درستی می‌فرستند و قرارداد L1 قبل از پذیرفتن state root جدید آن را بررسی می‌کند (در [Layer 2 و rollupها: optimistic و ZK](/fa/posts/bc-layer2-rollups/) دیدیم).
- **حریم خصوصی:** عضویت در یک Merkle tree را بدون نشان‌دادن برگ ثابت کنید. تراکنش‌های محافظت‌شده‌ی Zcash از zk-SNARK استفاده می‌کنند.

سیستم‌های واقعی از کتابخانه‌هایی مثل arkworks، halo2 یا RISC Zero استفاده می‌کنند. من این‌جا از هیچ‌کدام استفاده نکردم.

## کجا اثبات‌ها می‌شکنند

- همه‌چیز را در چالش hash کنید: برچسب دامنه، مولد، کلید عمومی، تعهد و پیام.
- هرگز nonce را تکرار نکنید و آن را سوگیرانه نسازید. یک تکرار، secret را می‌دهد.
- از کتابخانه‌های بازبینی‌شده استفاده کنید. این کد نه constant-time است و نه بازبینی شده.
- بپرسید trusted setup به چه کسی اعتماد دارد و چه کسی secretهایش را نابود کرده.

## تمرین

1. `pub_x` را از `challenge` بردارید و جعل کنید: اول `R` را انتخاب کنید، hash بگیرید، بعد کلید را برگزینید.
2. q = 5 را امتحان کنید (۴ در پیمانه‌ی ۱۱ مرتبه‌ی ۵ دارد) و نرخ تقلب را چک کنید.
3. `prove` را با nonceهای به‌سبک BIP-340 به یک امضا تبدیل کنید.
