یک نفر به شما می‌گوید: «گزارش درآمد ماهانه خیلی کند شده.» همین. نه planی دارید، نه مقصری، نه اشاره‌ای که کدام بخش کند است. این پست همین وضعیت است، به‌شکل یک بررسی تعریف‌شده: یک query گزارش، چهار رفع، و برای هر رفع اینکه به چه نگاه کردم، چه گفت و چه چیزی عوض شد. هیچ‌چیز اینجا نظریه‌ی تازه نیست؛ پست‌های قبلی همین سری است که روی یک مسئله به کار می‌افتد: [ایندکس B-tree و EXPLAIN](/fa/posts/db-indexes-btree-explain/)، [ایندکس‌های ترکیبی](/fa/posts/db-composite-partial-covering-indexes/) و [آمار planner](/fa/posts/db-planner-statistics/). بعد از [connection pool و حالت‌های خرابی](/fa/posts/db-connection-pooling/) می‌آید و آخرین پست این سری است.

> همه‌چیز روی PostgreSQL 18.3 واقعی اجرا شد (برای این نسخه‌ی پست کل case study را دوباره اجرا کردم) با seed فروشگاه (۲۰۰ هزار سفارش، ۶۰۰ هزار آیتم) به‌علاوه‌ی یک «import شبانه» از ۴۰ هزار سفارش مارس ۲۰۲۶ و ۱۲۰ هزار آیتم. برای import روی آن دو جدول autovacuum را خاموش کردم، پس تا خودم analyze نکنم کسی ردیف‌های جدید را تحلیل نمی‌کند. سیستم واقعی هم این پنجره را دارد: بین یک import بزرگ و analyze خودکار بعدی. ماشین شلوغ بود، پس به‌جای میلی‌ثانیه buffer نشان می‌دهم (هر buffer یک page هشت کیلوبایتی است که query به آن دست زده)، از `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, SUMMARY OFF)` با workerهای موازی خاموش. تعداد bufferها دقیق است و از اجرایی به اجرای دیگر تکرار می‌شود؛ برآورد ردیف‌ها از یک نمونه‌ی تصادفی می‌آید و ممکن است کمی فرق کند، و جاهایی که فرق کرد را گفته‌ام.

## گزارش

گزارش درآمد هر مشتری از سفارش‌های `paid` در یک ماه است، ۱۰ تای اول:

```sql
SELECT c.id, date_trunc('month', o.created_at) AS month, sum(oi.qty * oi.price_cents) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'paid' AND o.created_at >= '2026-03-01' AND o.created_at < '2026-04-01'
GROUP BY c.id, month ORDER BY revenue DESC LIMIT 10;
```

اولین حرکت همیشه یکی است: آن را با `EXPLAIN (ANALYZE, BUFFERS)` اجرا کن و پیش از دست‌زدن به هر چیز plan را بخوان. خط بالا می‌گوید `Buffers: shared hit=67367`: این یک query به ۶۷٬۳۶۷ page دست زد (بعضی را چند بار؛ با ۸ کیلوبایت برای هر page حدود ۵۲۶ مگابایت دسترسی به page می‌شود) تا ده ردیف برگرداند. خط‌های مهم:

```text
Seq Scan on orders o  (cost=0.00..6857.00 rows=1 ...) (actual rows=8000.00 loops=1)
Index Scan using order_items_pkey on order_items oi  (rows=3) (actual rows=3.00 loops=8000)
```

دو چیز را باید خواند. اول، `rows=1` در برابر `actual rows=8000`: planner یک سفارش مارس انتظار داشت و ۸٬۰۰۰ تا پیدا کرد. دوم، `loops=8000`: planner فکر کرد یک سفارش یعنی یک nested loop ارزان، پس برای هر کدام از آن ۸٬۰۰۰ سفارش `order_items` را با primary key اش کاوید، و (در بالا نیامده) `customers` را هم با primary key اش، هرکدام ۸٬۰۰۰ بار. bufferها جمع می‌خورند: ۳٬۳۵۷ برای اسکن `orders`، ۱۶٬۰۰۱ برای ۸٬۰۰۰ کاوش `customers` و ۴۸٬۰۰۰ برای ۸٬۰۰۰ کاوش `order_items` می‌شود ۶۷٬۳۵۸ از ۶۷٬۳۶۷. فاصله‌ی برآورد و واقعیت به این اندازه، پیش از هر چیز نشانه‌ی آمار بد است.

## رفع ۱: ANALYZE

چرا planner یک ردیف انتظار داشت؟ برای برنامه‌ریزی به خود جدول نگاه نمی‌کند؛ از {{< term "planner-statistics" "آمار" >}} استفاده می‌کند، خلاصه‌ای از مقدارهای ستون که `ANALYZE` قبلاً جمع کرده. آن آمار پیش از import جمع شده بود، پس تازه‌ترین `created_at` که می‌شناسند اوایل فوریه‌ی 2026 است. query مارس می‌خواهد، بیرون از هرچه planner تا حالا دیده، پس فرض کرد تقریباً هیچ ردیفی نمی‌خواند. رفع یک دستور است:

```sql
ANALYZE orders; ANALYZE order_items;
```

plan جدید حدود ۷٬۵۰۰ ردیف برآورد می‌کند در برابر ۸٬۰۰۰ واقعی (در این اجرا ۷٬۵۴۹؛ نمونه‌گیری باعث می‌شود هر بار کمی فرق کند)، به hash join می‌رود و `Buffers: shared hit=8862` می‌خواند. از ۶۷٬۳۶۷ page به ۸٬۸۶۲، بی‌هیچ تغییری در schema یا query. هزینه‌ی برآوردی از ۶٬۸۷۷ به حدود ۲۳٬۹۰۰ رفت: plan اول فقط روی کاغذ ارزان به نظر می‌رسید چون روی یک تعداد ردیف غلط ساخته شده بود. ببینید ۸٬۸۶۲ از چه ساخته شده: ۵٬۲۹۵ برای `order_items`، ۳٬۳۵۷ برای `orders` و ۲۰۷ برای `customers`. گزارش هنوز برای ۸٬۰۰۰ ردیف کل `orders` را می‌خواند.

## رفع ۲: ایندکس ترکیبی

همین مشاهده‌ی آخر گام بعد را نشان می‌دهد. شرط یک تساوی روی `status` و یک بازه روی `created_at` دارد، و این دقیقاً شکلی است که {{< term "composite-index" "ایندکس ترکیبی" >}} برایش ساخته شده: ستون تساوی اول، ستون بازه دوم.

```sql
CREATE INDEX orders_status_created_idx ON orders (status, created_at);
```

حالا planner `orders` را با {{< term "bitmap-scan" "bitmap scan" >}} می‌خواند: اول از ایندکس جمع می‌کند کدام pageهای جدول ردیف مطابق دارند، بعد فقط به همان pageها سر می‌زند. این ۳۷۱ page را لمس می‌کند (۳۳۷ hit و ۳۴ read) به‌جای ۳٬۳۵۷، و مجموع به ۵٬۸۷۶ رسید. توجه کنید چه چیزی عوض نشد: `order_items` هنوز با `Seq Scan` خوانده می‌شود (۵٬۲۹۵ page). این انتخاب درست است و مشکلی باقی‌مانده نیست: گزارش ۸٬۰۰۰ سفارش و حدود ۲۴٬۰۰۰ آیتم آن‌ها را لازم دارد و ۸٬۰۰۰ کاوش ایندکس خیلی بیشتر از یک بار خواندن جدول از اول تا آخر خرج دارد. هر `Seq Scan` باگ نیست.

## رفع ۳: تابع روی ستون

اینجا اشتباهی است که هنگام «بهتر کردن» یک query آسان اتفاق می‌افتد. یک همکار فیلتر ماه را خواناتر می‌نویسد:

```sql
WHERE status = 'paid' AND to_char(created_at, 'YYYY-MM') = '2026-03'
```

قشنگ‌تر به نظر می‌رسد، و دیگر {{< term "sargable" "sargable" >}} نیست: ایندکس نمی‌تواند برای شرطی روی `to_char(created_at, ...)` استفاده شود، چون ایندکس `created_at` را نگه می‌دارد، نه شکل متنی‌اش را. آن را با شکل بازه‌ای روی شمارش سفارش‌های paid مارس مقایسه کردم. پیش از آن روی `orders` یک `VACUUM` زدم تا PostgreSQL بتواند فقط از ایندکس جواب بدهد (index-only scan؛ بدون آن هر ۸٬۰۰۰ تطابق باید در جدول هم چک شود و هر دو query اینجا حدود ۷٬۰۰۰ page می‌خواندند که تفاوت را پنهان می‌کرد):

```text
to_char(...) form:  Buffers: shared hit=145   estimate 241 rows   Rows Removed by Filter: 40000
range form:         Buffers: shared hit=35    estimate 7709 rows
```

برآورد با تابع ۲۴۱ ردیف است در برابر ۸٬۰۰۰ واقعی، و planner برای عبارت آمار ندارد، پس حدس می‌زند. بخش `status` ایندکس هنوز استفاده شد، ولی تاریخ‌ها بعد از خواندن ورودی‌های ایندکس فیلتر شدند: ۴۰٬۰۰۰ ردیف با فیلتر حذف شد، و ۱۴۵ page به‌جای ۳۵. درس: ستون را لخت نگه دار و محاسبه را سمت ثابت ببر.

## رفع ۴: correlated subquery

گزارش دوم، برای تیمی دیگر، سفارش‌های paid مارس هر مشتری را در یک کشور می‌شمارد:

```sql
SELECT c.id, c.email,
  (SELECT count(*) FROM orders o WHERE o.customer_id = c.id AND o.status = 'paid'
     AND o.created_at >= '2026-03-01' AND o.created_at < '2026-04-01')
FROM customers c WHERE c.country = 'IR';
```

{{< term "correlated-subquery" "correlated subquery" >}} subqueryای است که به ردیف بیرونی ارجاع می‌دهد (اینجا `c.id`)، پس باید برای هر ردیف بیرونی یک بار اجرا شود. plan `loops=1666` نشان می‌دهد: یک اجرای subquery برای هر مشتری آن کشور. هر اجرا ۸٬۰۰۰ ردیف ماه را از ایندکس ترکیبی خواند و تقریباً همه را دور ریخت (`Rows Removed by Filter: 8000`)، پس مجموع شد ۶۱۸٬۲۹۳ page. دو گام، جداگانه اندازه‌گیری‌شده:

```text
 CREATE INDEX orders_customer_id_idx ON orders (customer_id)   -> 23493 pages
 rewrite as LEFT JOIN ... GROUP BY c.id                        ->   578 pages
```

گام اول ایندکس روی ستون {{< term "foreign-key" "foreign key" >}} یعنی `customer_id` است که ایندکس نداشت. حالا هر اجرای subquery ردیف‌های همان مشتری را (حدود ۱۲ تا) مستقیم پیدا می‌کند: ۲۶ برابر کاهش. گام دوم query را با `LEFT JOIN` و `GROUP BY` بازنویسی می‌کند که به planner اجازه می‌دهد سفارش‌های ماه را یک بار بخواند و در یک گذر با مشتری‌ها join کند: ۴۰ برابر دیگر. دقت کنید plan نهایی حتی از ایندکس تازه‌ی `customer_id` استفاده نمی‌کند؛ از ایندکس ترکیبی رفع ۲ استفاده می‌کند. ایندکس برای شکل میانی مهم بود و بازنویسی بقیه را انجام داد.

## پیدا کردن query از همان اول

در این داستان یک نفر query کند را دستم داد. در زندگی واقعی هیچ‌کس نمی‌دهد، و افزونه‌ی `pg_stat_statements` است که آن را پیدا می‌کند: برای هر query متمایز ثبت می‌کند چند بار اجرا شده و در مجموع به چند buffer دست زده. به `shared_preload_libraries = 'pg_stat_statements'` و ری‌استارت سرور نیاز دارد، که روی instance خودم می‌توانستم بگذارم. برای دیدن اینکه شکل‌های این پست را چطور توصیف می‌کند، در حالت نهایی case study گزارش را یک بار و شمارش هر مشتری را به‌صورت حلقه‌ای از ۱٬۶۶۶ prepared statement جدا اجرا کردم (کاری که کد برنامه وقتی داخل حلقه query می‌زند انجام می‌دهد):

```text
                           query                            | calls | rows | total_blocks | blocks_per_call
 PREPARE paid_count(int) AS SELECT count(*) FROM orders o W |  1666 | 1666 |        23289 |              14
 SELECT c.id, date_trunc($1, o.created_at) AS month, sum(oi |     1 |   10 |         5876 |            5876
```

حلقه در هر فراخوانی بی‌ضرر است: ۱۴ block برای هر کدام، چیزی که هیچ لاگ query کندی هرگز علامتش نمی‌زد. با این حال در مجموع چهار برابر bufferهای گزارشی را لمس کرد که همه را نگران کرده بود. این الگوی {{< term "n-plus-one" "N+1" >}} است: هیچ plan کندی نیست، فقط query های سریع زیادی هست. لاگ query های کند بر اساس مدت احتمالاً علامتش نمی‌زند؛ مرتب‌کردن بر اساس کار کل فوراً نشانش می‌دهد. اعداد `total_blocks` و `calls` دقیق‌اند؛ تقسیم بین hit و read به این بستگی دارد که چه چیزی در cache بود. (نسخه‌ی قبلی این پست می‌گفت `pg_stat_statements` اینجا قابل استفاده نیست. هست، اگر instance خودتان را با کتابخانه‌ی preload شده راه بیندازید.)

## آیا رفع‌ها به نوشتن آسیب زدند؟

هر ایندکس باید با هر insert به‌روز شود. پس پیش از اعلام پیروزی سمت نوشتن را اندازه گرفتم. دو کپی از `orders` ساختم (۲۴۰٬۰۰۰ ردیف): یکی فقط با primary key، یکی با primary key و دو ایندکس جدید. بعد همان ۲۰٬۰۰۰ ردیف را در هرکدام insert کردم و مقایسه کردم هر insert چقدر {{< term "wal" "WAL" >}} (write-ahead log) تولید کرد:

```text
 primary key only        3287696 bytes
 + two new indexes       8080248 bytes
```

حدود ۲٫۵ برابر WAL برای همان ردیف‌ها، و ایندکس‌های کپی ۱۳ مگابایت جا گرفتند در برابر ۵٬۲۸۸ کیلوبایت. این بهای رفع‌هاست. بایت‌های WAL تقریباً دقیق تکرار می‌شوند، نه تا آخرین رقم (چند ده بایت با یک اجرای قبلی خودم فرق دارند). روی جدول پرنوشتن من پیش از پرداختن این بها اندازه می‌گرفتم؛ روی این جدول، گزارش ماهانه‌ای که از ۶۷٬۳۶۷ page به ۵٬۸۷۶ رسید معامله‌ی خوبی است.

## درس‌های این case

- **اول `rows` را با `actual rows` مقایسه کن.** فاصله‌ی بزرگ به آمار اشاره می‌کند، و `ANALYZE` ارزان‌ترین رفع است.
- **هر بار یک چیز را عوض کن و بعد از هرکدام buffer را ثبت کن.** این‌طور می‌فهمی کدام گام کار کرد، و جدول بالا فقط چون هر رفع جدا اندازه‌گیری شد ممکن بود.
- **دنبال `loops=` در حد هزاران بگرد.** این هزینه‌ای است که برای هر ردیف پرداخت می‌شود.
- **هر `Seq Scan` را باگ نشمار.** اگر query بخش بزرگی از جدول را لازم دارد، یک بار خواندنش ارزان‌ترین plan است.
- **پیش از افزودن ایندکس به جدول شلوغ سمت نوشتن را اندازه بگیر.**

## چک‌لیست برای query کند بعدی

۱. query واقعی را بگیر (از `pg_stat_statements` یا لاگ‌ها) و روی داده‌ی واقع‌گرایانه `EXPLAIN (ANALYZE, BUFFERS)` بزن.
۲. برآوردها از واقعیت دورند؟ `ANALYZE`، و اگر لازم شد آمار گسترده.
۳. اسکن بزرگ برای ردیف‌های کم؟ ایندکس ستون‌های `WHERE` را به ترتیب چک کن.
۴. تابع یا cast روی ستون؟ بازنویسی‌اش کن.
۵. `loops` بالا؟ subquery یا N+1 را با join عوض کن.
۶. دوباره اندازه بگیر، بعد هزینه‌ی نوشتن را چک کن.
