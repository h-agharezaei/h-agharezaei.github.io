یک review را تصور کنید که کامنت اولش می‌گوید «تورفتگی این خط اشتباه است»، کامنت دومش می‌گوید «من اسم این متغیر را جور دیگری می‌گذاشتم» و تأییدش بعد از ده دقیقه می‌آید. در همین حال تغییر یک باگ واقعی دارد و هیچ‌کس آن را ندید، چون توجه reviewer خرج چیزهایی شد که یک برنامه هم می‌توانست پیدا کند.

برای اینکه ببینم یک ماشین چقدر می‌گیرد و چقدر نمی‌گیرد، هفت مشکل در یک pull request (PR) کوچک Go کاشتم و ابزارهای معمول را روی آن اجرا کردم. `gofmt`، `go vet` و race detector روی هم سه‌تا را گرفتند. body پاسخی که هرگز بسته نمی‌شود، goroutineهای نشت‌کرده و یک خطای مرزی از همه‌ی ابزارها رد شدند. {{< term "code-review" "code review" >}}، یعنی خواندن تغییر توسط یک آدم پیش از merge، شبکه‌ی ایمنی همین‌هاست. در عین حال گران است، چون توجه reviewer کمیاب‌ترین چیز در تیم است. قاعده‌ی من از همین می‌آید: اول ماشین‌ها بروند و آدم‌ها فقط چیزی را ببینند که ماشین نمی‌بیند.

برخلاف شبکه‌ی ایمنی [refactor امن](/fa/posts/eng-refactoring-safely/) که یک تست بود، این یکی از آدم‌ها ساخته شده است. مبانی تست در [تست در Go](/fa/posts/go-testing-basics/) آمده و لایه‌بندی در [ساختار پروژه و clean architecture](/fa/posts/go-project-layout-clean-architecture/). نظرهای خودم را با **به تجربه‌ی من** مشخص کرده‌ام. یافته‌های زیر از اجرای واقعی آمده‌اند.

> دمو یک repo محلی git با دو commit و یک branch است. در اجرای اولیه با Go 1.26 اجرایش کردم و برای این ویرایش با Go 1.27.3 دوباره اجرایش کردم. کد را خودم و عمداً معیوب نوشته‌ام. در این اجرای دوباره نتوانستم staticcheck را دوباره اجرا کنم، پس نتیجه‌ی آن در پایین از اجرای اولیه است.

## یک PR معیوب

روی `main` یک تابع کمکی `Page` هست که از قبل تست دارد. branch با نام `add-bulk-check` یک link checker اضافه می‌کند (برنامه‌ای که چند URL را درخواست می‌دهد و کد وضعیتشان را گزارش می‌کند). اندازه‌ی تغییر این است:

```text
$ git diff main --stat
 check.go      | 54 ++++++++++++++++++++++++++++++++++++++++++++++++++++++
 check_test.go | 25 +++++++++++++++++++++++++
 2 files changed, 79 insertions(+)
```

هفت مشکل کاشته‌شده این‌ها هستند:

1. یک خط با تورفتگی اشتباه؛
2. فعل نادرست `Printf` (`%s` برای یک عدد صحیح)؛
3. نوشتن هم‌زمان چند goroutine در یک map؛
4. خطای نادیده‌گرفته‌شده؛
5. body پاسخ HTTP که هرگز بسته نمی‌شود؛
6. یک goroutine نشت‌کرده (برای همیشه منتظر می‌ماند و هیچ‌وقت جمع نمی‌شود)؛
7. `LastPage` که `total / size` برمی‌گرداند و رو به پایین گرد می‌کند.

هسته‌ی diff این است، تا پیش از اینکه ببینید چه چیزی پیدا کرد خودتان دنبال مشکل‌ها بگردید:

```go
func Status(url string) (int, error) {
	resp, err := http.Get(url)
	if err != nil {
		return 0, err
	}
	return resp.StatusCode, nil
}

go func() {
	defer wg.Done()
	code, _ := Status(u)
	fmt.Printf("checked %s: %s\n", u, code)
	out[u] = code
}()
```

## اول ماشین‌ها

اول بررسی‌های ارزان و خودکار را اجرا کردم. `gofmt -l` فایل‌هایی را که قالب‌بندی نشده‌اند فهرست می‌کند و `go vet` دنبال ساختارهای مشکوک می‌گردد:

```text
$ gofmt -l .
check.go

$ go vet ./...
check.go:27:29: fmt.Printf format %s has arg code of wrong type int
```

مشکل ۱ (تورفتگی) و مشکل ۲ (فعل) پیدا شدند. بعد `go test -race` تست‌ها را با race detector اجرا می‌کند؛ این ابزار دسترسی‌ها به حافظه را زیر نظر دارد و وقتی دو goroutine بدون هماهنگی به یک متغیر دست بزنند گزارش می‌دهد. `-vet=off` را اضافه کردم، چون `go test` ساده یک زیرمجموعه‌ی vet را اجرا می‌کند و پیش از رسیدن به race روی همان خط `Printf` می‌ایستد. race detector پیام `WARNING: DATA RACE` را چاپ کرد، با stack هر دو goroutine که به نوشتن map در خط ۲۸ اشاره می‌کنند، و بعد `--- FAIL: TestCheckAll`. {{< term "race-condition" "race" >}} فقط گرفته شد چون تست اتفاقاً دو URL را هم‌زمان می‌زند. تستی با یک URL پاس می‌شد.

staticcheck را هم با نسخه‌ی ثابت اجرا کردم، با `go run honnef.co/go/tools/cmd/staticcheck@2025.1.1 ./...`. فقط یک مورد گزارش کرد، همان مشکل `Printf` (`SA5009`). خطای نادیده‌گرفته، body بسته‌نشده، نشت و خطای مرزی را **نگفت**. {{< term "static-analysis" "تحلیلگر ایستا" >}} فقط الگوهایی را می‌شناسد که برایشان نوشته شده. (این اجرای اولیه بود. وقتی برای این ویرایش خواستم دوباره اجرایش کنم، محیط من اجازه‌ی اجرای ابزاری را که تازه دانلود می‌شد نداد، پس دوباره اجرایش نکردم.)

توصیه‌ی عملی این است که هر چهار ابزار را در {{< term "ci" "CI" >}} بگذارید تا reviewer آدمی لازم نباشد برای این‌ها کامنت خرج کند.

## آنچه فقط آدم می‌گیرد

چهار مشکل مانده و `go test -vet=off` ساده سبز است. گزارش پوشش نشان می‌دهد چرا تست‌ها چیزی نفهمیدند:

```text
Status    75.0%
CheckAll  100.0%
FirstOK   0.0%
LastPage  66.7%
```

`FirstOK` را اصلاً هیچ تستی اجرا نمی‌کند. در `Status` و `LastPage` هم خط‌هایی هست که هرگز اجرا نمی‌شود. پس این یافته‌ها نمی‌توانستند از ابزارهای بالا بیایند:

- **خطای نادیده‌گرفته.** در `CheckAll`، `code, _ := Status(u)` خطا را دور می‌ریزد. وقتی درخواستی شکست می‌خورد `Status` صفر برمی‌گرداند و map فقط ۰ می‌گوید، پس کسی نمی‌تواند «در دسترس نیست» را از چیز دیگری تشخیص دهد.
- **body بسته‌نشده.** `Status` هیچ‌وقت `resp.Body.Close()` را صدا نمی‌زند. تست با این حال می‌گذرد، چون یک تست کوتاه اتصال‌ها را تمام نمی‌کند. در محیط واقعی، هر پاسخ بسته‌نشده جلوی استفاده‌ی دوباره از اتصالش را می‌گیرد.
- **goroutineهای نشت‌کرده.** `FirstOK` برای هر URL یک goroutine شروع می‌کند و اولین جواب را برمی‌گرداند. بقیه می‌خواهند جوابشان را روی channelی بفرستند که دیگر کسی نمی‌خواندش، پس برای همیشه منتظر می‌مانند. در یک تست موقت `FirstOK` را با سه URL سالم صدا زدم و بعد از ۲۰۰ میلی‌ثانیه goroutineهای گیرکرده روی ارسال به آن channel را شمردم. برای این ویرایش دوباره شمردم و دوتا دیدم، همان دو بازنده‌ی مسابقه. (در اجرای اولیه همه‌ی goroutineها را شمرده بودم: ۳ قبل و ۱۱ بعد، که goroutineهای اتصال را هم دربرمی‌گیرد و جدایشان نکردم.)
- **مرز.** `LastPage(11, 5)` عدد ۲ داد، در حالی که یازده مورد سه صفحه می‌خواهد. تنها تست ۱۰ و ۵ را زده بود، تنها موردی که اتفاقاً درست است.

بعد چیزهایی هست که هیچ ابزاری نمی‌تواند قضاوت کند. `Status` و `FirstOK` فراخوانی `http.Get` را پنهان می‌کنند، پس بدون سرور زنده تست‌پذیر نیستند، و HTTP client پیش‌فرض timeout ندارد. این طراحی است و جایش review است.

## به شکل what / why / suggestion بگویید

پیداکردن مشکل نصف کار است. نصف دیگر این است که چطور بگویید. من کامنتی را دوست دارم که سه بخش دارد: چه چیزی غلط است، چرا مهم است و چه پیشنهادی دارم:

```text
check.go:11  What: resp.Body is never closed.
             Why: connections are not reused and leak under load.
             Suggestion: defer resp.Body.Close() after the err check.

check.go:49  What: LastPage(11, 5) returns 2.
             Why: integer division rounds down, the last partial page is lost.
             Suggestion: (total+size-1)/size, plus a test with 11 and 5.
```

**به تجربه‌ی من** کامنتی که دلیل و راه‌حل دارد در یک دور درست می‌شود. «این غلط است» خالی بحث راه می‌اندازد. لحن هم کمک می‌کند. به‌جای حکم‌دادن بپرسید («اگر فراخوانی اول شکست بخورد این بلاک نمی‌شود؟»). موارد کوچک را با `nit:` شروع کنید تا نویسنده بداند اختیاری‌اند. و وقتی چیزی خوب است بگویید.

## سمت نویسنده

review کار دونفره است و نویسنده می‌تواند خیلی به آسان‌ترشدنش کمک کند.

- **اول diff خودتان را بخوانید.** **به تجربه‌ی من** چند مشکل را خودتان پیدا می‌کنید.
- **PR را کوچک نگه دارید.** برای نشان‌دادن اثرش دو branch موقت ساختم، یکی با ۴۰ و یکی با ۹۰۰ خط اضافه، و فقط آمار git را نگاه کردم: `1 file changed, 40 insertions(+)` در برابر `6 files changed, 900 insertions(+)`. **به تجربه‌ی من** دومی را کسی واقعاً نمی‌خواند؛ سرسری می‌گذرد و تأیید می‌کند.
- **توضیح کوتاه بنویسید.** چه چیزی عوض شد، چرا، چطور تست کردم و چه چیزی را تست نکردم.

## وقتی موافق نیستید

از سلیقه به شواهد بروید: تست شکست‌خورده، اندازه‌گیری، راهنمای سبک خود پروژه. اگر باز هم سلیقه بود، نویسنده تصمیم می‌گیرد و reviewer `nit:` می‌نویسد. اگر بحث طراحی بود، حضوری یا تماسی صحبت کنید و بعد نتیجه را در PR بنویسید تا تصمیم گم نشود.

## مفاهیمی که اجرا نکردم

فایل {{< term "codeowners" "CODEOWNERS" >}} از صاحبان یک مسیر می‌خواهد تغییرهای آن را review کنند. {{< term "branch-protection" "branch protection" >}} می‌تواند پیش از merge تأیید و CI سبز را اجباری کند. هر دو روی پلتفرم میزبان تنظیم می‌شوند و من این‌جا هیچ‌کدام را راه نینداختم.

## توجه reviewer کجا هدر می‌رود

- **review دستیِ سبک کد.** خودکارش کنید، همان‌طور که بالا گفتم.
- **خواندن کد پیش از تست.** اول تست‌ها را بخوانید. اگر روی باگ شکست نمی‌خورند، کد زیرشان عملاً review نشده است.
- **نشست‌های ماراتنی.** review را در نشست‌های کوتاه انجام دهید. **به تجربه‌ی من** توجه بعد از حدود یک ساعت شدید افت می‌کند. این اندازه‌گیری نیست.
- **تأیید نکردن بی‌دلیل.** وقتی چیزی مانع merge نیست، با کامنت تأیید کنید.

## تمرین

آخرین PR merge‌شده‌ی خودتان را بردارید. `gofmt -l`، `go vet`، `go test -race` و staticcheck را روی آن اجرا کنید. بعد برای چیزی که هیچ‌کدام نگفتند یک کامنت what / why / suggestion بنویسید.

## قدم بعدی

«طراحی API: نسخه‌بندی و pagination». review درباره‌ی یک تغییر و یک نویسنده است. در طراحی API یک تغییر باید هم‌زمان برای کلاینت‌های زیادی کار کند، پس اشتباه گران‌تر تمام می‌شود.
