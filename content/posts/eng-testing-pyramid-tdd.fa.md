یک مجموعه‌ی تست را تصور کنید که هم‌زمان از دو جهت خراب شده است. بعد از یک پاک‌سازی کوچک داخلی که هیچ رفتاری را عوض نکرده، تست‌های زیادی می‌شکنند و شما بعدازظهر را به‌جای درست‌کردن کد، صرف درست‌کردن تست می‌کنید. از آن طرف، یک باگ واقعی در قیمت‌گذاری به محیط تولید می‌رود، آن هم وقتی گزارش می‌گوید {{< term "code-coverage" "coverage" >}} صددرصد است. مشکل اول تغییر دادن کد را گران می‌کند. مشکل دوم یعنی تست‌ها از شما محافظت نمی‌کنند.

هر دو از یک جا می‌آیند: تست می‌نویسیم بی‌آنکه بپرسیم هر تست برای چه کاری است. این مقاله سری Software Engineering را با راهی برای فکر کردن به همین سؤال شروع می‌کند. اول {{< term "test-pyramid" "هرم تست" >}} را می‌بینیم، که راهی است برای تصمیم‌گرفتن اینکه از هر نوع تست چندتا بنویسیم. بعد سراغ {{< term "tdd" "TDD" >}} (توسعه‌ی تست‌محور) می‌رویم، یعنی اینکه تست را پیش از کد بنویسید. در آخر چهار راه مشخص را می‌بینیم که تست‌ها خراب می‌شوند. نظرهای شخصی خودم را با **نظر من** مشخص کرده‌ام تا از واقعیت‌ها جدا باشند.

مکانیک `go test` در [تست در Go](/fa/posts/go-testing-basics/) آمده و ساختار سرویسی که پایین استفاده می‌کنم از [ساختار پروژه و Clean Architecture در Go](/fa/posts/go-project-layout-clean-architecture/) است. همین ایده‌ها در [node:test](/fa/posts/node-testing-builtin/) و [تست در Rust](/fa/posts/rust-testing-docs/) هم هست.

> دموها مثال‌های محلی با Go هستند. در اجرای اولیه با Go 1.26 و `go test -race` اجرایشان کردم و برای این ویرایش دوباره با Go 1.27.3 اجرایشان کردم.

## هرم تست یک مدل هزینه است

تست‌ها اندازه‌های مختلف دارند و هر اندازه قیمت خودش را. {{< term "unit-test" "تست واحد" >}} یک تکه‌ی کوچک منطق را بررسی می‌کند، مثلاً یک تابع را، بدون شبکه و دیسک. {{< term "integration-test" "تست یکپارچگی" >}} بررسی می‌کند که چند تکه با هم درست کار می‌کنند، مثلاً یک سرویس و محل ذخیره‌ی داده‌اش. تست سرتاسری (end-to-end) کل سیستم را همان‌طور اجرا می‌کند که یک کاربر اجرا می‌کند، مثلاً با فرستادن یک درخواست HTTP واقعی به سیستم در حال اجرا.

هرم تست می‌گوید: تست واحد زیاد بنویس، تست یکپارچگی کمتر، و تست سرتاسری خیلی کم. دلیلش هزینه است. هرچه تست بالاتر باشد کندتر است، آماده‌سازی بیشتری می‌خواهد و به دلیل‌هایی می‌شکند که ربطی به کدی که عوض کرده‌اید ندارند (شبکه‌ی کند، یک رکورد باقی‌مانده در پایگاه داده). در یک دامنه‌ی کوچک سفارش‌ها این سه سطح این‌طور هستند:

- **واحد:** `cart.Total`، یک تابع خالص. آیتم‌ها و یک کد تخفیف می‌گیرد و یک عدد برمی‌گرداند. بدون I/O.
- **یکپارچگی:** `orders.Service` که با یک repository ساختگی (fake) کار می‌کند، که پایین‌تر می‌بینیمش.
- **سرتاسری:** یک درخواست HTTP واقعی به سیستم در حال اجرا. این‌جا چنین چیزی نساخته‌ام و اجرا نکرده‌ام.

**نظر من:** بیشتر منطق را در توابع خالص بگذارید و آن‌ها را زیاد تست کنید. هر نقطه‌ی اتصال بین اجزا را یک بار با fake تست کنید. یکی دو تست سرتاسری را هم برای مسیرهایی نگه دارید که پول درمی‌آورند، مثل پرداخت.

## TDD: red، green، refactor

TDD یک حلقه‌ی کوچک با سه گام است. **Red:** تستی برای رفتاری بنویسید که هنوز وجود ندارد و ببینید که می‌شکند. **Green:** کم‌ترین کدی را بنویسید که تست را سبز کند. **Refactor:** کد را تمیز کنید، در حالی که تست‌ها سبز می‌مانند. بعد با تکه‌ی کوچک بعدی از رفتار، دوباره از اول.

تابع `Total(items, code)` را این‌طور ساختم. قیمت‌ها به سنت هستند و یک کد تخفیف درصدی از قیمت کم می‌کند. روند کار این بود.

**گام ۱: سبد خالی.** اول تست را نوشتم. حتی کامپایل نمی‌شود، چون `Total` وجود ندارد، و این اولین red است:

```text
cart_test.go:6:14: undefined: Total
```

برگرداندن ۰ آن را سبز کرد.

**گام ۲: جمع آیتم‌ها.** تست جدید یک خودکار ۱۵۰ تایی دوتا به‌علاوه‌ی یک کتاب ۱۲۰۰ تایی است، یعنی ۱۵۰۰. شکست از نوع درست است، چون به همان دلیلی می‌شکند که می‌خواهم درستش کنم:

```text
--- FAIL: TestTotalSumsItems (0.00s)
    cart_test.go:16: Total = 0, want 1500
```

یک حلقه‌ی ساده آن را درست کرد.

**گام ۳: کد `SAVE10`.** دوباره red: تابع کد را نادیده می‌گیرد و قیمت کامل را برمی‌گرداند.

```text
Total = 1000, <nil>; want 900, nil
```

تنبل‌ترین راه‌حل یک `if code == "SAVE10"` ثابت بود. زشت است، ولی سبز است و این گام همین را می‌خواهد.

**گام ۴: کد ناشناخته باید `ErrUnknownCode` بدهد.** red و بعد یک `else if`.

**گام ۵: refactor.** حالا زنجیره‌ی `if` اذیتم می‌کند، پس آن را با یک map عوض کردم و یک تست برای کد دوم، `SAVE25`، اضافه کردم:

```go
var discounts = map[string]int{"SAVE10": 10, "SAVE25": 25}

percent, ok := discounts[code]
if !ok {
	return 0, ErrUnknownCode
}
return sum * (100 - percent) / 100, nil
```

اجرای تست‌ها نشان می‌دهد هر پنج تست سبزند:

```text
=== RUN   TestTotalEmpty
--- PASS: TestTotalEmpty (0.00s)
=== RUN   TestTotalSumsItems
--- PASS: TestTotalSumsItems (0.00s)
=== RUN   TestTotalWithDiscountCode
--- PASS: TestTotalWithDiscountCode (0.00s)
=== RUN   TestTotalUnknownCode
--- PASS: TestTotalUnknownCode (0.00s)
=== RUN   TestTotalSecondCode
--- PASS: TestTotalSecondCode (0.00s)
PASS
```

refactor امن بود چون تست‌ها از قبل وجود داشتند. اگر موقع بازنویسی محاسبه‌ی تخفیف را خراب کرده بودم، یکی از این پنج تست در کمتر از یک ثانیه خبرم می‌کرد. برای این مقاله مرحله‌های red را در یک نسخه‌ی موقت با Go 1.27.3 دوباره اجرا کردم و پیام‌های بالا همان چیزی است که چاپ شد.

**نظر من:** TDD را برای منطقی به کار می‌برم که قانون روشن دارد، مثل قیمت‌گذاری یا parse. وقتی هنوز دارم یک API ناشناخته را کاوش می‌کنم به کارش نمی‌برم، چون برای طراحی‌ای تست می‌نویسم که شاید دور بریزمش.

## Test double: stub، fake، mock

`orders.Service` با پایگاه داده‌ی واقعی حرف نمی‌زند. با یک interface به اسم `Repository` حرف می‌زند و در تست‌ها چیز دیگری به دستش می‌دهیم. هر چیزی که در تست جای یک وابستگی واقعی را بگیرد {{< term "test-double" "test double" >}} نام دارد. (اینکه وابستگی را از بیرون به سرویس بدهیم، به‌جای اینکه داخل خودش بسازیم، {{< term "dependency-injection" "تزریق وابستگی" >}} نامیده می‌شود.)

سه نوع رایج دارد و برای interface مربوط به `Repository` از هر کدام یکی نوشتم:

- **Stub:** جواب‌های از پیش تعیین‌شده می‌دهد و منطقی ندارد. `failingRepo{err}` همیشه از `Save` خطا برمی‌گرداند. تست می‌بیند که سرویس این خطا را بالا به فراخواننده می‌دهد.
- **Fake:** یک پیاده‌سازی ساده‌شده که واقعاً کار می‌کند. مال من یک map در حافظه است. تست یک سفارش ثبت می‌کند، بعد آن را از fake می‌خواند و مبلغ ذخیره‌شده را بررسی می‌کند.
- **Mock:** ثبت می‌کند چه فراخوانی‌هایی انجام شده تا تست بعداً راستی‌آزمایی‌شان کند. وقتی خودِ فراخوانی همان نتیجه‌ای است که می‌خواهید (مثلاً «ایمیل فرستاده شد») مفید است. در غیر این صورت پرخطر است و بخش بعد نشان می‌دهد چرا.

## تست بیش‌ازحد دقیق

کنار تست مبتنی بر fake یک تست mock هم نوشتم. این تست بررسی می‌کند که `Place` دقیقاً با این ترتیب repository را صدا بزند: `[Count Save]`. در آن زمان `Place` از repository می‌خواست سفارش‌های موجود را بشمارد تا شناسه‌ی جدید بسازد. هر دو تست سبز بودند.

بعد `Place` را refactor کردم تا شناسه‌ها را با یک شمارنده‌ی داخل خود سرویس بسازد و دیگر از repository نخواهد بشمارد. این جایگزین یک تغییر داخلی بی‌خطر است. این طراحی را خودم منتشر نمی‌کنم، ولی مشکل را خوب نشان می‌دهد. از بیرون هیچ چیز عوض نشده: همان سفارش با همان مبلغ ذخیره می‌شود. اجرا این است:

```text
--- PASS: TestPlaceStoresOrder (0.00s)
--- PASS: TestPlaceReturnsSaveError (0.00s)
    service_test.go:42: calls = [Save], want [Count Save]
--- FAIL: TestPlaceCallSequence (0.00s)
```

دو تستی که نتیجه را بررسی می‌کنند هنوز سبزند. تست mock می‌شکند، چون بررسی نکرده بود کد برای فراخواننده چه کار می‌کند؛ بررسی کرده بود کد چطور آن کار را می‌کند. «بیش‌ازحد دقیق» یعنی همین: تست به پیاده‌سازی امروز چسبیده است و هر پاک‌سازی‌ای، حتی درست، آن را می‌شکند. بعد از چند بار تکرار، آدم‌ها یا دست از refactor می‌کشند یا به red اعتماد نمی‌کنند.

**نظر من:** چیزی را assert کنید که فراخواننده می‌بیند، نه مسیری که کد برای رسیدن به آن رفته.

## یک تست flaky

{{< term "flaky-test" "تست flaky" >}} تستی است که با همان کد گاهی سبز می‌شود و گاهی قرمز. یک نمونه‌ی کوچک: یک `Session` بعد از مدتی (ttl) منقضی می‌شود و تست فرض می‌کند ۱ms کار هیچ‌وقت بیشتر از ۱.۲۵ms طول نمی‌کشد، آن هم روی sessionی که ساعت را واقعاً با `time.Now` می‌خواند:

```go
s := New(1250 * time.Microsecond)
time.Sleep(time.Millisecond) // the "work"
if s.Expired() { t.Fatal("session expired too early") }
```

روی ماشین بیکار این تست تقریباً همیشه سبز است. ولی `time.Sleep(time.Millisecond)` فقط قول می‌دهد دست‌کم ۱ms بخوابد. اگر ماشین مشغول باشد ممکن است دیرتر از ۱.۲۵ms بیدار شود و تست به دلیلی بشکند که ربطی به کد ندارد.

در اجرای اولیه `go test -count=50` را (که تست را ۵۰ بار اجرا می‌کند) چهار بار روی لپ‌تاپی که زیر بار بود اجرا کردم، با load average حدود ۵. تعداد شکست‌ها ۰، ۸، ۱ و ۰ بود. برای این ویرایش سه بار دیگر اجرایش کردم و ۱، ۰ و ۰ دیدم. عددها هر بار فرق می‌کنند و نکته همین است: کد یکی، نتیجه‌ها متفاوت.

راه‌حل این است که وابستگی به زمان واقعی را برداریم. ساعت را به‌صورت پارامتر می‌دهیم: `New(ttl, now func() time.Time)`. کد تولید `time.Now` را می‌دهد و تست یک ساعت ساختگی می‌دهد که با دست جلو می‌برد. در اجرای اولیه سه بار اجرای `-race -count=50` همه سبز شد. این بار هم نسخه‌ی اصلاح‌شده سبز شد (`ok`، ۵۰ اجرا)، چون دیگر چیزی به زمان واقعی وابسته نیست.

## Coverage یک نشانه است

Coverage گزارش می‌دهد کدام خط‌ها هنگام اجرای تست‌ها اجرا شده‌اند. شبیه معیار کیفیت به نظر می‌رسد، ولی فقط اجرا را می‌سنجد. این هم تابعی که باگ دارد:

```go
func BulkPrice(unit, qty int) int {
	if qty >= 10 {
		return unit * qty * 10 / 100 // bug: should be * 90 / 100
	}
	return unit * qty
}
```

تخفیف باید باعث شود مشتری ۹۰٪ قیمت را بدهد، ولی کد در ۱۰٪ ضرب می‌کند. حالا تستی را در نظر بگیرید که فقط `BulkPrice(100, 1)` و `BulkPrice(100, 10)` را صدا می‌زند و نتیجه را اصلاً بررسی نمی‌کند. همه‌ی خط‌ها اجرا می‌شوند، پس `go test -cover` چاپ می‌کند `coverage: 100.0% of statements` و تست سبز است. باگ زنده می‌ماند. حالا یک assert اضافه کنید و دوباره اجرا کنید:

```text
price_test.go:12: BulkPrice(100, 10) = 100, want 900
```

assert آن را می‌گیرد: ۱۰ واحد ۱۰۰ تایی باید ۹۰۰ شود ولی تابع ۱۰۰ برمی‌گرداند. پس coverage می‌گوید چه چیزی هرگز اجرا نشده، و این برای پیداکردن کد بدون تست مفید است. ولی نمی‌گوید چه چیزی واقعاً راستی‌آزمایی شده.

## دام‌های تست‌نویسی

- **اول سراغ mock رفتن.** fake و stub را ترجیح دهید. فقط وقتی از mock استفاده کنید که خودِ تعامل الزام است، چون mock تست را به پیاده‌سازی می‌چسباند.
- **نادیده‌گرفتن تست flaky.** آن را باگ بدانید، نه نویز. اگر آدم‌ها یاد بگیرند «دوباره اجرا کن تا سبز شود»، یک شکست واقعی هم با دوباره اجرا کردن گم می‌شود.
- **دنبال عدد coverage دویدن.** به‌عنوان نشانه برای پیداکردن کدی که کسی تستش نکرده خوب است. به‌عنوان هدف، تست‌هایی را تشویق می‌کند که کد را اجرا می‌کنند بی‌آنکه چیزی را بررسی کنند.
- **TDD را دین کردن.** ابزار است. اگر همه‌ی بقیه را کنار بگذارم، refactor زیر تست‌های سبز را نگه می‌دارم.

## تمرین

کد `FREESHIP` را اضافه کنید که فقط برای جمع بالای ۵۰۰۰ سنت معتبر است، با red-green-refactor. بعد یک تست mock و یک تست fake برایش بنویسید. اسم یک helper داخلی را عوض کنید و ببینید کدام‌یک از آن دو می‌شکند.

## قدم بعدی

«تست خاصیت‌محور»: همه‌ی ورودی‌های این مقاله را من دستی انتخاب کردم، یعنی فقط باگ‌هایی را پیدا کردیم که به ذهنمان رسیده بود. آنجا خود کامپیوتر ورودی می‌سازد.
