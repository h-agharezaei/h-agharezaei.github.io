فرض کنید به یک همکار می‌گویید: «فایل `config.go` را همان‌طور که دیروز بود برایم بیاور.» گیت چطور آن را پیدا می‌کند؟ و چرا بعد از یک rebase، commitهایی که ظاهرشان همان است شناسه‌ی دیگری دارند؟

بیشتر ما گیت را مثل فهرستی از دستورها یاد می‌گیریم، و اولین باری که یک rebase خراب می‌شود می‌ترسیم. اما زیر این دستورها چیز خیلی ساده‌ای هست: یک انبار کلید-مقدار (**key-value store**)، یعنی جایی که هر مقدار را با یک کلید ذخیره می‌کنند و بعد با همان کلید پس می‌گیرند. در گیت کلید همیشه هش خودِ محتواست. یعنی محتوای یکسان همیشه کلید یکسان می‌گیرد، و هیچ commitی بعد از ساخته‌شدن دیگر عوض نمی‌شود. وقتی این دو جمله را بدانید، `commit` و `branch` و `rebase` دیگر جادو نیستند. برای همین این سری ده‌تایی از همین‌جا شروع می‌کند.

> همه‌ی دستورهای زیر با git نسخه‌ی 2.39.2 در یک repository موقت اجرا شده‌اند و خروجی‌ها از همان اجراها کپی شده‌اند. نام نویسنده و تاریخ را با متغیرهای محیطی ثابت کرده‌ام تا هش commitها تکرارپذیر باشد. اگر شما با نام و ساعت خودتان اجرا کنید، هش commitها فرق می‌کند؛ ولی هش blob و tree فقط به محتوا بستگی دارد و همان می‌ماند.

## ذخیره‌سازی بر اساس محتوا

اول ببینیم «هش محتوا» یعنی چه. یک تابع hash هر ورودی را می‌گیرد و یک رشته‌ی ثابت‌طول تحویل می‌دهد که مثل اثر انگشت آن ورودی است. گیت به‌طور پیش‌فرض از {{< term "sha-1" "SHA-1" >}} استفاده می‌کند و خروجی‌اش ۴۰ کاراکتر hex است. دستور `git hash-object` همین هش را برای ما حساب می‌کند. سه بار آن را اجرا می‌کنیم، دو بار روی `hello` و یک بار روی `hello!`:

```bash
echo 'hello'  | git hash-object --stdin
echo 'hello'  | git hash-object --stdin
echo 'hello!' | git hash-object --stdin
```

```text
ce013625030ba8dba906f756967f9e9ca394464a
ce013625030ba8dba906f756967f9e9ca394464a
4effa19f4f75f846c3229b9dbdbad14eff362f32
```

دو خط اول یکی‌اند، چون محتوا یکی بود. خط سوم، با یک علامت تعجب بیشتر، هش کاملاً متفاوتی دارد. پس هش از روی محتوا ساخته می‌شود و فقط به محتوا بستگی دارد. تا این‌جا گیت چیزی ذخیره نکرده است؛ فقط هش را حساب کرده است.

با گزینه‌ی `-w` گیت محتوا را هم در پوشه‌ی `.git/objects` می‌نویسد. بعد می‌توانیم از روی هش بپرسیم آن چیست: `-t` نوعش را می‌گوید، `-s` اندازه‌اش را، و `-p` محتوایش را چاپ می‌کند:

```bash
H=$(echo 'hello' | git hash-object -w --stdin)
git cat-file -t $H   # type
git cat-file -s $H   # size
git cat-file -p $H   # pretty-print
```

```text
blob
6
hello
```

نوع این چیز `blob` است (کمی بعد می‌گویم یعنی چه)، اندازه‌اش ۶ بایت است (پنج حرف `hello` و یک خط جدید که `echo` آخرش می‌گذارد)، و محتوایش همان `hello` است.

## یک loose object فقط یک فایل فشرده است

هر چیزی که گیت نگه می‌دارد یک **object** است، و objectهای تازه‌نوشته‌شده یک فایل معمولی روی دیسک‌اند. اسم فایل همان هش است، با این تفاوت که دو کاراکتر اولش اسم پوشه می‌شود و بقیه اسم فایل:

```text
.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a
```

(این تقسیم کار را بین چند پوشه پخش می‌کند، تا همه‌ی objectها در یک پوشه نباشند.) به چنین فایلی **loose object** می‌گویند. فایل با zlib فشرده شده است، پس با ویرایشگر معمولی خوانا نیست. برای اینکه ببینیم داخلش چیست، با یک قطعه کد کوچک پایتون بازش می‌کنم:

```bash
python3 -c "import zlib;print(repr(zlib.decompress(open('.git/objects/ce/013625030ba8dba906f756967f9e9ca394464a','rb').read())))"
```

```text
b'blob 6\x00hello\n'
```

قالب واقعی این است: نوع (`blob`)، یک فاصله، اندازه (`6`)، یک بایت NUL (در خروجی `\x00`) و بعد خود محتوا (`hello\n`). هش را هم روی کل همین رشته حساب می‌کنند، با header. ببینید چه چیزی در آن نیست: نه اسم فایل و نه تاریخ. فقط محتوا کلید را تعیین می‌کند. برای همین دو فایل با نام‌های مختلف و محتوای یکسان در گیت یک object هستند.

## سه نوع object

اسم این نوع `blob` بود. هر {{< term "git-object" "Git object" >}} یکی از چند نوع است، و فعلاً سه‌تایش را لازم داریم:

- **{{< term "blob" "blob" >}}** فقط محتوای یک فایل است، بدون اسم و بدون هیچ چیز دیگر.
- **{{< term "git-tree" "tree" >}}** یک پوشه است: فهرستی از نام، mode و هش، که هر خطش به یک blob یا یک tree دیگر اشاره می‌کند. (mode نوع ورودی را نشان می‌دهد؛ مثلاً `100644` یعنی فایل معمولی و `040000` یعنی پوشه.)
- **{{< term "commit" "commit" >}}** به یک tree اشاره می‌کند (همان عکس کل پروژه در یک لحظه، یعنی snapshot) و علاوه بر آن والد یا والدها، author، committer و پیام را دارد.

پس یک commit در واقع یک زنجیره‌ی کوچک است: commit به tree ریشه اشاره می‌کند، آن tree به blobها و treeهای زیرپوشه‌ها، و همه با هش.

## ساختن دستی یک commit

بهترین راه برای باور کردن این ساختار این است که خودمان یک commit را بدون `git add` و `git commit` بسازیم. دستورهای روزمره از دستورهای سطح پایین‌تری ساخته شده‌اند که اسمشان **{{< term "plumbing" "plumbing" >}}** (لوله‌کشی) است. ما فقط از همین‌ها استفاده می‌کنیم. فرض کنید دو فایل `hello.txt` و `src/main.go` داریم و اول آن‌ها را در index می‌گذاریم (index همان جایی است که commit بعدی از آن ساخته می‌شود؛ مقاله‌ی بعد درباره‌اش است). بعد `git write-tree` از روی index یک tree می‌نویسد:

```bash
git update-index --add hello.txt src/main.go
T=$(git write-tree)
git cat-file -p $T
```

```text
100644 blob ce013625030ba8dba906f756967f9e9ca394464a	hello.txt
040000 tree b9270df7070cc6a5e7dbdec610a7ce4f54c47b20	src
```

دو خط داریم، یک خط برای هر ورودیِ پوشه‌ی ریشه. `hello.txt` یک blob است و هشش همان `ce0136…` است که قبلاً دیدیم، چون محتوایش همان `hello` است. `src` یک tree دیگر است، یعنی خودش فهرستی دارد که `main.go` در آن است. شناسه‌ی این tree ریشه `337d9a8…` شد.

حالا با `git commit-tree` یک commit می‌سازیم که به این tree اشاره کند، و با `git update-ref` اسم `main` را به آن وصل می‌کنیم:

```bash
C1=$(echo 'first commit' | git commit-tree $T)
git update-ref refs/heads/main $C1
git cat-file -p $C1
git log --oneline
```

```text
tree 337d9a8168ca5a97d9d3d9e24a6fe18e4a5cf75c
author Roham <roham@example.com> 1793169000 +0330
committer Roham <roham@example.com> 1793169000 +0330

first commit
c6c5da0 first commit
```

بخش اول خروجی خودِ commit است. اولین خطش `tree` است، یعنی همان snapshot. بعد author و committer می‌آیند با زمان (ثانیه از سال ۱۹۷۰، به‌علاوه‌ی اختلاف ساعت) و بعد از یک خط خالی، پیام. جای خط `parent` خالی است، چون این اولین commit است و والدی ندارد. خط آخر خروجی `git log --oneline` است که هش کوتاه شده‌ی commit را با پیامش نشان می‌دهد.

نکته‌ی مهم این است که branch در این مثال فقط یک فایل کوچک بود که هش یک commit در آن نوشته شد. برای همین ساختن branch آنی است. چطور کار می‌کند، موضوع مقاله‌ی سوم این سری است.

## تاریخچه یک گراف است

حالا چند commit دیگر اضافه می‌کنیم تا شکل تاریخچه را ببینیم. یک commit دوم روی `main` ساختم که با `-p $C1` والدش را مشخص کرده بود، و یک commit سوم روی branchی به اسم `side` که از همان والد اول جدا می‌شود. `git log --graph --oneline --all` شکلش را می‌کشد:

```text
* 66ddd7b second commit
| * 8798212 side work
|/  
* c6c5da0 first commit
```

هر `*` یک commit است. دو commit بالایی هر دو از `first commit` ادامه پیدا کرده‌اند، پس تاریخچه از آن نقطه دو شاخه شده است.

هر commit به والدهایش اشاره می‌کند، نه برعکس. یعنی از هر commit می‌شود به عقب رفت، ولی commit قدیمی‌تر هیچ خبری از بعدی‌هایش ندارد. اگر این اشاره‌ها را دنبال کنیم یک **{{< term "dag" "DAG" >}}** به دست می‌آید، یعنی یک گراف جهت‌دار بدون دور. جهت‌دار چون هر اشاره یک سو دارد (از فرزند به والد)، و بدون دور چون با رفتن به والدها هیچ‌وقت به نقطه‌ی شروع برنمی‌گردیم. commit مرج هم چیز خاصی نیست: فقط commitی است که به‌جای یک والد، دو والد دارد.

## چرا تاریخچه تغییرناپذیر است

حالا می‌توانیم به سؤال اول برگردیم: چرا بعد از rebase شناسه‌ها عوض می‌شوند؟ هر commit هش والدش را در خودش دارد، و هش commit روی کل محتوایش حساب می‌شود. پس اگر چیزی بالادست عوض شود، هش آن commit عوض می‌شود، و چون فرزندش هش او را در خودش دارد، هش فرزند هم عوض می‌شود، و همین‌طور تا آخر.

برای دیدنش دو commit ساختم، `A` و بعد `B` که والدش `A` است. بعد دوباره همین کار را کردم، فقط این بار پیام `A` را از `first` به `first!` تغییر دادم. tree و پیام `B` را همان نگه داشتم:

```text
original:  A=5dbfa36  B=dc8cab0
rewritten: A=2cfd71a  B=23bdee6
```

هش `A` عوض شد، که انتظارش را داشتیم. ولی هش `B` هم عوض شد، با اینکه tree و پیامش دقیقاً همان بود. تنها فرق این است که والدش `A` دیگری است. پس «بازنویسی تاریخچه» در گیت هیچ چیزی را ویرایش نمی‌کند. commitهای تازه می‌سازد و branch را به آن‌ها می‌برد. commitهای قدیمی همان‌جا در object database می‌مانند، تا وقتی که گیت بعداً objectهای بی‌استفاده را پاک کند. این هم دلیل این است که rebase هش همه‌ی commitهای بعد از نقطه‌ی ویرایش را عوض می‌کند.

## SHA-1 و SHA-256

گیت به‌طور پیش‌فرض از SHA-1 استفاده می‌کند که هشش ۴۰ کاراکتر hex است. گیت من گزینه‌ی `git init --object-format=sha256` را هم دارد، و همان blob با محتوای `hello\n` آن‌جا یک شناسه‌ی ۶۴ کاراکتری می‌گیرد:

```text
2cf8d83d9ee29543b34a87727421fdecb7e3f3a183d337639025de576db9ebb4
```

طبق مستندات گیت، repositoryهای SHA-256 با repositoryهای SHA-1 سازگار نیستند. برای همین فعلاً برای کار عادی به آن‌ها تکیه نمی‌کنم. push یا میزبانی چنین repositoryی را امتحان نکرده‌ام.

## پیامدهای این مدل

این مدل چند نتیجه‌ی عملی دارد که بعداً بارها به آن‌ها برمی‌گردیم:

- **هش، header و محتوا را با هم پوشش می‌دهد.** پس بایت‌های یکسان روی هر ماشین یک object یکسان‌اند.
- **commit یک snapshot را نگه می‌دارد، نه یک diff.** یعنی یک tree کامل. وقتی `git diff` یا `git show` می‌زنید، گیت تفاوت را همان لحظه حساب می‌کند.
- **اسم فایل در tree است، نه در blob.** پس دو فایل با محتوای یکسان یک blob مشترک دارند.
- **branch و tag فقط اشاره‌گر به commit هستند.** برای همین ارزان‌اند.
- **`.git/objects` را خارج از یک repository آزمایشی دستی ویرایش نکنید.** این پوشه را گیت مدیریت می‌کند و دست‌کاری‌اش ممکن است repository را خراب کند.

## تمرین

در یک پوشه‌ی موقت `git init` بزنید. با `git hash-object -w` یک blob بسازید، با `git mktree` یا با index یک tree، و با `git commit-tree` یک commit. با `git update-ref` یک branch به آن اشاره دهید و `git log` را ببینید. بعد یکی از objectها را با پایتون باز کنید و header آن را پیدا کنید.
