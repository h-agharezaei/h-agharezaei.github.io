یک فایل را ویرایش می‌کنید و `git add` می‌زنید. بعد یادتان می‌آید یک خط دیگر هم باید عوض شود و دوباره فایل را ویرایش می‌کنید. حالا `git status -s` کنار اسم فایل `MM` نشان می‌دهد، و `git diff` فقط همان خط آخر را نشان می‌دهد، انگار آن اولی هیچ‌وقت نبوده است. یا یک نمونه‌ی ساده‌تر: درست بعد از `git add`، دستور `git diff` هیچ چیزی چاپ نمی‌کند و آدم فکر می‌کند تغییرش گم شده.

این‌ها همه به یک سؤال برمی‌گردند که تازه‌واردها همیشه می‌پرسند: چرا اول `git add` و بعد `git commit`؟ جوابش این است که گیت دو جا برای فایل‌هایتان ندارد، سه جا دارد. زیر آن‌ها هم objectهایی هستند که [مقاله‌ی قبل](/fa/posts/git-how-git-thinks/) نشان داد و اسمشان هش محتواست. در این مقاله این سه جا را یکی‌یکی می‌بینیم و بعد سراغ چیزهایی می‌رویم که با آن‌ها ممکن می‌شود: stage کردن بخشی از یک فایل، برگرداندن تغییر، `.gitignore` و `git stash`.

> همه‌ی دستورهای زیر با Git نسخه‌ی 2.39.2 در repositoryهای موقت اجرا شده‌اند و خروجی‌ها از همان اجراها کپی شده‌اند. هش‌های commit در هر اجرا فرق می‌کنند، چون به نام و زمان بستگی دارند؛ اگر در خروجی‌ای هش commit دیدید، فقط شکلش مهم است.

## سه ناحیه

ایده‌ی اصلی این است: گیت بین فایل‌هایی که روی دیسک ویرایش می‌کنید و commit، یک مرحله‌ی میانی دارد. این سه جا را داریم:

1. **{{< term "working-tree" "Working tree" >}}**: فایل‌های روی دیسک، همان‌هایی که با ویرایشگر باز می‌کنید.
2. **{{< term "staging-area" "Index" >}}** (به آن staging area هم می‌گویند): عکسی از چیزی که commit بعدی خواهد داشت.
3. **{{< term "head" "HEAD" >}}**: آخرین commit، یعنی آخرین عکس ثبت‌شده.

یک تشبیه ساده: فرض کنید می‌خواهید از چند چیز عکس خانوادگی بگیرید. working tree صحنه‌ی واقعی است که مدام عوض می‌شود. index جایی است که دارید آدم‌ها را سر جایشان می‌چینید. commit لحظه‌ای است که دکمه‌ی دوربین را می‌زنید. تا چیدن تمام نشده، لازم نیست هر چه روی صحنه هست در عکس بیفتد.

سه دستور بین این جاها جابه‌جایی می‌کنند. `git add` محتوای فایل را از working tree به index می‌برد. `git commit` از روی index یک commit می‌سازد. و ویرایش یک فایل هرگز خودبه‌خود index را عوض نمی‌کند؛ باید دوباره `git add` بزنید.

## خواندن `git status -s`

حالا که سه جا داریم، می‌شود فهمید خروجی کوتاه `git status -s` چه می‌گوید. هر خط دو ستون دارد: ستون اول **index را با HEAD** مقایسه می‌کند (چه چیزی stage شده)، و ستون دوم **working tree را با index** (چه چیزی هنوز stage نشده). حالت‌های یک فایل را به ترتیب می‌بینیم:

```text
?? app.txt          # new file, untracked
A  app.txt          # after git add: staged as a new file
 M app.txt          # after commit and an edit: modified, not staged
MM app.txt          # staged, then edited again
```

- `??` یعنی گیت فایل را نمی‌شناسد (untracked).
- `A ` با فاصله‌ی ستون دوم یعنی فایل جدید stage شده و بعد از آن تغییری نکرده.
- ` M` با فاصله‌ی ستون اول یعنی فایل commit شده بود، ویرایش شد، و هنوز stage نشده.
- `MM` یعنی هر دو: بخشی از تغییر stage شده و بعد از آن باز هم ویرایش شده.

`MM` را یادتان بماند: فایل در هر دو جا فرق دارد، یعنی از آن فایل همزمان دو نسخه‌ی متفاوت وجود دارد.

## سه نوع diff

این دو نسخه را چطور ببینیم؟ `git diff` بسته به آرگومان، جفت‌های مختلفی از این سه جا را مقایسه می‌کند. برای دیدنش، فایلی با سه خط commit کردم، `line 4` را اضافه و stage کردم، و بعد `line 5` را بدون stage اضافه کردم. حالا فایل سه نسخه دارد: در HEAD (سه خط)، در index (چهار خط) و روی دیسک (پنج خط). هر سه دستور diff را زدم:

```text
$ git diff            # working tree vs index
+line 5
$ git diff --staged   # index vs HEAD
+line 4
$ git diff HEAD       # working tree vs HEAD
+line 4
+line 5
```

(هدر و شماره‌ی خط‌های diff را حذف کرده‌ام و فقط خط‌های تغییر مانده‌اند.) به ترتیب:

- `git diff` ساده دیسک را با index مقایسه می‌کند، پس فقط `line 5` را نشان می‌دهد؛ همان چیزی که هنوز stage نشده.
- `git diff --staged` index را با HEAD مقایسه می‌کند، یعنی چیزی که اگر همین حالا commit کنید وارد می‌شود: `line 4`.
- `git diff HEAD` دیسک را مستقیم با آخرین commit مقایسه می‌کند و هر دو تغییر را می‌بیند.

برای همین `git diff` ساده بلافاصله بعد از `git add` خالی است: تغییر در index هم هست و بین دیسک و index فرقی نمانده.

## index واقعاً چه چیزی نگه می‌دارد

گفتیم index یک «عکس» است. دقیقاً چه در آن نوشته شده؟ `git ls-files -s` محتوایش را فهرست می‌کند. این خروجی مربوط به همان فایل مثال بالاست، وقتی `line 4` stage شده بود:

```text
$ git ls-files -s
100644 9c2a7090627d0fffa9ed001bf7be98f86c2c8068 0	app.txt
```

هر ورودی چهار چیز دارد: mode فایل (`100644` یعنی فایل معمولی)، شناسه‌ی یک **{{< term "blob" "blob" >}}**، شماره‌ی stage (صفر یعنی conflict ندارد) و مسیر. blob همان object مقاله‌ی قبل است، یعنی محتوای فایل با هش آن. همان لحظه‌ی `git add` در object database نوشته شد. اگر `git cat-file -p 9c2a709…` را بزنیم، خط‌های `line 1` تا `line 4` چاپ می‌شود، بدون `line 5`.

پس `git add` همان لحظه محتوای فایل را ذخیره می‌کند، و commit فقط فهرست index را به یک tree و یک commit تبدیل می‌کند. برای همین اگر بعد از `add` فایل را عوض کنید، commit همان نسخه‌ی قبلی را ثبت می‌کند.

## stage کردن بخشی از فایل با `git add -p`

این جدایی index از دیسک یک کاربرد خیلی مفید دارد: می‌توانید از یک فایل فقط بخشی از تغییرها را وارد commit کنید. گیت diff را به تکه‌هایی به اسم **{{< term "hunk" "hunk" >}}** تقسیم می‌کند و با `git add -p` برای هر تکه می‌پرسد stage شود یا نه.

برای امتحان، فایلی ۲۰ خطی commit کردم و خط ۲ و خط ۱۹ را عوض کردم. چون این دو تغییر از هم دور هستند، گیت دو hunk می‌سازد (`@@ -1,5 +1,5 @@` و `@@ -16,5 +16,5 @@`). به hunk اول `y` (بله) و به دومی `n` (نه) می‌گوییم، و بعد commit می‌کنیم:

```text
$ printf 'y\nn\n' | git add -p
$ git status -s
MM f.txt
$ git commit -qm "change line 2"
$ git diff | grep '^[+-]line'
-line 19
+line 19 CHANGED
$ git commit -qam "change line 19"
```

بعد از `add -p` فایل `MM` است: تغییر خط ۲ در index است و تغییر خط ۱۹ فقط روی دیسک. بعد از commit اول، `git diff` فقط تغییر خط ۱۹ را نشان می‌دهد، که یعنی همان چیزی که stage نکرده بودیم هنوز روی دیسک مانده بود. commit دوم آن را هم ثبت می‌کند (`-a` یعنی همه‌ی فایل‌های tracked، `-q` یعنی بی‌سروصدا).

نتیجه: دو تغییر مستقل، دو commit. در `git log --stat` هر کدام `1 insertion(+), 1 deletion(-)` دارد. این راهی است که حتی وقتی هم‌زمان روی دو کار ویرایش کرده‌اید، commitها کوچک و هرکدام برای یک کار می‌مانند.

## برگرداندن: `restore`

حالا برعکسش: تغییری را که نمی‌خواهید چطور پس بگیرید؟ دستور `git restore` دو حالت دارد:

```text
$ git restore --staged f.txt   # index back to HEAD, edits stay on disk
$ git restore f.txt            # disk back to the index
```

هر دو را به ترتیب روی فایلی اجرا کردم که یک خط stage‌شده و یک خط stage‌نشده داشت. اولی (`--staged`) فقط index را به HEAD برمی‌گرداند. فایل ` M` شد و هر دو خط هنوز روی دیسک بودند، یعنی چیزی از کار شما گم نشد و فقط از stage بیرون آمد. دومی چیزی چاپ نکرد، با کد ۰ تمام شد، و دیسک را به حالت index برگرداند. چون index در آن لحظه با HEAD برابر بود، هر دو خط اضافه از بین رفتند.

به دومی دقت کنید: گیت هیچ سؤالی نپرسید. تغییری که نه stage شده و نه commit، جای دیگری ندارد. پس `git restore <file>` را نمی‌شود برگرداند.

## `.gitignore` و `git rm --cached`

یک اشتباه رایج: فایلی را که نباید وارد repository می‌شد commit می‌کنید و بعد می‌خواهید آن را ignore کنید. در یک repository آزمایشی `.env` و `build/out` را عمداً commit کردم، `.env` را کمی ویرایش کردم، و بعد یک {{< term "gitignore" ".gitignore" >}} با این سه خط ساختم: `.env`، `build/` و `*.log`.

انتظار داشتم `.env` دیگر دیده نشود، اما هنوز ` M .env` نشان می‌داد. و `git check-ignore -v .env` هیچ چیزی چاپ نکرد. دلیلش این است که قانون ignore فقط روی فایل‌های untracked اثر دارد، یعنی فایل‌هایی که گیت هنوز نمی‌شناسد. فایلی که یک بار commit شده، tracked است و ignore تأثیری روی آن ندارد.

برای اینکه گیت دیگر فایل را دنبال نکند ولی روی دیسک بماند، `--cached` را می‌زنیم، یعنی فقط از index حذف کن:

```text
$ git rm --cached -q .env
$ git rm -r --cached -q build
$ git status -s
D  .env
D  build/out
?? .gitignore
$ git check-ignore -v .env a.log
.gitignore:1:.env	.env
.gitignore:3:*.log	a.log
```

`D ` در ستون اول یعنی «از index حذف شد» (در commit بعدی فایل از repository می‌رود) و `.gitignore` هنوز untracked است. حالا `git check-ignore -v` برای هر فایل ignore‌شده فایل قانون، شماره‌ی خط و الگوی مطابق را نشان می‌دهد؛ برای `.env` خط اول و برای `a.log` الگوی `*.log` در خط سوم. `a.log` از اول untracked بود، پس قانون `*.log` از همان ابتدا روی آن اثر می‌کرد. بعد از این دستورها هر دو فایل `.env` و `build/out` هنوز روی دیسک بودند.

یک هشدار: این کار فایل را از commitهای بعدی بیرون می‌برد، نه از تاریخچه. اگر `.env` راز واقعی داشت، در commitهای قدیمی هنوز هست؛ آن راز را عوض کنید.

## کنار گذاشتن کار با `git stash`

گاهی وسط کار باید به چیز دیگری بپردازید و نمی‌خواهید نیمه‌کاره commit کنید. `git stash` تغییرهای tracked را کنار می‌گذارد و working tree را تمیز می‌کند، و `git stash pop` برمی‌گرداند. در همان repository، `main.go` را ویرایش کردم و یک فایل جدید `scratch.txt` هم ساختم:

```text
$ git stash
Saved working directory and index state WIP on main: 34282f1 stop tracking
$ git status -s
?? scratch.txt
$ git stash pop
```

{{< term "stash" "stash" >}} ساده `main.go` را برداشت اما `scratch.txt` را که untracked بود جا گذاشت. گزینه‌ی `-u` فایل‌های untracked را هم برمی‌دارد: با `git stash -u` هر دو برداشته شدند و درخت تمیز شد، `git stash list` یک ورودی نشان داد، و `pop` همه‌چیز را برگرداند. (شناسه‌ی commit که در پیام می‌بینید در هر اجرا فرق می‌کند.)

## غافلگیری‌های staging

- **`git commit -a` فقط برای فایل‌های tracked کار می‌کند.** مرحله‌ی staging را فقط برای فایل‌هایی رد می‌کند که گیت می‌شناسد؛ فایل جدید هنوز به `git add` نیاز دارد.
- **`git add -p` فایل‌های untracked را پیشنهاد نمی‌دهد.** آن‌ها را به‌طور عادی `add` کنید.
- **`git restore` روی تغییرهای stage‌نشده دائمی است.** اگر مطمئن نیستید، اول `git stash` بزنید.
- **اضافه کردن یک مسیر به `.gitignore` آن را untrack نمی‌کند.** برای فایل‌های از قبل tracked باید `git rm --cached` بزنید.
- **`git stash pop` ممکن است conflict بدهد.** طبق مستندات گیت، در آن صورت ورودی stash نگه داشته می‌شود تا کارتان از بین نرود.

## تمرین

1. یک repo بسازید، فایلی ۱۰ خطی را commit کنید، خط ۱ و خط ۱۰ را عوض کنید و با `git add -p` دو commit جدا بسازید.
2. عمداً به `MM` برسید و سه نوع `git diff` را ببینید. قبل از اجرا حدس بزنید هر کدام چه نشان می‌دهد.
3. یک فایل `.log` را commit کنید، `*.log` را ignore کنید و با `git rm --cached` آن را untrack کنید.

## قدم بعدی

مقاله‌ی بعد «branch، HEAD و ref: فقط اشاره‌گر» است. تا اینجا HEAD را فقط «آخرین commit» دیدیم؛ آنجا می‌بینیم برای گیت این اسم‌ها در واقع چه هستند.
