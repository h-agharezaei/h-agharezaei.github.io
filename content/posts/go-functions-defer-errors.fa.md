فرض کنید تابعی دارید که یک فایل را باز می‌کند، محتوایش را می‌خواند و عددی از آن بیرون می‌کشد. هر کدام از این سه مرحله می‌تواند شکست بخورد. در زبان‌هایی که استثنا (exception) دارند، شکست از وسط کد به بیرون پرتاب می‌شود و یک `try/catch` دور آن را می‌گیرد. Go راه دیگری دارد. استثنا به این معنا ندارد: تابع‌ها خطا را مثل یک مقدار معمولی برمی‌گردانند، فراخواننده بلافاصله `if err != nil` را چک می‌کند و کارِ پاک‌سازی، مثل بستن همان فایل، با `defer` انجام می‌شود.

وقتی این دو ایده را بفهمید، شکل بیشترِ کدهای Go و خیلی از سلیقه‌های این زبان معنی پیدا می‌کند. در این مقاله اول تابع‌ها را می‌بینیم (چون خطا از همان‌جا شروع می‌شود)، بعد `error`، بعد `defer`، و در آخر کوتاه درباره‌ی `panic`. پیش‌نیازش فقط [نوع‌ها، متغیرها و کنترل جریان](/fa/posts/go-types-control-flow/) است.

> همه‌ی مثال‌های زیر را با Go 1.26 اجرا کرده‌ام و خروجی‌ها از همان اجراها برداشته شده‌اند.

## تابع و چند مقدار برگشتی

در Go نوع پارامترها بعد از نامشان می‌آید، و یک تابع می‌تواند چند مقدار برگرداند. همین دومی پایه‌ی کل مدیریت خطای Go است، پس با یک مثال ساده شروع می‌کنیم. `divmod` خارج‌قسمت و باقی‌مانده را با هم برمی‌گرداند:

```go
func divmod(a, b int) (int, int) { return a / b, a % b }
```

نوع‌های برگشتی را داخل پرانتز می‌نویسیم و در جای صدازدن، دو متغیر را با هم می‌گیریم:

```go
q, r := divmod(17, 5)
fmt.Println(q, r)   // 3 2
```

۱۷ تقسیم بر ۵ می‌شود ۳ و باقی‌مانده‌ی ۲. در زبان‌های دیگر برای چنین کاری معمولاً باید آرایه یا شیء برگرداند و بعد بازش کرد. در Go همین دو مقدار مستقیم برمی‌گردند.

سه چیز دیگر درباره‌ی تابع‌ها:

```go
func sum(nums ...int) int {
	total := 0
	for _, n := range nums {
		total += n
	}
	return total
}

func counter() func() int {
	n := 0
	return func() int { n++; return n }
}
```

تابع `sum` از نوع **variadic** است، یعنی تعداد آرگومان‌هایش ثابت نیست. داخل تابع، `nums` یک slice از `int` است. می‌توانید بدون آرگومان، با چند آرگومان، یا با یک slice آماده و علامت `...` صدایش کنید. (`_` در حلقه یعنی اندیس را لازم نداریم و دور می‌اندازیمش.)

تابع‌ها خودشان هم مقدار هستند. `counter` یک تابع برمی‌گرداند، و آن تابعِ برگشتی به متغیر `n` که بیرون از خودش تعریف شده دسترسی دارد و آن را بین فراخوانی‌ها نگه می‌دارد. به چنین تابعی **closure** می‌گویند. هر بار که `counter()` را صدا بزنید، یک `n` تازه و مستقل ساخته می‌شود.

```go
fmt.Println(sum(), sum(1, 2, 3), sum([]int{4, 5}...)) // 0 6 9
next := counter()
fmt.Println(next(), next(), next())                 // 1 2 3
```

سه فراخوانی `sum` به ترتیب ۰ (بدون آرگومان)، ۶ و ۹ می‌دهند. سه بار `next()` هم ۱ و ۲ و ۳ برمی‌گرداند، چون `n` بین فراخوانی‌ها زنده می‌ماند.

مقدارهای برگشتی را می‌شود **نام‌دار** هم کرد، مثل `func f() (n int, err error)`. این متغیرها از ابتدا با مقدار صفر (zero value که در مقاله‌ی قبل دیدیم) ساخته می‌شوند و `return` خالی همین‌ها را برمی‌گرداند. نام‌دارکردن با `defer` به کار می‌آید که پایین‌تر می‌بینیم. ولی `return` خالی در یک تابع بلند باعث می‌شود خواننده دنبال جایی بگردد که مقدارها ست شده‌اند. من نام‌دارکردن را فقط برای تابع‌های کوتاه یا وقتی استفاده می‌کنم که یک تابع deferred باید نتیجه را عوض کند.

## اینترفیس error

حالا برسیم به خطا. در Go نوعی به اسم `error` داریم که در اصل فقط یک **اینترفیس** با یک متد است: `Error() string`. اینترفیس یعنی فهرستی از متدها؛ هر نوعی که آن متدها را داشته باشد، خودبه‌خود از آن اینترفیس است. (اینترفیس‌ها را در یکی از مقاله‌های بعد کامل بررسی می‌کنیم.) فعلاً کافی است بدانید خطا چیز پیچیده‌ای نیست: هر مقداری که بتواند خودش را به‌صورت یک متن توضیح بدهد.

قرارداد این است که خطا آخرین مقدار برگشتی تابع باشد و فراخواننده بلافاصله چکش کند. اگر مشکلی نبوده باشد، مقدار خطا `nil` (یعنی «هیچ‌چیز») است:

```go
n, err := strconv.Atoi(s)
if err != nil {
	return 0, err
}
```

`strconv.Atoi` یک رشته را به عدد تبدیل می‌کند. اگر نتواند، `err` پر است و ما همان را به فراخواننده‌ی خودمان پس می‌دهیم. این `if err != nil` را خیلی زیاد خواهید نوشت و این عمدی است: مسیر شکست در کد دیده می‌شود و یک `throw` پنهان وسط تابع‌ها گم نمی‌شود.

## ساختن، wrap کردن و بررسی خطا

یک خطای خالی، مثلاً «invalid syntax»، به کار خیلی نمی‌آید. وقتی چند لایه تابع بالا می‌روید، می‌خواهید بدانید کجا و در حین چه کاری شکست خورده. برای همین سه ابزار داریم:

- `errors.New` یک خطای ساده با یک متن می‌سازد.
- `fmt.Errorf` با فعل `%w` یک خطا را **wrap** می‌کند، یعنی متن و زمینه (context) تازه‌ای به آن اضافه می‌کند و خطای اصلی را هم داخل خودش نگه می‌دارد.
- `errors.Is` بررسی می‌کند که یک خطای مشخص جایی در زنجیره‌ی wrapها هست یا نه، و `errors.As` خطایی از یک نوع مشخص را در زنجیره پیدا می‌کند و به شما می‌دهد.

این برنامه‌ی کوچکی است که برای همین ساختم. سه تکه دارد. اولی یک **sentinel error** است، یعنی خطایی که در سطح پکیج یک بار تعریف می‌شود تا بعداً با آن مقایسه کنیم. دومی یک نوع خطای سفارشی است. (برای ساختنش از `struct` و متد استفاده کرده‌ام که در مقاله‌های بعد کامل می‌گویم؛ فعلاً: `struct` مجموعه‌ای از فیلدهاست و متد تابعی است که به یک نوع وصل شده. علامت `*` و `&` هم به اشاره‌گر مربوط‌اند که در [اشاره‌گرها و مدل حافظه در Go](/fa/posts/go-pointers-memory/) می‌آید.) متد `Unwrap` به `errors.Is` و `errors.As` می‌گوید خطای داخلی کجاست. سومی تابع‌هایی است که از این‌ها استفاده می‌کنند:

```go
var ErrDivideByZero = errors.New("divide by zero")

type ParseError struct {
	Input string
	Err   error
}

func (e *ParseError) Error() string { return fmt.Sprintf("parse %q: %v", e.Input, e.Err) }
func (e *ParseError) Unwrap() error { return e.Err }

func parse(s string) (int, error) {
	n, err := strconv.Atoi(strings.TrimSpace(s))
	if err != nil {
		return 0, &ParseError{Input: s, Err: err}
	}
	return n, nil
}

func divide(a, b string) (int, error) {
	x, err := parse(a)
	if err != nil {
		return 0, fmt.Errorf("divide: left operand: %w", err)
	}
	y, err := parse(b)
	if err != nil {
		return 0, fmt.Errorf("divide: right operand: %w", err)
	}
	if y == 0 {
		return 0, fmt.Errorf("divide %d by %d: %w", x, y, ErrDivideByZero)
	}
	return x / y, nil
}
```

`parse` رشته را (بعد از حذف فاصله‌های دو طرف) به عدد تبدیل می‌کند. اگر شکست بخورد، خطای `Atoi` را داخل یک `ParseError` می‌گذارد که ورودی اصلی را هم نگه می‌دارد. `divide` دو رشته می‌گیرد، هر دو را parse می‌کند و تقسیم می‌کند. اگر parse شکست بخورد، خطا را با اینکه «عملوند چپ» بود یا «راست» wrap می‌کند. اگر مخرج صفر باشد، `ErrDivideByZero` را با اعداد wrap می‌کند.

`main` چهار ورودی را امتحان می‌کند: `("84", "2")` و `("10", "0")` و `("abc", "2")` و `("7", " x1")`. برای هر خطا، پیام و نتیجه‌ی `errors.Is` و `errors.As` را چاپ می‌کند. خروجی:

```text
result: 42
error: divide 10 by 0: divide by zero
  is ErrDivideByZero: true
  is strconv.ErrSyntax: false
  as *ParseError: no
error: divide: left operand: parse "abc": strconv.Atoi: parsing "abc": invalid syntax
  is ErrDivideByZero: false
  is strconv.ErrSyntax: true
  as *ParseError: input="abc"
error: divide: right operand: parse " x1": strconv.Atoi: parsing "x1": invalid syntax
  is ErrDivideByZero: false
  is strconv.ErrSyntax: true
  as *ParseError: input=" x1"
```

بیایید ورودی به ورودی بخوانیم:

- **`84` و `2`:** خطایی نیست و نتیجه‌ی ۴۲ چاپ می‌شود.
- **`10` و `0`:** هر دو عدد درست parse می‌شوند، ولی مخرج صفر است. پیام می‌گوید `divide 10 by 0: divide by zero`. `errors.Is(err, ErrDivideByZero)` درست است و `ErrSyntax` نه، و چون `ParseError`ی در زنجیره نیست، `errors.As` جوابش «no» است.
- **`abc` و `2`:** پیام را مثل یک زنجیره بخوانید: هر لایه زمینه‌ای اضافه کرده است، از `divide: left operand` تا `parse "abc"` تا متن خطای خود `strconv`. این بار `errors.Is(err, strconv.ErrSyntax)` درست است، با اینکه خودمان هیچ‌جا اسمی از آن نیاوردیم: این تابع از میان `ParseError` ما (به‌لطف `Unwrap`) تا خطایی که `strconv` برگردانده پایین می‌رود. `errors.As` هم `ParseError` را پیدا کرده و ورودی اصلی، `abc`، را به ما داده.
- **`7` و ` x1`:** همین وضع، ولی برای عملوند راست. دقت کنید `ParseError` ورودی اصلی را با فاصله‌ی اولش نگه داشته (`" x1"`)، در حالی که `strconv` فقط `x1` را دیده، چون `parse` فاصله‌ها را قبل از تبدیل برداشته بود.

## defer

حالا پاک‌سازی. فرض کنید تابعی فایلی را باز می‌کند و بعد پنج جای مختلف می‌تواند زودتر با `return` از تابع خارج شود. در هر کدام از آن پنج جا باید یادتان باشد فایل را ببندید. `defer` این دردسر را حل می‌کند: یک فراخوانی را برای لحظه‌ی بازگشت تابع زمان‌بندی می‌کند، هر طور که تابع تمام شود. روش رایج این است که بستن منبع را درست کنار جایی بنویسید که آن را گرفته‌اید:

```go
f, err := os.Open(path)
if err != nil {
	return err
}
defer f.Close()
```

دو قاعده را باید بدانید. اول، فراخوانی‌های deferred به ترتیب **LIFO** اجرا می‌شوند: آخرین ثبت‌شده، اولین اجراشده، مثل ظرف‌هایی که روی هم می‌چینید و از بالا برمی‌دارید. دوم، آرگومان‌های یک `defer` در لحظه‌ی خودِ دستور `defer` محاسبه می‌شوند، نه وقتی که فراخوانی واقعاً اجرا می‌شود. این مثال هر دو را نشان می‌دهد:

```go
func demoDefer() {
	for i := 1; i <= 3; i++ {
		defer fmt.Println("deferred", i)
	}
	x := 10
	defer fmt.Println("x at defer time:", x)
	x = 20
	fmt.Println("x now:", x)
}
```

```text
x now: 20
x at defer time: 10
deferred 3
deferred 2
deferred 1
```

خروجی را از بالا بخوانیم. اولین خط `x now: 20` است، چون این تنها چاپی است که deferred نیست و همان لحظه اجرا می‌شود. بعد از آن، وقتی تابع تمام می‌شود، چاپ‌های deferred شروع می‌شوند، از آخرین ثبت‌شده به اولین. آخرین `defer` همان است که `x` را چاپ می‌کند، و مقدارش `10` است، نه `20`: چون آرگومان `x` همان وقتی که خط `defer` اجرا شد، کپی شد، نه وقتی چاپ واقعی انجام شد. بعد از آن سه `defer` حلقه می‌آیند، با ترتیب برعکس: ۳ و ۲ و ۱.

## کوتاه درباره‌ی panic و recover

در Go نوع دیگری از شکست هم هست: `panic`. `panic` اجرای عادی را متوقف می‌کند، تابع‌های deferred را اجرا می‌کند و برنامه را می‌اندازد، مگر اینکه داخل یکی از آن تابع‌های deferred کسی `recover` صدا بزند. مثلاً نوشتن در یک map برابر `nil` باعث panic می‌شود. در این مثال با یک مقدار برگشتی نام‌دار، panic را به یک error معمولی تبدیل می‌کنیم:

```go
func safeName() (name string, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)
		}
	}()
	var m map[string]int
	m["a"] = 1
	return "ok", nil
}
// prints:  recovered: assignment to entry in nil map
```

خط `m["a"] = 1` در map خالی می‌نویسد و panic می‌دهد. قبل از اینکه برنامه بیفتد، تابع deferred اجرا می‌شود، `recover()` پیام panic را می‌گیرد و آن را در `err` می‌گذارد. چون `err` یک مقدار برگشتی نام‌دار است، تابع در نهایت همان را برمی‌گرداند. خروجی واقعی `fmt.Println(safeName())` یک رشته‌ی خالی برای `name` و بعد پیام خطا بود، که همین خط بالاست (جای خالی اول همان `name` خالی است).

برای شکست‌های قابل انتظار، مثل ورودی بد یا فایل ناموجود، از panic استفاده نکنید و error برگردانید. panic برای باگ و حالت‌های غیرممکن است. `recover` هم بیشتر در مرزها کاربرد دارد، مثلاً سرور HTTP که نمی‌خواهد یک درخواست خراب کل برنامه را بیندازد.

## خطاهای رایج با error و defer

- **خطا را با `_` نادیده نگیرید**، مگر اینکه بتوانید دلیل امن‌بودنش را بگویید. نوشتن `n, _ := strconv.Atoi(s)` یعنی «اگر شکست خورد، نمی‌خواهم بدانم»، و بعد با `0` کار می‌کنید.
- **اگر فراخواننده ممکن است به `errors.Is` یا `errors.As` نیاز داشته باشد، با `%w` wrap کنید، نه `%v`.** `%v` فقط متن خطا را در پیام جدید می‌گذارد و خطای اصلی را از زنجیره حذف می‌کند.
- **وقتی wrap در کار است، خطاها را با `errors.Is` مقایسه کنید، نه `==`.** `==` فقط خودِ آن مقدار را می‌بیند، نه آنچه داخل wrap است.
- **`defer` داخل حلقه در پایان تابع اجرا می‌شود، نه در پایان هر تکرار.** اگر در حلقه فایل‌های زیادی باز می‌کنید، همه تا آخر تابع باز می‌مانند. بدنه‌ی حلقه را به یک تابع جدا ببرید.
- **آرگومان‌های فراخوانی deferred همان لحظه محاسبه می‌شوند**، همان‌طور که در مثال `x` دیدیم. اگر آخرین مقدار را می‌خواهید، از یک closure استفاده کنید: `defer func() { ... }()`.

## تمرین

۱. یک sentinel به نام `ErrNegative` به `divide` اضافه کنید و وقتی یکی از عملوندها منفی است آن را (wrap‌شده) برگردانید. با `errors.Is` بررسی‌اش کنید.
۲. تابع `func average(nums ...float64) (float64, error)` را بنویسید که برای ورودی خالی خطا برگرداند.
۳. تابعی بنویسید که سه `defer` با چاپ دارد؛ قبل از اجرا خروجی را حدس بزنید.
