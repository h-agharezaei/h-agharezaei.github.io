workerی را تصور کنید که وسط یک کار سه‌ثانیه‌ای است و شما نسخه‌ی جدید را deploy می‌کنید. ابزار deploy به workerِ قدیمی می‌گوید بایست و یکی تازه راه می‌اندازد. کاری که در جریان بود چه می‌شود؟ اگر workerِ قدیمی فقط بمیرد، کار نصفه می‌ماند و کسی هرگز تأییدش نمی‌کند. بعداً دوباره به کسی داده می‌شود. همان‌طور که [نوشته‌ی قبل](/fa/posts/nats-jetstream-idempotency/) گفت، رایج‌ترین راه برخورد با کار تکراری همین است.

این نوشته درباره‌ی بهتر کردن آن است: {{< term "graceful-shutdown" "خاموشی تمیز" >}} (graceful shutdown)، یعنی workerی که به او می‌گویند بایست، کار تازه نمی‌گیرد، کارهای دستش را تمام می‌کند و بعد خارج می‌شود. اول مشکل را با سیگنال‌های واقعی بازتولید می‌کنم، بعد درستش می‌کنم و بعد می‌بینم وقتی کارها زیادی طول بکشند چه می‌شود. اگر `context` برایتان تازه است، اول [sync، select و context در Go](/fa/posts/go-sync-select-context/) را بخوانید.

> همه‌چیز با Go 1.26 و یک `nats-server` توکار نسخه‌ی v2.15.1 و `nats.go` نسخه‌ی v1.54.0 اجرا شد. کد یک مثال محلی است، نه مخزن منتشرشده. زمان‌ها و شناسه‌ی پروسه‌ها در خروجی‌های زیر از اجرایی به اجرای دیگر فرق می‌کنند.

## چه چیزی را آزمایش می‌کنیم

اول چند کلمه درباره‌ی تکه‌ها، تا خروجی‌ها معنی بدهند.

**سیگنال** (signal) پیام کوچکی است که سیستم‌عامل یا پروسه‌ی دیگری به یک پروسه‌ی در حال اجرا می‌فرستد. `Ctrl+C` سیگنال `SIGINT` می‌فرستد. ابزار deploy معمولاً {{< term "sigterm" "SIGTERM" >}} می‌فرستد، یعنی سیگنال مؤدبانه‌ی «لطفاً بایست»، و برنامه اجازه دارد آن را بگیرد و اول تمیزکاری کند. اگر برنامه به‌موقع نایستد، ابزار `SIGKILL` می‌فرستد که قابل گرفتن نیست و پروسه را فوراً می‌کشد.

سمت NATS، دمو مثل نوشته‌های قبلی مجموعه از JetStream استفاده می‌کند. پیام‌ها در یک **stream** به نام `JOBS` ذخیره می‌شوند. worker آن‌ها را از طریق یک **consumer** می‌خواند. بعد از اینکه worker کاری را انجام داد باید یک **ack** (تأیید) بفرستد تا به سرور بگوید «این یکی تمام شد». اگر سرور ack را تا `AckWait` دریافت نکند، که اینجا ۵ ثانیه است، فرض می‌کند worker مرده و پیام را دوباره تحویل می‌دهد. این تحویل دوباره تور ایمنی است و همین‌جا هم کارِ تکراری پیدا می‌شود.

برای فرستادن سیگنال واقعی، دمو یک باینری ساخته‌شده با دو حالت است که هرکدام پروسه‌ی خودش را دارد. حالت `server` یک سرور توکار راه می‌اندازد، stream به نام `JOBS` و یک consumer با `AckWait` برابر ۵ ثانیه می‌سازد، دو کار (`job-1` و `job-2`) منتشر می‌کند و هر بار وضعیت consumer عوض شود آن را چاپ می‌کند. حالت‌های worker (یعنی `naive` و `graceful`) کارها را می‌خوانند و انجام می‌دهند. من `kill -TERM <pid>` را از یک اسکریپت shell می‌فرستم. در لاگ‌ها زمان، ساعت دیواری است و عدد داخل کروشه شناسه‌ی پروسه.

## worker ساده‌لوح

اولین worker ساده‌ترین حالت ممکن است. یک پیام می‌گیرد، ۳ ثانیه کار می‌کند و بعد ack می‌زند. مدیریت سیگنال ندارد. یک ثانیه بعد از شروعش `SIGTERM` فرستادم و بعد یک worker تازه راه انداختم (خروجی کوتاه شده):

```
23:41:38.900 [78489] start  job-1 (delivery #1), takes 3s
23:41:38.949 [78388] server: consumer pending=1 ackPending=1 redelivered=0
--- kill -TERM 78489
worker exit status: 143
23:41:40.918 [78620] start  job-2 (delivery #1), takes 3s
23:41:43.920 [78620] acked  job-2
23:41:43.920 [78620] start  job-1 (delivery #2), takes 3s
23:41:43.959 [78388] server: consumer pending=0 ackPending=1 redelivered=1
23:41:46.925 [78620] acked  job-1
```

بخوانیمش. worker اول (`78489`) `job-1` را شروع می‌کند. خط سرور بعد از آن می‌گوید یک پیام در انتظار است (`job-2`، هنوز گرفته نشده) و یکی در حال انجام (`ackPending=1`). بعد سیگنال را می‌فرستم و worker با وضعیت ۱۴۳ خارج می‌شود.

بدون handler، رفتار پیش‌فرض Go برای `SIGTERM` پایان دادن به پروسه است؛ پس کار نصفه ماند و ack نشد. وضعیت خروج ۱۴۳ یعنی ۱۲۸ به‌علاوه‌ی شماره‌ی سیگنال، که ۱۵ است. worker تازه (`78620`) در ۴۰٫۹ شروع می‌کند، اول `job-2` را می‌گیرد و ack می‌زند. بعد دوباره `job-1` را می‌گیرد، این بار با برچسب `delivery #2`: سرور `job-1` را تا تمام شدن `AckWait` در حالت انتظار نگه داشت (از ۳۸٫۹ تا ۴۳٫۹، پنج ثانیه) و بعد دوباره تحویل داد. چیزی گم نشد، ولی کار دوبار اجرا شد و پنج ثانیه دیر شد.

## سیگنال را با context بگیریم

برای تغییر این وضع، worker باید سیگنال را ببیند، نه اینکه بمیرد. `signal.NotifyContext` یک context برمی‌گرداند که وقتی یکی از سیگنال‌های فهرست‌شده برسد لغو می‌شود:

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
```

حالا سیگنال دیگر پروسه را نمی‌کشد. فقط `ctx.Done()` را می‌بندد، کانالی که می‌توانیم تماشایش کنیم. اینکه بعدش چه کنیم دست خودمان است و کل ماجرا همین است.

## توالی خاموشی

ایده‌ی اصلی ساده است: **کار تازه نگیر، کار دستت را تمام کن، مطمئن شو تأیید شده و بعد برو**. و برای اینکه برای کار گیرکرده تا ابد منتظر نمانیم، برای انتظار یک سقف زمانی بگذار. به ترتیب:

۱. گرفتن پیام تازه را متوقف کن.
۲. منتظر handlerهای در حال اجرا بمان، ولی فقط تا یک سقف.
۳. مطمئن شو ackها فرستاده شده‌اند.
۴. `nc.Drain()` و بعد خروج.

این هم حلقه‌ی worker و کد خاموشی:

```go
for ctx.Err() == nil { // stop fetching once the signal arrives
    msgs, err := sub.Fetch(1, nats.MaxWait(time.Second))
    if err != nil {
        continue
    }
    m := msgs[0]
    wg.Add(1)
    go func() {
        defer wg.Done()
        if err := handle(jobCtx, m, work); err != nil {
            return // not acked, will be redelivered
        }
        m.AckSync()
    }()
}

shutCtx, cancel := context.WithTimeout(context.Background(), grace)
defer cancel()
done := make(chan struct{})
go func() { wg.Wait(); close(done) }()
select {
case <-done:
case <-shutCtx.Done():
    cancelJobs() // jobCtx: ask handlers to give up
    wg.Wait()
    code = 1
}
nc.Drain()
os.Exit(code)
```

طرز کار: حلقه‌ی `for` هر بار یک پیام می‌گیرد و `ctx.Err() == nil` وقتی سیگنال برسد نادرست می‌شود؛ پس حلقه خودش تمام می‌شود. هر پیام در goroutine خودش پردازش می‌شود و یک `sync.WaitGroup` (یعنی `wg`) تعداد handlerهای در حال اجرا را می‌شمارد. بعد از حلقه، یک goroutine کمکی منتظر می‌ماند شمارنده به صفر برسد و کانال `done` را می‌بندد. `select` هم منتظر هرکدام می‌ماند که زودتر برسد: `done` (همه‌ی کارها تمام شد) یا مهلت `shutCtx` (زمان مجاز تمام شد).

دو نکته راحت از چشم می‌افتد. handlerها `jobCtx` می‌گیرند، نه `ctx`: خودِ سیگنال نباید کاری را که می‌خواهیم تمام شود لغو کند، فقط مهلت باید لغو کند. و `AckSync` منتظر تأیید سرور می‌ماند، پس ack هنگام خروج هنوز در یک بافر نمانده. `Drain` هم می‌گذارد اتصال درست flush و بسته شود.

حالا اجرایی با مهلت خاموشی ۱۰ ثانیه و `SIGTERM` یک ثانیه بعد از شروع. هر دو کار ۳ ثانیه طول می‌کشند و همزمان اجرا می‌شوند:

```
23:41:54.845 [79434] start  job-1 (delivery #1), takes 3s
23:41:54.845 [79434] start  job-2 (delivery #1), takes 3s
--- kill -TERM 79434
23:41:55.845 [79434] signal received, no more fetching; waiting for in-flight jobs
23:41:57.846 [79434] acked  job-1
23:41:57.846 [79434] acked  job-2
23:41:57.846 [79434] all in-flight jobs finished
23:41:57.846 [79434] drained, exit code 0
worker exit status: 0
23:41:57.862 [79388] server: consumer pending=0 ackPending=0 redelivered=0
```

هر دو کار در ۵۴٫۸ شروع شدند و سیگنال یک ثانیه بعد آمد. worker نوشت که دیگر چیزی نمی‌گیرد، ولی نمرد: صبر کرد تا ۵۷٫۸ که هر دو کار تمام و ack شدند، یعنی همان ۳ ثانیه‌ی اصلی از لحظه‌ی شروع. بعد drain کرد و با وضعیت ۰ خارج شد. خط سرور در آخر `redelivered=0` و هیچ چیز در انتظار را نشان می‌دهد. workerی که بعداً راه انداختم کاری برای انجام پیدا نکرد. با اجرای ساده مقایسه کنید: همان سیگنال، ولی نه کار تکراری و نه تأخیر پنج‌ثانیه‌ای.

## وقتی handler از مهلت بیشتر طول بکشد

خاموشی تمیز نمی‌تواند تا ابد صبر کند. ببینیم وقتی کارها ۸ ثانیه طول می‌کشند ولی مهلت خاموشی فقط ۱٫۵ ثانیه است چه می‌شود:

```
23:42:08.264 [80234] start  job-1 (delivery #1), takes 8s
--- kill -TERM 80234
23:42:09.264 [80234] signal received, no more fetching; waiting for in-flight jobs
23:42:10.765 [80234] shutdown timeout: true, cancelling jobs
23:42:10.765 [80234] abort  job-1: context canceled (not acked)
23:42:10.766 [80234] drained, exit code 1
23:42:13.266 [80428] start  job-1 (delivery #2), takes 1s
23:42:13.309 [80227] server: consumer pending=0 ackPending=2 redelivered=2
```

(خروجی کوتاه شده؛ خط‌های کار دوم حذف شده‌اند و برای همین سرور دو پیام را نشان می‌دهد.) بعد از سیگنال، worker ۱٫۵ ثانیه صبر می‌کند، تا ۱۰٫۷۶۵. بعد مهلت تمام می‌شود، `jobCtx` را لغو می‌کند، handler منصرف می‌شود (`context canceled`) و ack نمی‌زند و پروسه با کد ۱ خارج می‌شود. پیام‌ها با تمام شدن `AckWait` (۰۸٫۳ به‌علاوه‌ی ۵ ثانیه، یعنی ۱۳٫۳) به شکل `delivery #2` برگشتند و worker تازه گرفتشان.

پس خاموشی تمیز تضمین نیست. فقط پنجره‌ای را که یک کار می‌تواند نصفه بماند کوچک می‌کند. handler idempotent از نوشته‌ی قبل هنوز لازم است.

## کد خروج و Kubernetes

کد خروج غیرصفر به کسی که پروسه را نظارت می‌کند می‌گوید خاموشی تمیز نبوده؛ برای همین هنگام تمام شدن مهلت ۱ برمی‌گردانم. در Kubernetes، تا جایی که از رفتار مستندشده می‌فهمم، pod اول `SIGTERM` می‌گیرد و بعد از `terminationGracePeriodSeconds` سیگنال `SIGKILL` که قابل گرفتن نیست. من اینجا Kubernetes را اجرا نکردم و هیچ مقدار پیش‌فرضی را ادعا نمی‌کنم. قاعده‌ای که از آن برمی‌دارم: مهلت خاموشی را کمتر از grace period بگذارید و grace period را بیشتر از کندترین کار عادی‌تان.

## دام‌های خاموشی

- **`MaxWait` بلند خاموشی را کند می‌کند.** با `Fetch` همراه `MaxWait`، حلقه حداکثر ظرف یک ثانیه سیگنال را می‌فهمد. این انتظار را کوتاه نگه دارید.
- **اگر می‌خواهید handlerها کارشان را تمام کنند، context سیگنال را به آن‌ها ندهید.** از یک context جدا استفاده کنید که فقط مهلت لغوش می‌کند.
- **handlerهای طولانی باید context‌شان را چک کنند.** وگرنه مهلت نمی‌تواند متوقفشان کند و `wg.Wait()` بعد از آن بلوکه می‌ماند.
- **`SIGKILL` همه‌ی این‌ها را رد می‌کند.** خاموشی تمیز تحویل دوباره را کم می‌کند، حذف نمی‌کند.
- **سرورهای دیگر هم همین مراقبت را می‌خواهند.** اگر پروسه HTTP هم سرو می‌کند، آن را هم در همین توالی خاموش کنید.
