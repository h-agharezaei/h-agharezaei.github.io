تا این‌جا همه‌ی مثال‌های این مجموعه در یک فایل جا می‌شدند. ولی برنامه‌ای که بزرگ شود، دیر یا زود به هزار خط در یک فایل می‌رسد: پیدا کردن هر چیز سخت می‌شود، هر تغییر ترس می‌آورد و نمی‌دانید کدام تکه‌ی کد را می‌توان با خیال راحت عوض کرد. باید برنامه را به تکه‌ها تقسیم کرد، و برای این کار Go دو مفهوم دارد که تازه‌کارها معمولاً با هم قاطی می‌کنند: **پکیج** و **ماژول**.

بعد از [اشاره‌گرها و مدل حافظه در Go](/fa/posts/go-pointers-memory/)، در این مقاله یک پروژه‌ی کوچک چندپکیجی می‌سازیم و می‌بینیم کامپایلر چه چیزهایی را اجباری می‌کند: چه کسی چه چیزی را می‌بیند، پوشه‌ی `internal/` چه می‌کند، پکیج‌ها به چه ترتیبی راه می‌افتند، چرا دو پکیج نمی‌توانند همدیگر را import کنند، و وابستگی بیرونی چطور اضافه می‌شود.

> همه‌ی مثال‌ها را با Go 1.26 روی macOS (arm64) اجرا کرده‌ام. کدها یک مثال محلی‌اند.

## پکیج در برابر ماژول

ساده‌ترین تعریف را اول بگویم. **پکیج** (package) یک پوشه از فایل‌های `.go` است که همه با یک خط `package name` شروع می‌شوند. پکیج واحد کامپایل است و واحد دسترسی: چیزی که داخل یک پکیج است، یا از بیرون دیده می‌شود یا نه (در بخش بعد می‌بینیم چطور).

**ماژول** (module) یک درخت از پکیج‌هاست که با هم نسخه‌بندی می‌شوند. ماژول را فایل `go.mod` در ریشه‌اش مشخص می‌کند و با `go mod init <path>` ساخته می‌شود. نامی که در `go.mod` نوشته‌اید (module path) پیشوند آدرس import همه‌ی پکیج‌های داخل آن ماژول است. به‌طور خلاصه: پکیج یعنی «یک پوشه‌ی کد»، و ماژول یعنی «یک پروژه یا کتاب‌خانه‌ی کامل که دور چند پکیج حلقه زده».

ماژول نمونه‌ی ما `example.com/shop` است و این شکل را دارد:

```
shop/
  go.mod                  // module example.com/shop
  cmd/app/main.go         // package main
  internal/store/store.go // package store
  internal/audit/audit.go // package audit
  pkg/slug/slug.go        // package slug
```

آدرس import هر پکیج برابر است با module path به‌علاوه‌ی پوشه‌ی آن: مثلاً `example.com/shop/internal/store`. نام پوشه و نام پکیج معمولاً یکی‌اند، ولی فقط نام پوشه جزو آدرس است. تا وقتی فقط آزمایش می‌کنید، module path لازم نیست آدرس واقعی باشد. برای کتاب‌خانه‌ای که منتشر می‌کنید، همان آدرس repository است.

## exported و unexported

چطور تعیین می‌کنیم چه چیزی از بیرون پکیج دیده شود؟ در Go کلیدواژه‌ی `public` و `private` وجود ندارد. قاعده فقط حرف اول نام است: اگر بزرگ باشد، آن نام **exported** است و پکیج‌های دیگر می‌توانند از آن استفاده کنند. اگر کوچک باشد، فقط داخل همان پکیج دیده می‌شود.

در پکیج `slug` ما تابع `Make` (exported) و تابع `clean` (unexported) را داریم. این برنامه‌ی کوچک از یک ماژول دیگر می‌خواهد `clean` را صدا بزند:

```go
import "example.com/shop/pkg/slug"

func main() { _ = slug.clean(" x ") }
```

```
$ go build .
# example.com/bu
./main.go:5:24: undefined: slug.clean
```

(این برنامه ماژول جداگانه‌ای است که با یک خط `replace` در `go.mod` به پوشه‌ی محلی `shop` وصل شده. فقط برای آزمایش.) پیام می‌گوید `undefined` و نه «unexported»، که اول کمی گیج‌کننده است: از دید کامپایلر، نامی که دیده نمی‌شود وجود ندارد. اگر این خطا را برای نامی دیدید که مطمئنید تعریف شده، املای حرف اول (بزرگ یا کوچک) را بررسی کنید.

## قاعده‌ی `internal/`

گاهی می‌خواهید یک پکیج را در پروژه‌ی خودتان از همه‌جا استفاده کنید ولی نخواهید دیگران آن را import کنند. Go برای این یک پوشه‌ی ویژه دارد: پکیجی که زیر پوشه‌ای به نام `internal` باشد، فقط توسط کدی قابل import است که در ریشه‌ی والدِ همان `internal` قرار دارد. در مثال ما والد، ریشه‌ی `example.com/shop` است. حالا ماژول دیگری (`outsider`) را در نظر بگیرید که می‌خواهد `store` را import کند:

```
$ go build .
package example.com/outsider
	main.go:3:8: use of internal package example.com/shop/internal/store not allowed
```

پیام روشن است: استفاده از پکیج internal مجاز نیست. این را خود ابزار Go اجباری می‌کند، نه یک قرارداد بین آدم‌ها. نتیجه این است که جزئیات پیاده‌سازی را می‌توانید خصوصی نگه دارید و در عین حال داخل ماژول آزادانه به اشتراک بگذارید.

## `init()` و ترتیب مقداردهی اولیه

وقتی برنامه راه می‌افتد، قبل از `main` چه کدی اجرا می‌شود؟ هر پکیج اول متغیرهای سطح پکیج را مقدار می‌دهد، بعد تابع‌های `init()` خودش را اجرا می‌کند. یک پکیج می‌تواند چند `init` داشته باشد؛ به ترتیبی اجرا می‌شوند که فایل‌ها و تعریف‌ها به کامپایلر داده شده‌اند. و یک پکیج فقط بعد از همه‌ی پکیج‌هایی که import می‌کند آماده می‌شود. `main` هم آخر از همه اجرا می‌شود.

در مثال ما، هر پکیج در ابتدای کارش یک خط چاپ می‌کند. `main` پکیج‌های `store` و `slug` را import می‌کند و `store` هم `audit` را. خروجی `go run ./cmd/app`:

```
$ go run ./cmd/app
var: audit.Prefix
init: audit
init: store (first)
init: store (second)
init: slug
init: main
main starts
[audit] added Blue Mug
1 blue-mug
```

خط اول مال متغیر `audit.Prefix` است: متغیرهای سطح پکیج قبل از هر `init` مقدار می‌گیرند. بعد `init` پکیج `audit` اجرا شد، قبل از `store`، چون `store` به آن وابسته است. `store` دو تابع `init` دارد و هر دو به ترتیب نوشتن اجرا شدند. بعد `slug` آمد و آخر سر `main`. فقط وقتی همه‌ی این‌ها تمام شد، `main starts` چاپ شد. ترتیب نسبی پکیج‌های مستقل از هم (این‌جا `store` و `slug`) چیزی نیست که رویش حساب کنم و فکر نمی‌کنم شما هم باید حساب کنید.

با این حال، منطق پیچیده در `init()` نگذارید: ضمنی اجرا می‌شود، نمی‌تواند error برگرداند و تست‌کردنش سخت است. یک سازنده‌ی صریح مثل `store.New()` بهتر است.

## import cycle خطاست

حالا فرض کنید پکیج `a` پکیج `b` را import کند و `b` هم `a` را. هیچ‌کدام بدون دیگری قابل کامپایل نیست، و Go اصلاً اجازه نمی‌دهد:

```
$ go build ./...
package example.com/cyc/a
	imports example.com/cyc/b from a.go
	imports example.com/cyc/a from b.go: import cycle not allowed
```

پیام زنجیره‌ی import را نشان می‌دهد: `a` به `b` می‌رسد و `b` دوباره به `a` برمی‌گردد. راه‌حل معمول دو چیز است. یکی اینکه type مشترک را به پکیج سومی ببرید که هر دو import کنند. دیگر اینکه interface را در پکیجی تعریف کنید که به آن رفتار نیاز دارد، به‌جای اینکه پکیج پیاده‌ساز را import کند. cycle اغلب علامت این است که مرز پکیج‌ها جای درستی نیست.

## افزودن وابستگی بیرونی

تا این‌جا فقط کد خودمان را داشتیم. برای استفاده از کتاب‌خانه‌ی دیگران، پکیج `github.com/google/uuid` را در `main.go` import کردم و `go mod tidy` را اجرا کردم. این دستور requirementهای جاافتاده را به `go.mod` اضافه و موارد بی‌استفاده را حذف می‌کند.

یک نکته‌ی صادقانه: وقتی این را اجرا کردم، proxy ماژولِ تنظیم‌شده‌ی من با خطای TLS handshake timeout شد، پس با `GOPROXY=off` و `GOSUMDB=off` و نسخه‌ی `v1.6.0` که از قبل در module cache محلی بود کار کردم. روی اتصال سالم همان `go mod tidy` کافی است و بهتر است بررسی checksum روشن بماند. نتیجه:

```
$ cat go.mod
module example.com/shop

go 1.26

require github.com/google/uuid v1.6.0

$ cat go.sum
github.com/google/uuid v1.6.0 h1:NIvaJDMOsjHA8n1jAhLSgzrAzy1Hgr+hNrb57e+94F0=
github.com/google/uuid v1.6.0/go.mod h1:TIyPZe4MgqvfeYDBFedMoGGpEw/LqOeaOT+nhxU+yHo=

$ go list -m all
example.com/shop
github.com/google/uuid v1.6.0
```

`go.mod` ثبت می‌کند چه چیزی لازم دارید: یک خط `require` با نام و نسخه. `go.sum` هش‌های رمزنگاری‌شده‌ی همان نسخه‌ها را نگه می‌دارد، تا اگر بعداً محتوای دانلودشده عوض شد، build بفهمد؛ هر دو فایل را commit کنید. `go list -m all` همه‌ی ماژول‌های پروژه را فهرست می‌کند: خود ماژول ما و `uuid`. اگر `uuid` خودش به چیز دیگری وابسته بود، آن‌ها (وابستگی‌های indirect) هم این‌جا می‌آمدند؛ در این مورد هیچ‌کدام نیست.

## ساختار پیشنهادی، بدون جزم‌اندیشی

- با `main.go` و `go.mod` شروع کنید. جدی می‌گویم: یک ابزار کوچک بیشتر از این نمی‌خواهد.
- وقتی ماژول بیش از یک باینری دارد، یا می‌خواهید `main` نازک بماند، `cmd/<name>/main.go` اضافه کنید.
- کدی که نمی‌خواهید دیگران import کنند زیر `internal/` بگذارید.
- پکیج را وقتی بسازید که هدف روشن و نامی یک‌کلمه‌ای دارد، نه چون نمودار قشنگ‌تر می‌شود.
- `pkg/` اختیاری است. بعضی پروژه‌ها برای کتاب‌خانه‌های قابل import استفاده‌اش می‌کنند و خیلی‌ها نه. هیچ ساختاری را مقدس نکنید.

## دام‌های ساختاردهی پروژه

- **ساختار بیش‌ازحد رایج‌ترین تله‌ی مبتدی‌هاست.** ده پکیج با یک تابع به cycle و importهای بدقواره مثل `utils` و `common` می‌رسد.
- **نام پکیج کوتاه، با حروف کوچک و مفرد باشد و در نام‌ها تکرار نشود.** `store.Store` خوب است، `store.StoreItem` تکرار است.
- **عوض‌کردن حرف اول یک نام، API عمومی شما را عوض می‌کند.** نام exported یعنی تعهد به کسانی که از آن استفاده می‌کنند.
- **`go.sum` را دستی ویرایش نکنید.** این کار با `go mod tidy` است.
- **کار سنگین در `init()` نکنید.** دلیلش را بالا دیدیم: ضمنی است، خطا برنمی‌گرداند و تست‌کردنش سخت است.

## تمرین

۱. پکیج `internal/config` با تابع exported `Load() Config` بسازید و از `main` استفاده کنید. ببینید `init`ها به چه ترتیبی چاپ می‌شوند.
۲. عمداً یک import cycle بسازید و خطایش را بخوانید.
۳. وابستگی دیگری اضافه کنید، `go mod tidy` بزنید و `go.mod` و `go list -m all` را قبل و بعد مقایسه کنید.
