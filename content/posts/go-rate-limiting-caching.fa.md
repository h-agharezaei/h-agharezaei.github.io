فرض کنید یک اسکریپت توی حلقه‌ی بی‌پایان گیر کرده و ثانیه‌ای ۵۰۰ درخواست به API شما می‌فرستد. سرویس سالم است و به همه‌ی درخواست‌ها جواب می‌دهد، ولی مشتری‌های دیگر هم پاسخ کند می‌گیرند، چون آن یک کلاینت همه‌ی ظرفیت را می‌خورد. حالا مشکل برعکس را تصور کنید: صد کلاینت مختلف همه یک سفارش پربازدید را می‌خواهند و هر درخواست تا دیتابیس می‌رود. دیتابیس یک سؤال تکراری را ثانیه‌ای هزار بار جواب می‌دهد.

ریشه‌ی هر دو یکی است: سرویسی که در دسترس است باید از مشتری‌هایش هم جان سالم به در ببرد. در این نوشته دو محافظ به سرویس سفارش‌ها اضافه می‌کنیم. اولی {{< term "rate-limiting" "rate limit" >}} است، یعنی قاعده‌ای که می‌گوید «هر کلاینت فقط به این تعداد در ثانیه درخواست بفرستد» و بقیه را رد می‌کند. دومی یک cache جلوی `GetOrder` است تا سفارش پربازدید یک بار از دیتابیس خوانده شود و بعد از حافظه جواب بگیرد.

هر دو را به نسخه‌ی REST از [مقاله‌ی net/http](/fa/posts/go-http-api-stdlib/) اضافه می‌کنم، نه به [در ورودی gRPC](/fa/posts/go-grpc-service/): یک middleware برای rate limit و یک cache که متد `Pay` هر وقت سفارش عوض شد ورودی‌اش را پاک می‌کند. آخرین نوشته‌ی Go پیش از این، [ارتباط Go و Rust با gRPC](/fa/posts/go-rust-grpc-interop/)، درباره‌ی مرز دیگری بود؛ این‌جا داخل یک سرویس می‌مانیم.

> همه‌ی مثال‌ها را دوباره با Go 1.27 روی macOS (arm64) و با `golang.org/x/time` نسخه‌ی v0.16.0، `golang.org/x/sync` نسخه‌ی v0.24.0 و `golang-lru/v2` نسخه‌ی v2.0.7 اجرا کردم. برنامه‌ها ساعتی را به کار می‌برند که خودم تعیین می‌کنم، پس در خروجی زمان واقعی نیست و هر بار همین چیز چاپ می‌شود. کد یک مثال محلی است و ریپوی منتشرشده ندارد. برنامه‌ی اصلی `cmd/api` تغییری نکرده؛ برنامه‌های کوچک دمو همان handler را می‌سازند و قطعه‌های تازه را به آن اضافه می‌کنند.

## سطل توکن، با عدد

رایج‌ترین راه محدودکردن درخواست‌ها {{< term "token-bucket" "token bucket" >}} (سطل توکن) است. سطلی را تصور کنید که حداکثر `burst` توکن در آن جا می‌شود. توکن‌ها با سرعت `rate` در ثانیه توی سطل می‌چکند و وقتی سطل پر باشد چکه‌های اضافی هدر می‌روند. هر درخواست باید یک توکن از سطل بردارد. اگر سطل خالی باشد، درخواست رد می‌شود (یا باید صبر کند).

پس دو عدد برای انتخاب دارید. `rate` میانگین بلندمدتی است که اجازه می‌دهید. `burst` اندازه‌ی جهش ناگهانی‌ای است که تحمل می‌کنید، چون کلاینتی که مدتی ساکت بوده سطل پر دارد و می‌تواند همه‌اش را یک‌جا خرج کند.

یک مثال کوچک: سطلی با ظرفیت ۳ که ثانیه‌ای ۲ توکن پر می‌شود و اول کار پر است.

- در لحظه‌ی صفر سه درخواست می‌رسد. هرکدام یک توکن برمی‌دارد و سطل خالی می‌شود. درخواست چهارم و پنجم چیزی پیدا نمی‌کنند و جواب رد می‌گیرند.
- نیم ثانیه بعد، ۰٫۵ ثانیه × ۲ توکن در ثانیه = ۱ توکن تازه چکیده است. یک درخواست می‌تواند عبور کند.

بسته‌ی `golang.org/x/time/rate` همین را پیاده کرده است. `rate.NewLimiter(2, 3)` را با متدهایی که زمان را صریح می‌گیرند (`AllowN(t, n)` و هم‌خانواده‌هایش) اجرا کردم تا خودم تعیین کنم «الان» چه ساعتی است و `time.Sleep` لازم نباشد:

```go
lim := rate.NewLimiter(2, 3)
lim.AllowN(t0, 1)                          // true x3, then false x2
lim.AllowN(t0.Add(500*time.Millisecond), 1) // true: one token refilled
r := lim.ReserveN(t0.Add(500*time.Millisecond), 1)
r.DelayFrom(t0.Add(500*time.Millisecond))   // 500ms
lim.Wait(ctx)                               // ctx has a 10ms deadline
```

خروجی واقعی `go run ./cmd/limiter` (پنج خط `Allow` را برای خوانایی در دو خط جمع کرده‌ام):

```
Allow #1..#3: true   Allow #4, #5: false   Allow at t+0.5s: true
Reserve delay: 500ms
Wait: rate: Wait(n=1) would exceed context deadline
```

خط اول دقیقاً همان مثال بالاست. limiter سه راه برای گرفتن توکن دارد و فرقشان وقتی پیداست که سطل خالی است:

- `Allow` همین حالا جواب بله یا نه می‌دهد. جواب «نه» چیزی از سطل برنمی‌دارد.
- `Reserve` همیشه توکن را برمی‌دارد، حتی اگر هنوز وجود نداشته باشد، و می‌گوید تا آماده‌شدنش چقدر باید صبر کرد. این‌جا `Allow` در ثانیه‌ی ۰٫۵ سطل را خالی کرده بود و توکن بعدی نیم ثانیه دیگر می‌رسد، پس تأخیر ۵۰۰ میلی‌ثانیه است.
- `Wait` تا وجود توکن بلاک می‌شود. اگر deadline‌ی context زودتر برسد، الکی صبر نمی‌کند و فوراً خطا برمی‌گرداند. این‌جا context فقط ۱۰ میلی‌ثانیه وقت می‌داد و توکن ۵۰۰ میلی‌ثانیه لازم داشت.

در یک API HTTP نمی‌خواهیم درخواست‌ها را صف کنیم؛ می‌خواهیم سریع بگوییم «زیاد است». پس رفتار `Allow` مناسب است. اما همان‌طور که بخش بعد نشان می‌دهد، باز هم از `Reserve` استفاده می‌کنم، چون به ما می‌گوید کلاینت چقدر باید صبر کند.

## برای هر کلاینت یک سطل

یک سطل برای کل سرویس به درد نمی‌خورد: کلاینت پرسر و صدای مقدمه آن را خالی می‌کند و بقیه جواب رد می‌گیرند. پس برای هر کلاینت یک سطل نگه می‌داریم، در یک map از کلید به limiter، و چون درخواست‌های زیادی هم‌زمان به map می‌رسند آن را با یک {{< term "mutex" "mutex" >}} محافظت می‌کنیم.

کلید چیست؟ اگر درخواست هدر `X-API-Key` داشته باشد، همان را به کار می‌بریم. وگرنه آدرس IP طرف مقابل را، که از خود اتصال خوانده می‌شود. عمداً `X-Forwarded-For` را نمی‌خوانیم، چون آن هدر فقط متنی است که کلاینت می‌فرستد و کلاینتی که محدود شده می‌تواند در هر درخواست مقدار تازه‌ای بنویسد.

`Take` برای یک کلید یک توکن خرج می‌کند. وقتی سطل خالی است باید بگوید «کی دوباره امتحان کنم؟»، و برای این از `Reserve` استفاده می‌کند. اما `Reserve` توکن را همان لحظه برداشته، پس هنگام رد کردن آن را با `CancelAt` پس می‌دهیم:

```go
res := e.lim.ReserveN(now, 1)
if d := res.DelayFrom(now); d > 0 {
	res.CancelAt(now) // no token now: give the reservation back
	return false, 0, d
}
return true, int(e.lim.TokensAt(now)), 0
```

بدون این لغو، هر درخواست ردشده از آینده توکن قرض می‌گرفت و کلاینتی که مدام می‌کوبد گودال عمیق‌تر و عمیق‌تری برای خودش می‌کند. دمو در بخش بعد نتیجه را نشان می‌دهد: بعد از آن درخواست‌های ردشده، سطل هنوز عادی پر می‌شود.

### تله‌ی این map

هیچ چیز در این map کلیدی را پاک نمی‌کند. هر آدرس IP تازه برای همیشه در حافظه می‌ماند و روی یک سرویس عمومی آدرس تازه بی‌پایان است. `cmd/leak` از ۱۰۰٬۰۰۰ آدرس مختلف، از هرکدام یک درخواست می‌فرستد:

```
entries after 100000 one-off clients: 100000
cleanup right away removed: 0 - still 100000
cleanup after 11 idle minutes removed: 99999 - still 1
```

هر ورودی به یاد دارد کلاینتش آخر بار کی دیده شده و `Cleanup(idle)` ورودی‌هایی را که بیش از `idle` بی‌کار بوده‌اند پاک می‌کند. بلافاصله بعد از درخواست‌ها هیچ‌کدام آن‌قدر کهنه نیستند، پس چیزی پاک نمی‌شود. در دمو بعد ساعت ۱۱ دقیقه جلو می‌رود و یک کلاینت برمی‌گردد؛ همان یک ورودی می‌ماند و ۹۹٬۹۹۹ تای دیگر پاک می‌شوند. در سرور واقعی یک goroutine این پاک‌سازی را با یک ticker صدا می‌زند، این‌جا هر یک دقیقه:

```go
go limiter.Run(ctx, time.Minute, 10*time.Minute)
```

دور انداختن کلاینت بی‌کار بی‌خطر است، به شرط اینکه پرشدن کامل سطل کمتر از زمان بی‌کاری طول بکشد: چنین کلاینتی به هر حال سطل پر دارد، و ورودی تازه هم دقیقاً با سطل پر شروع می‌شود.

## Middleware

حالا limiter را به HTTP وصل می‌کنیم. middleware تابعی است که دور یک handler می‌پیچد: پیش از handler اصلی اجرا می‌شود و تصمیم می‌گیرد آن را صدا بزند یا نه. `RateLimit` ته زنجیره‌ی موجود اضافه می‌شود، بعد از request ID، لاگ دسترسی و recover. این ترتیب مهم است: درخواست ردشده هم request ID می‌گیرد و هم در لاگ دسترسی می‌آید، پس می‌توانید ببینید چه کسی محدود شده. رد کردن از همان مسیر خطای بقیه می‌گذرد: `errLimited` تازه در تنها تابع `statusOf` به `429 Too Many Requests` نگاشت می‌شود.

```go
ok, remaining, retry := t.Take(clientKey(r))
w.Header().Set("X-RateLimit-Limit", strconv.Itoa(burst))
w.Header().Set("X-RateLimit-Remaining", strconv.Itoa(remaining))
if !ok {
	w.Header().Set("Retry-After", strconv.Itoa(ratelimit.Seconds(retry)))
	writeErr(w, r, errLimited)
	return
}
```

هر پاسخ سقف کلاینت و تعداد درخواست‌های باقی‌مانده‌اش را می‌گوید و پاسخ ردشده `Retry-After` هم دارد، یعنی تعداد ثانیه‌هایی که باید صبر کند (به بالا گرد شده). کلاینت درست‌رفتار می‌تواند به‌جای حدس زدن از این‌ها استفاده کند.

برای آزمودن سرتاسری، `cmd/burst` یک سرور واقعی با `httptest` راه می‌اندازد، با rate برابر ۱ در ثانیه و burst برابر ۵، و با یک کلاینت HTTP واقعی با آن حرف می‌زند. ساعت یک متغیر است که برنامه با دست جلو می‌برد. اول ۲۰ درخواست یک‌جا می‌فرستد، بعد ساعت را ۳ ثانیه جلو می‌برد و ۱۰ درخواست دیگر می‌فرستد، و بعد ۱۰ درخواست با یک API key:

```
  first 429: Retry-After=1 Limit=5 Remaining=0
burst of 20 at t+0s:  5 passed, 15 denied
10 more at t+3s:      3 passed, 7 denied
10 with an API key:   5 passed, 5 denied
```

برنامه خط «first 429» را برای هر گروهی که ردشده داشته یک بار چاپ می‌کند؛ من آن را یک بار نشان داده‌ام. بقیه را بخوانیم:

- از ۲۰ درخواست اول دقیقاً ۵ تا عبور می‌کند: همان burst. اولین رد شدن `Retry-After=1` دارد، چون با ۱ توکن در ثانیه توکن بعدی یک ثانیه دیگر می‌رسد.
- بعد از سه ثانیه‌ی ساختگی، ۳ تا از ۱۰ درخواست بعدی عبور می‌کند. سه ثانیه پرشدن یعنی سه توکن. این هم نشان می‌دهد ۱۵ درخواست ردشده بدهی درست نکرده‌اند، به لطف `CancelAt`.
- درخواست‌های دارای `X-API-Key` سطل جدا دارند، پس ۵ تا عبور می‌کند با اینکه سطل IP خالی است.

تست‌های واحد هم همین عددها را بدون sleep بررسی می‌کنند.

یک محدودیت این طراحی: سطل‌ها در حافظه‌ی یک پروسه‌اند. اگر N نسخه از سرویس را پشت load balancer اجرا کنید، هرکدام سطل‌های خودش را دارد و کلاینت می‌تواند تا N برابر سقف درخواست بفرستد. سقفی که بین همه‌ی نسخه‌ها مشترک باشد حالت مشترک می‌خواهد، مثلاً Redis. این را این‌جا اجرا نکردم.

## Cache برای GetOrder

مشکل دوم: یک سفارش که بارها و بارها خوانده می‌شود. cache پاسخ‌های اخیر را در حافظه نگه می‌دارد. `cache.TTL` یک map کوچک generic با سه ایده است:

- قفل خواندن و نوشتن (`RWMutex`): چند goroutine می‌توانند هم‌زمان بخوانند و نوشتن قفل را تنها می‌گیرد.
- زمان انقضا روی هر ورودی، همان {{< term "ttl" "TTL" >}}. بعد از آن ورودی «نیست» حساب می‌شود.
- شمارنده‌های hit و miss، تا ببینیم cache چه می‌کند.

`cached.Service` دور سرویس واقعی سفارش‌ها می‌پیچد. `Get` از cache می‌گذرد. `Pay` سفارش را عوض می‌کند، پس بعد از پرداخت موفق ورودی cache را پاک می‌کند؛ وگرنه خواننده‌ها تا پایان TTL وضعیت قدیمی را می‌دیدند. دمو یک سفارش می‌سازد، ده بار می‌خواندش، پرداختش می‌کند و یک بار دیگر می‌خواند:

```
after 10 GETs:        hits=9 misses=1
pay -> {"id":"1","customer":"ali","cents":1500,"status":"paid"}
get -> {"id":"1","customer":"ali","cents":1500,"status":"paid"}
after pay and 1 GET:  hits=9 misses=2
```

خواندن اول miss شد و سفارش را از store آورد؛ نه‌تای بعدی hit بودند. بعد از پرداخت، خواندن بعدی عمداً miss شد: ورودی پاک شده بود، پس سفارش تازه را آورد و `paid` را نشان می‌دهد. بدون `Delete`، آخرین خواندن تا پایان TTL وضعیت قدیمی `new` را برمی‌گرداند.

## Stampede و singleflight

یک مشکل ظریف‌تر هم هست. وقتی ورودی پربازدیدی منقضی می‌شود، هر درخواستی که پیش از بارگذاری دوباره برسد هم‌زمان miss می‌خورد و همه با یک سؤال به دیتابیس می‌روند. به این می‌گویند {{< term "cache-stampede" "cache stampede" >}} (هجوم گله). cacheای که قرار بود از دیتابیس محافظت کند، در بدترین لحظه گله‌ای را سمت آن می‌فرستد.

درمانش ساده است: بگذار اولین درخواست بارگذاری کند و بقیه منتظر جواب او بمانند. Go این را در `golang.org/x/sync/singleflight` دارد که من پایین‌تر {{< term "singleflight" "singleflight" >}} صدایش می‌کنم. `GetOrLoad` بارگذار را داخل `singleflight.Group.Do` اجرا می‌کند: فراخوانی‌های هم‌کلید نتیجه‌ی فراخوانی اول را شریک می‌شوند.

`cmd/stampede` ۵۰ goroutine را به یک کلید خالی می‌فرستد. بارگذار ۵۰ میلی‌ثانیه می‌خوابد، مثل یک کوئری کند، و می‌شمارد چند بار اجرا شده. یک بار با کد ساده‌ی «چک کن، بارگذاری کن، ذخیره کن» و یک بار با `singleflight` اجرا می‌شود:

```
naive          50 requests -> 50 loader calls
singleflight   50 requests -> 1 loader calls
```

پنجاه کوئری یکسان یکی شد. دمو کاملاً قطعی نیست، چون ۵۰ goroutine باید در همان پنجره‌ی ۵۰ میلی‌ثانیه هم‌پوشانی داشته باشند؛ این را عوض نکردم و این‌جا هم همین چاپ شد، ولی روی زمان‌بندی این‌طوری یک تست سخت‌گیرانه نمی‌سازم.

## سقف اندازه

TTL map ما یک مشکل بی‌صدا دارد: ورودی منقضی را هرگز پاک نمی‌کند. خواندن کلید منقضی فقط miss گزارش می‌دهد و مقدار قدیمی در map می‌ماند تا همان کلید دوباره بارگذاری شود. با کلیدهای بسیار متفاوت map مدام بزرگ می‌شود. برای سقف سخت از `hashicorp/golang-lru/v2` استفاده کردم، یک {{< term "lru-cache" "LRU cache" >}}: وقتی پر شود، ورودی‌ای را که دیرتر از همه استفاده شده بیرون می‌اندازد. ظرفیت ۳ است: `a` و `b` و `c` را اضافه می‌کنیم، `a` را می‌خوانیم و بعد `d` و `e` را اضافه می‌کنیم:

```
add d:
  evicted b=2
add e:
  evicted c=3
keys oldest to newest: [a d e] len: 3
```

خواندن `a` آن را «تازه‌ترین» کرد، پس وقتی `d` آمد قدیمی‌ترین `b` بود و وقتی `e` آمد `c`. `a` هر دو بار ماند.

## کجا این محافظ‌ها می‌شکنند

- **cache یعنی معاوضه‌ی تازگی با سرعت.** TTL بلندتر یعنی بارگذاری کمتر و داده‌ی کهنه‌ی بیشتر. روی نوشتن‌هایی که خودتان کنترل می‌کنید ورودی را پاک کنید (مثل `Pay`) و برای تغییرهای دیگر TTL را بدترین حالت بدانید.
- **پاک‌کردن ورودی می‌تواند در رقابت ببازد.** بارگذاری کندی که پیش از `Delete` شروع شده ممکن است بعد از آن تمام شود و مقدار قدیمی را دوباره بنویسد. این را بازتولید نکردم؛ TTL کوتاه شبکه‌ی ایمنی است.
- **`singleflight` context و خطای اولین فراخواننده را بین همه شریک می‌کند.** اگر او لغو شود، کسانی که پشتش منتظرند همان شکست را می‌بینند.
- **محدودیت بر پایه‌ی IP آدم‌های بی‌گناه را تنبیه می‌کند.** کاربران زیادی پشت یک NAT یک آدرس و یک سطل دارند. جایی که API key دارید از آن استفاده کنید. نکته‌ی دیگر اینکه این دمو API key را اعتبارسنجی نمی‌کند: هر رشته‌ای کلید حساب می‌شود، پس محدودیتی که به یک هدر بررسی‌نشده تکیه دارد با ساختن کلید جعلی دور زده می‌شود. در سرویس واقعی باید اول کلید را اعتبارسنجی کرد.

## قدم بعدی

limiter و cache حدس‌هایی درباره‌ی جای فشار هستند. قدم بعدی «پروفایلینگ با pprof در Go» است که نشان می‌دهد زمان و حافظه واقعاً کجا می‌روند، به‌جای حدس.
