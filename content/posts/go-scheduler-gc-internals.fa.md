۱۰۰ goroutine را راه بیندازید که همه روی یک channel منتظرند؛ برنامه حتی یک thread تازه نمی‌گیرد. ۱۰۰ goroutine راه بیندازید که همه داخل یک فراخوانی سیستمی مسدودکننده‌ی خام منتظرند؛ برنامه حدود ۹۸ thread تازه می‌سازد. یک goroutine را در حلقه‌ی خالی `for {}` بگذارید؛ باقی برنامه باز هم کار می‌کند. heap را پر از زباله کنید؛ یک جمع‌کننده آن را پاک می‌کند، در حالی که کد شما همچنان به درخواست‌ها جواب می‌دهد.

هیچ‌کدام جادو نیست. این‌ها کاری است که runtime گو پشت `go f()` و `make([]byte, n)` می‌کند، و دانستن کلیاتش وقتی به کار می‌آید که سرویسی تعداد thread عجیب، حافظه‌ی پله‌پله‌بالارونده یا جهش تأخیری نشان بدهد که هیچ handlerی توضیحش نمی‌دهد. این نوشته به دو بخش از runtime نگاه می‌کند که از همه مهم‌ترند: **زمان‌بند** (scheduler) که تصمیم می‌گیرد کدام goroutine کجا اجرا شود، و **garbage collector** (GC) که حافظه‌ای را که کسی به آن نیاز ندارد آزاد می‌کند.

روش کار آزمایش‌های کوچک است. هر آزمایش یک برنامه‌ی ریز است که چیزی قابل وارسی چاپ می‌کند و می‌گویم چه چیزی را ثابت می‌کند و چه چیزی را نه. پایه‌ی نوشته [goroutine و channel](/fa/posts/go-goroutines-channels/)، [پروفایلینگ با pprof](/fa/posts/go-profiling-pprof/) و [escape analysis و heap](/fa/posts/go-pointers-memory/) است و بعد از [Docker، CI و دیپلوی سرویس Go](/fa/posts/go-docker-ci-deploy/) می‌آید: سرویسی که فرستادیم روی همین runtime اجرا می‌شود.

> Go 1.27 روی macOS (arm64) با ۸ CPU. load average حین اجراها بین ۲ و ۳٫۵ بود، پس **هیچ زمانی** نشان نمی‌دهم؛ فقط شمارش و اندازه‌ی تقریبی. شمارش‌هایی مثل تعداد چرخه‌های GC از اجرایی به اجرای دیگر کمی فرق می‌کنند، پس بازه می‌دهم. هر جا کار runtime را فراتر از چیزی که برنامه چاپ می‌کند توضیح می‌دهم، می‌گویم از مستندات است و خودم راستی‌آزمایی نکرده‌ام. کد یک مثال محلی است و ریپوی منتشرشده ندارد.

## مدل G-M-P با زبان ساده

مستندات و سخنرانی‌ها زمان‌بند را با سه حرف توصیف می‌کنند:

- **G** یک goroutine است: تابعی که هم‌زمان اجرا می‌شود و stack کوچک خودش را دارد.
- **M** یک «ماشین» است: یک thread (رشته‌ی اجرایی) سیستم‌عامل.
- **P** یک «پردازنده» است: توکنی که thread برای اجرای کد Go باید در دست داشته باشد. دقیقاً به تعداد `GOMAXPROCS` وجود دارد، به‌طور پیش‌فرض یکی برای هر CPU.

هر P یک **صف اجرای محلی** دارد: goroutineهایی که آماده‌اند و منتظر نوبتشان روی همان P هستند. یک **صف سراسری** هم هست. Pای که کارش تمام شود در صف سراسری نگاه می‌کند و بعد نصف صف یک P دیگر را می‌دزدد، پس کار خودبه‌خود پخش می‌شود. به این کار دزدی کار (work stealing) می‌گویند. به‌صورت تصویر:

```
global queue:  G  G  G  G  ...

   P0            P1            P2      ...    (GOMAXPROCS of them)
   local: G G    local: G      local: -
     |             |             |
     M0            M1            M2           (threads, one per busy P)
   running G     running G     running G
```

goroutine فقط وقتی اجرا می‌شود که یک M یک P را در دست داشته باشد و آن را انتخاب کند. چرا این‌همه لایه؟ goroutine ارزان است چون فقط یک G است: چند کیلوبایت stack و کمی حسابداری. threadها گران‌اند، پس runtime تعدادشان را نزدیک تعداد CPUها نگه می‌دارد و goroutineها را روی آن‌ها جابه‌جا می‌کند.

اول چند عدد درباره‌ی ماشین، از `go run ./info`:

```go
fmt.Println("NumCPU       =", runtime.NumCPU())
fmt.Println("GOMAXPROCS   =", runtime.GOMAXPROCS(0)) // 0 = query only
fmt.Println("NumGoroutine =", runtime.NumGoroutine())
```

```
NumCPU       = 8
GOMAXPROCS   = 8
NumGoroutine = 1
NumGoroutine = 51 after starting 50
GOMAXPROCS   = 2 (was 8 )
```

ماشین ۸ CPU دارد و runtime هم ۸ تا P ساخته است. اول کار یک goroutine هست (`main`). بعد از راه‌انداختن ۵۰ goroutine خوابیده، ۵۱ تا می‌شوند. خط آخر `GOMAXPROCS` را به ۲ تغییر می‌دهد و نشان می‌دهد این فراخوانی مقدار قبلی، یعنی ۸، را برمی‌گرداند.

## تماشای زمان‌بند: schedtrace

runtime می‌تواند وضعیت خودش را چاپ کند. `GODEBUG=schedtrace=1000` هر ثانیه یک خط چاپ می‌کند. برنامه‌ی داخل `sched/` ۲۰۰ goroutine راه می‌اندازد که هرکدام ۲٫۵ ثانیه روی CPU می‌چرخد، پس کار خیلی بیشتر از Pهاست. دو خط از خروجی (بخش `schedticks` آخر هر خط را بریده‌ام):

```
SCHED 0ms: gomaxprocs=8 idleprocs=6 threads=3 spinningthreads=1 ... runqueue=0 [ 0 0 0 0 0 0 0 0 ]
SCHED 1011ms: gomaxprocs=8 idleprocs=0 threads=9 spinningthreads=0 ... runqueue=84 [ 8 9 6 6 32 7 8 32 ]
```

چطور بخوانیمشان:

- `gomaxprocs=8` تعداد Pهاست.
- `idleprocs` تعداد Pهایی است که کاری ندارند. در ۰ میلی‌ثانیه ۶ است، چون برنامه تازه شروع شده. در ۱۰۱۱ میلی‌ثانیه ۰ است: همه‌ی Pها مشغول‌اند.
- `threads=9` تعداد Mها (threadها) است. هشت P مشغول هشت thread می‌خواهد؛ بررسی نکردم thread نهم چه می‌کند.
- `runqueue=84` صف **سراسری** است. عددهای داخل کروشه **صف‌های محلی** هشت Pاند.

می‌شود خط دوم را با حساب ساده سنجید. ۲۰۰ goroutine در آن لحظه همه زنده‌اند: ۸ تا در حال اجرا (یکی روی هر P)، ۸+۹+۶+۶+۳۲+۷+۸+۳۲ = ۱۰۸ تا در صف‌های محلی منتظرند و ۸۴ تا در صف سراسری. ۸ + ۱۰۸ + ۸۴ = ۲۰۰. هیچ‌چیز گم نشده.

وقتی کار تمام شد (آخرین خط trace)، خروجی `idleprocs=8` و `threads=9` را نشان داد: همه‌ی Pها بیکار، ولی threadها هنوز بودند: threadهای بیکار فوراً نابود نمی‌شوند. عددهای دقیق داخل کروشه از اجرایی به اجرای دیگر فرق می‌کنند؛ مجموعشان نه.

## threadها: مسدود در syscall یا مسدود در Go

آیا goroutine مسدود یک thread خرج می‌کند؟ بستگی دارد *چطور* مسدود شده باشد. آزمایش ۱۰۰ goroutine را به یکی از سه شکل راه می‌اندازد و بعد با `pprof.Lookup("threadcreate").Count()` می‌شمارد پروسه تا حالا چند thread ساخته است:

```go
case "syscall":
	r, _, _ := os.Pipe() // nothing is ever written
	go func() { buf := make([]byte, 1); syscall.Read(int(r.Fd()), buf) }()
case "sleep":
	go time.Sleep(time.Minute)
case "chan":
	c := make(chan int)
	go func() { <-c }()
```

در حالت `syscall` هر goroutine فراخوانی سیستمی ({{< term "syscall" "syscall" >}}) خام `read` را روی pipeای صدا می‌زند که کسی در آن نمی‌نویسد، پس داخل سیستم‌عامل مسدود می‌شود. در حالت `sleep` روی یک تایمر Go می‌خوابد و در حالت `chan` منتظر مقداری روی channelی می‌ماند که کسی نمی‌فرستد. سه اجرا این را چاپ کردند:

```
syscall  threadcreate before=5 after=103
sleep    threadcreate before=5 after=5
chan     threadcreate before=5 after=5
```

در حالت `syscall` پروسه حدود ۹۸ thread تازه ساخت، یکی برای هر goroutine گیرکرده. در دو حالت دیگر هیچ (در اجرای اصلی این نوشته `sleep` عدد ۶ را نشان داده بود، پس اختلاف یک‌تایی بین اجراها نویز است).

دلیلش، طبق طراحی مستند زمان‌بند: threadی که داخل یک فراخوانی سیستمی مسدود است نمی‌تواند کد Go اجرا کند، پس runtime Pِ آن را به thread دیگری می‌دهد (و اگر لازم باشد یکی می‌سازد) تا goroutineهای دیگر به کار ادامه بدهند. goroutineای که روی channel یا تایمر منتظر است فرق دارد: زمان‌بند آن را فقط «پارک» می‌کند، بدون هیچ threadی، و thread خرج نمی‌کند. یک احتیاط درباره‌ی این آزمایش: من خودم فراخوانی سیستمی خام را روی file descriptor صدا زدم، که مدیریت I/O خود runtime را دور می‌زند. خواندن‌های معمولی فایل و شبکه در Go معمولاً جور دیگری مدیریت می‌شوند؛ این را این‌جا امتحان نکردم.

نتیجه: هزاران goroutine که روی channel، تایمر یا شبکه منتظرند ارزان‌اند. هزاران goroutine داخل فراخوانی‌های سیستمی مسدودکننده (یا فراخوانی‌های cgo، مثل [صدا زدن Rust از Go با FFI](/fa/posts/go-calls-rust-ffi/)) می‌توانند هزاران thread هزینه داشته باشند.

## Preemption: چرا یک حلقه‌ی مشغول همه‌چیز را فریز نمی‌کند

یک نگرانی: اگر یک goroutine هیچ‌وقت Pاش را رها نکند چه؟ آزمایش `GOMAXPROCS(1)` می‌گذارد، پس فقط یک P هست. یک goroutine `for {}` اجرا می‌کند، حلقه‌ای بدون فراخوانی تابع و بدون عملیات channel. goroutine اصلی روی یک ticker با دوره‌ی ۱۰۰ میلی‌ثانیه منتظر می‌ماند و برای هر tick یک خط چاپ می‌کند:

```
tick 1
tick 2
tick 3
tick 4
tick 5
```

هر پنج tick رسید. حلقه‌ی مشغول main را گرسنه نگذاشت، حتی با یک P. دلیلش **{{< term "preemption" "preemption ناهم‌زمان" >}}** است: runtime می‌تواند goroutine در حال اجرا را از بیرون، با یک سیگنال، قطع کند و P را به دیگری بدهد. طبق یادداشت‌های انتشار Go این از Go 1.14 وجود دارد. پیش از آن preemption فقط **همکارانه** بود: goroutine را فقط در نقطه‌های مشخصی مثل فراخوانی تابع می‌شد جابه‌جا کرد، پس حلقه‌ای بدون آن‌ها می‌توانست بقیه را مسدود کند. نسخه‌های قدیمی Go را اجرا نکردم، پس این بخش تاریخچه‌ی مستند است و چیزی نیست که خودم اندازه گرفته باشم.

## Garbage collector

در Go حافظه را با `make`، `new` یا گرفتن آدرس چیزی می‌گیرید و هیچ‌وقت آزادش نمی‌کنید. {{< term "garbage-collector" "garbage collector" >}} اشیایی را که دیگر چیزی به آن‌ها نمی‌رسد پیدا و بازپس‌گیری می‌کند. طبق مستندات Go، جمع‌کننده‌ی Go **هم‌زمان** است (وقتی کد شما اجرا می‌شود کار می‌کند)، **غیرنسلی** است (اشیای جوان را جدا برخورد نمی‌کند) و از الگوریتم **tri-color mark-and-sweep** استفاده می‌کند: هر شیء قابل‌دسترس از ریشه‌ها (متغیرهای سراسری، stackها) را *علامت‌گذاری* (mark) می‌کند و بعد بقیه را *جارو* (sweep) می‌کند. فقط مرحله‌های کوتاهی به اسم {{< term "stop-the-world" "stop-the-world" >}} همه‌ی goroutineها را متوقف می‌کنند.

`GODEBUG=gctrace=1` برای هر چرخه‌ی GC یک خط چاپ می‌کند. این چرخه‌ی سوم از `gcdemo` است:

```
gc 3 @0.003s 2%: 0.006+0.091+0.011 ms clock, 0.049+0.011/0.071/0.011+0.094 ms cpu, 15->16->8 MB, 16 MB goal, 0 MB stacks, 0 MB globals, 8 P
```

فیلد به فیلد، طبق مستندات runtime برای `GODEBUG`:

- `gc 3 @0.003s 2%`: چرخه‌ی شماره‌ی ۳ است، ۰٫۰۰۳ ثانیه بعد از شروع برنامه شروع شد و حدود ۲٪ از زمان تا این‌جا صرف GC شده.
- `0.006+0.091+0.011 ms clock`: سه مرحله به زمان دیواری. اول یک مکث stop-the-world در شروع (sweep termination)، بعد mark هم‌زمان (کد شما در این مدت اجرا می‌شود)، بعد یک مکث stop-the-world در پایان (mark termination). مکث‌ها عدد اول و سوم‌اند.
- `0.049+0.011/0.071/0.011+0.094 ms cpu`: همین کار به زمان CPU و به تفکیک نقش، جمع روی همه‌ی CPUها.
- `15->16->8 MB`: اندازه‌ی heap هنگام شروع چرخه، هنگام پایان و مقدار زنده (قابل‌دسترس) بعد از آن. این‌جا heap هنگام شروع ۱۵ مگابایت بود، در پایان ۱۶ مگابایت، و فقط ۸ مگابایتش زنده از آب درآمد.
- `16 MB goal`: اندازه‌ی heap که چرخه‌ی بعد قرار است در آن شروع شود.
- `8 P`: همان `GOMAXPROCS`.

از زمان‌ها نتیجه‌ای نمی‌گیرم، چون ماشین مشغول بود. اگر همین عددها را داخل برنامه‌تان بخواهید، `runtime.ReadMemStats` مقدار `NumGC` و `HeapAlloc` را می‌دهد (آزمایش‌های بعدی هر دو را به کار می‌برند).

## GOGC و GOMEMLIMIT: معاوضه‌ی حافظه با کار GC

چرا هدف ۱۶ مگابایت بود وقتی ۸ مگابایت زنده بود؟ تنظیم اصلی **GOGC** است که پیش‌فرضش ۱۰۰ است. طبق راهنمای GC، چرخه‌ی بعد وقتی شروع می‌شود که heap به حدود «heap زنده به‌علاوه‌ی `GOGC` درصدِ آن» برسد. با ۸ مگابایت زنده و `GOGC=100` این می‌شود حدود ۸ + ۸ = ۱۶ مگابایت، که دقیقاً همان هدف خط بالاست. پس `GOGC` بالاتر یعنی چرخه‌ی کمتر و heap بزرگ‌تر، و پایین‌تر یعنی برعکس.

برای آزمودنش، `gcdemo` ۲۰۰٬۰۰۰ slice چهار کیلوبایتی (کیبی‌بایتی) تخصیص می‌دهد (در کل حدود ۷۸۰ مگابایت)، ولی فقط یک پنجره‌ی چرخان ۲٬۰۰۰تایی از آن‌ها را زنده نگه می‌دارد، حدود ۸ مگابایت. بین اجراها فقط `GOGC` عوض می‌شود. شمارش‌ها بین اجراها کمی فرق می‌کنند، پس این‌ها بازه‌ی سه اجرای هر ردیف‌اند:

| GOGC | چرخه‌های GC | اوج HeapAlloc (نمونه‌برداری‌شده) |
|---|---|---|
| 50 | ۱۸۵ تا ۱۸۷ | ~۱۴ تا ۱۵ MiB |
| 100 | ~۹۰ تا ۹۲ | ~۱۸ تا ۱۹ MiB |
| 200 | ~۴۴ تا ۴۵ | ~۲۹ تا ۳۰ MiB |
| 400 | ~۲۲ | ~۴۶ تا ۵۰ MiB |
| off | ۰ | ~۷۷۷ MiB |

اوج یک مقدار نمونه‌برداری‌شده است (برنامه آن را هر ۱٬۰۰۰ تخصیص یک بار می‌خواند)، پس تقریبی است. الگو با فرمول جور است: دو برابر کردن `GOGC` چرخه‌ها را تقریباً نصف می‌کند و اوج از ۸ MiB × (۱ + GOGC/100) به‌علاوه‌ی کمی اضافه پیروی می‌کند. با خاموش بودن جمع‌کننده (`GOGC=off`) هیچ‌چیز آزاد نمی‌شود و اوج برابر هر بایتی است که تا حالا تخصیص داده شده، حدود ۷۷۷ مگابایت.

**GOMEMLIMIT** دستگیره‌ی دیگری است: یک سقف حافظه‌ی نرم. وقتی کل حافظه به آن نزدیک شود GC سخت‌تر کار می‌کند. با `GOGC=off GOMEMLIMIT=24MiB` برنامه حدود ۱۰۸ تا ۱۱۱ چرخه اجرا کرد و اوجش نزدیک ۱۷ تا ۱۸ مگابایت بود، به‌جای ۷۷۷ مگابایت. راه داشتن یک سقف حافظه در کانتینر همین است.

سقفی که به heap زنده خیلی نزدیک باشد خطرناک است. با `GOMEMLIMIT=12MiB`، وقتی همیشه حدود ۸ مگابایت زنده است، همان برنامه ۱٬۳۶۹ و ۱٬۵۵۶ چرخه اجرا کرد: جمع‌کننده تقریباً مدام در حال کار بود. سقف **نرم** است: runtime نمی‌تواند از مقدار زنده پایین‌تر برود و تضمین نمی‌کند زیر سقف بمانید.

## sync.Pool: از اول کمتر تخصیص بدهیم

ارزان‌ترین زباله زباله‌ای است که هرگز نساخته‌اید. **sync.Pool** اشیای موقتی را برای استفاده‌ی دوباره نگه می‌دارد. benchmark یک متن کوچک را در یک `bytes.Buffer` رندر می‌کند، یک بار با بافر تازه در هر دور و یک بار با بافر از pool (`-benchmem`، ۲۰٬۰۰۰ تکرار):

```
BenchmarkNoPool-8   20000   1984 B/op   5 allocs/op
BenchmarkPool-8     20000      0 B/op   0 allocs/op
```

بدون pool هر دور حدود ۲ کیلوبایت در ۵ تخصیص می‌گیرد. با آن، هیچ (بعد از گرم‌شدن). تخصیص کمتر یعنی چرخه‌ی GC کمتر. اما pool یک cache است، نه انبار: runtime ممکن است در هر GC اشیای داخل pool را دور بریزد، پس هرگز به ماندن یک شیء تکیه نکنید.

## دام‌های تنظیم runtime

- **`NumGoroutine` و تعداد thread به دو پرسش متفاوت جواب می‌دهند.** یکی Gها را می‌شمارد و دیگری Mها را. در پروداکشن هر دو را زیر نظر بگیرید: goroutine زیاد عادی است، ولی تعداد threadی که مدام بالا می‌رود به syscallهای مسدودکننده اشاره می‌کند.
- **اول `GOGC` را تنظیم نکنید.** اول پروفایل بگیرید (نگاه کنید به [پروفایلینگ با pprof](/fa/posts/go-profiling-pprof/)) و تخصیص‌ها را کم کنید؛ تنظیم فقط معاوضه را جابه‌جا می‌کند.
- **از `runtime.SetFinalizer` دوری کنید.** finalizerها در زمانی غیرقابل‌پیش‌بینی اجرا می‌شوند، یا هرگز.
- **شیء pool را پیش از استفاده‌ی دوباره ریست کنید و بعد از `Put` هرگز به آن دست نزنید.** ممکن است goroutine دیگری همین حالا آن را داشته باشد.
- **به یک خط trace اعتماد نکنید.** `schedtrace` و `gctrace` خروجی دیباگ‌اند؛ قالبشان ممکن است بین نسخه‌های Go عوض شود.

## تمرین

۱. برنامه‌ی threads را با ۱٬۰۰۰ goroutine در حالت `syscall` اجرا کنید و تعداد thread را مقایسه کنید. آیا متناسب بالا می‌رود؟
۲. تعداد چرخه‌های GC برای `GOGC=800` را از روی فرمول پیش‌بینی کنید، بعد `gcdemo` را با آن اجرا کنید و مقایسه کنید.
