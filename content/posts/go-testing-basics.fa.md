تابعی را عوض کرده‌اید و می‌خواهید بدانید هنوز درست کار می‌کند یا نه. راه کند این است که برنامه را اجرا کنید، این‌ور و آن‌ور کلیک کنید و امیدوار باشید. راه بهتر این است که چند برنامه‌ی کوچک نگه دارید که تابع را با ورودی‌های مشخص صدا بزنند و اگر جواب غلط بود بلند اعتراض کنند. این برنامه‌های کوچک همان **تست** هستند و بعد از هر تغییر، در یکی دو ثانیه اجرا می‌شوند.

Go این کار را ساده کرده، چون ابزارش جزو خود زبان است. پکیج `testing` و دستور `go test` همراه Go می‌آیند؛ پس چیزی نصب نمی‌کنید و لازم نیست بین فریم‌ورک‌ها انتخاب کنید. بعد از [generics](/fa/posts/go-generics/)، در این نوشته می‌بینیم تست چطور نوشته می‌شود، شکست تست را چطور بخوانیم، چطور چند حالت را بدون تکرار تست کنیم (سبک **table-driven**)، coverage یا «میزان پوشش تست» را چطور اندازه بگیریم و **benchmark** چیست؛ یعنی تستی که به‌جای درستیِ جواب، سرعت را اندازه می‌گیرد.

> همه‌ی مثال‌ها را روی macOS (arm64) با Go 1.27 اجرا کرده‌ام و خروجی‌ها از همان اجراها کپی شده‌اند. کد یک مثال محلی است، نه مخزن منتشرشده.

## اولین تست

Go تست‌ها را با یک قرارداد نام‌گذاری پیدا می‌کند، نه با تنظیمات. فایلی که نامش با `_test.go` تمام شود فایل تست است و معمولاً کنار کدی که تست می‌کند قرار می‌گیرد. داخل آن، هر تابعی که اسمش `TestChizi` باشد و یک پارامتر `*testing.T` بگیرد، یک تست است. این `t` دستگیره‌ی شما به تست است و با آن شکست را گزارش می‌دهید.

اول چیزی برای تست لازم داریم. این هم یک پکیج کوچک با یک تابع که دو عدد صحیح را تقسیم می‌کند و اگر مقسوم‌علیه صفر باشد خطا برمی‌گرداند:

```go
package calc

var ErrDivideByZero = errors.New("divide by zero")

func Divide(a, b int) (int, error) {
	if b == 0 {
		return 0, fmt.Errorf("divide %d by %d: %w", a, b, ErrDivideByZero)
	}
	return a / b, nil
}
```

و دو تست برایش. اولی حالت عادی را چک می‌کند و دومی اینکه تقسیم بر صفر همان خطای درست را بدهد:

```go
func TestDivide(t *testing.T) {
	got, err := Divide(10, 2)
	if err != nil {
		t.Fatalf("unexpected error: %v", err)
	}
	if got != 5 {
		t.Errorf("Divide(10, 2) = %d, want 5", got)
	}
}

func TestDivideByZero(t *testing.T) {
	_, err := Divide(1, 0)
	if !errors.Is(err, ErrDivideByZero) {
		t.Fatalf("err = %v, want ErrDivideByZero", err)
	}
}
```

توجه کنید که تابع `assert` ویژه‌ای در کار نیست. تست در Go کد معمولی است: نتیجه را با چیزی که انتظار دارید مقایسه می‌کنید و اگر فرق داشت، `t.Errorf` یا `t.Fatalf` را با یک پیام صدا می‌زنید.

این دو فقط در یک چیز فرق دارند. هر دو تست را شکست‌خورده علامت می‌زنند، ولی `t.Errorf` اجازه می‌دهد تست ادامه پیدا کند و `t.Fatalf` همان‌جا تست را متوقف می‌کند. جایی `Fatalf` بزنید که ادامه دادن بی‌معناست. در `TestDivide` اگر `err` برابر `nil` نباشد، مقدار `got` بی‌معنی است و چک کردنش فایده ندارد.

تست دوم از `errors.Is` استفاده می‌کند که در [توابع، defer و مدیریت خطا در Go](/fa/posts/go-functions-defer-errors/) دیدیم. `Divide` خطا را با `%w` بسته‌بندی می‌کند؛ پس مقایسه با `==` شکست می‌خورد، ولی `errors.Is` داخل بسته‌بندی را هم نگاه می‌کند.

تست‌ها را با `go test` اجرا می‌کنید. من تقریباً همیشه دو فلگ اضافه می‌کنم:

- `-v` هر تست و نتیجه‌اش را چاپ می‌کند، نه فقط خلاصه‌ی آخر را.
- `-count=1` حافظه‌ی نهان (cache) تست را خاموش می‌کند. Go نتیجه‌ی پکیجی را که کد و تستش عوض نشده به خاطر می‌سپارد و به‌جای اجرای دوباره، `(cached)` چاپ می‌کند. این برای سرعت خوب است، ولی وقتی می‌خواهید اجرای واقعی تست را ببینید گیج‌کننده است.

فلگ `-run` هم هست که یک عبارت باقاعده (regular expression) می‌گیرد و فقط تست‌هایی را اجرا می‌کند که نامشان با آن بخواند. دقت کنید که هر جای نام را می‌تواند بگیرد؛ پس `-run TestDivide` هر دو تست ما، یعنی `TestDivide` و `TestDivideByZero`، را اجرا می‌کند.

## شکست تست چه شکلی است

تست سبز چیز زیادی یاد نمی‌دهد؛ برای همین یکی را عمداً خراب کرده‌ام. این `add` باگ دارد و به‌جای جمع، تفریق می‌کند. در پوشه‌ی جدایی از پروژه‌ی دمو است:

```go
func add(a, b int) int { return a - b } // bug

func TestAdd(t *testing.T) {
	if got := add(2, 3); got != 5 {
		t.Errorf("add(2, 3) = %d, want 5", got)
	}
}
```

اجرای `go test` در آنجا این را چاپ می‌کند:

```text
--- FAIL: TestAdd (0.00s)
    b_test.go:9: add(2, 3) = -1, want 5
FAIL
FAIL	example.com/brokentest	0.973s
FAIL
```

خط دوم مهم‌ترین است: فایل و شماره‌ی خطِ چکی که شکست خورد، و بعد پیام خودمان. برای همین پیام را به شکل `got ..., want ...` می‌نویسیم. بدون باز کردن کد می‌بینید چه چیزی صدا زده شد، چه برگشت و چه باید برمی‌گشت. عدد `0.973s` زمان اجراست و هر بار فرق می‌کند. یک نکته‌ی دیگر: وقتی تستی شکست بخورد `go test` با کد خروج غیرصفر تمام می‌شود، و سیستم‌های CI از همین می‌فهمند که باید build را قرمز کنند.

## تست‌های table-driven

حالا فرض کنید تابعی دارید که ورودی‌های جالب زیادی دارد. این `Slug` است که عنوان را به رشته‌ای مناسب آدرس اینترنتی تبدیل می‌کند:

```go
func Slug(s string) string {
	return strings.Join(strings.Fields(strings.ToLower(s)), "-")
}
```

می‌توانستیم برای هر ورودی یک تابع تست بنویسیم، ولی هر کدام همان پنج خط را تکرار می‌کرد. جواب رایج در Go **تست table-driven** است: حالت‌ها را در یک slice از structها («جدول») می‌گذارید که هر ردیفش نام، ورودی و خروجی مورد انتظار دارد، و روی آن حلقه می‌زنید. اضافه کردن یک حالت می‌شود فقط یک خط.

برای هر ردیف `t.Run(name, func...)` را صدا می‌زنیم که یک **subtest** می‌سازد؛ یعنی تستی با نام، داخل یک تست. هر subtest خودش قبول یا رد می‌شود و با نامش در گزارش می‌آید.

مقایسه را هم در یک helper کوچک گذاشته‌ام. این helper، `t.Helper()` را صدا می‌زند که به Go می‌گوید «شکست را در خطِ من گزارش نکن، در خطِ کسی که مرا صدا زده گزارش کن». بدونش هر شکستی داخل `assertSlug` را نشان می‌داد، نه خطِ حالت تست را.

```go
func assertSlug(t *testing.T, in, want string) {
	t.Helper()
	if got := Slug(in); got != want {
		t.Errorf("Slug(%q) = %q, want %q", in, got, want)
	}
}

func TestSlug(t *testing.T) {
	tests := []struct {
		name string
		in   string
		want string
	}{
		{"simple", "Hello World", "hello-world"},
		{"extra spaces", "  Go   is fun ", "go-is-fun"},
		{"empty", "", ""},
		{"single", "Go", "go"},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			t.Parallel()
			assertSlug(t, tt.in, tt.want)
		})
	}
}
```

هر subtest `t.Parallel()` هم صدا می‌زند. این یعنی به Go می‌گوید subtest می‌تواند همزمان با همتاهایش اجرا شود. از Go 1.22 به بعد هر دور حلقه `tt` مخصوص خودش را دارد، پس closure امن است. فقط برای تست‌هایی از `t.Parallel()` استفاده کنید که state قابل‌تغییر مشترک ندارند.

برای اجرای فقط یک subtest، در الگوی `-run` یک اسلش بگذارید: بخش قبل از اسلش تست را می‌گیرد و بخش بعدش subtest را. فاصله‌ی داخل نام به underscore تبدیل می‌شود. اجرای حالت «extra spaces»:

```text
$ go test -v -count=1 -run 'TestSlug/extra' .
=== RUN   TestSlug
=== RUN   TestSlug/extra_spaces
=== PAUSE TestSlug/extra_spaces
=== CONT  TestSlug/extra_spaces
--- PASS: TestSlug (0.00s)
    --- PASS: TestSlug/extra_spaces (0.00s)
PASS
```

خط‌های `RUN` شروع تست و subtest را نشان می‌دهند. `PAUSE` و `CONT` (یعنی ادامه) از `t.Parallel()` می‌آیند: subtest موازی صبر می‌کند تا خودِ تابع تستِ والد کارش (اینجا حلقه‌ای که subtestها را شروع می‌کند) تمام شود و بعد کنار بقیه ادامه می‌دهد. وقتی چند subtest داریم، ترتیب خط‌های `CONT` و نتیجه‌ها می‌تواند از اجرایی به اجرای دیگر فرق کند. دو خط `PASS` آخر نتیجه است و subtest زیر والدش تورفتگی دارد.

## Coverage

بعد از نوشتن تست‌ها شاید بپرسید آیا واقعاً به همه‌ی کدتان می‌رسند. Go این را می‌تواند اندازه بگیرد. **Coverage** درصد دستورهایی است که حداقل یک بار هنگام اجرای تست‌ها اجرا شده‌اند:

```text
$ go test -count=1 -cover .
ok  	example.com/testing-basics	0.290s	coverage: 100.0% of statements
```

در این پکیج کوچک همه‌ی دستورها اجرا شد و ۱۰۰٪ گرفتیم. به آنچه این عدد می‌گوید دقت کنید. می‌گوید کدام خط‌ها هرگز اجرا نشده‌اند و این برای پیدا کردن کدِ بدون تست مفید است. اما نمی‌گوید چک‌های شما خوب‌اند یا نه: تستی که تابع را صدا می‌زند و هیچ‌چیز را چک نمی‌کند هم coverage می‌دهد. آن را ابزاری برای پیدا کردن حفره‌ها بدانید، نه هدف.

## Benchmark

تا اینجا سؤال این بود که «جواب درست است؟». سؤال دیگر این است که «چقدر سریع است؟». benchmark جوابش را می‌دهد. تابعی است به نام `BenchmarkChizi` که یک `*testing.B` می‌گیرد و Go بدنه‌اش را آن‌قدر تکرار می‌کند تا اندازه‌گیری پایدار شود. از Go 1.24 حلقه را با `b.Loop()` می‌نویسیم.

برای اینکه چیزی برای اندازه‌گیری داشته باشیم، دو روش چسباندن رشته‌های کوتاه را مقایسه می‌کنیم. اولی با `+=` است. دومی `strings.Builder` است که تکه‌ها را در یک بافر جمع می‌کند:

```go
func ConcatPlus(parts []string) string {
	s := ""
	for _, p := range parts {
		s += p
	}
	return s
}

func ConcatBuilder(parts []string) string {
	var sb strings.Builder
	for _, p := range parts {
		sb.WriteString(p)
	}
	return sb.String()
}

func BenchmarkConcatPlus(b *testing.B) {
	for b.Loop() {
		ConcatPlus(parts)
	}
}
```

`BenchmarkConcatBuilder` دقیقاً همین است، فقط تابع دیگر را صدا می‌زند. `parts` یک slice سطح پکیج با ۱۰۰۱ رشته‌ی کوتاه است و یک تست معمولی هم چک می‌کند که هر دو تابع نتیجه‌ی یکسان بدهند؛ پس مطمئنیم چیزهای هم‌ارز را مقایسه می‌کنیم.

حالا دستور. benchmarkها با `go test` ساده اجرا نمی‌شوند و `-bench .` همه‌ی آن‌ها را انتخاب می‌کند. `-run xxx` تست‌های معمولی را رد می‌کند (تستی به این نام نداریم) و `-benchmem` عددهای حافظه را هم اضافه می‌کند:

```text
$ go test -count=1 -run xxx -bench . -benchmem .
goos: darwin
goarch: arm64
pkg: example.com/testing-basics
cpu: Apple M1
BenchmarkConcatPlus-8      	   10000	    110425 ns/op	 1063869 B/op	     999 allocs/op
BenchmarkConcatBuilder-8   	  296140	      3936 ns/op	    5368 B/op	      10 allocs/op
```

یک ردیف را بخوانیم. `BenchmarkConcatPlus-8` نام است و `-8` مقدار `GOMAXPROCS`، یعنی تعداد thread‌هایی که Go اجازه دارد استفاده کند. عدد بعدی تعداد دفعاتی است که حلقه اجرا شده. بعد سه عدد جالب می‌آید: نانوثانیه در هر فراخوانی (`ns/op`)، بایتِ تخصیص‌یافته در هر فراخوانی (`B/op`) و تعداد دفعاتی که حافظه جداگانه گرفته شده (`allocs/op`).

دو ردیف داستان روشنی می‌گویند. در اجرای اصلی، نسخه‌ی `+=` حدود ۲۸ برابر کندتر بود و در هر فراخوانی نزدیک هزار allocation داشت، در برابر ده تا. دلیلش این است که رشته در Go تغییرناپذیر است؛ پس هر `+=` یک رشته‌ی تازه می‌سازد و هرچه تا اینجا جمع شده را کپی می‌کند. چسباندن ۱۰۰۱ تکه به این روش بارها و بارها کپی می‌کند. `strings.Builder` در بافری اضافه می‌کند که فقط گاهی بزرگ می‌شود.

زمان‌ها به ماشین و به کارهای دیگری که اجرا می‌شوند بستگی دارند؛ پس روی ماشین شما فرق می‌کنند. عددهای `ns/op` را از اجرای اصلی خودم برداشته‌ام. وقتی برای این نوشته دوباره اجرایش کردم ماشین مشغول بود و نسبت مشابه درآمد (تعداد allocationها، یعنی ۹۹۹ و ۱۰، هر بار یکی است).

## fuzzing در یک پاراگراف

Go {{< term "fuzzing" "fuzzing" >}} هم دارد. تابعی به نام `FuzzChizi(f *testing.F)` می‌نویسید، با `f.Add` چند ورودی شروع می‌دهید و Go هزاران تغییر از آن‌ها می‌سازد تا ورودی‌ای پیدا کند که قاعده‌ی شما را بشکند. با `go test -fuzz FuzzReverse -fuzztime 5s` اجرا می‌شود. من آن را روی تابعی امتحان کردم که rune‌های رشته را برعکس می‌کند، با این قاعده که «دوبار برعکس کردن باید همان ورودی را برگرداند» (ورودی‌های UTF-8 نامعتبر رد می‌شوند). در اجرای اصلی در ۵ ثانیه حدود ۳۰۰ هزار تلاش انجام شد و چیزی پیدا نکرد؛ این تعداد از اجرایی به اجرای دیگر فرق می‌کند. اگر ورودی شکست‌دهنده پیدا می‌شد، Go آن را زیر `testdata/` ذخیره می‌کرد و `go test` ساده از آن به بعد دوباره اجرایش می‌کرد.

## دام‌های رایج

- **تستی که «اجرا نمی‌شود».** اگر `-count=1` را نگذارید و `(cached)` ببینید، یعنی چیزی عوض نشده و Go نتیجه‌ی قبلی را به کار می‌برد. این عادی است، ولی ممکن است شبیه گیر کردن تست به نظر برسد.
- **`Fatal` یا `Error`.** وقتی خط‌های بعدی به چکی که همین حالا شکست خورد وابسته‌اند، `t.Fatal` بزنید. وقتی می‌خواهید همه‌ی شکست‌ها را در یک اجرا ببینید، `t.Error`.
- **ردیف‌های بی‌نام در جدول.** به هر حالت نام روشن بدهید. با همین نام شکست‌خورده را در خروجی پیدا می‌کنید و با `-run` تنها اجرایش می‌کنید.
- **benchmark کدی که کامپایلر می‌تواند حذفش کند.** اگر نتیجه‌ی کدِ اندازه‌گیری‌شده هرگز استفاده نشود، ممکن است کامپایلر کار را حذف کند و benchmark چیزی اندازه نگیرد. استفاده از نتیجه کمک می‌کند. طبق مستندات Go، `b.Loop()` هم جلوی حذف شدن فراخوانی‌های داخل حلقه را می‌گیرد.
- **state مشترک در subtestهای موازی.** اگر subtestهای موازی در یک متغیر بنویسند، data race دارید. آن‌ها را مستقل نگه دارید.

## تمرین

۱. یک تست table-driven برای `Divide` بنویسید با حالت عادی، عدد منفی و تقسیم بر صفر (خطا را با `errors.Is` چک کنید).
۲. تابع `ConcatJoin` را با `strings.Join` بنویسید و benchmark سوم را اضافه کنید. قبل از اجرا حدس بزنید کجا قرار می‌گیرد.
۳. `go test -cover` را اجرا کنید و شاخه‌ای را پیدا کنید که تستش نکرده‌اید.
