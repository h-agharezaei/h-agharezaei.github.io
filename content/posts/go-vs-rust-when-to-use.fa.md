«سرویس بعدی را با Go بنویسیم یا Rust؟» سؤال درستی است و هر جوابی که بدون زمینه بیاید مشکوک است. بنچمارک‌هایی که یک زبان را برنده اعلام می‌کنند معمولاً یک کار را روی یک ماشین با یک مجموعه تنظیم پیش‌فرض اندازه گرفته‌اند. جواب صادقانه از اینجا شروع می‌شود که چه می‌سازید و چه کسی نگهش می‌دارد.

من بیشتر با Go و Node.js کار می‌کنم و Rust را هنوز یاد می‌گیرم. پس این نوشته نظر یک نفر است همراه با کمی داده، نه حکم نهایی. مشخص کرده‌ام کجا اندازه گرفته‌ام، کجا از یک واقعیتِ مستند مطمئنم و کجا فقط تجربه‌ی خودم است. بعد از سری‌های [Go](/fa/posts/go-getting-started/) و [Rust](/fa/posts/rust-ownership/)، این اولین جایی است که دو زبان به هم می‌رسند.

برای اینکه بحث فقط نظر نباشد، با یک اندازه‌گیری کوچک شروع می‌کنم. در آن، Go سریع‌تر شمرد، Rust کمتر از نصف حافظه مصرف کرد و باینری‌اش زیر یک‌پنجم باینری Go شد، و با عوض‌کردن یک تنظیم پیش‌فرض، Rust از هر دو سریع‌تر شد. بخش آخر برایم مفیدترین است، چون نشان می‌دهد چقدر آسان است پیش‌فرض‌ها را مقایسه کنیم و خیال کنیم زبان‌ها را مقایسه کرده‌ایم.

## یک اندازه‌گیری کوچک

کار این است: شمردن اینکه هر کلمه چند بار در متنی تولیدشده با ۱۰ میلیون کلمه آمده. کار معمولیِ «بریز در hash map و یکی اضافه کن» است. متن حدود ۹۹٬۵۰۰ کلمه‌ی متمایز دارد و برنامه را در هر زبان به ساده‌ترین شکل رایج نوشتم.

متن را خود هر برنامه با یک **LCG** کوچک تولید می‌کند (linear congruential generator، یک مولد عدد شبه‌تصادفی که در دو خط جا می‌شود). هر دو برنامه از یک seed شروع می‌کنند و دقیقاً یک متن می‌سازند، و ساختن متن جزو زمان‌گیری نیست. هسته‌ی هر برنامه این است:

```go
counts := make(map[string]int)
for w := range strings.FieldsSeq(text) {
	counts[w]++
}
```

```rust
let mut counts: HashMap<&str, usize> = HashMap::new();
for w in text.split_whitespace() {
    *counts.entry(w).or_insert(0) += 1;
}
```

هر دو حلقه متن را روی فاصله‌ها می‌شکنند و شمارنده‌ی هر کلمه را در یک {{< term "hash-table" "hash map" >}} یکی زیاد می‌کنند. هر دو برنامه در پایان تعداد کلمه‌های متمایز و پرتکرارترین کلمه را چاپ می‌کنند. هر دو را دوباره با Go 1.27 و Rust 1.90 اجرا کردم و همین خط را چاپ کردند:

```text
distinct=99501 top=w2709:259
```

یعنی 99,501 کلمه‌ی متفاوت، و پرتکرارترین‌شان `w2709` است که ۲۵۹ بار آمده. اینکه دو زبان خروجی یکسان دادند، یعنی کار یکسانی انجام داده‌اند.

جدول زمان‌ها از اجرای اولیه‌ی من است، با Go 1.26 و Rust 1.90 (`cargo build --release` با تنظیمات پیش‌فرض) روی یک لپ‌تاپ arm64 با macOS. ماشین بیکار نبود و کارهای دیگری هم اجرا می‌شد. برای همین فقط میانه نمی‌دهم و پراکندگی را هم می‌آورم. **میانه** مقدار وسط اجراهاست و چند اجرای غیرعادی کند را نادیده می‌گیرد. هنگام بازنویسی این نوشته هم ماشین دوباره مشغول بود، برای همین زمان‌های تازه‌ای منتشر نکردم.

| اندازه‌گیری‌شده در اجرای اولیه | Go | Rust |
|---|---|---|
| زمان شمارش، میانه‌ی ۱۵ اجرا | 249 ms (کمینه 239، بیشینه 337) | 357 ms (کمینه 321، بیشینه 465) |
| اندازه‌ی باینری | 2,544,610 بایت | 445,600 بایت |
| build کامل release | ۲٫۴ تا ۳٫۳ ثانیه (با پاک‌کردن cache، ۳ اجرا) | ۰٫۳ تا ۰٫۹ ثانیه (با `cargo clean`، ۳ اجرا) |
| حافظه‌ی پیک (`/usr/bin/time -l`) | 167 تا 207 MB (۳ اجرا) | 81 MB (۳ اجرا) |

(در اجرای دوباره، باینری release در Rust باز هم 445,600 بایت شد؛ باینری Go 1.27 برابر 2,482,114 بایت بود، پس اندازه‌ی باینری Go به نسخه‌ی ابزار بستگی دارد.)

دو ردیف زمان build هم‌ارز نیستند. پاک‌کردن cache در Go باعث می‌شود کتابخانه‌ی استاندارد هم دوباره کامپایل شود. اما Cargo کتابخانه‌ی استاندارد از پیش‌ساخته‌ی `rustup` را لینک می‌کند و `cargo clean` فقط crate کوچک خودم را دوباره می‌سازد. این دو ردیف را «آنچه دیدم» بخوانید، نه مقایسه‌ی دو کامپایلر.

جدول چه می‌گوید؟ در همین آزمایش، شمارش در Go سریع‌تر بود و Rust حافظه و حجم باینری کمتری داشت. دلیلش را پروفایل نکرده‌ام، پس حدس نمی‌زنم.

یک چیز را آزمودم. `HashMap` در Rust به‌صورت پیش‌فرض یک {{< term "hash-collision" "hasher" >}} دارد (تابعی که کلید را به شماره‌ی سطل تبدیل می‌کند) که طوری طراحی شده در برابر حمله‌ی منع سرویس مقاوم باشد، یعنی وقتی کسی کلیدهایی می‌فرستد که عمداً با هم برخورد کنند. این ایمنی هزینه دارد. من یک hasher ساده‌ی FNV جایگزین کردم، حدود ده خط (باینری `fnv` در همان پروژه است و کامنتش می‌گوید مقاوم در برابر DoS نیست). میانه‌ی ۱۱ اجرا 214 ms شد، یعنی سریع‌تر از هر دوی اول. پس یک تنظیم پیش‌فرض، نه فقط خودِ زبان، این نتیجه را ساخت. با عوض شدن کار، رتبه‌ها هم می‌توانند عوض شوند. و این آزمایش درباره‌ی سرویس‌های شبکه‌ای چیزی نمی‌گوید.

## تفاوت‌هایی که از آن‌ها مطمئنم

عددها شکننده‌اند. تفاوت‌های زیر انتخاب‌های طراحیِ مستندند، نه اندازه‌گیری:

| | Go | Rust |
|---|---|---|
| حافظه | {{< term "garbage-collector" "garbage collector" >}}؛ [اشاره‌گر هست اما حافظه را مالکیت نمی‌کنید](/fa/posts/go-pointers-memory/) | بدون GC؛ [ownership](/fa/posts/rust-ownership/) و [borrowing](/fa/posts/rust-borrowing-references/) موقع کامپایل بررسی می‌شوند |
| خطا | [مقدار برگشتیِ تابع](/fa/posts/go-functions-defer-errors/)، بررسی‌اش قراردادی است | [`Result` و `?`](/fa/posts/rust-error-handling-result/)، جزو نوع است و نادیده‌گرفتنش هشدار می‌دهد |
| همزمانی | [goroutine و channel](/fa/posts/go-goroutines-channels/) در خود زبان و runtime | thread سیستم‌عامل در کتاب‌خانه‌ی استاندارد؛ async به یک crate برای runtime نیاز دارد؛ data race خطای کامپایل است |
| runtime | در هر باینری یک runtime (scheduler و GC) هست | runtime‌ای همراه نیست |

خلاصه‌اش این است: Go حافظه و همزمانی را با کار کردن برای شما در زمان اجرا آسان می‌کند. Rust اول از شما می‌خواهد به کامپایلر ثابت کنید همه‌چیز درست است، و در عوض چیزی پشت سرتان در زمان اجرا کار نمی‌کند.

چیزهایی هم هست که باور دارم ولی اینجا نمی‌توانم ثابتشان کنم: Go حتی روی پروژه‌های بزرگ سریع کامپایل می‌شود و Rust معمولاً کندتر؛ اکوسیستم Go برای کار بک‌اند جاافتاده‌تر است و اکوسیستم Rust جوان‌تر و در حال رشد. این‌ها را با stack خودتان بسنجید.

درباره‌ی منحنی یادگیری فقط تجربه‌ی خودم معتبر است. در Go ظرف چند روز مولد شدم. در Rust چند هفته طول کشید تا کامپایلر دیگر غافلگیرم نکند، هرچند پیام‌هایش معلم‌های خوبی‌اند. پیشینه‌ی شما این را تغییر می‌دهد.

## چه زمانی کدام

**Go وقتی مناسب است** که سرویس شبکه‌ای، ابزار خط فرمان یا ابزار داخلی می‌سازید و تیم باید زود مولد شود. زبان کوچک است، کتاب‌خانه‌ی استاندارد HTTP و JSON و تست را پوشش می‌دهد و [ابزارها](/fa/posts/go-getting-started/) یک دستور است. برای بیشتر سرویس‌ها garbage collector معامله‌ی قابل‌قبولی است.

**Rust وقتی مناسب است** که محدودیت سخت تأخیر یا حافظه دارید و توقف‌هایی را که ممکن است garbage collector بیاورد نمی‌توانید بپذیرید. همچنین وقتی هدفتان سیستم‌های نهفته یا WebAssembly بدون runtime است، یا کتاب‌خانه‌ای می‌نویسید که درستی‌اش آن‌قدر مهم است که می‌خواهید کامپایلر دسته‌هایی از باگ‌ها را رد کند.

برای بیشتر APIهای CRUD، مصرف‌کننده‌های صف و کدهای واسط، فرق چندانی نمی‌کند. دیتابیس، شبکه و کیفیت طراحی بیش از زبان اثر دارند. چیزی را انتخاب کنید که تیمتان بتواند نگهش دارد.

## دام‌های مقایسه

- یک ریزبنچمارک درباره‌ی بار کاری شما مدرک نیست. خودتان اندازه بگیرید.
- پیش‌فرض‌ها مهم‌اند. hasher بالا یک نمونه است؛ allocator، پروفایل build و تنظیمات GC هم عددها را عوض می‌کنند.
- نوسان بین اجراها روی ماشین مشغول می‌تواند از فرق دو زبان بیشتر باشد. برای همین جدول کمینه و بیشینه را هم نشان می‌دهد.
- «سریع‌تر» به‌ندرت نیاز واقعی است. بپرسید چه محدودیتی در تأخیر، حافظه یا استخدام دارید.
- هر دو زبان یادگرفتنی‌اند. من هنوز برای بیشتر سرویس‌ها Go را انتخاب می‌کنم و Rust را یاد می‌گیرم تا بدانم کجا ابزار بهتری است.
