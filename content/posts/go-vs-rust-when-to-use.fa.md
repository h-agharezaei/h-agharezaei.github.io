مبانی Go تمام شده و سری Rust هم به ownership، borrowing و مدیریت خطا رسیده است. پس وقت خوبی است به پرسشی جواب بدهم که همیشه پرسیده می‌شود: کدام را انتخاب کنم؟ من بیشتر با Go و Node.js کار می‌کنم و Rust را هنوز یاد می‌گیرم؛ پس این نوشته نظر یک نفر همراه با کمی داده است، نه حکم نهایی. هرجا چیزی را اندازه گرفته‌ام صریح می‌گویم و هرجا فقط تجربه‌ی خودم است هم همین‌طور.

## یک اندازه‌گیری کوچک

کار: شمردن تکرار کلمه‌ها در متنی تولیدشده با ۱۰ میلیون کلمه (حدود ۹۹٬۵۰۰ کلمه‌ی متمایز)، به ساده‌ترین شکل رایج در هر زبان. متن را هر دو برنامه با یک LCG کوچکِ یکسان در حافظه می‌سازند و زمان ساخت جزو اندازه‌گیری نیست. هسته‌ی هر برنامه:

```go
counts := make(map[string]int)
for w := range strings.FieldsSeq(text) {
	counts[w]++
}
```

```rust
let mut counts: HashMap<&str, usize> = HashMap::new();
for w in text.split_whitespace() {
    *counts.entry(w).or_insert(0) += 1;
}
```

هر دو یک نتیجه چاپ می‌کنند، و از همین می‌دانم کار یکسانی انجام می‌دهند:

```text
distinct=99501 top=w2709:259
```

همه‌ی اعداد زیر روی یک لپ‌تاپ arm64 با macOS، Go 1.26 و Rust 1.90 (`cargo build --release` با تنظیمات پیش‌فرض) اندازه‌گیری شده‌اند. ماشین بیکار نبود (کارهای دیگری اجرا می‌شد)، پس پراکندگی به اندازه‌ی میانه اهمیت دارد.

| اندازه‌گیری‌شده در اینجا | Go | Rust |
|---|---|---|
| زمان شمارش، میانه‌ی ۱۵ اجرا | 249 ms (کمینه 239، بیشینه 337) | 357 ms (کمینه 321، بیشینه 465) |
| اندازه‌ی باینری | 2,544,610 بایت | 445,600 بایت |
| build کامل release | ۲٫۴ تا ۳٫۳ ثانیه (با پاک‌کردن cache، ۳ اجرا) | ۰٫۳ تا ۰٫۹ ثانیه (با `cargo clean`، ۳ اجرا) |
| حافظه‌ی پیک (`/usr/bin/time -l`) | 167 تا 207 MB (۳ اجرا) | 81 MB (۳ اجرا) |

دو ردیف زمان build هم‌ارز نیستند. پاک‌کردن cache در Go باعث می‌شود کتابخانه‌ی استاندارد هم دوباره کامپایل شود، در حالی که Cargo کتابخانه‌ی استاندارد از پیش‌ساخته‌ی rustup را لینک می‌کند و `cargo clean` فقط crate کوچک خودم را دوباره می‌سازد. آن‌ها را «آنچه دیدم» بخوانید، نه مقایسه‌ی دو کامپایلر.

این فقط یک ریزبنچمارک است. در همین آزمایش، شمارش در Go سریع‌تر بود و Rust حافظه و حجم باینری کمتری داشت. دلیلش را پروفایل نکرده‌ام. یک چیز را آزمودم: `HashMap` در Rust به‌صورت پیش‌فرض یک hasher مقاوم در برابر حمله‌ی DoS دارد. با جایگزین کردن یک hasher ساده‌ی FNV (حدود ده خط، در bin به نام `fnv` در همان پروژه) میانه‌ی ۱۱ اجرا به 214 ms رسید، یعنی از هر دو سریع‌تر. پس یک تنظیم پیش‌فرض، نه فقط خودِ زبان، این نتیجه را ساخت. با عوض شدن کار، رتبه‌ها هم می‌توانند عوض شوند، و این عددها درباره‌ی سرویس‌های شبکه‌ای چیزی نمی‌گویند.

## تفاوت‌هایی که از آن‌ها مطمئنم

| | Go | Rust |
|---|---|---|
| حافظه | garbage collector؛ [اشاره‌گر هست اما حافظه را مالکیت نمی‌کنید](/fa/posts/go-pointers-memory/) | بدون GC؛ [ownership](/fa/posts/rust-ownership/) و [borrowing](/fa/posts/rust-borrowing-references/) موقع کامپایل بررسی می‌شوند |
| خطا | [مقدار برگشتیِ تابع](/fa/posts/go-functions-defer-errors/)، بررسی‌اش قراردادی است | [`Result` و `?`](/fa/posts/rust-error-handling-result/)، جزو نوع است و نادیده‌گرفتنش هشدار می‌دهد |
| همزمانی | [goroutine و channel](/fa/posts/go-goroutines-channels/) در خود زبان و runtime | thread سیستم‌عامل در کتاب‌خانه‌ی استاندارد؛ async به یک crate برای runtime نیاز دارد؛ data race خطای کامپایل است |
| runtime | در هر باینری یک runtime (scheduler و GC) هست | runtime‌ای همراه نیست |

چیزهایی که باور دارم ولی اینجا نمی‌توانم ثابتشان کنم: Go روی پروژه‌های بزرگ سریع کامپایل می‌شود و Rust معمولاً کندتر؛ اکوسیستم Go برای کار بک‌اند جاافتاده‌تر است و اکوسیستم Rust جوان‌تر و در حال رشد. این‌ها را با stack خودتان بسنجید.

درباره‌ی منحنی یادگیری فقط تجربه‌ی خودم معتبر است: در Go ظرف چند روز مولد شدم، اما در Rust چند هفته طول کشید تا کامپایلر دیگر غافلگیرم نکند، هرچند پیام‌هایش معلم‌های خوبی‌اند. پیشینه‌ی شما این را تغییر می‌دهد.

## چه زمانی کدام

Go وقتی مناسب است که سرویس شبکه‌ای، CLI یا ابزار داخلی می‌سازید و تیم باید زود مولد شود. زبان کوچک است، کتاب‌خانه‌ی استاندارد HTTP و JSON و تست را پوشش می‌دهد و [ابزارها](/fa/posts/go-getting-started/) یک دستور است. برای بیشتر سرویس‌ها GC معامله‌ی قابل‌قبولی است.

Rust وقتی مناسب است که محدودیت سخت تأخیر یا حافظه دارید و توقف GC را نمی‌توانید بپذیرید، هدفتان سیستم‌های نهفته یا WebAssembly بدون runtime است، یا کتاب‌خانه‌ای می‌نویسید که درستی‌اش آن‌قدر مهم است که می‌خواهید کامپایلر دسته‌هایی از باگ‌ها را رد کند.

برای بیشتر APIهای CRUD، مصرف‌کننده‌های صف و کدهای واسط، فرق چندانی نمی‌کند. دیتابیس، شبکه و کیفیت طراحی بیش از زبان اثر دارند. چیزی را انتخاب کنید که تیمتان بتواند نگهش دارد.

## چند نکته

- یک ریزبنچمارک درباره‌ی بار کاری شما مدرک نیست. خودتان اندازه بگیرید.
- پیش‌فرض‌ها مهم‌اند: hasher، allocator، پروفایل build و تنظیمات GC همگی عددها را عوض می‌کنند.
- نوسان بین اجراها روی ماشین مشغول می‌تواند از فرق دو زبان بیشتر باشد.
- «سریع‌تر» به‌ندرت نیاز واقعی است؛ بپرسید چه محدودیتی در تأخیر، حافظه یا استخدام دارید.
- هر دو زبان یادگرفتنی‌اند. من هنوز برای بیشتر سرویس‌ها Go را انتخاب می‌کنم و Rust را یاد می‌گیرم تا بدانم کجا ابزار بهتری است.

## قدم بعدی

سری Rust با closure و iterator ادامه پیدا می‌کند. در سری Go Backend، مقاله‌ی بعد درباره‌ی config، structured logging و خطاها در Go است.
