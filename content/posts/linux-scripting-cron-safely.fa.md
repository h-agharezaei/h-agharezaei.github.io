اسکریپتی وقتی دستی اجرایش می‌کنید کار می‌کند. آن را در cron می‌گذارید و ساعت ۳ صبح بی‌صدا شکست می‌خورد. کسی خطایی نمی‌بیند، چون cron ترمینالی ندارد که خطا را نشان بدهد. چند روز بعد یکی می‌فهمد پشتیبان از آخرین deploy تا حالا اجرا نشده است. وقتی بالاخره نگاه می‌کنید، علت کوچک است: ابزاری که در `PATH` شما هست ولی در `PATH` خود cron نیست، یا متغیری که خالی بود، یا دو اجرا که روی هم افتادند و یکدیگر را بازنویسی کردند.

این آخرین پست سری Linux درباره‌ی نوشتن اسکریپت‌های کوچک اطراف سرویس‌هاست، طوری که بلند و واضح شکست بخورند و نه بی‌صدا، و درباره‌ی واقعیت‌هایی از cron که آدم‌ها را غافلگیر می‌کند. روی [پوسته‌ی کاربردی: pipe، redirect و xargs](/fa/posts/linux-shell-practical/)، [پروسه و سیگنال](/fa/posts/linux-processes-signals/) (برای `trap` که برای پاک‌سازی به کار می‌بریمش) و [systemd: واحدها و timerها](/fa/posts/linux-systemd-units-timers/) بنا شده، که جایگزین مدرن cron است. پست قبلی، [strace و perf برای عیب‌یابی](/fa/posts/linux-strace-perf/)، همان چیزی است که وقتی اسکریپتی باز هم بد رفتار می‌کند سراغش می‌روید.

> نکته‌ی صادقانه: همه‌چیز اینجا روی **macOS** اجرا شد، با `/bin/sh` و `/bin/bash` (نسخه‌ی 3.2) و ابزارهای BSD. `flock` و `shellcheck` اینجا نصب نیستند (`command -v` چیزی چاپ نکرد)، پس اجرایشان نکردم. این macOS یک `timeout` از نوع BSD دارد که پایین‌تر به آن اشاره می‌کنم. به crontab واقعی‌ام دست نزدم. الگوهای خطرناک فقط با `echo` چاپ شدند، یا در یک پوشه‌ی دورریختنی که خودم ساخته بودم اجرا شدند.

## باگ‌های کلاسیک، واقعاً اجراشده

قاعده‌ی اول اسکریپت‌های shell این است که shell پیش از اجرای دستور، متن را جایگزین می‌کند و اگر متن آن چیزی نباشد که می‌خواستید هشدار نمی‌دهد. مثال معروف متغیر خالی همراه با glob است. `rm` را اجرا نکردم. فقط چاپ کردم shell چه چیزی را به آن می‌دهد:

```sh
dir=""; echo rm -rf $dir/*
```
```
rm -rf /Applications /Library /System /Users /Volumes /bin /cores /...
```

`$dir` خالی ناپدید شد، `$dir/*` شد `/*` و shell آن را به پوشه‌های واقعی سطح بالای ماشین باز کرد. (فهرست را کوتاه کردم؛ ادامه دارد.) با `rm -rf` واقعی این یک فاجعه است. دو ویژگی shell جلویش را می‌گیرند. `set -u` استفاده از متغیر تعریف‌نشده را خطا می‌کند و `${dir:?پیام}` وقتی متغیر تعریف‌نشده یا خالی باشد اسکریپت را متوقف می‌کند:

```sh
sh -c 'set -u; echo "$undefined_v"'     # sh: undefined_v: unbound variable
sh -c 'dir=""; echo "${dir:?dir is empty}/x"'   # sh: dir: dir is empty
```

هر دو دستور روی این مک با کد خروج 127 متوقف شدند. (کد دقیق و متن پیام به shell بستگی دارد.)

تله‌ی بعدی **word splitting** است. وقتی `$var` را بدون کوتیشن می‌نویسید، shell مقدار را سر فاصله‌ها می‌برد و تکه‌ها را آرگومان‌های جدا حساب می‌کند. {{< term "word-splitting" "word splitting" >}} به نام فایل‌ها هم می‌خورد. روی glob حلقه بزنید، نه روی خروجی `ls`. اینجا پوشه دو فایل دارد، `a` و `b c` (اسمی با فاصله):

```sh
for f in $(ls d2); do echo "[$f]"; done    # [a] [b] [c]     "b c" was split in two
for f in d2/*;     do echo "[$f]"; done    # [d2/a] [d2/b c]
```

حلقه‌ی اول سه کلمه دید، پس سه بار اجرا شد و نام واقعی را هرگز ندید. دومی glob را مستقیم به shell می‌دهد و هر تطبیق یک مورد می‌ماند، با فاصله‌اش. و داخل حلقه هم همیشه متغیر را کوتیشن کنید: `"$f"`.

سومی: `cd` شکست‌خورده اسکریپت را متوقف نمی‌کند. این را در پوشه‌ای به نام `sandbox` اجرا کردم:

```sh
cd nodir; echo "now in: $(basename "$PWD")"     # now in: sandbox
```

`cd` شکست خورد، اسکریپت ادامه داد و دستور بعدی در پوشه‌ی اشتباه اجرا شد. اگر آن دستور `rm` بود، فایل‌های جای اشتباه پاک می‌شد. بنویسید `cd nodir || exit 1`.

چند مورد کوچک‌تر که اجرا کردم:

- `read l` فاصله‌های ابتدا و انتها را می‌برد: `  lead  ` شد `[lead]`. `IFS= read -r l` دقیقاً نگهش داشت: `[  lead  ]`. `-r` جلوی تفسیر بک‌اسلش را هم می‌گیرد.
- با `v` خالی، `[ $v = x ]` می‌شود `[ = x ]` و با `unary operator expected` شکست می‌خورد (کد 2). `[[ $v = x ]]` در bash تمیز 1 (نادرست) برگرداند. ولی `[[ ]]` ویژگی bash است و بخشی از POSIX `sh` نیست، پس به‌جایش متغیر را کوتیشن کنید: `[ "$v" = x ]`.
- نام فایلی که با خط تیره شروع شود شبیه گزینه است. `rm -- -n` فایلی به نام `-n` را پاک می‌کند، چون `--` تجزیه‌ی گزینه‌ها را تمام می‌کند. (در پوشه‌ی موقت امتحانش کردم.)

## set -e: تور ایمنی با سوراخ

بسیاری اسکریپت را با `set -e` شروع می‌کنند، یعنی «اگر دستوری شکست خورد خارج شو». کمک می‌کند، ولی استثناهایی دارد که آدم‌ها را غافلگیر می‌کند. هر کدام از این‌ها اجرای واقعی روی این مک است. تک‌خطی‌هایی هستند که به `sh -c` داده شدند:

```sh
set -e; false && echo no; echo "reached"                 # reached          (exit 0)
set -e; f() { false; echo "in f"; }; f || echo failed    # in f             (set -e is off inside f)
set -e; ( false; echo inner ) || echo handled            # inner            (set -e is off in the subshell, too)
set -e; false | true; echo "pipe hidden"                 # pipe hidden
set -eo pipefail; false | true; echo no                  # (nothing)        exit 1
```

خط‌به‌خط. در اولی، شکست در سمت چپ `&&` «مدیریت‌شده» حساب می‌شود، پس اسکریپت نمی‌ایستد. در دومی، تابعی که به‌عنوان بخشی از `f || ...` صدا زده شود با `set -e` نادیده‌گرفته‌شده اجرا می‌شود، پس `false` آن را متوقف نکرد و با اینکه `false` شکست خورده بود `in f` چاپ شد. سومی همین ایده برای subshell داخل یک فهرست `||` است: `inner` چاپ شد و `handled` نه، چون آخرین دستور subshell موفق بود. در چهارمی، وضعیت یک pipeline وضعیت **آخرین** دستور آن است، پس `false` شکست‌خورده پشت `true` پنهان شد. `pipefail` این را درست می‌کند: با آن، اگر هر بخش pipeline شکست بخورد کل آن شکست می‌خورد و اسکریپت با کد 1 خارج شد.

درس: `set -e` تور ایمنی است، نه برنامه. `set -u` و، در shellهایی که پشتیبانی می‌کنند، `pipefail` را هم اضافه کنید و باز هم دستورهای مهم را صریح بررسی کنید.

## فایل موقت و نوشتن اتمیک

دو اسکریپت که نام ثابتی برای فایل موقت دارند، مثل `/tmp/foo`، می‌توانند به هم بخورند و نام قابل‌پیش‌بینی دعوت‌نامه‌ی {{< term "race-condition" "race condition" >}} و حمله است. با `mktemp -d` یک پوشه‌ی خصوصی بسازید و با `trap` هنگام خروج اسکریپت پاکش کنید.

مشکل مرتبط: می‌خواهید فایل پیکربندی‌ای را عوض کنید که برنامه‌های دیگر می‌خوانند. اگر فایل را خالی کنید و بعد محتوای تازه را بنویسید، خواننده‌ای که بین این دو لحظه نگاه کند فایل خالی یا نیمه‌نوشته می‌بیند. راهش {{< term "atomic-write" "نوشتن اتمیک" >}} است: محتوای تازه را در فایل موقتی در همان پوشه بنویسید و بعد با `mv` روی فایل قدیمی بگذارید. روی یک فایل‌سیستم، rename اتمیک است، پس خواننده یا فایل قدیمی را می‌بیند یا تازه را، هرگز چیزی بین این دو را.

این را با `atomic.sh` آزمودم: نویسنده‌ای `cfg.txt` را 300 بار بازنویسی می‌کند، یک بار به روش ساده (خالی کن، بعد پر کن) و یک بار با نوشتن و rename، و در همین حال خواننده‌ای در حلقه فایل را تا جایی که می‌تواند سریع می‌خواند. خواندنی را بد می‌شمارد که محتوایش کامل به نظر نیاید. خروجی واقعی یک اجرا:

```
naive:  reads=8   bad_reads=6
atomic: reads=216 bad_reads=0
```

در حالت ساده، بیشتر خواندن‌ها فایل را خالی گرفتند. در حالت اتمیک هیچ‌کدام. شمارش‌ها در هر اجرا فرق می‌کنند (هر حالت را سه بار اجرا کردم: حالت ساده هر بار 5 یا 6 خواندن بد از 8 یا 9 داشت و حالت اتمیک همیشه 0) و این ماشین مشغول بود. تعداد کل خواندن‌ها بین دو حالت فرق دارد، چون دو نویسنده زمان متفاوتی می‌برند. پس فقط مقایسه‌ی صفر خواندن بد با خواندن بد زیاد معنی دارد.

## قفلی که روی macOS و Linux کار می‌کند

اگر اسکریپتی هر دقیقه اجرا شود و یک اجرا گاهی دو دقیقه طول بکشد، دو نسخه روی هم می‌افتند. جواب معمول در Linux دستور `flock -n` از util-linux است. طبق man pageش، flock قفل‌های `flock(2)` را از shell مدیریت می‌کند و `-n` باعث می‌شود وقتی قفل گرفته است به‌جای منتظر ماندن شکست بخورد. `flock` **فقط Linux** است و اینجا اجرایش نکردم.

روی macOS (و هر سیستم POSIX) می‌توانید از چیزی استفاده کنید که همه‌جا هست: `mkdir`. ساختن پوشه اتمیک است، پس دقیقاً یک پروسه در ساختنش موفق می‌شود. `lock.sh` من یک پوشه‌ی قفل می‌سازد، pid خودش را داخلش می‌نویسد و هنگام خروج با `trap` پوشه را پاک می‌کند. اگر پوشه از قبل باشد، بررسی می‌کند pid داخلش هنوز زنده است یا نه (`kill -0` سیگنالی نمی‌فرستد، فقط بررسی می‌کند). یک نسخه را شروع کردم که 3 ثانیه کار می‌کند و یک ثانیه بعد نسخه‌ی دیگری:

```
<utc-time> pid 80555: got the lock, working for 3s
<utc-time> pid 80560: already running as pid 80555, exiting       (exit status 75)
<utc-time> pid 80555: done
```

اجرای دوم مالک زنده دید و با 75 خارج شد (کد «شکست موقت» در `sysexits.h`؛ خود عدد انتخاب من است). pidها در هر اجرا فرق می‌کنند. برای آزمودن حالت مالک مرده، پوشه‌ی قفلی ساختم که فایل pidش `99999` می‌گفت، pidی که اجرا نمی‌شد، و اسکریپت را شروع کردم:

```
<utc-time> pid 80569: stale lock (pid 99999 is gone), taking over
<utc-time> pid 80569: got the lock, working for 1s
<utc-time> pid 80569: done
```

متوجه شد مالک رفته، قفل را کهنه نامید، تحویل گرفت و تمام کرد. این قفل محدودیت دارد. دو پروسه هنوز می‌توانند هنگام تحویل‌گرفتن race کنند (اسکریپت با بررسی دوباره‌ی `mkdir` سعی می‌کند بفهمد) و pidها دوباره استفاده می‌شوند، پس pid یک مالک مرده می‌تواند بعداً مال پروسه‌ی بی‌ربطی باشد. برای کار شبانه خوب است و برای محافظت از پول کافی نیست.

## خود cron

حالا cron. این واقعیت‌ها از `man 5 crontab` روی همین مک است که صفحه‌ای به سبک Vixie است. صفحه‌ی یک توزیع Linux ممکن است در جزئیات فرق کند، پس صفحه‌ی خودتان را بررسی کنید.

- هر خط پنج فیلد زمان دارد: دقیقه، ساعت، روز ماه، ماه، روز هفته (هم 0 و هم 7 یکشنبه است) و بعد دستور. فیلدها بازه، فهرست و گام می‌پذیرند. ثانیه ندارد.
- اگر **هر دو** فیلد روز (روز ماه و روز هفته) محدود شده باشند، دستور وقتی اجرا می‌شود که **یکی** از آن‌ها بخواند. پس `30 4 1,15 * 5` روز اول، روز پانزدهم و هر جمعه اجرا می‌شود، نه فقط جمعه‌هایی که اول یا پانزدهم‌اند.
- `%` در دستور به خط جدید تبدیل می‌شود (و آنچه بعدش می‌آید به‌عنوان ورودی به دستور می‌رسد) مگر اینکه `\%` بنویسید. این `date +%F` را در crontab خراب می‌کند، که تله‌ای کلاسیک است.
- خروجی به مالک، یا به `MAILTO`، ایمیل می‌شود مگر ریدایرکتش کنید. با `MAILTO=""` خالی ایمیلی فرستاده نمی‌شود.
- بخش BUGS صفحه هشدار می‌دهد کارهای زمان‌بندی‌شده هنگام تغییر ساعت تابستانی تحت تأثیر قرار می‌گیرند، پس در آن بازه زمان‌بندی نکنید.
- محیط حداقلی است. این صفحه سه متغیر را نام می‌برد که cron می‌گذارد: `SHELL` (برابر `/bin/sh`)، `LOGNAME` و `HOME`. نمی‌گوید `PATH` چیست، پس `PATH` خودتان را بالای crontab یا در اسکریپت بگذارید.
- این صفحه درباره‌ی جبران اجراهای ازدست‌رفته وقتی ماشین خاموش بود چیزی نمی‌گوید. timer در systemd با `Persistent=true` طبق systemd.timer جبران می‌کند.

برای حس کردن مشکل «محیط حداقلی»، آن را با `env -i` شبیه‌سازی کردم، که دستور را با محیط خالی شروع می‌کند، و بعد همان سه متغیر را اضافه کردم. این **cron نیست**، فقط جایگزین است:

```
$ env -i SHELL=/bin/sh LOGNAME=demo HOME=/nonexistent /bin/sh -c 'echo "PATH=[$PATH]"; command -v go || echo "go: not found"'
PATH=[/usr/gnu/bin:/usr/local/bin:/bin:/usr/bin:.]
go: not found
```

در shell معمولی من `go` پیدا می‌شود، زیر `/opt/homebrew/bin`. با محیط خالی، shell به `PATH` پیش‌فرض داخلی خودش برمی‌گردد که آن پوشه را ندارد و دستور پیدا نمی‌شود. اسکریپتی که برای شما کار می‌کند و در cron نه، دقیقاً همین شکلی است. `PATH` پیش‌فرض داخلی مال همین shell است و مقدار cron ممکن است فرق کند، پس آن خط را به‌عنوان واقعیتی درباره‌ی cron کپی نکنید.

یک parser عبارت cron، یک محاسبه‌گر «اجراهای بعدی» و یک linter هم با Go نوشتم. تست‌هایش (`go test -race` سبز می‌شود) مثال‌هایی از man page دارند. این اجراهای بعدی به UTC است، شمرده از دوشنبه 2027-06-07 ساعت 10:00:

```
"30 4 1,15 * 5"   Fri 2027-06-11 04:30, Tue 06-15, Fri 06-18, Fri 06-25, Thu 07-01
"0 0 31 2 *"      never runs
"@daily"          Tue 2027-06-08 00:00, Wed 06-09, Thu 06-10, ...
```

(کوتاه‌شده: خروجی واقعی هر زمان را در خط جدا، با سال و `UTC` چاپ می‌کند.) خط اول قاعده‌ی «یا این یا آن» را در عمل نشان می‌دهد: جمعه‌ی 11، بعد سه‌شنبه‌ی 15 (تطبیق روز ماه) و بعد جمعه‌ها. دومی تاریخ ناممکن 31 فوریه است و برنامه به‌جای حلقه‌ی بی‌پایان همین را می‌گوید. برای یک خط کامل crontab، linter دنبال اشتباه‌های رایج می‌گردد. این خروجی واقعی برای `0 3 * * * backup.sh` است:

```
  WARN: minute 0: many jobs start together; pick an odd minute
  WARN: command backup.sh has no absolute path; cron's PATH is minimal
  WARN: output is not redirected; cron will mail it (or drop it)
```

هشدار دقیقه‌ی 0 توصیه‌ی خودم است، نه قاعده‌ی cron: اگر همه‌ی تیم‌ها کارها را روی دقیقه‌ی 0 بگذارند، ماشین یک‌دفعه موجی از کار می‌گیرد، پس دقیقه‌ی فرد انتخاب کنید یا تأخیر تصادفی کوچکی اضافه کنید.

## جایگزین‌های cron

timer در systemd برای زمان‌های تقویمی `OnCalendar=` دارد، برای جبران اجراهای ازدست‌رفته‌ی زمان خاموشی `Persistent=` و برای پخش کردن کارها `RandomizedDelaySec=`، همه طبق systemd.timer. اینجا اجرایشان نکردم. و CronJob در Kubernetes فیلدی به نام `concurrencyPolicy` دارد (`Allow` یا `Forbid` یا `Replace`) که می‌گوید وقتی اجرای قبلی هنوز در جریان است چه شود، پس طبق مستندات لازم نیست آنجا قفل خودتان را بنویسید.

## الگویی که همه را کنار هم می‌گذارد

این رویه‌ها را در `template.sh` کنار هم گذاشتم (حدود 30 خط `sh` مطابق POSIX). `set -eu`، `PATH` ثابت، `umask 077`، تجزیه‌ی گزینه با `getopts`، پرچم dry-run یعنی `-n`، قفل `mkdir`، پوشه‌ی کار `mktemp -d` همراه `trap` و لاگ‌های UTC روی stderr دارد. برای آزمون، اسکریپت تعداد خط‌های فایل‌های ورودی را می‌شمارد و شمارش‌ها را در یک پوشه‌ی خروجی می‌نویسد. اجراهای واقعی، با مسیر اسکریپت جایگزین‌شده با `<demo>`:

```
$ sh template.sh
usage: <demo>/template.sh [-n] [-o outdir] [--] input...      (exit 2)
$ sh template.sh -n -o res in1.log "in 2.log"
<utc-time> dry run: would write 2 files to res                (exit 0, no res directory)
$ sh template.sh missing.log
<utc-time> cannot read missing.log                            (exit 1, temp dir and lock removed)
```

اجرای اول، بدون آرگومان، usage چاپ می‌کند و با 2 خارج می‌شود. دومی dry run است: کار را در پوشه‌ی موقت انجام داد، گفت چه می‌نویسد و پوشه‌ی `res` را باقی نگذاشت. سومی روی ورودی ناموجود شکست خورد و بررسی کردم `trap` هم پوشه‌ی موقت و هم قفل را پاک کرده است. یک بار هم واقعی اجرایش کردم و `res/in1.log.count` و `res/in 2.log.count` را نوشت (فایل با فاصله در نامش کار کرد، چون همه‌ی متغیرها کوتیشن شده‌اند). و هر سه اسکریپت را با `sh -n` بررسی کردم، که فقط تجزیه‌شان می‌کند و خطای نحو گزارش می‌دهد.

## پیش از زمان‌بندی یک اسکریپت

- **مسیرهای مطلق، `PATH` تنظیم‌شده و کاربر با حداقل دسترسی.** [سیستم فایل و مجوزها](/fa/posts/linux-filesystem-permissions/) را ببینید.
- **راز در اسکریپت یا خط crontab نباشد.** هرکه بتواند آن‌ها را بخواند راز را می‌خواند. [مدیریت راز و کلید](/fa/posts/sec-secrets-management/) را ببینید.
- **خروجی را ریدایرکت کنید و کد خروج را زیر نظر بگیرید.** یک {{< term "dead-mans-switch" "dead man's switch" >}} اضافه کنید: کار بعد از موفقیت به یک سرویس پایش ping می‌زند و پایش وقتی ping نرسد هشدار می‌دهد. این حالت «cron اصلاً اجرا نشد» را می‌گیرد که هیچ لاگ خطایی نمی‌گیرد.
- **کار را {{< term "idempotency" "idempotent" >}} کنید.** دو بار اجرا باید همان نتیجه‌ی یک بار را بدهد، تا تلاش دوباره یا اجرای روی‌هم‌افتاده آسیبی نزند.
- **زمان اجرا را محدود کنید.** این macOS یک `timeout` از نوع BSD دارد (`timeout 1 sleep 5` با کد 124 تمام شد، که man pageش آن را کد «تمام شدن زمان» مستند کرده). در Linux معمولاً `timeout` از GNU است که اینجا اجرایش نکردم؛ گزینه‌هایش کمی با نسخه‌ی BSD فرق دارد.
- **اسکریپت‌های deploy هم از همین قاعده‌ها پیروی می‌کنند.** [طراحی pipeline برای CI/CD](/fa/posts/eng-ci-cd-pipeline-design/) را ببینید.

## تمرین

`lock.sh` را در دو ترمینال دوبار شروع کنید، بعد کسی را که قفل را دارد با `kill -9` بکشید و نسخه‌ی سومی شروع کنید. پیام stale-lock را بخوانید و فکر کنید اگر pid دوباره استفاده شده بود چه می‌توانست خراب شود.

## قدم بعدی

سری Linux اینجا تمام می‌شود. سری سیستم‌های توزیع‌شده با «چرا سیستم توزیع‌شده سخت است» ([لینک](/fa/posts/ds-why-distributed-is-hard/)) شروع می‌شود، جایی که مشکل‌های یک ماشین به مشکل‌های چند ماشین تبدیل می‌شود. یک نکته‌ی صادقانه‌ی دیگر درباره‌ی کل این سری: همه‌چیز روی مک نوشته شد، پس هیچ کرنل Linux واقعی، کانتینر یا systemd اجرا نکردم. بخش‌های مخصوص Linux از مستندات آمده و علامت خورده‌اند.
