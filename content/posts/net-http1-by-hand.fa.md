یک ترمینال باز کنید و این را تایپ کنید، بدون مرورگر و بدون هیچ کتابخانه‌ی HTTP:

```
printf 'GET /hello HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n' | nc 127.0.0.1 <port>
```

یک وب‌سرور آن طرف با چند خط متن ساده جواب می‌دهد و خط آخر خود صفحه است. {{< term "http" "HTTP" >}}/1.1 همین است و بیش از این نیست: متنی که دو برنامه توافق کرده‌اند روی یک اتصال {{< term "tcp" "TCP" >}} برای هم بنویسند. اگر HTTP را فقط از راه کتابخانه‌ها می‌شناسید (ببینید [ساخت API با net/http در Go](/fa/posts/go-http-api-stdlib/) و [سرور HTTP با node:http](/fa/posts/node-http-server/))، این پست نشان می‌دهد زیر کار چه می‌فرستند و چه می‌گیرند.

یک مسئله‌ی واقعی این‌جا هست. TCP یک جریان از بایت‌ها بدون مرز به ما می‌دهد، پس یک پیام کجا تمام می‌شود و پیام بعدی از کجا شروع؟ [سرور TCP ما](/fa/posts/net-sockets-tcp-from-scratch/) فریم‌بندی خودش را اختراع کرد و [UDP](/fa/posts/net-udp-sockets/) از پرسش فرار کرد، چون هر datagram خودش یک پیام است. HTTP/1.1 جوابش را با headerهایی می‌دهد که طول بدنه را می‌گویند. ما آن را با بایت‌های خام و بدون کتابخانه‌ی HTTP در سمت کلاینت حرف می‌زنیم.

> همه‌چیز روی `127.0.0.1` با port تصادفی اجرا شد، با Go 1.27.3، Python 3.14، `nc` و curl 8.7.1 روی macOS (Darwin، arm64)؛ اجرای اولیه با Go 1.26 بود. هدف یک سرور `net/http` در Go بود و کلاینت یک socket خام Python (و `nc`). port، header `Date` و مقدارهای مشابه در هر اجرا فرق می‌کنند. روی Linux اجرا نکردم و ماشین مشغول بود، پس زمان‌بندی‌ای نشان نمی‌دهم. دمو یک پوشه‌ی نمونه‌ی محلی است.

## شکل یک درخواست

یک درخواست چند خط متن است. این هم همان است به‌صورت بایت‌های Python، همان‌طور که دمو می‌فرستد:

```python
b"GET /hello HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n"
```

هر خط با CRLF تمام می‌شود، یعنی دو نویسه‌ی `\r\n` (carriage return و line feed). خط‌به‌خط بخوانیم:

- `GET /hello HTTP/1.1` **خط درخواست** است: متد (چه کاری)، هدف (روی چه چیزی) و نسخه‌ی پروتکل.
- `Host: localhost` و `Connection: close` **header** هستند، هر خط یک `Name: value`. `Connection: close` از سرور می‌خواهد بعد از جواب اتصال را ببندد. بدون آن سرور اتصال را برای درخواست بعدی باز نگه می‌دارد، که بعداً از آن استفاده می‌کنیم.
- یک خط خالی headerها را تمام می‌کند. هرچه بعدش بیاید بدنه است و GET بدنه ندارد.

جواب سرور Go، با CRLFها در انتهای خط‌ها (`Date` مال لحظه‌ی اجرای من است و هر بار فرق می‌کند):

```
HTTP/1.1 200 OK\r\n
Date: Wed, 04 Nov 2026 16:48:45 GMT\r\n
Content-Length: 6\r\n
Content-Type: text/plain; charset=utf-8\r\n
Connection: close\r\n
\r\n
hello\n
```

خط اول **خط وضعیت** است: نسخه، کد وضعیت (`200`) و یک توضیح کوتاه. بعدش headerها و یک خط خالی می‌آیند و بعد بدنه، یعنی `hello\n`. header `Content-Length: 6` جواب مسئله‌ی فریم‌بندی ماست. می‌گوید بدنه دقیقاً شش بایت است (`hello` و یک خط جدید)، پس خواننده بدون هیچ جداکننده‌ای می‌داند پیام کجا تمام می‌شود. همین درخواست را با `nc` بفرستید، دقیقاً همین بایت‌ها برمی‌گردند، چون HTTP فقط متن روی یک {{< term "socket" "socket" >}} است.

## Host اجباری است

header با نام `Host` می‌گوید کدام سایت را می‌خواهید. وجودش برای این است که یک آدرس IP بتواند چند سایت را سرویس بدهد: سرور با آن می‌فهمد منظور شما کدام است. طبق RFC 9112 یک درخواست HTTP/1.1 بدون آن خطاست و سرور Go هم همین را اجرا می‌کند. وقتی آن را نگذاشتم این جواب را داد:

```
HTTP/1.1 400 Bad Request: missing required Host header\r\n
Content-Type: text/plain; charset=utf-8\r\n
Connection: close\r\n
\r\n
400 Bad Request: missing required Host header
```

`400` یعنی «درخواست شما ایراد ساختاری دارد» و سرور بعد از آن اتصال را بست.

## بدنه و HEAD

برای درخواستی که بدنه دارد همین ایده در جهت مخالف کار می‌کند. در یک POST، `Content-Length: 10` و ده بایت (`name=roham`) فرستادم. handler جواب داد `got 10 bytes: name=roham` و لاگ سرور `body=10 bytes` را تأیید کرد. این header به گیرنده می‌گوید چند بایت بخواند تا پیام کامل شود. همان ایده‌ی پیشوند طول از {{< term "message-framing" "فریم‌بندی پیام" >}} است، با این تفاوت که طول در header نوشته می‌شود، نه جلوی بایت‌ها.

درخواست `HEAD` همان چیزی را می‌خواهد که GET می‌خواهد، اما بدون بدنه. سرور همان headerها را برگرداند، از جمله `Content-Length: 6`، و بعد هیچ. طول، آن چیزی را توصیف می‌کند که یک GET برمی‌گرداند؛ و چون جواب HEAD هیچ‌وقت بدنه ندارد، کلاینت نباید منتظر آن شش بایت بماند.

## Chunked: فریم‌بندی بدون طول

اگر سرور هنگام شروع جواب اندازه را نداند چه؟ مثلاً وقتی داده را همان‌طور که تولید می‌شود می‌فرستد. آن‌وقت نمی‌تواند `Content-Length` بنویسد. HTTP/1.1 راه دومی برای فریم‌بندی بدنه دارد: `Transfer-Encoding: chunked`. بدنه تکه‌تکه فرستاده می‌شود و پیش از هر تکه اندازه‌اش در مبنای شانزده (hex) می‌آید. تکه‌ای با اندازه‌ی ۰ بدنه را تمام می‌کند.

در دمو handler مقدارهای `alpha` و `bravo-bravo` و `c` را می‌نویسد و بعد از هرکدام flush می‌کند، پس هرکدام یک chunk جدا می‌شود. کلاینت Python من دستی رمزگشایی می‌کند: یک خط اندازه می‌خواند، بعد همان‌قدر بایت، بعد CRLF بعد از آن‌ها، تا اندازه ۰ شود. این خروجی کامل آن است، با headerها:

```
b'HTTP/1.1 200 OK\r\n'
b'Date: Wed, 04 Nov 2026 16:48:45 GMT\r\n'
b'Content-Type: text/plain; charset=utf-8\r\n'
b'Connection: close\r\n'
b'Transfer-Encoding: chunked\r\n'
size line b'5\r\n' -> 5
  data b'alpha'
size line b'b\r\n' -> 11
  data b'bravo-bravo'
size line b'1\r\n' -> 1
  data b'c'
size line b'0\r\n' -> 0
  data b''
```

دقت کنید که میان headerها `Content-Length` نیست. هر `size line` خطی است که سرور فرستاده و عدد بعد از `->` برداشت کلاینت از آن است. `b` در مبنای شانزده برابر ۱۱ است، یعنی طول `bravo-bravo`. آخرین chunk اندازه‌ی ۰ دارد و کلاینت از همین می‌فهمد بدنه تمام شده است. این همان {{< term "chunked-encoding" "chunked encoding" >}} است.

## یک اتصال، چند درخواست

باز کردن یک اتصال TCP یک دست‌دادن هزینه دارد، برای همین اتصال‌های HTTP/1.1 به‌طور پیش‌فرض {{< term "keep-alive" "پایدار" >}} هستند: بعد از یک جواب، همان اتصال می‌تواند درخواست بعدی را حمل کند. برای دیدنش، دمو سه درخواست روی یک socket می‌فرستد و فقط سومی `Connection: close` دارد:

```
client local port 57354
b'HTTP/1.1 200 OK' [] b'hello\n'
b'HTTP/1.1 200 OK' [] b'hello\n'
b'HTTP/1.1 200 OK' [b'Connection: close'] b'hello\n'
after close, recv -> b''
```

خط اول port خود کلاینت است. هر خط بعدی یک جواب است: وضعیت، header `Connection` اگر بود (`[]` خالی یعنی نبود) و بدنه. دو جواب اول header `Connection` ندارند، یعنی سرور اتصال را باز نگه می‌دارد. سومی، که خودمان خواسته بودیم، با `Connection: close` برمی‌گردد و بعد از آن سرور اتصال را می‌بندد. بعد `recv` مقدار `b''` برمی‌گرداند، یعنی پایان جریان.

لاگ خود سرور هم نشان می‌دهد هر سه درخواست از یک port کلاینت آمده‌اند:

```
server: GET /hello from client port 57354
server: GET /hello from client port 57354
server: GET /hello from client port 57354
```

درخواست‌های یک‌باره‌ی قبلی هرکدام اتصال تازه داشتند، پس هرکدام port دیگری در لاگ گذاشتند (در این اجرا ۵۷۳۴۹ و ۵۷۳۵۱ و ۵۷۳۵۲). portها در هر اجرا فرق می‌کنند. یک port تکراری برای سه درخواست یعنی یک اتصال هر سه را حمل کرده است.

برای همین کلاینتی که از یک اتصال پایدار می‌خواند باید دقیقاً یک پیام بخواند و با `Content-Length` یا chunkها بفهمد کجا تمام می‌شود، نه اینکه «تا آخر جریان» بخواند. جریان تمام نمی‌شود.

## یک سرور ۵۰ خطی

تا اینجا `net/http` در Go سرویس می‌داد. برای اینکه خودمان سرور باشیم چه لازم است؟ فقط یک listener، حلقه‌ای که خط‌ها را تا خط خالی بخواند، و جوابی با `Content-Length` درست:

```go
line, _ := br.ReadString('\n')          // request line
for {                                    // headers
    h, _ := br.ReadString('\n')
    if strings.TrimRight(h, "\r\n") == "" { break }
}
fmt.Fprintf(c, "HTTP/1.1 200 OK\r\nContent-Type: text/plain\r\n"+
    "Content-Length: %d\r\n\r\n%s", len(body), body)
```

فایل کامل (مدیریت خطا، یک goroutine برای هر اتصال، پشتیبانی از `Connection: close`) ۵۳ خط است. آن را روی port تصادفی (در زیر `PORT` نوشته شده) اجرا کردم و `curl -v --http1.1` را رویش زدم. خط‌هایی که با `>` شروع می‌شوند آن چیزی است که curl فرستاد و خط‌های `<` جواب سرور ماست:

```
> GET /path?x=1 HTTP/1.1
> Host: 127.0.0.1:PORT
> User-Agent: curl/8.7.1
> Accept: */*
>
< HTTP/1.1 200 OK
< Content-Type: text/plain
< Content-Length: 13
<
hi from tiny
```

curl، که یک کلاینت HTTP واقعی است، این ۵۳ خط را به‌عنوان سرور پذیرفت. سرور ما هم همان خط درخواست و سه headerی را که گرفته بود لاگ کرد (`Host` و `User-Agent` و `Accept`) که با خط‌های `>` می‌خواند. کار می‌کند، اما بدنه‌ی درخواست، درخواست chunked، سقف اندازه‌ی header، timeout، pipelining و خیلی از حالت‌های لبه را نادیده می‌گیرد. برای همین در محیط واقعی از `net/http` استفاده می‌کنید.

## چرا parserها باید هم‌نظر باشند

یک مفهوم را حتی بدون نمایش دادنش باید دانست. یک درخواست می‌تواند طولش را به دو شکل بگوید: `Content-Length` و `Transfer-Encoding: chunked`. اگر پروکسیِ جلوی سرور و خودِ سرور در این اختلاف داشته باشند که کدام‌یک پایان درخواست را تعیین می‌کند، چند بایت ممکن است برای یکی پایان درخواست اول باشد و برای دیگری آغاز درخواستی دوم. این {{< term "request-smuggling" "request smuggling" >}} است. جایش در سری امنیت است.

## جاهایی که HTTP دست‌نویس خراب می‌شود

- خط‌ها با CRLF تمام می‌شوند و headerها با یک خط خالی. پذیرفتن یک `\n` تنها مهربانانه به نظر می‌رسد، اما دقیقاً همان نوع تفاوتی است که باعث می‌شود دو parser هم‌نظر نباشند.
- بدنه به `Content-Length` یا فریم‌بندی chunked نیاز دارد. بدون یکی از آن‌ها گیرنده نمی‌داند بدنه کجا تمام می‌شود و باید منتظر بسته‌شدن اتصال بماند.
- `Host` اجباری است. بدون آن انتظار `400` داشته باشید.
- روی اتصال پایدار دقیقاً یک پیام بخوانید، نه «تا EOF». بین درخواست‌ها جریان تمام نمی‌شود.
- برای هر کاری فراتر از یادگیری از یک کتابخانه‌ی HTTP واقعی استفاده کنید. حالت‌های لبه‌ای که بالا شمردیم همان جاهایی است که parser دست‌نویس اشتباه می‌کند.

## تمرین

سرور کوچک را طوری گسترش دهید که `Content-Length` را بخواند و بدنه را پس بفرستد. بعد بدنه‌ای کوتاه‌تر از آنچه header ادعا می‌کند بفرستید و ببینید سرورتان در حین انتظار چه می‌کند. یک read deadline چه چیزی را عوض می‌کرد؟
