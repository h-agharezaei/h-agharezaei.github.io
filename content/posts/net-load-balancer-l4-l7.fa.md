سه نسخه از یک سرویس را پشت یک {{< term "load-balancer" "load balancer" >}} گذاشته‌اید، ترافیک می‌فرستید و داشبوردها را نگاه می‌کنید. دو سرور بیکارند و سومی در آتش می‌سوزد. load balancer همان‌طور که طراحی شده کار می‌کند. فقط تصمیمش را در سطحی گرفته که شما فکر نمی‌کردید.

load balancer برنامه‌ای است که جلوی چند سرور یکسان (به آن‌ها backend می‌گوییم) می‌نشیند و تصمیم می‌گیرد هر تکه از کار به کدام‌یک برود. سؤال مهم این است که «یک تکه کار» برای او چیست. فرض کنید پذیرشِ ساختمانی با سه باجه. یک پذیرش هر کسی را که از در می‌آید به باجه‌ی بعدیِ آزاد می‌فرستد و کاری ندارد آن آدم چه می‌خواهد. پذیرش دیگر به تک‌تک سؤال‌ها گوش می‌دهد و می‌تواند سؤال اول را به باجه‌ی ۱ و سؤال دوم را به باجه‌ی ۲ بفرستد، حتی اگر از یک نفر باشند. اولی روی **اتصال** (لایه‌ی ۴) کار می‌کند و دومی روی **درخواست** (لایه‌ی ۷). این شماره‌ها لایه‌های مدل هفت‌لایه‌ی OSI را می‌شمارند که [مدل TCP/IP و مسیر یک بسته](/fa/posts/net-tcp-ip-model/) معرفی‌اش کرد: لایه‌ی ۴ لایه‌ی انتقال است، جایی که {{< term "tcp" "TCP" >}} زندگی می‌کند، و لایه‌ی ۷ لایه‌ی برنامه است، جایی که HTTP هست.

[پست قبل](/fa/posts/net-grpc-over-http2/) با یک اتصال HTTP/2 تمام شد که ۷۱ فراخوانی gRPC را حمل کرد. اینجا این سؤال دیگر نظری نیست: balancerی که فقط اتصال می‌بیند یک اتصال می‌بیند و فقط می‌تواند هر ۷۱ فراخوانی را به یک backend بفرستد. در این پست هر دو نوع balancer را با Go می‌سازم، یک proxy لایه‌ی ۴ و یک proxy لایه‌ی ۷، و می‌شمارم درخواست‌ها کجا می‌نشینند. سمت معماری (service discovery و balancing در خود کلاینت) در [service discovery و load balancing](/fa/posts/ds-service-discovery-load-balancing/) آمده است.

> همه‌چیز روی `127.0.0.1` با port تصادفی (چاپ نشده)، macOS (Darwin arm64)، Go 1.27.3 و فقط کتابخانه‌ی استاندارد اجرا شد. دمو را اول با Go 1.26 نوشته بودم و برای این نسخه با 1.27.3 دوباره اجرا کردم. ماشین مشغول بود، پس تعداد منتشر می‌کنم و زمان‌سنجی نه. nginx، HAProxy، Envoy و load balancer ابری را اجرا نکردم؛ این پست درباره‌ی ایده‌هاست، نه آن محصولات.

## محیط آزمایش

دمو سه سرور کوچک HTTP به نام‌های `b0`، `b1` و `b2` راه می‌اندازد. هرکدام با نام خودش جواب می‌دهد تا کلاینت بفهمد چه کسی جواب داده. یک proxy جلوی آن‌ها گوش می‌دهد و کلاینت به proxy درخواست می‌فرستد. می‌شمارم هر backend چند درخواست گرفته. در همه‌ی آزمایش‌های زیر همین شمارش به کار می‌رود.

## لایه‌ی ۴: پخش اتصال‌ها

proxy لایه‌ی ۴ کار خیلی کمی می‌کند. یک اتصال TCP را می‌پذیرد، یک اتصال دوم به backend بعدی نوبتی باز می‌کند (این round robin است: b0، b1، b2، دوباره b0 و...) و بایت‌ها را در هر دو جهت کپی می‌کند. HTTP داخلش را هرگز نمی‌خواند. قلب کار این است، که از دمو کوتاه شده (مدیریت خطا و شمارنده‌ها حذف شده):

```go
c, _ := ln.Accept()                      // a client connected
b := backends[next % len(backends)]      // choose once, for this connection
up, _ := net.Dial("tcp", b.addr)         // connect to that backend
go io.Copy(up, c)                        // client -> backend
io.Copy(c, up)                           // backend -> client
```

انتخاب یک‌بار انجام می‌شود، در خطی که `b` برداشته می‌شود. بعد از آن هر بایت این اتصال به همان backend می‌رود. دو بار امتحانش کردم. اول ۳۰ کلاینت که هرکدام برای تنها درخواستشان اتصال تازه باز می‌کنند. دوم یک کلاینت که یک اتصال باز می‌کند و بازش نگه می‌دارد ({{< term "keep-alive" "keep-alive" >}}) و ۳۰ درخواست رویش می‌فرستد:

```
L4, 30 new connections:    b0=10 b1=10 b2=10 | proxy accepted 30
L4, 1 keep-alive conn x30: b0=30 | proxy accepted 1
```

در خط اول بار کاملاً یکنواخت است: ۳۰ اتصال، ۱۰ تا برای هرکدام. در خط دوم هر ۳۰ درخواست به `b0` رسید و proxy فقط یک اتصال پذیرفت. این تله‌ی لایه‌ی ۴ است. balancer اتصال‌ها را پخش می‌کند، نه کار را؛ پس یک کلاینت ماندگار همه‌چیز را به یک backend می‌فرستد. gRPC و هر کلاینت HTTP/2 مثل خط دوم رفتار می‌کنند، چون برای باز نگه‌داشتن یک اتصال ساخته شده‌اند.

## لایه‌ی ۷: پخش درخواست‌ها

proxy لایه‌ی ۷ HTTP را می‌فهمد. اتصال کلاینت را می‌پذیرد و هر درخواست را می‌خواند. برای هر درخواست خودش یک درخواست به backend می‌فرستد و backend را دوباره برای هر درخواست انتخاب می‌کند. در Go این `httputil.ReverseProxy` است، یک {{< term "reverse-proxy" "reverse proxy" >}}: برنامه‌ای که به‌جای سرورهای واقعی درخواست می‌گیرد و رد می‌کند. بخش مهم تنظیم من:

```go
rp := &httputil.ReverseProxy{
    Rewrite: func(pr *httputil.ProxyRequest) {
        pr.SetURL(chosenBackend.u)   // chosen per request
        pr.SetXForwarded()           // add X-Forwarded-For and friends
        pr.Out.Header.Set("X-Request-ID", ...)
    },
}
```

همان آزمایش قبل: یک اتصال کلاینت و ۳۰ درخواست.

```
L7, 1 client conn x30: b0=10 b1=10 b2=10 | proxy accepted 1
```

باز هم یک اتصال از کلاینت، ولی حالا درخواست‌ها به‌طور مساوی بین سه backend پخش شدند. بهایش این است که proxy باید هر درخواست را بخواند و بفهمد و خودش هم یک کلاینت HTTP دوم است.

چون درخواست را parse می‌کند، می‌تواند عوضش هم بکند. در تنظیم من `Rewrite` یک هدر `X-Forwarded-For` و یک `X-Request-ID` اضافه می‌کند. این جواب آخرین backend است که چاپ می‌کند چه دیده:

```
b2|/|xff=127.0.0.1|rid=req-0030
```

اجزایش به ترتیب نام backend، path، مقدار `X-Forwarded-For` و شناسه‌ی درخواست (درخواست سی‌ام) است. `X-Forwarded-For` آدرس کلاینت اصلی را می‌برد، چون backend روی اتصال خودش فقط آدرس proxy را می‌بیند. اینجا آدرس loopback است چون کلاینت روی همین ماشین بود. backend واقعی باید این هدر را فقط وقتی باور کند که از proxy خودتان آمده باشد. وگرنه هر کلاینتی می‌تواند یک مقدار جعلی بفرستد.

proxy می‌تواند بر اساس محتوای درخواست هم مسیریابی کند. دو استخر پشت یک proxy گذاشتم: `/api/` به b0 و b1 می‌رود و `/static/` به b2. با ۱۰ درخواست از هر نوع:

```
path routing: api->b0=5 api->b1=5 static->b2=10
```

لایه‌ی ۴ این کار را اصلاً نمی‌تواند بکند. path را هرگز نمی‌بیند.

## مسیریابی چسبنده و consistent hashing

گاهی می‌خواهید یک کاربر همیشه به یک backend برسد، مثلاً چون cache یا session آنجاست. ساده‌ترین قاعده این است که از چیزی که کاربر را مشخص می‌کند hash بگیرید، باقی‌مانده‌ی تقسیم بر تعداد backendها را حساب کنید و آن را شماره‌ی backend بدانید. این را با هدر `X-User` انجام دادم:

```
  X-User=ada -> b1
  X-User=bob -> b2
  X-User=cy -> b1
  X-User=ada -> b1
  X-User=bob -> b2
  X-User=cy -> b1
  X-User=ada -> b1
```

یک نام همیشه همان backend را می‌دهد. ضعف وقتی دیده می‌شود که تعداد backendها عوض شود. ۱۰٬۰۰۰ کلید برداشتم، یکی از سه backend را حذف کردم و شمردم چند کلید حالا به backend دیگری می‌روند. این را یک بار با `hash % N` انجام دادم و یک بار با یک **حلقه** (ring)، که ایده‌ی {{< term "consistent-hashing" "consistent hashing" >}} است: برای هر backend نقطه‌های زیادی روی یک دایره از مقدارهای hash می‌گذارید، هر کلید را هم روی همان دایره hash می‌کنید و به اولین نقطه‌ای می‌دهید که در حرکت دور دایره می‌رسید. هر backend ۱۰۰ نقطه گرفت.

```
mod-N                    remapped 6672 of 10000 keys (3335 of them did not live on b1)
ring (100 points/node)   remapped 2302 of 10000 keys (0 of them did not live on b1)
```

فقط کلیدهایی که روی backend حذف‌شده بودند باید جابه‌جا شوند. با `hash % N` تعداد backendها از ۳ به ۲ رفت و تقریباً هر کلید جواب تازه گرفت: ۶۶۷۲ کلید جابه‌جا شد و ۳۳۳۵ تای آن‌ها کلیدهایی بودند که روی backend حذف‌شده نبودند و دلیلی برای جابه‌جایی نداشتند. در سیستم واقعی یعنی session از دست‌رفته یا cache سرد. با حلقه ۲۳۰۲ کلید جابه‌جا شد و هیچ‌کدام بی‌گناه نبود؛ آن ۲۳۰۲ کلید همان کلیدهای backend حذف‌شده بودند. (از یک‌سوم کمترند چون ۱۰۰ نقطه برای هر backend حلقه را کاملاً مساوی تقسیم نمی‌کند.) عددهای دقیق به hash نوع FNV و نام کلیدهای من بستگی دارند و با انتخاب‌های دیگر عدد دیگری می‌بینید، ولی الگو مهم است.

## Health check

balancer باید ترافیک را از backendی که مرده برگرداند. یکی از سه backend را متوقف کردم و ۳۰ درخواست از proxy لایه‌ی ۷ با round robin فرستادم، در سه حالت:

```
no detection:    failed 10 of 30
passive (mark down on first transport error): failed 1 of 30; b1 down = true
active (2 failed probes -> down): failed 0 of 30 after removal; b0=15 b2=15
```

- **بدون تشخیص.** proxy یک‌بار از هر سه بار backend مرده را انتخاب می‌کند: ۱۰ درخواست از ۳۰ تا شکست خورد.
- **غیرفعال (passive).** proxy از ترافیک واقعی یاد می‌گیرد. اولین درخواست به backend مرده شکست می‌خورد، proxy آن را پایین علامت می‌زند و بقیه موفق می‌شوند. یک درخواست واقعی کاربر هزینه‌ی درس را داد.
- **فعال (active).** یک حلقه‌ی جدا هر ۲۰ میلی‌ثانیه به `/healthz` هر backend یک {{< term "health-check" "health check" >}} می‌فرستد و بعد از ۲ پروب ناموفق backend را پایین علامت می‌زند. در آزمایش صبر کردم تا backend مرده برداشته شود و بعد ۳۰ درخواست فرستادم، پس هیچ‌کدام شکست نخورد و ترافیک نصف‌نصف به `b0` و `b2` رفت. در زندگی واقعی درخواست‌هایی که پیش از برداشتن برسند هنوز می‌توانند شکست بخورند.

بررسی فعال ترافیک اضافه می‌خواهد و ممکن است دیر برسد، و بررسی غیرفعال شکست واقعی لازم دارد. سیستم‌های production معمولاً هر دو را کنار هم می‌گذارند و برای درخواست‌هایی که تکرارشان بی‌خطر است (درخواست‌های {{< term "idempotency" "idempotent" >}}) retry هم اضافه می‌کنند. من retry را به این دمو اضافه نکردم.

## الگوریتم‌ها: round robin و least connections

round robin به هر backend تعداد مساوی درخواست می‌دهد و کاری ندارد چقدر مشغول است. برای دیدن اینکه چرا این می‌تواند ضرر بزند، `b0` را کند کردم (۱۰۰ میلی‌ثانیه برای هر درخواست) و ۶۰ درخواست با ۶ worker هم‌زمان فرستادم. round robin (`rr`) را با least connections (`lc`) مقایسه کردم، که هر درخواست را به backendی می‌دهد که الان کمترین درخواست در حال اجرا را دارد:

```
rr: b0(slow)=20 b1=20 b2=20
lc: b0(slow)=2 b1=35 b2=23
```

round robin یک‌سوم کامل کار را به backend کند داد. least connections دید که `b0` همیشه درخواست نیمه‌تمام دارد و فقط ۲ تا به آن داد. تقسیم بین `b1` و `b2` ثابت نیست: در دو اجرا `b1=33 b2=25` و `b1=35 b2=23` دیدم. ایده‌ی شناخته‌شده‌ی دیگری هم هست، «دو انتخاب تصادفی» (دو backend را تصادفی بردار و سبک‌تر را انتخاب کن) که فقط اسمش را می‌آورم و اجرایش نکردم.

## لایه‌ی ۴ یا ۷؟

اگر لایه‌ی ۷ این‌همه کار می‌کند، چرا کسی لایه‌ی ۴ را انتخاب می‌کند؟ چون لایه‌ی ۷ هم هزینه دارد.

- لایه‌ی ۷ می‌تواند بر اساس path یا هدر مسیریابی کند، هدر را عوض کند، retry کند، درخواست‌های HTTP/2 را پخش کند و {{< term "tls" "TLS" >}} را تمام کند. برای این‌ها باید هر درخواست را buffer و parse کند، وقتی TLS را تمام می‌کند کلید خصوصی پیش اوست و یک جزء دیگر است که باید پروتکل شما را بفهمد (برای gRPC باید HTTP/2 و trailer را پشتیبانی کند).
- لایه‌ی ۴ ساده‌تر است و برای هر پروتکلی روی TCP کار می‌کند. داخل را نمی‌بیند، که یک فایده دارد: با TLS passthrough بایت‌های رمزشده را بی‌آنکه کلیدی داشته باشد رد می‌کند، ولی آن‌وقت path را هم نمی‌بیند. در termination، balancer لایه‌ی ۷ ترافیک را رمزگشایی می‌کند و اغلب برای backend دوباره رمزش می‌کند.

بخش TLS را اینجا فقط توصیف می‌کنم؛ گواهی‌ها در [TLS و گواهی با openssl](/fa/posts/net-tls-openssl/) آمده‌اند.

## دام‌های load balancing

- **اتصال‌های ماندگار با لایه‌ی ۴.** کلاینت‌های HTTP/2، gRPC و WebSocket مدت طولانی یک اتصال نگه می‌دارند، پس balancer لایه‌ی ۴ هر کلاینت را به یک backend می‌چسباند. برای آن‌ها پخش لایه‌ی ۷ بگذارید، یا بگذارید خود کلاینت بار را پخش کند.
- **باور کردن `X-Forwarded-For` از هر کسی.** این هدر فقط متنی است که هر کلاینتی می‌تواند بفرستد. فقط وقتی باورش کنید که درخواست از proxy خودتان آمده، و بگذارید proxy خودتان آن را بنویسد، نه اینکه آنچه کلاینت فرستاده را رد کند.
- **تکیه به یک نوع تشخیص خرابی.** تشخیص غیرفعال یک درخواست واقعی را قربانی می‌کند و تشخیص فعال می‌تواند دیر برسد. هر دو را با هم بگذارید و retry را به درخواست‌های idempotent محدود کنید.
- **`hash % N` برای مسیریابی چسبنده.** وقتی N عوض شود تقریباً هر کلید جابه‌جا می‌شود. اگر استخر زیاد تغییر می‌کند حلقه یا روش consistent دیگری بگذارید.

## تمرین

یک آزمایش با حالت `lc` اضافه کنید که backendی دارد فقط برای `/report` کند است. آیا تعداد اتصال‌های در حال اجرا هنوز بار واقعی را نشان می‌دهد؟ به‌جایش چه چیزی را باید ردیابی کرد؟

## قدم بعدی

پست بعد «عیب‌یابی شبکه با curl، dig و traceroute» است. balancer یک جعبه‌ی دیگر بین کلاینت و سرور است و وقتی درخواستی شکست می‌خورد روشی لازم دارید تا بفهمید کدام جعبه و کدام لایه خراب شده.
