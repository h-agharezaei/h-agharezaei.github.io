«این درخواست کند است. چرا؟» هر مهندس backend این سؤال را می‌شنود، و اولین جواب معمولاً یک عدد است، مثلاً ۸۰۰ میلی‌ثانیه. این عدد کمکی نمی‌کند، همان‌طور که «مرسوله‌ی شما پنج روز طول کشید» کمکی نمی‌کند. رویدادهای ردیابی را لازم دارید: کی از انبار خارج شد، کی از گمرک گذشت، کی پیک برداشت. درخواست هم رویدادهای ردیابی دارد و کل مهارت این است که به‌جای مجموع به آن‌ها نگاه کنید.

رویدادهای یک درخواست HTTPS این‌هاست: جست‌وجوی نام ({{< term "dns" "DNS" >}})، باز شدن اتصال {{< term "tcp" "TCP" >}}، دست‌دادن {{< term "tls" "TLS" >}}، انتظار برای اولین بایت پاسخ ({{< term "ttfb" "TTFB" >}}، «زمان تا اولین بایت») و دانلود بدنه. اگر یکی کند باشد، مجموع کند می‌شود و اینکه کدام باشد می‌گوید باید با چه کسی تماس بگیرید: ارائه‌دهنده‌ی DNS، شبکه، تنظیم گواهی، برنامه، یا هیچ‌کس، چون جواب فقط بزرگ است. این پست با ابزارهای [پست قبل](/fa/posts/net-troubleshooting-curl-traceroute/) این کار را روی یک آزمایشگاه کوچک انجام می‌دهد و آخرین پست سری شبکه است. این‌ها را هم ببینید: [مدل TCP/IP و مسیر یک بسته](/fa/posts/net-tcp-ip-model/) و [DNS در عمل](/fa/posts/net-dns-in-practice/).

> محیط: همه‌چیز روی `127.0.0.1` با port تصادفی، macOS (Darwin arm64)، Go 1.27.3، curl 8.7.1 و یک گواهی خودامضا برای `localhost` اجرا شد که داخل دمو ساخته می‌شود (کلاینت بررسی گواهی را رد می‌کند که فقط برای همین دموی محلی درست است). دمو را اول با Go 1.26 نوشته بودم. این یک **آزمایشگاه است، نه حادثه‌ی واقعی**: هر تأخیر را خودم تزریق کردم، پس جواب درست را از قبل می‌دانم و سؤال این است که اندازه‌گیری به آن اشاره می‌کند یا نه. زمان‌های loopback با زمان‌های اینترنت یکی نیستند. وقتی دوباره اجرایش کردم load average ماشین بین ۳ و ۶ بود، بیشتر از چیزی که برای عدد زمانی دوست دارم. برای همین عددهای کلاینت را به ۵۰ میلی‌ثانیه گرد کرده‌ام (تأخیرهای تزریق‌شده‌ی ۳۰۰ تا ۴۰۰ میلی‌ثانیه غالب‌اند) و عددهای curl پایین خام و نویزی‌اند: الگو را بخوانید، نه رقم‌ها را. خروجی گردشده دقیقاً همان اجرای اصلی بود، وقتی ماشین حتی شلوغ‌تر بود. DNS واقعی، تأخیر واقعی ISP، از دست رفتن بسته و packet capture را امتحان نکردم.

## آزمایشگاه

دمو یک برنامه‌ی کوچک Go است (مثال محلی، بدون repository). یک سرور دارد و یک کلاینت.

سرور می‌تواند در هر مرحله، یکی‌یکی، تأخیر تزریق کند:

- listenerی که بعد از `Accept` می‌خوابد (`-accept`)؛
- تابع `GetCertificate` در TLS که می‌خوابد (`-tls`) و دست‌دادن را کند می‌کند؛
- handlerی که پیش از نوشتن هر هدر می‌خوابد (`?h=400`)؛
- بدنه‌ای که قطره‌قطره می‌آید، ده بایت ده بایت با مکث بین تکه‌ها (`?b=3&bd=100`)؛
- بدنه‌ی بزرگی که آهسته و در تکه‌های ۱۶ کیلوبایتی نوشته می‌شود (`?big=15`).

کلاینت از بسته‌ی `net/http/httptrace` در Go استفاده می‌کند که در هر رویداد درخواست تابع شما را صدا می‌زند (اتصال گرفته شد، TLS شروع شد، TLS تمام شد، درخواست نوشته شد، اولین بایت رسید). از روی زمان‌ها شش عدد چاپ می‌کند، هرکدام به میلی‌ثانیه و گردشده به ۵۰: `dns`، `connect`، `tls`، `wait` (انتظار برای یک اتصال آزاد از pool، پیش از اینکه چیزی dial شود)، `ttfb` (از لحظه‌ی نوشته‌شدن درخواست تا اولین بایت جواب) و `body` (از اولین بایت تا پایان). یک نکته‌ی صادقانه: تأخیر «تبدیل نام» فقط یک `sleep` داخل تابع dial کلاینت است. یک جست‌وجوی کند را شبیه‌سازی می‌کند و DNS واقعی نیست.

## اول یک مقدار پایه

پیش از بررسی هر چیزی، یک درخواست سالم را اندازه بگیرید. سرور اینجا هیچ تأخیری ندارد:

```
dns=  0 connect=  0 tls=  0 wait=  0 ttfb=  0 body=  0 ms  bytes=3 reused=false HTTP/1.1 200 OK
```

همه‌چیز زیر ۲۵ میلی‌ثانیه است (پس به ۰ گرد می‌شود)، سه بایت رسید (`ok\n`) و اتصال تازه بود (`reused=false`). حالا معماها.

## چهار درخواست معماگونه

هر چهار درخواست بعدی کند هستند و هرکدام به دلیلی متفاوت. فقط خروجی را نشان می‌دهم. پیش از ادامه‌ی خواندن، از روی آن علت را حدس بزنید.

```
dns=300 connect=  0 tls=  0 wait=  0 ttfb=  0 body=  0 ms  bytes=3 reused=false HTTP/1.1 200 OK
dns=  0 connect=  0 tls=300 wait=  0 ttfb=  0 body=  0 ms  bytes=3 reused=false HTTP/1.1 200 OK
dns=  0 connect=  0 tls=  0 wait=  0 ttfb=400 body=  0 ms  bytes=3 reused=false HTTP/1.1 200 OK
dns=  0 connect=  0 tls=  0 wait=  0 ttfb=  0 body=300 ms  bytes=30 reused=false HTTP/1.1 200 OK
```

من آن‌ها را این‌طور می‌خوانم، یکی‌یکی.

1. **`dns=300`.** زمان پیش از وجود هر socket مصرف شده. کلاینت منتظر است نامی به آدرس تبدیل شود. هنوز نمی‌شود شبکه یا سرور را مقصر دانست: resolver را ببینید. (در آزمایشگاه این را با یک sleep ۳۰۰ میلی‌ثانیه‌ای در تابع dial تزریق کردم.)
2. **`tls=300`.** اتصال TCP فوری بود (`connect=0`) ولی دست‌دادن ۳۰۰ میلی‌ثانیه طول کشید. لایه‌ی TLS سرور دیر جواب می‌دهد یا مشغول است. علت تزریق‌شده: `GetCertificate` برای ۳۰۰ میلی‌ثانیه خوابید.
3. **`ttfb=400`.** همه‌چیز تا نوشته‌شدن درخواست سریع است، بعد ۴۰۰ میلی‌ثانیه سکوت. اتصال و دست‌دادن مشکلی ندارند. سرور درخواست را گرفت و ۴۰۰ میلی‌ثانیه فکر کرد پیش از اینکه حرفی بزند: handler کند است و مشکل شبکه نیست. علت تزریق‌شده: `?h=400`.
4. **`body=300` و `bytes=30`.** هدرها سریع آمدند ولی ۳۰ بایت ۳۰۰ میلی‌ثانیه طول کشید. این مشکل پهنای باند نیست. سی بایت نمی‌تواند بزرگ باشد؛ بدنه قطره‌قطره می‌آید، سه تکه با مکث ۱۰۰ میلی‌ثانیه. علت تزریق‌شده: `?b=3&bd=100`.

در هر مورد یک مرحله تأخیر را دارد و بقیه صفرند، پس نام مرحله مظنون را معلوم می‌کند. حالا مورد ۴ را با یک پاسخ **بزرگ** که آهسته نوشته می‌شود مقایسه کنید:

```
dns=  0 connect=  0 tls=  0 wait=  0 ttfb=  0 body=300 ms  bytes=245760 reused=false HTTP/1.1 200 OK
```

همان ۳۰۰ میلی‌ثانیه `body` ولی ۲۴۵٬۷۶۰ بایت (۱۵ تکه‌ی ۱۶ کیلوبایتی که هرکدام نوشته می‌شود و بعد ۲۰ میلی‌ثانیه مکث). دانلود طولانی با دانلود کند یکی نیست. تعداد بایت می‌گوید بدنه چون بزرگ است کند است یا چون سرور بین تکه‌ها گیر می‌کند. بدون بایت‌ها نمی‌توانستید مورد ۴ و این یکی را از هم تشخیص دهید.

## curl چه می‌بیند

curl با `-w` همین مرحله‌ها را از بیرون اندازه می‌گیرد. متغیرهایش تجمعی‌اند: هر زمان از شروع انتقال حساب می‌شود، پس زمان یک مرحله تفاضل دو عدد است. چهار اجرا: TLS کند، handler کند، بدنه‌ی قطره‌قطره و یک مقدار پایه‌ی سالم:

```
$ curl -sk -o /dev/null -w 'connect=%{time_connect} tls_done=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' https://127.0.0.1:PORT/...
connect=0.000343 tls_done=0.378337 first_byte=0.378910 total=0.379055     (slow TLS)
connect=0.000359 tls_done=0.004378 first_byte=0.407458 total=0.407849     (slow handler, ?h=400)
connect=0.000491 tls_done=0.004823 first_byte=0.005215 total=0.310811     (trickling body)
connect=0.000469 tls_done=0.004856 first_byte=0.005240 total=0.005353     (baseline)
```

جهش‌ها داستان را می‌گویند. در خط اول `tls_done` به ۰٫۳۷۸ ثانیه می‌پرد و بعد از آن چیزی زمان نمی‌برد. در خط دوم `tls_done` برابر ۰٫۰۰۴ ثانیه است ولی `first_byte` برابر ۰٫۴۰۷ ثانیه: انتظار بعد از دست‌دادن است. در خط سوم اولین بایت در ۰٫۰۰۵ ثانیه می‌رسد و مجموع ۰٫۳۱۱ ثانیه است: زمان در بدنه رفته. عدد TLS کند (۰٫۳۷۸ ثانیه برای ۳۰۰ میلی‌ثانیه‌ی تزریق‌شده) از بقیه بزرگ‌تر است چون ماشین مشغول بود؛ من الگو را می‌گیرم، نه رقم‌ها را. curl تأخیر DNS شبیه‌سازی‌شده‌ی من را نمی‌بیند: آن تأخیر داخل کلاینت Go من است و به curl آدرس IP دادم، پس اصلاً جست‌وجویی انجام نداد.

## یک تله: accept دیرهنگام

اینجا موردی است که تصویر کلاینت گمراه‌کننده است. سرور را با تأخیری *بعد* از `Accept` راه انداختم، یعنی برنامه‌ی سرور اتصال‌ها را آهسته می‌پذیرد، و TLS عادی و سریع:

```
dns=  0 connect=  0 tls=300 wait=  0 ttfb=  0 body=  0 ms  bytes=3 reused=false HTTP/1.1 200 OK
```

کلاینت `connect=0` و `tls=300` نشان می‌دهد، دقیقاً مثل مورد ۲. دلیلش: سیستم‌عامل دست‌دادن TCP را خودش تمام می‌کند، پیش از آنکه برنامه `accept` را صدا بزند. پس connect فوری به نظر می‌رسد و تأخیر به‌شکل دست‌دادن TLS کند ظاهر می‌شود، چون پیام hello در TLS در صف منتظر است. فقط از روی کلاینت، `GetCertificate` کند و حلقه‌ی accept گیرکرده از هم قابل تشخیص نیستند. برای تفکیک‌شان داده‌ی سمت سرور لازم است: لاگ‌ها، یا اینکه چند اتصال در صف listen منتظرند (نگاه کنید به [TCP: دست‌دادن و حالت‌های اتصال](/fa/posts/net-tcp-handshake-states/)).

## استفاده‌ی دوباره، pool و HTTP/2

مرحله‌های اول فقط برای اتصال‌های تازه مهم‌اند. با {{< term "keep-alive" "keep-alive" >}} درخواست دوم روی همان اتصال از آن‌ها رد می‌شود. دو درخواست پشت‌سرهم فرستادم، با جست‌وجوی شبیه‌سازی‌شده‌ی ۳۰۰ میلی‌ثانیه‌ای و handlerی با ۱۰۰ میلی‌ثانیه تأخیر:

```
request 1: dns=300 connect=  0 tls=  0 wait=  0 ttfb=100 body=  0 ms  bytes=3 reused=false HTTP/1.1 200 OK
request 2: dns=  0 connect=  0 tls=  0 wait=  0 ttfb=100 body=  0 ms  bytes=3 reused=true HTTP/1.1 200 OK
```

دومی `reused=true` دارد، که از `GotConn.Reused` می‌آید، و جست‌وجو (و هزینه‌ی connect و TLS) ناپدید شده. فقط ۱۰۰ میلی‌ثانیه‌ی handler مانده. برای همین «درخواست اول همیشه کند است» این‌قدر رایج است.

مشکل دیگری هست که شبیه درخواست کند به نظر می‌رسد ولی اصلاً روی سیم نیست: انتظار برای یک اتصال از pool. کلاینت را به `MaxConnsPerHost=1` محدود کردم و سه درخواست را هم‌زمان به handlerی فرستادم که ۲۰۰ میلی‌ثانیه طول می‌کشد. `wait` زمان پیش از آزاد شدن یک اتصال است و `done at` زمان از شروع:

```
HTTP/1.1:
req 0: wait=  0 ms  done at 200 ms  reused=false HTTP/1.1 200 OK
req 1: wait=200 ms  done at 400 ms  reused=true HTTP/1.1 200 OK
req 2: wait=400 ms  done at 600 ms  reused=true HTTP/1.1 200 OK
HTTP/2:
req 0: wait=  0 ms  done at 200 ms  reused=false HTTP/2.0 200 OK
req 1: wait=  0 ms  done at 200 ms  reused=true HTTP/2.0 200 OK
req 2: wait=  0 ms  done at 200 ms  reused=true HTTP/2.0 200 OK
```

در HTTP/1.1 یک اتصال هر بار یک درخواست را جواب می‌دهد. درخواست دوم ۲۰۰ میلی‌ثانیه منتظر ماند تا اولی تمام شود و سومی ۴۰۰ میلی‌ثانیه. هیچ‌چیز در شبکه یا سرور کند نیست: درخواست‌ها برای {{< term "connection-pool" "connection pool" >}} در صف‌اند. در HTTP/2 سه درخواست هم‌زمان یک اتصال را شریک شدند ({{< term "multiplexing" "multiplexing" >}}، نگاه کنید به [HTTP/2 و فرق‌هایش](/fa/posts/net-http2/))، پس هر سه در ۲۰۰ میلی‌ثانیه تمام شدند. نسخه‌ی پایگاه‌داده‌ی همین مشکل در [connection pool و حالت‌های خرابی](/fa/posts/db-connection-pooling/) آمده و سمت کلاینت HTTP در [ساخت API با net/http در Go](/fa/posts/go-http-api-stdlib/). یک تله‌ی مرتبط retry است: کلاینتی که بی‌صدا دوباره می‌فرستد می‌تواند یک درخواست کند را دو درخواست کند و به‌شکل یک درخواست طولانی دیده شود. این حالت را اجرا نکردم.

## روش حذف لایه‌به‌لایه

چهار معما ترتیبی برای بررسی پیشنهاد می‌کنند. از سمت کلاینت شروع کنید و به سمت سرور بروید؛ در هر قدم بپرسید چه چیزی آن مرحله را بزرگ می‌کند:

| ترتیب | لایه | مرحله‌ای که بزرگ می‌شود | اولین سؤال |
|---|---|---|---|
| 1 | کلاینت | wait پیش از dns | pool تمام شده، CPU مشغول است؟ |
| 2 | DNS | dns | کدام resolver جواب داد؟ (در آزمایشگاه شبیه‌سازی‌شده) |
| 3 | connect | connect | refused، timeout، دور؟ |
| 4 | TLS | tls | زنجیره‌ی گواهی، صف accept؟ |
| 5 | صف سرور | tls یا ttfb | threadها، backlog پر است؟ |
| 6 | handler | ttfb | query کند، lock، upstream؟ |
| 7 | بدنه | body | بزرگ است یا قطره‌قطره؟ |
| 8 | دوباره کلاینت | بعد از body | parse؟ |

جدول درس‌های بالا را تکرار می‌کند: انتظار pool پیش از همه‌چیز دیده می‌شود، handler کند یک `ttfb` بلند است و تعداد بایت بدنه‌ی بزرگ را از بدنه‌ی قطره‌قطره جدا می‌کند. ردیف‌های ۴ و ۵ از سمت کلاینت می‌توانند یکسان به نظر برسند، که همان تله‌ی accept دیرهنگام است. این فهرست قانون نیست. ترتیبی است که من چیزها را بررسی می‌کنم، و آزمایشگاه ردیف‌های ۱، ۲، ۴، ۵، ۶ و ۷ را پوشش می‌دهد. ردیف‌های ۳ و ۸ را نساختم.

## چهار درخواست چه آموختند

- پیش از حدس‌زدن مرحله‌های یک درخواست را اندازه بگیرید. مجموع مقصر را پنهان می‌کند.
- بدنه‌ی بزرگ و بدنه‌ی قطره‌قطره هر دو دانلود طولانی نشان می‌دهند. پیش از متهم‌کردن شبکه تعداد بایت را بررسی کنید.
- عددهای فقط‌کلاینت نمی‌توانند دست‌دادن کند را از حلقه‌ی accept گیرکرده جدا کنند. از سرور هم یک عدد بگیرید.
