این واقعیت اولین بار تقریباً همه را غافلگیر می‌کند. اگر یک طرف دو بار `Write` بزند، ممکن است طرف دیگر همه‌چیز را با یک `Read` بگیرد. و اگر یک طرف یک بار `Write` بزند، ممکن است طرف دیگر برای جمع‌کردنش سه بار `Read` لازم داشته باشد. دلیلش این است که {{< term "tcp" "TCP" >}} پیام ندارد. یک جریان از بایت‌ها را حمل می‌کند و مرز writeهای شما جزئی از آن نیست.

خود API مربوط به {{< term "socket" "socket" >}} کوچک است: listen، accept، read، write، close. قسمت سخت چیزی است که روی آن می‌سازید، چون خودتان باید تصمیم بگیرید یک پیام کجا تمام می‌شود و بعدی کجا شروع. در این مقاله هر دو سر یک گفت‌وگوی TCP را در Go می‌نویسیم: سروری که چند کلاینت را می‌پذیرد، و یک پروتکل کوچک key-value روی آن، اول با یک دستور در هر خط و بعد با طول پیش از هر پیام. در راه با چیزهایی روبه‌رو می‌شویم که سرورهای واقعی را خراب می‌کنند: کلاینتی که دروغ می‌گوید، کلاینتی که ساکت است، و خاموش‌کردن تمیز.

[مقاله‌ی قبل](/fa/posts/net-tcp-handshake-states/) باز و بسته‌شدن یک اتصال را از طرف kernel تماشا کرد و [مقاله‌ی مدل TCP/IP](/fa/posts/net-tcp-ip-model/) جریان را نشان داد. کد از goroutine استفاده می‌کند، مثل [Goroutine و Channel در Go](/fa/posts/go-goroutines-channels/).

> همه‌چیز روی `127.0.0.1` با port تصادفی (`:0`)، Go 1.27.3 و macOS اجرا شده است. دمو را اول با Go 1.26 نوشته بودم. هیچ آدرسی از ماشین من دیده نمی‌شود؛ portهای موقت در یک خط خطا با `PORT` جایگزین شده‌اند. دمو یک پوشه‌ی مثال محلی است. هیچ زمان‌سنجی نشان نمی‌دهم.

## listen، accept و یک goroutine برای هر اتصال

یک سرور سه کار می‌کند. روی یک آدرس **listen** می‌کند، یعنی به kernel می‌گوید «اتصال‌های ورودی را برایم در صف بگذار». اتصال‌ها را یکی‌یکی **accept** می‌کند: هر بار `Accept` منتظر می‌ماند تا یک کلاینت handshake را تمام کند و بعد socket تازه‌ای برای همان کلاینت برمی‌گرداند. و هر کلاینت را، این‌جا در goroutine جداگانه‌اش، اداره می‌کند تا کلاینت کند جلوی بقیه را نگیرد:

```go
ln, _ := net.Listen("tcp", "127.0.0.1:0")
for {
    c, err := ln.Accept()
    if err != nil {
        if errors.Is(err, net.ErrClosed) { return nil } // listener closed: normal stop
        return err
    }
    go func() { defer c.Close(); handle(c) }()
}
```

آدرس `127.0.0.1:0` یعنی «loopback، هر port آزادی»؛ port واقعی را از `ln.Addr()` می‌گیرید. socket در حالت listen باز می‌ماند و به پذیرفتن ادامه می‌دهد؛ هر socket پذیرفته‌شده `c` مال یک کلاینت است. `defer c.Close()` مطمئن می‌شود وقتی handler برگردد، به هر شکلی که برگردد، اتصال بسته شود. بررسی ویژه‌ی `net.ErrClosed` برای خاموشی است: وقتی کسی listener را ببندد، `Accept` دقیقاً با همین خطا شکست می‌خورد و این یک راه عادی برای توقف است، نه شکستی که باید گزارش شود.

## TCP جریان بایت است

پیش از طراحی پروتکل، خود مشکل را ببینیم. حالت `glue` در دمو سروری دارد که یک اتصال را می‌پذیرد، ۳۰۰ میلی‌ثانیه صبر می‌کند و بعد می‌خواند. کلاینت `hello\n` و `world\n` را با دو `Write` جدا می‌نویسد. بعد کلاینت `0123456789` را با یک write می‌فرستد و سرور آن را با بافری فقط ۴ بایتی می‌خواند:

```
one Read: 12 bytes "hello\nworld\n"
Read(4):  4 bytes "0123"
Read(4):  4 bytes "4567"
Read(4):  2 bytes "89"
```

دو write یک read دوازده‌بایتی شد. و یک write ده‌بایتی در سه تکه خوانده شد. اثر دوم صرفاً به این دلیل است که به `Read` بافر ۴ بایتی دادم و پس در هر بار حداکثر ۴ بایت برمی‌گرداند؛ بافر کوچک یکی از راه‌هایی است که نشان می‌دهد read به write گره نخورده است. sleep در سرور فقط چسبیدن را تکرارپذیر می‌کند: تا اولین read انجام شود هر دو write رسیده‌اند. بدون sleep نتیجه به زمان‌بندی بستگی دارد.

نتیجه این است که TCP بایت‌ها را به ترتیب به شما می‌دهد و هیچ چیز دیگر. مرز پیام باید جزئی از پروتکلی باشد که خودتان روی آن می‌گذارید، و به آن {{< term "message-framing" "framing" >}} می‌گویند. دو راه کلاسیک برای انجامش هست و هر دو را با همین پروتکل کوچک امتحان می‌کنیم.

## framing اول: یک دستور در هر خط

پروتکل سه دستور دارد: `SET key value` و `GET key` و `QUIT`. هر دستور با یک خط جدید `\n` تمام می‌شود. سرور با `bufio.Reader.ReadString('\n')` می‌خواند که تا رسیدن به جداکننده از جریان می‌خواند، مهم نیست بایت‌ها در راه چطور تکه‌تکه شده باشند. map نگه‌دارنده‌ی داده بین همه‌ی اتصال‌ها مشترک است، پس یک `sync.Mutex` (درباره‌اش {{< term "mutex" "mutex" >}}) از آن محافظت می‌کند. در حالت `line`، یک کلاینت چهار دستور می‌فرستد و جواب‌ها را چاپ می‌کند:

```
> SET lang go  < OK
> GET lang     < VALUE go
> GET nope     < NOTFOUND
> QUIT         < BYE
```

هر خط دستور فرستاده‌شده (بعد از `>`) و جواب (بعد از `<`) را نشان می‌دهد. `GET nope` کلیدی را می‌خواهد که هرگز set نشده و `NOTFOUND` می‌گیرد. `QUIT` سرور را وادار می‌کند `BYE` بگوید و اتصال را ببندد.

این قالب ساده است و با چشم هم خوانده می‌شود. ولی دو نقطه‌ضعف دارد. مقدار نمی‌تواند خط جدید داشته باشد، چون خط جدید پایان دستور است. و اگر کلاینتی بی‌پایان بایت بفرستد و هرگز `\n` نفرستد، reader آن‌ها را در حافظه جمع می‌کند، پس در سرور واقعی باید طول خط را محدود کنید.

## framing دوم: طول در ابتدا

راه دیگر این است که طول را پیش از داده بنویسیم. در قالب frame ما هر پیام یک عدد ۴ بایتی big-endian است (طول) و بعد همان‌قدر بایت داده. مثلاً `SET lang go` یازده بایت است، پس frame آن چهار بایت `00 00 00 0b` است و بعد یازده بایت متن، در مجموع ۱۵ بایت. reader اول دقیقاً ۴ بایت می‌خواند و بعد دقیقاً همان‌قدر بایت دیگر:

```go
var hdr [4]byte
if _, err := io.ReadFull(r, hdr[:]); err != nil { return nil, err }
n := binary.BigEndian.Uint32(hdr[:])
if n > max { return nil, fmt.Errorf("%w: %d bytes (max %d)", ErrFrameTooLarge, n, max) }
p := make([]byte, n) // only after the guard
_, err := io.ReadFull(r, p)
```

`io.ReadFull` تابع مهم است. یک `Read` ساده ممکن است کمتر از ظرفیت بافر برگرداند، همان‌طور که همین حالا دیدیم. `ReadFull` آن‌قدر `Read` را صدا می‌زند تا بافر کاملاً پر شود یا جریان تمام شود. و نویسنده برعکس عمل می‌کند: یک `Write` که هم header و هم داده را با هم دارد (`WriteFrame` در دمو).

حالت `frame` همین دستورها را اجرا می‌کند و همان نوع جواب‌ها را چاپ می‌کند:

```
> SET lang go  < OK
> GET lang     < VALUE go
> QUIT         < BYE
```

این قالب می‌تواند هر بایتی را حمل کند، حتی خط جدید. ولی فیلد طول از شبکه می‌آید، پس ورودی یک غریبه است، و دو کلاینت بدخواه نشان می‌دهند چرا جزئیات reader مهم است. اولی یک frame صد‌بایتی اعلام می‌کند، پنج بایت می‌فرستد و می‌بندد. دومی frame‌ای به اندازه‌ی ۲۱۴۷۴۸۳۶۴۷ بایت، یعنی حدود ۲ گیگابایت، ادعا می‌کند. این‌ها خطوطی است که سرور چاپ می‌کند:

```
server: read error: unexpected EOF
server: read error: frame too large: 2147483647 bytes (max 1048576)
```

برای کلاینت اول، `ReadFull` مقدار `io.ErrUnexpectedEOF` را برمی‌گرداند که یعنی «جریان وسط یک frame تمام شد». آن را با `io.EOF` ساده مقایسه کنید که یعنی جریان *بین* frameها تمام شد: خداحافظی مؤدبانه. برای کلاینت دوم، بررسی اندازه، frame را رد می‌کند (حد ۱ مگابایت است) پیش از آنکه برنامه چیزی تخصیص دهد. همین ترتیب اصل کار است: اگر اول `make([]byte, n)` را اجرا می‌کردیم، یک پیام ۴ بایتی از یک غریبه می‌توانست سرور را وادار کند ۲ گیگابایت حافظه بخواهد.

## deadline و half-close

کلاینتی که وصل می‌شود و هیچ نمی‌گوید راه آرامی برای آسیب‌زدن به سرور است: بدون محدودیت زمانی، goroutine آن برای همیشه منتظر می‌ماند و اگر تعدادشان زیاد شود همه‌ی منابع را می‌خورند. راه‌حل **deadline** است. سرور پیش از هر read، `SetReadDeadline(now + idle)` را صدا می‌زند. {{< term "deadline" "deadline" >}} یک نقطه‌ی مطلق در زمان است، نه یک مدت، پس باید پیش از هر درخواست تمدید شود؛ وگرنه وقتی اتصال کاملاً سالم است منقضی می‌شود. در حالت `deadline` حد بیکاری سرور ۳۰۰ میلی‌ثانیه است و کلاینت وصل می‌شود و ۶۰۰ میلی‌ثانیه ساکت می‌ماند:

```
server: read error: read tcp 127.0.0.1:PORT->127.0.0.1:PORT: i/o timeout
client read after server gave up: EOF
```

خط اول سرور است که با `i/o timeout` تسلیم می‌شود (دو port در پیام واقعی با `PORT` جایگزین شده‌اند). handler برمی‌گردد، `defer c.Close()` اجرا می‌شود و وقتی کلاینت بالاخره می‌خواند `EOF` می‌بیند: سرور اتصال را بسته است.

ابزار دیگر همان {{< term "half-close" "half-close" >}} از مقاله‌ی قبل است. فرض کنید درخواست نه طول دارد نه خط جدید و پایانش را بستنِ سمت ارسال کلاینت نشان می‌دهد. در حالت `halfclose` کلاینت یک body می‌فرستد، `CloseWrite()` را صدا می‌زند و هنوز جواب را می‌خواند. سرور از `io.ReadAll` استفاده می‌کند که فقط بعد از دیدن آن EOF برمی‌گردد:

```
server got 17 bytes, now replying
client got: counted 17 bytes
```

body یعنی `some request body` هفده بایت دارد. سرور بعد از پایان جریان آن‌ها را شمرد و روی همان اتصال جواب داد، که ثابت می‌کند `CloseWrite()` کلاینت فقط یک جهت را بسته بود.

## خاموشی تمیز، و تست

`Shutdown` اول listener را می‌بندد، پس `Accept` مقدار `net.ErrClosed` برمی‌گرداند و حلقه تمام می‌شود. بعد روی یک `sync.WaitGroup` منتظر می‌ماند تا handler هر اتصال باز تمام شود. برای بیشتر درباره‌ی این الگو، [خاموشی تمیز Workerها در Go](/fa/posts/go-graceful-shutdown-workers/) و [sync، select و context در Go](/fa/posts/go-sync-select-context/) را ببینید. در حالت `shutdown` یک کلاینت `QUIT` می‌زند، سرور خاموش می‌شود و برنامه دوباره سعی می‌کند وصل شود:

```
Serve returned: <nil>
dial after shutdown: refused=true
```

`Serve` مقدار `nil` برگرداند، یک توقف عادی، و اتصال تازه رد می‌شود چون دیگر کسی گوش نمی‌دهد. این همان `connection refused` مقاله‌ی قبل است، این بار ساخته‌ی کد خودمان.

یک تست ۲۰ کلاینت را هم‌زمان راه می‌اندازد و هرکدام ۵۰ جفت `SET`/`GET` روی کلیدهای خودش انجام می‌دهد. `go test -race` را اجرا کردم (race detector مراقب دسترسی بدون هماهنگی به حافظه‌ی مشترک است) و گذشت؛ تست همچنین بررسی می‌کند دقیقاً ۱۰۰۰ کلید در map باشد. mutex را برنداشتم تا شکست را ببینم، پس نمی‌توانم آن را نشانتان بدهم؛ تست آنجاست تا چنین اشتباهی دیده شود.

## همین در Python

ماژول `socket` در Python پوسته‌ی نازکی روی همین فراخوانی‌هاست: `bind`، `listen`، `accept`، `recv`، `sendall`. یک سرور و کلاینت echo کوتاه در یک پردازش (`echo.py`) چاپ کرد `client got b'ping\n'`. Node هم `net.createServer` دارد که برای هر اتصال یک callback صدا می‌زند (مقایسه کنید با [سرور HTTP با node:http](/fa/posts/node-http-server/))؛ نسخه‌ی Node را اینجا اجرا نکردم.

## فهرست سخت‌کردن

- **فرض نکنید یک `Write` برابر یک `Read` است.** آن‌قدر بخوانید که به آنچه لازم دارید برسید، یا از `io.ReadFull` استفاده کنید.
- **هر طولی را که از شبکه می‌خوانید پیش از تخصیص حافظه محدود کنید.** بررسی اندازه در `ReadFrame` تنها چیزی است که میان یک پیام ۴ بایتی و تخصیص ۲ گیگابایتی ایستاده است. برای طول خط در پروتکل متنی هم همین‌طور.
- **روی هر اتصالی که کنترلش با شما نیست deadline بگذارید.** یک کلاینت ساکت یک goroutine و یک socket خرج دارد؛ هزاران تای آن‌ها سرور را از پا می‌اندازد.
- **`net.ErrClosed` را بررسی کنید** تا خاموشی عادی به‌عنوان خطا لاگ نشود.
- **وضعیت مشترک را محافظت کنید و تست‌ها را با `-race` اجرا کنید.** یک goroutine برای هر اتصال یعنی map از همان روز اول هم‌زمان دست‌خورده می‌شود.

## تمرین

دستور `DEL k` را به هر دو حالت اضافه کنید. بعد reader مربوط به frame را طوری بنویسید که کلاینتی را بپذیرد که header چهاربایتی را یک بایت یک بایت می‌فرستد (با یک حلقه و sleepهای کوتاه) و نشان دهید هنوز کار می‌کند. کدام تابع در reader این را ممکن می‌کند؟

## قدم بعدی

مقاله‌ی بعدی «UDP و تفاوتش با TCP» است. UDP پروتکلی است که مرز پیام‌ها را نگه می‌دارد، پس کار framing این مقاله از بین می‌رود، ولی ضمانت‌هایی که TCP این‌جا به ما داد هم از بین می‌روند: رسیدن، ترتیب و اتصال.
