دو ماشین را در نظر بگیرید، با `package.json` یکسان و دستور یکسان: `npm install`. روی لپ‌تاپ شما برنامه کار می‌کند. در CI خراب می‌شود، چون CI یک نسخه‌ی minor جدیدتر از یک کتابخانه را نصب کرده که در این فاصله منتشر شده بود. هیچ فایلی عوض نشده، و باز هم دو ماشین کد متفاوتی گرفته‌اند. این نوع شگفتی از نفهمیدن این می‌آید که **{{< term "npm" "npm" >}}** و `package.json` دقیقاً چه چیزی را تضمین می‌کنند و چه چیزی را نه.

ایده‌ی اصلی در دو جمله جا می‌شود. `package.json` می‌گوید **چه چیزی را می‌پذیرید**: برای هر کتابخانه یک اسم و یک *بازه* از نسخه‌ها. **{{< term "lockfile" "lockfile" >}}** (یعنی `package-lock.json`، که فارسی‌اش می‌شود «قفل وابستگی») ثبت می‌کند **چه چیزی واقعاً نصب شد**، تا دقیق‌ترین نسخه. بازه یک آرزوست و lockfile یک رسید.

[ماژول‌ها: ESM و CommonJS](/fa/posts/node-modules-esm-cjs/) نشان داد Node کدی را که روی دیسک است چطور بارگذاری می‌کند؛ اینجا می‌بینیم کدِ دیگران چطور به دیسک می‌رسد. اگر می‌پرسید چرا سری از loop شروع شد، آن مقاله‌ی [event loop در Node.js](/fa/posts/node-event-loop/) است.

> با Node نسخه‌ی v20.13.1 و npm نسخه‌ی 10.5.2 در یک پوشه‌ی دموی تازه و با registry واقعی npm (سرور عمومی‌ای که پکیج‌ها در آن منتشر می‌شوند) اجرا شده است. دستورها اول در جلسه‌ی اصلی اجرا شدند و برای این نسخه‌ی مقاله دوباره آن‌ها را روی یک نسخه‌ی موقت از دمو و با `npm ci --ignore-scripts` اجرا کردم. نتیجه‌های registry (آخرین نسخه‌ها، `npm audit`) «تا روزی که اجرا کردم» هستند و عوض می‌شوند.

## package.json، فیلد به فیلد

**پکیج** پوشه‌ای است که یک فایل `package.json` دارد و آن را توصیف می‌کند. `npm init -y` یک اسکلت می‌نویسد و من چند فیلد را با `npm pkg set` اضافه کردم. مهم‌ترین‌ها:

- `name` و `version`: هویت پکیج. `private: true` باعث می‌شود `npm publish` از منتشر کردنش امتناع کند، و این برنامه را از منتشر شدن ناخواسته حفظ می‌کند.
- `type`: مقدار `commonjs` یا `module`. تعیین می‌کند فایل‌های `.js` پکیج چطور بارگذاری شوند (مقاله‌ی قبل).
- `engines`: نسخه‌های Node که پشتیبانی می‌کنید. طبق مستندات npm این فقط توصیه است: npm هشدار می‌دهد، مگر اینکه `engine-strict` را بگذارید.
- `scripts`: دستورهای نام‌دار که با `npm run <name>` اجرا می‌شوند.
- `main` و `exports`: کسی که پکیج شما را `require` یا `import` کند کدام فایل را می‌گیرد.
- `files`: کدام فایل‌ها در پکیج منتشرشده می‌آیند. در آخر مقاله بیشتر درباره‌اش می‌گویم، چون نبودن `files` می‌تواند یک راز را لو بدهد.

scriptها ساده‌ترین چیز برای امتحان‌اند. این یک script است با دو script کمکی که اسمشان با `pre` و `post` شروع می‌شود:

```json
"scripts": { "hello": "node -e \"console.log('hello')\"", "prehello": "echo pre", "posthello": "echo post" }
```

npm نسخه‌های `pre` و `post` را خودکار دور script هم‌نام اجرا می‌کند. `npm run hello` به ترتیب `pre`، `hello`، `post` چاپ کرد. و `npx <tool>` برنامه‌ای را که یک پکیج می‌دهد اجرا می‌کند و اول نسخه‌ی `node_modules` محلی را به کار می‌برد.

## چهار نوع وابستگی

**وابستگی** (dependency) پکیجی است که پکیج شما به آن نیاز دارد. در دمو `semver` و `ms` را به‌عنوان وابستگی معمولی نصب کردم و `prettier` (یک ابزار قالب‌بندی کد) را با `npm install -D` که آن را در فهرست دیگری می‌گذارد. اینکه یک پکیج در کدام فهرست باشد به npm می‌گوید کِی لازم است:

- `dependencies`: وقتی برنامه اجرا می‌شود لازم است.
- `devDependencies`: ابزارهای فقط برای توسعه و تست، مثل یک formatter.
- `peerDependencies`: «پروژه‌ای که از من استفاده می‌کند باید این را فراهم کند»، معمولاً برای pluginها. یک plugin برای یک framework باید از همان frameworkای استفاده کند که پروژه‌ی میزبان دارد، نه اینکه نسخه‌ی خودش را بیاورد.
- `optionalDependencies`: اگر نصبش شکست بخورد، npm ادامه می‌دهد.

وابستگی‌های زمان اجرا این‌طور دیده شدند:

```text
$ npm ls --omit=dev
├── ms@2.1.3
└── semver@7.6.0
```

`npm ls` ساده `prettier@3.2.5` را هم فهرست می‌کند. در image پروداکشن ابزارهای توسعه را نمی‌خواهید، پس با `npm ci --omit=dev` (یا `npm install --omit=dev`) نصب می‌کنید.

## بازه‌های semver

چرا نسخه سه عدد دارد؟ **{{< term "semver" "نسخه‌گذاری معنایی" >}}** (semantic versioning) به این سه عدد معنا می‌دهد: **MAJOR.MINOR.PATCH**. patch (از 1.2.3 به 1.2.4) رفع باگ است، minor (از 1.2.3 به 1.3.0) قابلیت اضافه می‌کند بی‌آنکه چیزی بشکند، و major (از 1.x به 2.0) ممکن است کد شما را بشکند. این قولی است که نویسنده‌ی کتابخانه می‌دهد و بازه‌ها در `package.json` روی آن بنا شده‌اند.

برای دیدن اینکه هر بازه واقعاً چه چیزی را می‌پذیرد، از خود پکیج `semver` پرسیدم. این script چهار بازه را با شش نسخه می‌سنجد:

```js
const semver = require('semver');
const ranges = ['^1.2.3', '~1.2.3', '1.2.3', '^0.2.3'];
const vers = ['1.2.3', '1.2.9', '1.3.0', '2.0.0', '0.2.9', '0.3.0'];
for (const r of ranges) console.log(r.padEnd(7), vers.filter(v => semver.satisfies(v, r)).join(' '));
```

```text
^1.2.3  1.2.3 1.2.9 1.3.0
~1.2.3  1.2.3 1.2.9
1.2.3   1.2.3
^0.2.3  0.2.9
```

هر خط یک بازه و نسخه‌هایی از فهرست را نشان می‌دهد که آن بازه می‌پذیرد:

- `^1.2.3` (caret) نسخه‌های minor و patch جدید را می‌پذیرد، ولی 2.0.0 را نه.
- `~1.2.3` (tilde) فقط patchهای جدید را می‌پذیرد.
- `1.2.3` بدون علامت یعنی دقیقاً همین نسخه.
- `^0.2.3` خیلی سخت‌گیرتر است: زیر 1.0.0 هر چیزی هنوز ممکن است عوض شود، پس caret فقط اجازه می‌دهد عدد آخر جلو برود. برای همین فقط `0.2.9` جور شد و `0.3.0` نه.

شکل خط فرمان `npx semver -r '^1.2.3' 1.9.0 2.0.0` است که فقط `1.9.0` را چاپ کرد.

## lockfile

حالا برگردیم به ابتدای مقاله. بازه‌ای مثل `^7.6.0` نسخه‌های زیادی را می‌پذیرد و اینکه کدام را بگیرید به روز نصب بستگی دارد. lockfile این شانس را حذف می‌کند. این ورودی `semver` در `package-lock.json` است، کمی کوتاه‌شده (hash را بریده‌ام و فیلد `bin` را حذف کرده‌ام):

```json
"node_modules/semver": {
  "version": "7.6.0",
  "resolved": "https://registry.npmjs.org/semver/-/semver-7.6.0.tgz",
  "integrity": "sha512-EnwXhrlwXMk9gKu5/...",
  "dependencies": { "lru-cache": "^6.0.0" }
}
```

`version` دقیق را نگه می‌دارد، نشانی `resolved` که از آن دانلود می‌شود، و یک hash به نام `integrity` که npm بعد از دانلود بررسی‌اش می‌کند تا فایل دست‌خورده شناخته شود. برای برنامه‌ها lockfile را commit کنید: آن‌وقت لپ‌تاپ‌ها و CI همان درخت را نصب می‌کنند.

`npm ls --all` چیز دیگری هم نشان می‌دهد: خود `semver` به پکیج‌های دیگری نیاز دارد. این‌ها **{{< term "transitive-dependency" "وابستگی‌های transitive" >}}** هستند، یعنی وابستگی‌های وابستگی‌های شما: `lru-cache@6.0.0` که خودش `yallist@4.0.0` را می‌خواهد. npm آن‌ها را مسطح در `node_modules` سطح بالا گذاشته، کنار `ms` و `prettier`. حالتی که دو نسخه از یک پکیج داشته باشیم تولید نکردم، پس مثالی از deduplication نشان نمی‌دهم.

## npm install و npm ci

دو راه نصب هست و با lockfile متفاوت رفتار می‌کنند. `npm install` مجاز است lockfile را عوض کند. `npm ci` («clean install») `node_modules` را پاک می‌کند، دقیقاً همان چیزی را نصب می‌کند که lockfile می‌گوید، و اگر `package.json` و lockfile با هم نخوانند شکست می‌خورد. برای دیدن این شکست، `ms` را در `package.json` به نسخه‌ی دقیق `1.0.0` تغییر دادم بی‌آنکه lockfile را دست بزنم و `npm ci` را اجرا کردم:

```text
npm ERR! code EUSAGE
npm ERR! 
npm ERR! `npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync. Please update your lock file with `npm install` before continuing.
npm ERR! 
npm ERR! Invalid: lock file's ms@2.1.3 does not satisfy ms@1.0.0
```

npm بعد از این راهنمای استفاده چاپ کرد که حذفش کرده‌ام. خط آخر مهم است: lockfile `ms@2.1.3` دارد و `package.json` حالا `1.0.0` می‌خواهد. در CI این شکست همان چیزی است که می‌خواهید: نمی‌گذارد چیزی غیر از آنچه تست کرده‌اید تحویل شود.

## outdated، view و audit

سه دستور فقط‌خواندنی کمک می‌کنند با registry هم‌گام بمانید. در اجرای دوباره‌ی من (تا همان روز):

```text
$ npm outdated
Package   Current  Wanted  Latest  Location               Depended by
prettier    3.2.5  3.9.10  3.9.10  node_modules/prettier  demo
semver      7.6.0   7.8.6   7.8.6  node_modules/semver    demo
```

`Current` نسخه‌ی نصب‌شده است، `Wanted` بالاترین نسخه‌ای است که بازه‌ی شما اجازه می‌دهد، و `Latest` جدیدترین نسخه در registry است. این‌جا برابرند، چون هر دو بازه caret هستند و جدیدترین انتشارها هنوز داخل آن‌ها می‌افتند.

`npm view ms dist-tags` چاپ کرد `latest: '2.1.3'` به‌علاوه‌ی tagهای beta و canary و nightly، و `npm view semver@7 version` همه‌ی نسخه‌های 7.x را فهرست می‌کند. `npm audit` چاپ کرد `found 0 vulnerabilities`. این دستور registry را می‌پرسد، پس شبکه می‌خواهد و جوابش با زمان عوض می‌شود: نتیجه‌ی تمیز امروز درباره‌ی هفته‌ی بعد چیزی ثابت نمی‌کند.

## چه چیزی منتشر می‌شود

در پوشه‌ی دوم یک `lib/index.js`، یک `test/t.js`، یک فایل `.env` با یک راز ساختگی و `NOTES.md` داشتم، با `"files": ["lib"]`. `npm pack --dry-run` نشان می‌دهد چه چیزی در پکیج می‌رود، بی‌آنکه چیزی منتشر کند، و فقط `lib/index.js` و `package.json` را فهرست کرد.

بعد در یک نسخه‌ی موقت فیلد `files` را برداشتم و دوباره اجرا کردم. این بار هر پنج فایل را فهرست کرد، از جمله `.env`. یعنی بدون `files` هیچ چیز جلوی منتشر شدن یک راز را نمی‌گیرد؛ npm به قاعده‌های فایل‌های نادیده‌گیری مثل `.npmignore` یا `.gitignore` برمی‌گردد و پوشه‌ی من هیچ‌کدام را نداشت. پیش از منتشر کردن همیشه با dry run بررسی کنید. ابزارهای دیگری مثل pnpm و yarn هم هستند و `.npmrc` تنظیمات registry را نگه می‌دارد؛ این‌جا از آن‌ها استفاده نکردم.

## جاهایی که وابستگی‌ها غافلگیرتان می‌کنند

- **ویرایش دستی `package-lock.json`.** آن را commit کنید ولی بگذارید npm بنویسدش. یک hash یا نسخه‌ی دستی‌ویرایش‌شده باگی است که هیچ‌کس پیدایش نمی‌کند.
- **استفاده از `npm install` در CI یا build داکر.** از `npm ci` استفاده کنید، تا وقتی فایل‌ها نمی‌خوانند build بشکند، نه اینکه بی‌صدا چیز جدیدی نصب شود.
- **زیاد به `^` اعتماد کردن.** caret به همه‌ی نگهدارنده‌ها اعتماد می‌کند که semver را کامل رعایت کنند. تور اطمینان واقعی شما lockfile است.
- **اضافه کردن وابستگی بدون نگاه کردن.** install scriptهای یک وابستگی هنگام نصب روی ماشین شما کد اجرا می‌کنند (برای همین در اجرای دوباره‌ام `--ignore-scripts` گذاشتم). آنچه اضافه می‌کنید را بررسی کنید.
- **ضمانت دانستن `npm audit`.** عکس لحظه‌ای از چیزی است که امروز شناخته شده.

## تمرین

یک پروژه بسازید، `ms` را نصب کنید، بعد بازه‌اش را در `package.json` به چیزی تغییر دهید که lockfile نتواند برآورده کند و خطای `npm ci` را بخوانید. بعد یک فیلد `files` اضافه کنید و با `npm pack --dry-run` بررسی‌اش کنید.
