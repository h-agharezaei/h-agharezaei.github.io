سرویس شما کند است، یا حافظه‌اش هر ساعت بیشتر می‌شود تا کشته شود. واکنش طبیعی حدس‌زدن است: «حتماً parse کردن JSON است»، «حتماً آن cache است». حدس وقتی غلط باشد وقت می‌گیرد و فقط بعد از تمام‌شدن کار می‌فهمید. این مقاله درباره‌ی حدس‌نزدن است. Node.js می‌تواند بگوید زمان کجا می‌رود، چه چیزی حافظه را نگه داشته و آیا event loop بلوکه شده. بعد با نیمه‌ی دیگر یک سرویس سالم تمام می‌کنیم: بی‌آنکه درخواستی را از دست بدهیم متوقف شدن.

برای ملموس‌شدنش از یک سرور آزمایشی با cacheای استفاده می‌کنم که هیچ‌چیز را بیرون نمی‌اندازد. در ۵۰۰۰۰ درخواست، heap آن از ۳ به ۳۱ مگابایت رسید. پیش از اضافه‌کردن thread و process بیشتر از [worker thread و cluster در Node.js](/fa/posts/node-worker-threads-cluster/)، باید بدانید زمان و حافظه کجا می‌رود و process بتواند بدون از دست دادن درخواست متوقف شود. این همان داستان [پروفایل Go با pprof](/fa/posts/go-profiling-pprof/) و [خاموشی تمیز Workerها در Go](/fa/posts/go-graceful-shutdown-workers/) است، با زبان Node.js و روی [event loop](/fa/posts/node-event-loop/) و [سرور HTTP](/fa/posts/node-http-server/).

> همه‌چیز را با Node نسخه‌ی v20.13.1 و به‌صورت اسکریپت‌های محلی اجرا کردم و خروجی‌ها واقعی‌اند. ماشین مشغول بود، پس تعداد و اندازه منتشر می‌کنم، نه زمان. heap snapshotها و پروفایل‌ها بعداً پاک شدند. پورت دموی خاموشی تصادفی است. DevTools و `--inspect` را نشان نمی‌دهم و اجرا نکردم. عددهایی مثل تعداد sample از اجرایی به اجرای دیگر فرق می‌کنند؛ هر جا مهم بود گفته‌ام.

## CPU کجا می‌رود

اولین سؤال این است: «کدام تابع زمان را مصرف می‌کند؟» پروفایلر با نمونه‌برداری جواب می‌دهد: چندین بار در ثانیه نگاه می‌کند برنامه همین الان چه می‌کند و نام تابع را یادداشت می‌کند. بعد از مدتی، تابع‌هایی که بیشتر دیده شده‌اند همان‌هایی‌اند که زمان را می‌خورند.

`node --cpu-prof script.js` این کار را می‌کند و وقتی برنامه تمام می‌شود یک {{< term "cpu-profile" "پروفایل CPU" >}} می‌نویسد، یک فایل JSON با پسوند `.cpuprofile`. Chrome DevTools می‌تواند آن را به‌شکل {{< term "flame-graph" "flame graph" >}} باز کند؛ من از DevTools استفاده نکردم و فایل را با یک اسکریپت کوتاه خواندم. اسکریپت می‌شمارد در چند sample هر تابع در بالای stack بوده.

برنامه عمداً سنگین است: یک `fib(34)` بازگشتی و ۳۰۰۰۰۰ بار `JSON.stringify`، در دو تابع به اسم `fib` و `render`. خروجی:

```text
total samples 146
    55 fib cpu.js:1
    55 render cpu.js:2
     6 (garbage collector) :0
     5 compileForInternalLoader realm:383
```

برنامه تقریباً همه‌ی زمانش را در `fib` و `render` گذراند، تقریباً به یک اندازه، و کمی در {{< term "garbage-collector" "garbage collector" >}} (بخشی از runtime که اشیایی را که دیگر چیزی به آن‌ها نمی‌رسد آزاد می‌کند) و در کد راه‌اندازی خود Node. عدد اول تعداد sample برای هر تابع است. عددهای دقیق از اجرایی به اجرای دیگر عوض می‌شوند: نسخه‌ی اول این مقاله برای `render` عدد ۷۰ و برای `fib` عدد ۵۰ را گرفته بود و اجرای امروز من برای هر دو ۵۵. چیزی که عوض نمی‌شود ایده‌ی رتبه‌بندی است: اول پروفایل بگیرید، بعد فقط خط‌های بالا را بهینه کنید.

## نشتی که می‌شود تماشایش کرد

حالا حافظه. {{< term "memory-leak" "نشت حافظه" >}} در زبانی با garbage collector یعنی حافظه‌ای که فراموش شده نیست، یعنی حافظه‌ای که هنوز *قابل‌دسترس* است: چیزی هنوز به آن اشاره می‌کند و collector باید نگهش دارد، با اینکه برنامه دیگر هرگز از آن استفاده نمی‌کند. علت کلاسیک، cache یا فهرستی است که فقط بزرگ می‌شود.

سرور زیر یک `Map` در سطح ماژول نگه می‌دارد و در حالت «leak» به‌ازای هر درخواست یک عضو اضافه می‌کند و هرگز پاکش نمی‌کند. در حالت «ok» چیزی اضافه نمی‌کند. ۵۰۰۰۰ درخواست روی اتصال‌های keep-alive فرستادم و قبل از خواندن `process.memoryUsage().heapUsed` تابع `global.gc()` را صدا زدم (این به پرچم `--expose-gc` نیاز دارد). اجبار به یک جمع‌آوری مهم است: بدون آن زباله‌ای را اندازه می‌گرفتید که در آستانه‌ی آزادشدن است.

```js
const cache = new Map();            // module level: lives as long as the process
const leaky = process.argv[2] === 'leak';
const server = http.createServer((req, res) => {
  const body = { id: cache.size, payload: 'x'.repeat(1000) };
  if (leaky) cache.set(req.url + Math.random(), body);   // never evicted
  res.end('ok');
});
```

خروجی دو اجرا، پشت سر هم:

```text
ok before: 3 MB, cache 0
ok after 50000 requests: 4 MB, cache 0
leak before: 3 MB, cache 0
leak after 50000 requests: 31 MB, cache 50000
```

اجرای «ok» تقریباً به همان اندازه‌ای که شروع شد تمام می‌شود. اجرای نشت‌دار بعد از یک جمع‌آوری کامل ۳۱ مگابایت نگه داشته، با ۵۰۰۰۰ عضو در cache. این همان نشت است: حافظه هنوز قابل‌دسترس است.

برای دیدن اینکه *چه چیزی* آن را نگه داشته، یک {{< term "heap-snapshot" "heap snapshot" >}} بگیرید: تخلیه‌ی همه‌ی اشیای زنده‌ی heap با اندازه و ارجاع‌هایشان. `v8.writeHeapSnapshot()` یکی نوشت (حدود ۵۹ مگابایت روی دیسک). Chrome DevTools می‌تواند بازش کند و اشیا را نشان بدهد. من از DevTools استفاده نکردم؛ اندازه‌ها را با یک اسکریپت بر حسب نوع جمع زدم:

```text
nodes 854769 edges 2455490 self size MB 31
  18.4 MB concatenated string
   4.6 MB string
   2.5 MB array
   2.1 MB code
```

خط اول می‌گوید snapshot حدود ۸۵۵ هزار شیء («node») و ۲٫۵ میلیون ارجاع («edge») بین آن‌ها دارد، جمعاً ۳۱ مگابایت، که با ۳۱ مگابایتی که اندازه گرفتیم می‌خواند. خط‌های بعد بزرگ‌ترین نوع‌های شیء‌اند. رشته‌ها غالب‌اند و این مستقیم به عضوهای cache اشاره می‌کند (هرکدام یک payload هزار‌کاراکتری دارد). در یک سرویس واقعی بعدش نگاه می‌کنید چه چیزی آن رشته‌ها را زنده نگه داشته. در سرویس در حال اجرا هم می‌توانید process را با `--heapsnapshot-signal=SIGUSR2` راه بیندازید تا هر وقت خواستید snapshot بنویسد؛ آن پرچم را اجرا نکردم.

## سقف، و لاگ GC

اگر نشت ادامه پیدا کند چه؟ V8 برای heap سقفی دارد و بعد از آن process می‌میرد. سقف را با `--max-old-space-size=20` (مگابایت) پایین آوردم و اسکریپتی اجرا کردم که مدام شیء می‌سازد و هرگز رهایشان نمی‌کند:

```text
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
exit code 134
```

process با کد خروج ۱۳۴ کشته می‌شود. این ظاهر یک کرش out-of-memory از بیرون است و دلیل اینکه یک نشت آهسته در production به یک حلقه‌ی restart تبدیل می‌شود.

پرچم `--trace-gc` برای هر جمع‌آوری یک خط چاپ می‌کند تا کار collector را ببینید. ستون‌های شناسه‌ی process و زمان را از این خط‌ها بریدم. اولین خط‌های یک اسکریپت کوچکِ در حال ساخت شیء:

```text
Scavenge 3.7 (4.0) -> 3.5 (5.0) MB
```

و از اسکریپتِ محکوم به شکست، جمع‌آوری‌های کامل بعدی:

```text
Mark-Compact 20.4 (29.7) -> 16.4 (50.5) MB
Mark-Compact (reduce) 21.1 (50.5) -> 19.7 (21.5) MB
```

«Scavenge» یک پاک‌سازی سریع اشیای جوان است. «Mark-Compact» یک جمع‌آوری کامل است. عددها heap مصرفی قبل و بعد هستند (و اندازه‌ی کل داخل پرانتز). در اجرای محکوم، جمع‌آوری‌های کامل heap را به‌سختی کوچک می‌کنند (۲۰٫۴ به ۱۶٫۴ و بعد ۲۱٫۱ به ۱۹٫۷ مگابایت)، چون تقریباً همه‌چیز هنوز قابل‌دسترس است. وقتی این را در یک لاگ دیدید، یک نشت می‌بینید.

## تأخیر event loop

مشکل دیگر: حافظه خوب است ولی درخواست‌ها کندند چون چیزی event loop را بلوکه می‌کند، مثل مقاله‌ی قبل. `perf_hooks.monitorEventLoopDelay` اندازه می‌گیرد تایمرها چقدر دیر اجرا می‌شوند، که مستقیم نشان می‌دهد حلقه چقدر مشغول بوده. آن را فعال کردم، حلقه را با یک `while` مشغول به مدت ۲۰۰ میلی‌ثانیه بلوکه کردم و نتیجه را خواندم:

```text
samples > 0: true
max delay >= 150 ms: true  | median < 50 ms: true
```

به‌جای میلی‌ثانیه، boolean چاپ می‌کنم چون ماشین زیر بار بود و نمی‌خواهم زمان‌بندی منتشر کنم. معنا: مانیتور sample جمع کرد، بدترین تأخیر دست‌کم ۱۵۰ میلی‌ثانیه بود (بلوکه ۲۰۰ میلی‌ثانیه‌ای دیده شد) و تأخیر میانه هنوز کوچک بود. یک فراخوانی بلوکه‌کننده یک بیشینه‌ی عظیم می‌سازد در حالی که میانه کوچک می‌ماند؛ پس در سرویس واقعی بیشینه و یک صدک بالا را زیر نظر بگیرید، نه میانگین را.

## خاموش‌کردن سرور HTTP

حالا نیمه‌ی دیگر. وقتی deploy یا یک orchestrator می‌خواهد سرویس شما متوقف شود، {{< term "sigterm" "SIGTERM" >}} می‌فرستد. اگر process همین‌طوری بمیرد، درخواست‌هایی که نیمه‌کاره بودند از دست می‌روند. یک خاموشی خوب پذیرفتن کار تازه را متوقف می‌کند، آنچه در جریان است تمام می‌کند و بعد خارج می‌شود.

برای یک سرور HTTP، `server.close()` پذیرفتن اتصال تازه را متوقف می‌کند و وقتی همه‌ی اتصال‌های موجود تمام شدند callback می‌زند. گیرش {{< term "keep-alive" "keep-alive" >}} است: کلاینت ممکن است بعد از پاسخ اتصالش را برای استفاده‌ی دوباره باز نگه دارد و یک اتصال بیکارِ باز `close` را منتظر نگه می‌دارد. در 20.13.1 هر دوی `closeIdleConnections` و `closeAllConnections` وجود دارند (اسکریپت برای هر دو `function` چاپ کرد).

سرور دمو یک مسیر `/slow` دارد که ۱ ثانیه طول می‌کشد. کلاینت از یک اتصال keep-alive استفاده می‌کند، یک درخواست گرم‌کردن می‌فرستد و بعد یک درخواست slow، و من وقتی درخواست slow در حال اجراست به سرور `SIGTERM` می‌فرستم. handler سرور این است:

```js
process.once('SIGTERM', () => {
  console.log('SIGTERM: server.close()');
  const hard = setTimeout(() => { console.log('timeout: closeAllConnections()'); server.closeAllConnections(); }, 3000);
  hard.unref();
  server.close((err) => { console.log('close callback, err =', err ?? null); process.exit(0); });
  if (mode === 'idle') { server.closeIdleConnections(); setInterval(() => server.closeIdleConnections(), 100).unref(); }
});
```

در حالت ساده فقط `server.close()` را صدا می‌زند و یک timeout سخت ۳ ثانیه‌ای دارد. خروجی سرور این بود:

```text
SIGTERM: server.close()
timeout: closeAllConnections()
close callback, err = null
```

و کلاینت `client: in-flight -> slow done` چاپ کرد. پس درخواست در جریان تمام شد. ولی سوکت keep-alive آن بعدش باز ماند و callback مربوط به close فقط وقتی آمد که timeout سخت ۳ ثانیه‌ای من اجرا شد و اتصال را برید.

آیا اتصال گرم‌کردن بود که وقتی `SIGTERM` رسید بیکار بود؟ نه. با کلاینتی که فقط درخواست گرم‌کردن می‌فرستاد بررسی کردم: در این نسخه `close()` خودش اتصال‌هایی را که همان لحظه بیکارند می‌بندد و سرور فوراً خارج شد. مشکل اتصالی است که *بعداً* بیکار می‌شود، وقتی درخواست slow تمام می‌شود.

راه‌حل حالت `idle` در handler بالاست: `closeIdleConnections()` را فوراً و بعد هر ۱۰۰ میلی‌ثانیه صدا بزنید. با آن، خروجی این شد:

```text
SIGTERM: server.close()
close callback, err = null
```

process درست بعد از پاسخ و بدون منتظرماندن برای timeout، با کد خروج ۰ بیرون رفت.

یک کلاینت دیگر: نصف یک درخواست فرستاد (`GET /slow HTTP/1.1` بدون خط خالیِ پایان) و بعد ساکت شد. نه بیکار است و نه تمام‌شده، پس `closeIdleConnections()` به آن دست نمی‌زند. فقط `closeAllConnections()` در timeout ۳ ثانیه‌ای آن را برداشت: سرور پیش از بستن خط `timeout:` را چاپ کرد و کلاینت `stuck client: connection closed by server` را گزارش داد.

این دستور پخت {{< term "graceful-shutdown" "خاموشی تمیز" >}} است: پذیرفتن را متوقف کن، بگذار کار در جریان تمام شود، سوکت‌های بیکار را ببند و یک timeout سخت نگه دار تا یک کلاینت گیرکرده نتواند یک deploy را تا ابد معطل کند. `http.Server.Shutdown` در Go سه مورد اول را برایتان انجام می‌دهد؛ یک deadline از نوع `context` نقش timeout را بازی می‌کند.

## اندازه‌گرفتن چیز اشتباه

- **پروفایل یک اجرای غیرواقعی.** زیر بار واقعی پروفایل بگیرید و هر بار فقط یک چیز را عوض کنید.
- **خواندن حافظه پیش از جمع‌آوری.** heap را بعد از GC اجباری بخوانید؛ پیش از آن زباله را اندازه می‌گیرید.
- **cache بدون سقف.** هر cache را محدود کنید (با اندازه یا زمان)، وگرنه نشت می‌شود.
- **جاگذاشتن snapshot.** heap snapshot می‌تواند به بزرگی خود heap باشد و ممکن است رازهایی مثل token داشته باشد. پاکش کنید.
- **خروج زودهنگام.** `process.exit()` مستقیم در handler مربوط به SIGTERM مسیر تمیز را می‌پرد؛ وقتی `close` callback زد خارج شوید.

## تمرین

مسیر `/leak` را به سرور مقاله‌ی HTTP اضافه کنید، با یک اسکریپت زیر بار ببریدش، دو heap snapshot بگیرید و اندازه‌ی رشته‌ها را مقایسه کنید. بعد برای cache سقف اندازه بگذارید و تکرار کنید.
