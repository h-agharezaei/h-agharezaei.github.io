این آخرین مقاله‌ی سری Node.js است. [مقاله‌ی قبل](/fa/posts/node-profiling-memory-shutdown/) درباره‌ی پروفایل، حافظه و خاموشی تمیز بود. حالا به پرسشی می‌رسیم که بیش از همه می‌شنوم: Node.js یا Go؟ من سر کار از هر دو استفاده می‌کنم، پس این نوشته دیدگاه یک نفر است همراه با کمی شواهد. یک سرویس کوچک یکسان را دو بار ساختم، بدون فریم‌ورک، با Node 20.13.1 و Go 1.26، بر پایه‌ی مقاله‌هایم درباره‌ی [`node:http`](/fa/posts/node-http-server/) و [`net/http`](/fa/posts/go-http-api-stdlib/). کد یک دموی محلی است.

## یک سرویس، دو بار

سه endpoint: `POST /echo` همان JSON دریافتی را برمی‌گرداند، `GET /primes?n=200000` مجموع اعداد اولِ کوچک‌تر از n را با غربال می‌گیرد (کاری {{< term "cpu-bound" "وابسته به CPU" >}}) و `GET /slow` به یک سرویس بالادستیِ کوچک روی loopback می‌زند که همیشه ۲۰ میلی‌ثانیه صبر می‌کند (کاری {{< term "io-bound" "وابسته به I/O" >}}). بدنه‌ی خراب، پاسخ 400 می‌دهد. هر دو از یک upstream استفاده کردند.

```js
const r = await fetch(upstream);
send(200, await r.json());
```

```go
resp, err := http.Get(upstream)
```

هر دو پاسخ یکسان دادند (`{"n":200000,"sum":1709600813}`) و ۳٬۰۰۰ درخواست ترکیبیِ من به هرکدام (۲۰ تا همزمان) همه 200 گرفتند.

## آنچه شمردم

| اندازه‌گیری‌شده در اینجا | Node | Go |
|---|---|---|
| خط کد | 41 | 75 (قالب gofmt) |
| وابستگی | 0 (بدون `node_modules`) | 0 (بدون `go.sum`) |
| چیزی که تحویل می‌شود | برنامه به‌علاوه‌ی runtime نود (باینری `node` اینجا 94,112,064 بایت) | یک باینری، 9,058,098 بایت |
| RSS در شروع | 87,872 KB | 11,872 KB |
| RSS بعد از ۳٬۰۰۰ درخواست | 108,832 KB | 17,968 KB |

مقایسه‌ی خط‌ها منصفانه نیست: فایل Node من فشرده است و فرمتر Go کد را باز می‌کند. RSS با `ps -o rss` فقط روی پردازش‌های خودم گرفته شد. سرویس واقعی و تنظیم‌شده فرق می‌کند. توان عملیاتی و تأخیر را اندازه نگرفتم: میانگین بار ماشین هنگام بررسی بالای ۶ بود و هر عددی نویز می‌شد. اگر لازم دارید، روی ماشین آرام و با بار کاری خودتان بسنجید.

## وقتی خراب می‌شود

به هرکدام `GET /boom` اضافه کردم. در Go روی map تهی می‌نویسد. در Node بعد از پاسخ‌دادن، داخل callback یک timer خطا پرتاب می‌کند.

```text
http: panic serving 127.0.0.1:52808: assignment to entry in nil map
goroutine 3837 [running]:
```

سرور Go همان panic را داخل همان اتصال گرفت، stack trace نوشت و درخواست بعدی درست کار کرد. کلاینتِ `/boom` پاسخی نگرفت. در Node:

```text
Error: boom in a callback
    at Timeout._onTimeout (server.mjs:35:30)
Node.js v20.13.1
```

کلاینت 200 گرفت و بعد کل پردازش بسته شد. panic داخل goroutineای که خودتان شروع کرده‌اید را آزمایش نکردم؛ `net/http` آن را نمی‌گیرد و Go هم می‌افتد. قاعده‌ی Node در [خطاها و unhandled rejection](/fa/posts/node-errors-unhandled-rejections/) آمده است: یا مدیریتش کنید یا بگذارید یک supervisor دوباره راه‌اندازتان کند.

## همزمانی، کوتاه

Node کد جاوااسکریپت شما را روی یک thread اجرا می‌کند و [event loop](/fa/posts/node-event-loop/) کارهای منتظر را درهم می‌بافد. این برای `/slow` عالی است. یک `/primes` طولانی همه‌چیز را می‌بندد و پاسخش [worker thread یا cluster](/fa/posts/node-worker-threads-cluster/) است. Go برای هر درخواست یک {{< term "goroutine" "goroutine" >}} روی همه‌ی هسته‌ها شروع می‌کند، پس handler سنگین فقط جای خودش را می‌گیرد ([goroutine و channel](/fa/posts/go-goroutines-channels/)). این تفاوت را اینجا بنچمارک نکردم.

## راهنمای انتخاب (به تجربه‌ی من)

| عامل | تمایل من |
|---|---|
| تیم JavaScript یا TypeScript بلد است | Node.js |
| گستردگی اکوسیستم (SDK، ابزار، اشتراک با front-end) | Node.js |
| نوع ایستا از همان ابتدا | Go (TypeScript این را برای Node هم می‌دهد) |
| سادگی استقرار | Go، یک باینری |
| کار وابسته به CPU | Go |
| streaming و proxy | هر دو خوب؛ در Node باید مراقب [backpressure](/fa/posts/node-streams-backpressure/) بود |
| اتصال‌های بلندمدت زیاد | هر دو جواب می‌دهند؛ استدلال درباره‌ی Go ساده‌تر است |

## چند نکته‌ی مهم

- جدول من نظر است. عددها از یک ماشین و یک سرویس خیلی کوچک آمده‌اند.
- حافظه در شروع، حافظه زیر بار واقعی شما نیست.
- انتخاب زبان به‌ندرت از کیفیت دیتابیس، شبکه و طراحی مهم‌تر است.
- مهارت تیم معمولاً زودتر از هر بنچمارک تصمیم می‌گیرد.
- در مقایسه‌ی خودتان نسخه‌ی Node و Go را ثابت نگه دارید.

## تمرین

endpointی مثل `GET /sum?n=...` اضافه کنید که کار را در Node داخل worker thread انجام دهد. سپس هنگام اجرای یک درخواست `/primes`، رفتارش را با نسخه‌ی Go مقایسه کنید؛ با شمارش یا ترتیب پاسخ‌ها، نه حدس.

## قدم بعدی

سری Node.js اینجا تمام می‌شود. بعد از آن سری‌های مهندسی نرم‌افزار، الگوریتم‌ها و سیستم‌های توزیع‌شده می‌آیند.
