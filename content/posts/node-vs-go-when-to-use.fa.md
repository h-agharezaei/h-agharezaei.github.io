عمداً یک باگ به دو نسخه‌ی یک سرویس کوچک اضافه کردم. در نسخه‌ی Go هزینه‌ی باگ فقط یک درخواست بود: سرور یک stack trace لاگ کرد و به سرویس‌دادن ادامه داد. در نسخه‌ی Node.js کلاینت جواب عادی‌اش را گرفت و بعد کل process بیرون رفت. هر درخواست بعدی شکست خورد، تا وقتی که چیزی سرور را دوباره راه انداخت.

«Node.js یا Go؟» سؤالی است که بیشتر از هر سؤال دیگر از من می‌پرسند و این مقاله‌ی آخر سری با یک آزمایش کوچک جوابش را می‌دهد، نه با یک شعار. [مقاله‌ی قبل](/fa/posts/node-profiling-memory-shutdown/) درباره‌ی پروفایل، حافظه و خاموشی بود. من هر دو زبان را سر کار استفاده می‌کنم، پس آنچه می‌آید دیدگاه یک نفر است همراه با کمی شواهد، نه حکم. همان سرویس را دو بار ساختم، بدون هیچ فریم‌ورکی، با Node.js نسخه‌ی 20.13.1 و Go، به‌پیروی از نوشته‌هایم درباره‌ی [`node:http`](/fa/posts/node-http-server/) و [`net/http`](/fa/posts/go-http-api-stdlib/). کد یک دموی محلی است.

> دمو را برای این نسخه‌ی مقاله دوباره اجرا کردم، با Node نسخه‌ی v20.13.1 و Go نسخه‌ی 1.27.3 (اجرای اصلی Go نسخه‌ی 1.26 بود)، روی یک لپ‌تاپ macOS arm64 و با پورت‌های آزاد تصادفی. اندازه‌ها و حافظه‌ی زیر «اندازه‌گیری همین اجرا» هستند. سرعت اندازه نگرفتم.

## همان سرویس، دو بار

اول دو اصطلاح. کار وقتی {{< term "cpu-bound" "وابسته به CPU" >}} است که پردازنده محدودکننده باشد، مثل محاسبه‌ی تعداد زیادی عدد. وقتی {{< term "io-bound" "وابسته به I/O" >}} است که بیشتر زمان صرف منتظرماندن برای چیز دیگری شود، مثل سرویس دیگر یا دیسک. یک سرویس وب معمولاً هر دو نوع را دارد و دو زبان با آن‌ها متفاوت رفتار می‌کنند.

سرویس سه endpoint دارد:

- `POST /echo` همان JSON دریافتی را برمی‌گرداند. بدنه‌ی بد ۴۰۰ می‌دهد.
- `GET /primes?n=200000` مجموع اعداد اول کوچک‌تر از `n` را با غربال حساب می‌کند. این کار وابسته به CPU است.
- `GET /slow` یک سرویس بالادستی کوچک روی loopback را صدا می‌زند که همیشه پیش از جواب‌دادن ۲۰ میلی‌ثانیه صبر می‌کند. این کار وابسته به I/O است. همان upstream به هر دو نسخه سرویس داد.

شکل کد در هر دو یکی است. مثلاً صدازدن upstream این‌طور است:

```js
const r = await fetch(upstream);
send(200, await r.json());
```

```go
resp, err := http.Get(upstream)
```

هر دو نسخه برای درخواست‌های آزمایشی من جواب‌های یکسان دادند (برای `/primes` این بود: `{"n":200000,"sum":1709600813}`). بعد ۳۰۰۰ درخواست مخلوط به هرکدام فرستادم، ۲۰ تا ۲۰ تا، و همه‌شان ۲۰۰ برگرداندند (برای هر دو `ok=3000/3000`).

## چه چیزی را شمردم

این است آنچه اندازه گرفتم، و فقط همین:

| اندازه‌گیری همین اجرا | Node | Go |
|---|---|---|
| خط کد | 41 | 75 (به سبک gofmt) |
| وابستگی | 0 (بدون `node_modules`) | 0 (بدون `go.sum`) |
| چیزی که تحویل می‌شود | برنامه به‌اضافه‌ی runtime ‏Node (باینری `node` اینجا 94,112,064 بایت است) | یک باینری، 10,040,642 بایت |
| RSS در شروع | 86,016 KB | 10,944 KB |
| RSS بعد از ۳۰۰۰ درخواست | 107,248 KB | 18,672 KB |

RSS (resident set size) حافظه‌ای است که سیستم‌عامل همین الان به process داده؛ آن را با `ps -o rss` فقط از process‌های خودم خواندم. چند نکته برای خواندن جدول:

- شمار خط‌ها مسابقه‌ی منصفانه‌ای نیست: فایل Node من فشرده است و formatter ‏Go کد را پهن می‌کند.
- اندازه‌ی باینری Go به نسخه‌ی toolchain بستگی دارد. اجرای اصلی با Go 1.26 عدد 9,058,098 بایت داد؛ اعداد حافظه هم از اجرایی به اجرای دیگر کمی جابه‌جا می‌شوند (اجرای اصلی برای Node اعداد 87,872 و 108,832 KB و برای Go اعداد 11,872 و 17,968 KB داشت).
- یک سرویس بهینه‌شده یا واقعی فرق خواهد داشت. این‌ها دو برنامه‌ی کوچک‌اند.

توان عملیاتی و latency را اندازه نگرفتم. وقتی نگاه کردم load average ماشین بالای ۴ بود، پس هر عددی نویز می‌شد. اگر لازمشان دارید، روی ماشین آرام و با بار خودتان اندازه بگیرید.

## وقتی خراب می‌شود

به هر سرویس `GET /boom` اضافه کردم. در Go، handler روی یک map برابر nil می‌نویسد و panic می‌شود. در Node، handler جواب می‌دهد و بعد داخل callback یک تایمر throw می‌کند، پس خطا بیرون از هر درخواستی رخ می‌دهد.

سرور Go پانیک را داخل همان یک اتصال recover کرد، یک stack trace لاگ کرد و درخواست بعدی کار کرد. کلاینت `/boom` جوابی نگرفت. این‌ها خط‌های اول لاگ‌اند (پورت کلاینت و شماره‌ی goroutine هر بار فرق می‌کند و timestamp لاگ را بریدم):

```text
http: panic serving 127.0.0.1:51897: assignment to entry in nil map
goroutine 4297 [running]:
```

درخواست `/primes?n=100` درست بعدش جواب `{"n":100,"sum":1060}` داد و process هنوز زنده بود.

در Node کلاینت ۲۰۰ خودش را گرفت و بعد process خطا را چاپ کرد و بیرون رفت:

```text
file://<demo>/node/server.mjs:35
    setTimeout(() => { throw new Error('boom in a callback'); }, 0);
                       ^

Error: boom in a callback
    at Timeout._onTimeout (file://<demo>/node/server.mjs:35:30)
    ...
Node.js v20.13.1
```

(`<demo>` جای پوشه‌ی دموی محلی من است و خط‌های آخر stack را بریدم.) خطایی که throw شود و کسی نگیرد، process ‏Node را و با آن هر درخواست در جریان دیگر را تمام می‌کند.

دو تذکر. panic داخل goroutineای را که خودتان شروع می‌کنید امتحان نکردم: `net/http` آن یکی را recover نمی‌کند و یک برنامه‌ی Go را هم می‌اندازد. و قاعده‌ی Node در [خطا و unhandled rejection در Node.js](/fa/posts/node-errors-unhandled-rejections/) آمده: خطا را مدیریت کنید، یا بگذارید یک supervisor process را دوباره راه بیندازد.

## همزمانی، کوتاه

Node کد JavaScript شما را روی یک thread اجرا می‌کند و [event loop](/fa/posts/node-event-loop/) کارهای منتظر را لابه‌لای هم می‌چرخاند. این برای `/slow` عالی است. ولی یک فراخوانی طولانی `/primes` همه‌چیز را تا پایانش بلوکه می‌کند. جواب در Node [worker thread یا cluster](/fa/posts/node-worker-threads-cluster/) است. Go برای هر درخواست یک {{< term "goroutine" "goroutine" >}} شروع می‌کند و آن‌ها را روی همه‌ی هسته‌ها پخش می‌کند، پس handlerی که CPU زیاد می‌خواهد فقط goroutine خودش را مشغول می‌کند ([goroutine و channel در Go](/fa/posts/go-goroutines-channels/)). این تفاوت را این‌جا benchmark نکردم.

## راهنمای تصمیم

این جدول دیدگاه خودم است، ساخته‌شده از نکته‌های بالا و از کار با هر دو. نظر است، نه اندازه‌گیری:

| عامل | به کدام متمایلم |
|---|---|
| تیم از قبل JavaScript یا TypeScript بلد است | Node.js |
| وسعت اکوسیستم (SDK، ابزار، اشتراک با front-end) | Node.js |
| نوع‌های ایستا از همان ابتدا | Go (TypeScript این را برای Node هم می‌دهد) |
| سادگی deploy | Go، یک باینری |
| کار وابسته به CPU | Go |
| streaming و proxy | هر دو خوب‌اند؛ stream در Node با [backpressure](/fa/posts/node-streams-backpressure/) دقت می‌خواهد |
| اتصال‌های طولانی‌مدت زیاد | هر دو جواب می‌دهند؛ استدلال درباره‌ی Go ساده‌تر است |

## جاهایی که این مقایسه کم می‌آورد

- **نظر است.** عددها از یک ماشین و یک سرویس خیلی کوچک‌اند و جدول دیدگاه من است.
- **حافظه‌ی شروع حافظه‌ی production نیست.** مصرف یک سرویس زیر بار واقعی شما سؤال دیگری است.
- **زبان کمتر تعیین‌کننده است.** کیفیت دیتابیس، شبکه و طراحی معمولاً مهم‌تر است.
- **آدم‌ها از benchmark مهم‌ترند.** چیزی که تیم‌تان از قبل خوب بلد است معمولاً سریع‌تر از هر عددی تصمیم می‌گیرد.
- **نسخه‌ها نتیجه را عوض می‌کنند.** نسخه‌های Node و Go را در مقایسه‌ی خودتان ثابت کنید؛ همان‌طور که اندازه‌ی باینری بالا نشان داد، حتی نسخه‌ی toolchain عددها را جابه‌جا می‌کند.
