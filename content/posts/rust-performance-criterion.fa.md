فرض کنید می‌خواهید بدانید کدام یک از دو روش ساختن یک رشته سریع‌تر است. ساده‌ترین کار این است که هر کدام را یک بار اجرا کنید و با ساعت زمانش را بگیرید. ولی اگر همین کار را دوباره انجام دهید، عدد دیگری می‌گیرید: برنامه‌ی دیگری روی کامپیوتر کاری کرده، پردازنده یک لحظه کندتر شده، حافظه‌ی نهان خالی بوده. یک عدد تنها نشان نمی‌دهد چقدر می‌شود به آن اعتماد کرد.

و بدتر از نویز این است که گاهی اصلاً چیزی را اندازه نمی‌گیرید. اگر benchmark شما حدود ۰٫۳ نانوثانیه گزارش کند، کامپایلر کار را کلاً حذف کرده است و شما زمان یک حلقه‌ی خالی را می‌بینید. در این مقاله با {{< term "criterion" "Criterion" >}} این دو مشکل را حل می‌کنیم: Criterion کار را بارها تکرار می‌کند، از نمونه‌ها آمار می‌گیرد و می‌گوید نتیجه چقدر نویزی است. و یاد می‌گیریم جلوی حذف شدن کار را بگیریم.

این مقاله بعد از [Unsafe و FFI](/fa/posts/rust-unsafe-ffi/) می‌آید: آن‌جا کدی نوشتیم که کار می‌کرد، و حالا می‌پرسیم چقدر سریع است. اگر Go بلدید، معادل‌های Criterion `testing.B` از [مقاله‌ی تست](/fa/posts/go-testing-basics/)، ابزار `benchstat` و [pprof](/fa/posts/go-profiling-pprof/) هستند. [مقاله‌ی مقایسه‌ی Go و Rust](/fa/posts/go-vs-rust-when-to-use/) هم قبلاً هشدار داده بود که یک microbenchmark چیز زیادی ثابت نمی‌کند؛ اینجا یاد می‌گیریم همان یکی را حداقل درست اندازه بگیریم.

> نسخه‌ها: Rust 1.90، edition 2024، `criterion` نسخه‌ی 0.8.2 (طبق `Cargo.lock`)، macOS روی arm64 و crate محلی `strbench`. **اعداد زمانی این مقاله را از اجرای اول demo برداشته‌ام، نه از اجرای دوباره.** در آن اجرا هر benchmark را فقط وقتی شروع کردم که میانگین بار (load average) یک‌دقیقه‌ای ماشین زیر ۲ بود (شروع‌ها بین ۱٫۷ و ۱٫۹۹؛ یک اجرا با ۲٫۵ تمام شد). هنگام آماده‌کردن این نسخه میانگین بار ماشین بین ۵ و ۱۰ بود، پس زمان‌ها را دوباره اندازه نگرفتم؛ فقط demo را دوباره کامپایل کردم، تست‌ها را اجرا کردم و تعداد تخصیص‌های حافظه (که به بار ماشین بستگی ندارد) را شمردم. اعداد را مثال بدانید، نه معیار کامپیوتر خودتان.

## یک benchmark چه چیزی را اندازه می‌گیرد؟

ایده‌ی Criterion ساده است. یک تابع کوچک (closure) به آن می‌دهید و می‌گویید «زمان یک اجرای این را اندازه بگیر». Criterion اول چند ثانیه آن را اجرا می‌کند تا ماشین «گرم» شود (حافظه‌ی نهان پر شود، پردازنده روی سرعت پایدار برسد)، بعد ۱۰۰ **نمونه** جمع می‌کند. هر نمونه یک دسته اجراست که زمان کل‌اش اندازه‌گیری می‌شود. از روی نمونه‌ها زمان یک اجرا را تخمین می‌زند و یک **بازه‌ی اطمینان** هم می‌دهد: بازه‌ای که با احتمال بالا (به‌طور پیش‌فرض ۹۵٪، طبق مستندات Criterion) زمان واقعی داخل آن است. بازه‌ی باریک یعنی اندازه‌گیری پایدار بوده؛ بازه‌ی پهن یعنی نویز زیاد.

## کدی که اندازه می‌گیریم

دو روش ساخت یک رشته‌ی یکسان، یکی با رشد تدریجی و دیگری با تخصیص از قبل:

```rust
pub fn build_grow(n: usize) -> String {
    let mut s = String::new();
    for _ in 0..n { s += "ab"; }
    s
}

pub fn build_with_capacity(n: usize) -> String {
    let mut s = String::with_capacity(n * 2);
    for _ in 0..n { s.push_str("ab"); }
    s
}
```

هر دو یک رشته‌ی `ab` تکرارشده‌ی `n` بار می‌سازند. اولی با رشته‌ی خالی شروع می‌کند و هر وقت جا کم آورد حافظه‌ی بیشتری می‌گیرد. دومی از اول به اندازه‌ی نهایی (`n * 2` بایت) حافظه می‌گیرد. اول درستی، بعد سرعت: یک تست معمولی برای `n` برابر ۰، ۱، ۱۰ و ۱۰۰۰ چک می‌کند که هر دو یک رشته‌ی یکسان برمی‌گردانند، و پاس می‌شود.

پیش از هر اندازه‌گیری می‌شود حدس زد چرا اولی کندتر است: چند بار از سیستم حافظه می‌خواهد. این را بدون ساعت و با شمردن می‌شود دید. یک برنامه‌ی کوچک جدا (در یک کپی موقت از demo، نه در خود demo) یک allocator شمارنده می‌گذارد و تعداد درخواست‌های حافظه را می‌شمارد:

```text
n = 10: grow = 3 allocations, with_capacity = 1
n = 1000: grow = 9 allocations, with_capacity = 1
n = 100000: grow = 16 allocations, with_capacity = 1
```

این اعداد را دوباره اجرا کردم و هم در حالت debug و هم release یکسان بودند. `with_capacity` همیشه یک بار حافظه می‌گیرد، ولی `grow` هر وقت جایش تمام می‌شود، یک تخصیص یا بزرگ‌کردن تازه می‌کند: ۳ بار برای ۲۰ بایت، ۹ بار برای ۲٬۰۰۰ بایت و ۱۶ بار برای ۲۰۰٬۰۰۰ بایت. تعداد با اندازه کم‌کم زیاد می‌شود (نه یکی‌به‌یکی)، چون ظرفیت هر بار چند برابر می‌شود. پس انتظار داریم تفاوت زمانی در اندازه‌های کوچک بیشتر دیده شود، چون سهم تخصیص در کل کار بزرگ‌تر است. ببینیم اندازه‌گیری همین را می‌گوید.

## راه‌اندازی

Criterion یک dev-dependency است و هر فایل benchmark باید `harness = false` داشته باشد. معنایش این است که ابزار آزمون پیش‌فرض Rust (libtest) به کار نمی‌آید و Criterion خودش تابع `main` را می‌سازد:

```toml
[dev-dependencies]
criterion = "0.8.2"

[[bench]]
name = "strings"
harness = false
```

`cargo bench` با پروفایل `bench` کامپایل می‌کند که مثل `--release` بهینه است. اندازه‌گیری روی کد debug بی‌معنی است، چون debug عمداً بهینه نشده.

## benchmark پارامتری

می‌خواهیم دو روش را با سه اندازه‌ی ورودی مقایسه کنیم. فایل `benches/strings.rs` برای این کار یک **BenchmarkGroup** می‌سازد (گروهی که نتیجه‌ها زیر یک نام جمع می‌شوند) و برای هر ترکیب روش و اندازه یک **BenchmarkId** می‌دهد:

```rust
use criterion::{BenchmarkId, Criterion, Throughput, criterion_group, criterion_main};
use std::hint::black_box;
use strbench::{build_grow, build_with_capacity};

fn bench_builders(c: &mut Criterion) {
    let mut group = c.benchmark_group("build_string");
    for n in [10usize, 1_000, 100_000] {
        group.throughput(Throughput::Bytes((n * 2) as u64));
        group.bench_with_input(BenchmarkId::new("grow", n), &n, |b, &n| {
            b.iter(|| build_grow(black_box(n)))
        });
        group.bench_with_input(BenchmarkId::new("with_capacity", n), &n, |b, &n| {
            b.iter(|| build_with_capacity(black_box(n)))
        });
    }
    group.finish();
}

criterion_group!(benches, bench_builders);
criterion_main!(benches);
```

`b.iter(|| ...)` همان closure‌ای است که زمانش گرفته می‌شود. تابع {{< term "black-box" "black_box" >}} را در بخش بعد توضیح می‌دهم. `Throughput::Bytes` به Criterion می‌گوید هر اجرا چند بایت تولید می‌کند تا علاوه بر زمان، نرخ (بایت در ثانیه) هم گزارش کند. `cargo bench` اول ۳ ثانیه warm-up می‌کند و بعد ۱۰۰ نمونه جمع می‌کند. این خروجی **اجرای اول** است، با ماشینی که بارش پایین بود:

```text
build_string/grow/10    time:   [88.683 ns 88.900 ns 89.242 ns]
build_string/with_capacity/10   time: [28.566 ns 28.615 ns 28.669 ns]
build_string/grow/1000  time:   [776.62 ns 778.16 ns 779.80 ns]
build_string/with_capacity/1000 time: [392.20 ns 392.86 ns 393.53 ns]
build_string/grow/100000        time: [37.815 µs 37.879 µs 37.981 µs]
build_string/with_capacity/100000 time: [35.663 µs 35.736 µs 35.805 µs]
```

هر خط یک benchmark است: نامش (گروه/روش/اندازه) و `time: [کم میانه زیاد]`. عدد وسط بهترین تخمین است و دو عدد کناری دو سر بازه‌ی اطمینان. بازه‌ها این‌جا خیلی باریک‌اند (مثلاً ۸۸٫۷ تا ۸۹٫۲ نانوثانیه)، یعنی اندازه‌گیری پایدار بود.

حالا بخوانیم. برای `n = 10`، `with_capacity` با ۲۸٫۶ نانوثانیه در برابر ۸۸٫۹ حدود ۳ برابر سریع‌تر بود. برای `n = 1000` حدود ۲ برابر (۳۹۲٫۹ در برابر ۷۷۸٫۲). برای `n = 100000` فقط چند درصد (۳۵٫۷ در برابر ۳۷٫۹ میکروثانیه)، چون آن‌جا خود کپی کردن ۲۰۰ هزار بایت غالب است و تخصیص‌ها سهم کوچکی دارند. همان چیزی که از شمارش تخصیص‌ها انتظار داشتیم: برنده همان است که کمتر حافظه می‌خواهد، ولی هرچه ورودی بزرگ‌تر شود فاصله کمتر می‌شود.

Criterion علاوه بر این چیزهای دیگری هم چاپ می‌کند. مثلاً `Found 15 outliers among 100 measurements (15.00%)` با تفکیک `high mild` و `high severe`: **outlier** نمونه‌ای است که خیلی از بقیه دورتر است (معمولاً چون در آن لحظه چیز دیگری روی ماشین اجرا شده). از `Throughput` هم یک خط `thrpt:` می‌سازد. پیام `Gnuplot not found, using plotters backend` هم آمد: gnuplot نصب نبود، ولی نمودارها باز هم ساخته می‌شوند.

## وقتی کامپایلر benchmark شما را حذف می‌کند

حالا همان مشکل اول مقاله. کامپایلر بهینه‌ساز اگر ببیند نتیجه‌ی یک محاسبه هرگز استفاده نمی‌شود، می‌تواند کل محاسبه را دور بیندازد. اگر ورودی هم ثابت باشد، ممکن است نتیجه را موقع کامپایل حساب کند و موقع اجرا فقط یک عدد آماده بگذارد. در هر دو حالت benchmark شما چیزی را اندازه نمی‌گیرد. تابع `mix` یک حلقه‌ی xorshift خالص است (فقط عدد می‌گیرد و عدد برمی‌گرداند)، و چهار نسخه از benchmark آن را امتحان کردم:

```rust
c.bench_function("mix/result_dropped", |b| b.iter(|| { mix(black_box(1000)); }));
c.bench_function("mix/constant_input_8", |b| b.iter(|| mix(8)));
c.bench_function("mix/black_box_input_8", |b| b.iter(|| mix(black_box(8))));
c.bench_function("mix/honest_1000", |b| b.iter(|| mix(black_box(1000))));
```

```text
mix/result_dropped      time:   [312.81 ps 312.93 ps 313.05 ps]
mix/constant_input_8    time:   [312.99 ps 313.20 ps 313.47 ps]
mix/black_box_input_8   time:   [3.5703 ns 3.5730 ns 3.5766 ns]
mix/honest_1000         time:   [1.8343 µs 1.8347 µs 1.8351 µs]
```

واحد `ps` پیکوثانیه است: ۰٫۳ نانوثانیه. هیچ حلقه‌ای با ۱۰۰۰ تکرار این‌قدر سریع نیست؛ پس کاری انجام نشده. حالت اول: نتیجه را دور ریختم (`;` بعد از `mix(...)`) و چون `mix` خالص است، کامپایلر خود فراخوانی را حذف کرد. حالت دوم: ورودی ثابت ۸ است و حلقه‌ی کوچک موقع کامپایل حل شد. هر دو حدود ۰٫۳۱۳ نانوثانیه دادند؛ احتمالاً هر دو فقط سربار خود حلقه‌ی benchmark را اندازه گرفتند. حالت سوم با ورودی پنهان‌شده ۳٫۵۷ نانوثانیه شد و حالت چهارم، `honest`، با ۱۰۰۰ تکرار ۱٫۸۳۵ میکروثانیه.

راه‌حل `std::hint::black_box` است: مقداری را که از آن رد می‌شود از دید بهینه‌ساز «ناشناخته» می‌کند، پس نمی‌تواند فرض کند چه مقداری است. `b.iter` هم خودش خروجی closure را black-box می‌کند، پس برگرداندن نتیجه (بدون `;`) کافی است. من اسمبلی را بررسی نکردم؛ این توضیح که چرا حذف شد از روی اعداد است، نه از روی کد ماشین. یک نکته‌ی نسخه: `criterion::black_box` در نسخه‌ی 0.8.2 منسوخ (deprecated) است. دوباره کامپایل کردم و کامپایلر هشدار داد «use `std::hint::black_box()` instead». نسخه‌ی std را بگذارید.

## خواندن اجرای دوم

همان دستور را دوباره بزنید؛ Criterion نتیجه را با اجرای قبلی در `target/criterion` مقایسه می‌کند. این بخشی از خروجی اجرای دوم همان اجرای اصلی است:

```text
build_string/grow/1000  time:   [794.15 ns 799.88 ns 807.90 ns]
                        change: time: [+1.6851% +3.2524% +5.4679%] (p = 0.00 < 0.05)
                        Performance has regressed.
build_string/with_capacity/1000
                        change: time: [+0.0077% +0.4590% +1.1443%] (p = 0.12 > 0.05)
                        No change in performance detected.
```

خط `change` تغییر نسبی نسبت به اجرای قبل را با بازه‌اش نشان می‌دهد و `p` می‌گوید اگر در واقع چیزی عوض نشده بود، چقدر احتمال داشت چنین اختلافی ببینیم. اگر `p` از ۰٫۰۵ کمتر باشد، Criterion تغییر را «معنادار» می‌داند. حالت اول `p = 0.00` است و `Performance has regressed` (کندتر شده) را می‌گوید؛ دومی `p = 0.12` است و `No change in performance detected`.

ولی دقت کنید: **کد تغییر نکرده بود**. از شش benchmark، دو تا «regressed» گفتند (این یکی و `with_capacity/100000`). روی یک لپ‌تاپ چند درصد نوسان عادی است، چون پردازنده، دما و برنامه‌های دیگر هر لحظه عوض می‌شوند. نتیجه‌ی آماری هم فقط می‌گوید «اختلاف در همین اندازه‌گیری‌ها نویز نیست»، نه اینکه کد کندتر شده. پس یک پیام را مدرک ندانید. پیام‌های ممکن این‌هاست: `No change in performance detected`، `Change within noise threshold`، `Performance has regressed` و مشابه improved.

برای مقایسه‌ی عمدی یک baseline اسم‌دار بسازید. `cargo bench -- --save-baseline before` نتیجه را با اسم `before` ذخیره می‌کند. بعد کد را عوض کنید و `cargo bench -- --baseline before` را بزنید تا با آن مقایسه شود. یک فیلتر آخر دستور مثل `"/1000"` benchmarkها را با اسم انتخاب می‌کند (توجه کنید که `/100000` را هم می‌گیرد، چون فیلتر روی بخشی از اسم کار می‌کند). گزارش HTML در `target/criterion/report/index.html` ساخته می‌شود.

## مقایسه با Go

`testing.B` در Go برای هر اجرا یک خط می‌دهد. برای آمار با `-count` چند بار تکرار می‌کنید و فایل‌ها را با `benchstat` مقایسه می‌کنید. Criterion نمونه‌گیری، شمارش outlier و مقایسه را در یک `cargo bench` انجام می‌دهد. attribute داخلی `#[bench]` فقط روی nightly کار می‌کند، پس در Rust پایدار عملاً سراغ Criterion (یا ابزار مشابه) می‌روید. Criterion می‌گوید چقدر طول کشید؛ برای فهمیدن **چرا**، از profiler مثل `cargo flamegraph` یا `perf` استفاده کنید، که اینجا فقط اسمشان را می‌آورم.

## وقتی benchmark دروغ می‌گوید

- **با پروفایل bench یا release اندازه بگیرید**، نه با `cargo run` در debug، چون کد debug عمداً کند است و نتیجه‌اش درباره‌ی برنامه‌ی واقعی چیزی نمی‌گوید.
- **زمان زیر نانوثانیه یعنی کار حذف شده.** از `black_box` برای ورودی استفاده کنید و نتیجه را برگردانید.
- **اول ماشین را ساکت کنید.** کارهای دیگر را ببندید و `uptime` را ببینید؛ بار زیاد بازه‌ها را پهن و عددها را بی‌معنی می‌کند. (به همین دلیل این مقاله اعداد جدید ندارد.)
- **یک پیام «regressed» می‌تواند نویز باشد.** قبل از باور کردنش تکرار کنید.
- **با اندازه‌ی ورودی واقعی benchmark بگیرید.** برنده با اندازه عوض می‌شود، مثل `grow` و `with_capacity` در بالا.

## تمرین
