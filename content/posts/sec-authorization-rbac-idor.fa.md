Alice در یک برنامه‌ی مدیریت سند حساب دارد. یکی از سندهای خودش را باز می‌کند و در نوار آدرس `/documents/1` را می‌بیند. از سر کنجکاوی `/documents/2` را تایپ می‌کند. اگر برنامه سند شخص دیگری را به او نشان بدهد، یک باگ خیلی رایج دارد: بررسی کرده که او وارد شده، ولی بررسی نکرده که سند مال خودش است یا نه.

این همان فرق «دانستن اینکه فراخواننده کیست» و «تصمیم‌گرفتن درباره‌ی اینکه او چه کاری می‌تواند بکند» است. توکنی که [OAuth2 و OIDC](/fa/posts/sec-oauth2-oidc/) با آن تمام شد به پرسش اول جواب می‌دهد: او کیست و چه scopeهایی دارد. پرسش دوم {{< term "authorization" "مجوزدهی" >}} است و سرور باید برای هر تابع و هر شیء دوباره به آن جواب بدهد. باگ بالا اسمش {{< term "idor" "IDOR" >}} است (insecure direct object reference): شیء با شناسه‌اش بازیابی می‌شود و کسی بررسی نمی‌کند که این فراخواننده اجازه‌ی دیدنش را دارد. در [OWASP Top 10 در کد واقعی](/fa/posts/sec-owasp-top10-in-code/) خیلی کوتاه نشانش دادم. این‌جا عمیق‌تر می‌روم: roleها، باگ دومی که در آن کاربر خودش را ارتقا می‌دهد، و تستی که از همه‌ی routeها نگهبانی می‌کند. سبک API همان [net/http مقاله‌های قبل](/fa/posts/go-http-api-stdlib/) است.

> فقط دفاعی. یک برنامه‌ی کوچک Go روی `127.0.0.1` با داده‌ی درون حافظه و کد خودم (Go 1.27.3 روی macOS با معماری arm64؛ در `go.mod` خود دمو عدد 1.26 نوشته شده). احراز هویت ساده شده و به توکن‌های ثابت (`tok-alice`، `tok-bob`، `tok-carol`) تبدیل شده تا تمرکز روی مجوزدهی بماند. فلگ `-mode vuln|fixed` هر نسخه را می‌سازد. کاربرها: alice (role برابر `viewer`، tenant برابر `acme`)، bob (`editor`، tenant برابر `globex`) و carol (`admin`، tenant برابر `acme`). دو سند داریم: 1 مال alice است و 2 مال bob. درخواست‌ها را با `curl` به هر نسخه فرستادم.

## 401، 403 یا 404

سه کد وضعیت بیشترِ ماجرا را می‌گویند، پس اول بگویم من چطور از آن‌ها استفاده می‌کنم:

- **401**: نمی‌دانم تو کی هستی. توکن نیست یا بد است.
- **403**: می‌دانم کی هستی و اجازه‌ی این کار را نداری. توجه کنید که این جواب لو می‌دهد آن چیز وجود دارد.
- **404**: جوابی که برای شیءهای دیگران می‌دهم، تا غریبه نتواند «مال تو نیست» را از «اصلاً نیست» تشخیص بدهد.

## نسخه‌ی آسیب‌پذیر

اول نسخه‌ی آسیب‌پذیر. Alice فقط `viewer` است و شش درخواست می‌فرستد، به همین ترتیب (بدنه‌ی `PATCH` برابر `{"name":"alice","role":"admin"}` بود):

```
200 GET /documents/2 => {"id":2,"owner":"bob","title":"bob secret"}
404 GET /documents/99 => not found
200 GET /documents/1 => {"id":1,"owner":"alice","title":"alice plan"}
200 GET /admin/users => [{"name":"alice","tenant":"acme","role":"viewer"},{"name":"bob","tenant":"globex","role":"editor"},{"name":"carol","tenant":"acme","role":"admin"}]
200 PATCH /users/me => {"name":"alice","tenant":"acme","role":"admin"}
204 DELETE /documents/2 => 
```

ترتیب کاربرها در فهرست ممکن است از اجرایی به اجرای دیگر فرق کند، چون دمو کاربرها را در یک map نگه می‌دارد. خط‌های مربوط به سند 99 و 1 رفتار عادی‌اند: سندِ ناموجود 404 است و سند خودش خواندنی است. چهار خط دیگر مشکل‌ها هستند:

1. **سطح شیء.** او سند bob را فقط با خواستن شناسه‌اش می‌خواند. این همان IDOR است.
2. **سطح تابع.** او یک سند را پاک می‌کند، در حالی که یک viewer اصلاً نباید بتواند پاک کند.
3. **باز هم سطح تابع.** او فهرست همه‌ی کاربرها را می‌گیرد، که کار admin است.
4. {{< term "mass-assignment" "Mass assignment" >}}. handler، JSON ارسالی او را مستقیم در struct به نام `User` decode می‌کند، پس او `role` خودش را انتخاب کرد. در پاسخ می‌بینیم `"role":"admin"`.

طبق OWASP API Security Top 10 (ویرایش 2023)، مورد اول «API1: Broken Object Level Authorization» است، مورد دوم و سوم «API5: Broken Function Level Authorization»، و mass assignment بخشی از «API3: Broken Object Property Level Authorization» است.

توجه کنید که هیچ‌کدام از این‌ها حمله‌ی پیچیده‌ای لازم نداشت. هرکدام فقط درخواستی است که سرور رد کردنش را فراموش کرده.

## اصلاح‌ها

**سطح شیء.** مالکیت جزو خود جست‌وجو می‌شود و جواب برای شیء دیگران 404 است:

```go
if d == nil || d.Owner != u.Name {
    http.Error(w, "not found", 404)
    return
}
```

با پایگاه داده همین ایده می‌شود `WHERE id = $1 AND owner_id = $2`: یک query، پس مرحله‌ی جدای «اول بگیر، بعد بررسی کن» وجود ندارد که کسی فراموشش کند. دمو از map استفاده می‌کند؛ این را روی Postgres اجرا نکردم.

**سطح تابع.** roleها به permissionها نگاشت می‌شوند و هر route می‌گوید چه permissionای لازم دارد:

```go
var perms = map[string][]string{
    "viewer": {"doc:read"},
    "editor": {"doc:read", "doc:write"},
    "admin":  {"doc:read", "doc:write", "doc:delete", "users:read"},
}
a.protect("DELETE /documents/{id}", "doc:delete", a.deleteDoc)
```

کد permission را بررسی می‌کند، نه اسم role را. همین نکته‌ی اصلی {{< term "rbac" "RBAC" >}} (کنترل دسترسی مبتنی بر نقش) است: roleها جدولی هستند که می‌شود ویرایشش کرد، و با اضافه‌شدن role تازه handlerها عوض نمی‌شوند. wrapper به نام `protect` اول توکن را بررسی می‌کند (401) و بعد permission را (403).

**Mass assignment.** در نوعی decode کنید که دقیقاً همان فیلدهایی را دارد که کلاینت اجازه‌ی تغییرشان را دارد:

```go
var in struct {
    Name string `json:"name"`
}
json.NewDecoder(r.Body).Decode(&in)
```

حالا همان Alice، این بار با نسخه‌ی اصلاح‌شده:

```
404 GET /documents/2 => not found
404 GET /documents/99 => not found
200 GET /documents/1 => {"id":1,"owner":"alice","title":"alice plan"}
403 GET /admin/users => forbidden
200 PATCH /users/me => {"name":"alice","tenant":"acme","role":"viewer"}
403 DELETE /documents/2 => forbidden
```

از بالا بخوانید. سند bob (شماره‌ی 2) و سندی که وجود ندارد (99) حالا یکسان به نظر می‌رسند: Alice حتی نمی‌تواند تأیید کند که 2 وجود دارد. سند خودش هنوز کار می‌کند. فهرست admin و پاک‌کردن با 403 رد می‌شوند، چون viewer هیچ‌کدام از آن دو permission را ندارد. و `PATCH`ای که می‌خواست `role` را عوض کند `"role":"viewer"` برمی‌گرداند: فیلد اضافی فقط نادیده گرفته شد. بدون توکن سرور `401` می‌دهد (و `/healthz` عمومی می‌ماند و `ok` جواب می‌دهد).

سرور هر ردشدن را هم لاگ کرد:

```
level=WARN msg="authz denied" user=alice doc=2 owner=bob
level=WARN msg="authz denied" user=alice role=viewer need=users:read route="GET /admin/users"
level=WARN msg="authz denied" user=alice role=viewer need=doc:delete route="DELETE /documents/{id}"
```

هر ردشدن را با اینکه چه کسی، چه چیزی و کدام قاعده لاگ کنید ([لاگ ساخت‌یافته](/fa/posts/go-config-logging-errors/) جست‌وجویش را ممکن می‌کند). پشت‌سرهم آمدن 404 و 403 از یک کاربر شکل کسی است که شناسه‌ها را یکی‌یکی امتحان می‌کند. توکن را لاگ نکنید.

## چیزی که «اصلاح‌شده» هنوز پوشش نمی‌دهد

اصلاح‌های بالا چهار حفره را می‌بندند، ولی باید صادقانه بگویم در همین نسخه‌ی اصلاح‌شده حفره‌ی پنجمی هم هست. carol ادمین tenant به نام `acme` است و سند bob مال tenant به نام `globex` است. با توکن او دو درخواست اضافه فرستادم (این‌ها در اسکریپت اصلی دمو نبودند؛ در یک نسخه‌ی موقت از همین build اصلاح‌شده اجرایشان کردم):

```
404 GET /documents/2 => not found
204 DELETE /documents/2 => 
```

خواندن سند bob رد شد، چون جست‌وجو مالک را در نظر می‌گیرد. ولی پاک‌کردن انجام شد. `deleteDoc` فقط permission به نام `doc:delete` می‌خواهد و هیچ‌وقت بررسی نمی‌کند سند مال کیست. بررسی سطح تابع رد شد و کسی بررسی سطح شیء را آنجا اضافه نکرد. شکل معمول این باگ همین است: این دو نوع بررسی از هم جدا هستند و هر route به هر دو نیاز دارد. تمرین پایین همین حفره را می‌بندد.

## پیش‌فرضِ ردکردن و تستی که آن را اجرا می‌کند

برای مشکل «بررسی را فراموش کردم» یک قاعده‌ی طراحی کمک می‌کند: {{< term "deny-by-default" "رد کردن به‌صورت پیش‌فرض" >}} (deny by default). هر route توکن معتبر می‌خواهد، مگر اینکه صریحاً عمومی اعلام شده باشد. یک تست هم باعث می‌شود این قاعده بعد از ویرایش‌های آینده سالم بماند. routeها با دو تابع کمکی ثبت می‌شوند که هر الگو را ثبت می‌کنند، و تست هر route را بدون توکن صدا می‌زند:

```go
var publicRoutes = map[string]bool{"GET /healthz": true}
// for every registered route not in publicRoutes: expect 401
```

برای اینکه ببینیم این تست چیزی را می‌گیرد یا نه، در یک نسخه‌ی موقت `GET /debug/vars` بدون محافظ را با تابع `public(...)` اضافه کردم. این چیزی است که `go test` چاپ کرد:

```
--- FAIL: TestEveryRouteRequiresAuth (0.00s)
    --- FAIL: TestEveryRouteRequiresAuth/GET_/debug/vars (0.00s)
        routes_test.go:26: GET /debug/vars answered 200 without a token, want 401
FAIL
FAIL	authzdemo	0.321s
FAIL
```

زیرتست شکست‌خورده اسم route و وضعیتی را که جواب داده نشان می‌دهد. بعد از برداشتن route، مجموعه‌ی تست دوباره پاس شد (`TestViewerCannotDelete` هم بررسی می‌کند که viewer 403 می‌گیرد). محدودیت این تست: فقط routeهایی را می‌شناسد که با تابع‌های کمکی من ثبت شده‌اند. handlerای که با دست روی mux بسته شود برایش نامرئی است.

## فراتر از role

وقتی قاعده به ویژگی‌ها (مالک، tenant، ساعت روز) یا رابطه‌ها («عضو تیمی که صاحب این پوشه است») بستگی دارد، RBAC سخت می‌شود. برای این حالت‌ها مدل‌های مبتنی بر ویژگی (ABAC) و مبتنی بر رابطه (ReBAC) وجود دارد. فقط اسمشان را می‌آورم؛ هیچ‌کدام را اجرا نکردم.

## فهرست بررسی برای هر route

- مجوز را در سرور بررسی کنید، برای هر تابع و هر شیء. پنهان‌کردن یک دکمه در UI بررسی نیست، چون درخواست را می‌شود بدون آن دکمه فرستاد.
- هویت را از توکن تأییدشده بگیرید، نه از شناسه‌ی کاربری در بدنه یا URL. وگرنه فراخواننده می‌تواند ادعا کند کس دیگری است.
- درخواست‌ها را در نوعی decode کنید که فیلدهای مجاز را فهرست کرده، نه مستقیم در struct پایگاه داده یا دامنه. وگرنه کلاینت فیلدهایی مثل `role` را خودش تعیین می‌کند.
- در جواب‌هایتان یکدست باشید: 404 برای شیء دیگران، 403 برای تابعی که role شما ندارد.
- ردشدن‌ها را لاگ کنید و تست کنید که route تازه نتواند اتفاقی عمومی بماند.

## تمرین

حفره‌ی پاک‌کردن را ببندید: `deleteDoc` باید سندی را که مال فراخواننده نیست رد کند (مثل `getDoc` با 404 جواب بدهد)، و تستی باید نشان دهد carol، ادمین `acme`، وقتی سند `globex` مال bob را پاک می‌کند 404 می‌گیرد. بعد تصمیم بگیرید یک ادمین داخل tenant خودش چه کارهایی را حق دارد و قاعده را tenant-aware کنید.
