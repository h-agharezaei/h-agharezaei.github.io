فرض کنید یک parser کوچک برای یک فرمت باینری می‌نویسید. یک سرآیند می‌خواند و بعد دنباله‌ای از رکوردها، که هرکدام نوع، طول و مقدار دارند. با چند فایل سالم و چند فایل آشکارا خراب تستش می‌کنید و همه‌چیز پاس می‌شود. بعد می‌گذارید برنامه‌ای جهش‌های تصادفی همان فایل‌ها را به آن بدهد. بعد از حدود ۲۵۰ تلاش parser با `slice bounds out of range` از کار می‌افتد. دلیلش ساده است: به فیلد طول داخل فایل اعتماد کرده بود.

آن برنامه یک fuzzer است و این مقاله درباره‌ی این است که چطور کار می‌کند، harness‌اش چقدر کوچک است و با crashی که پیدا می‌کند چه باید کرد. [امنیت حافظه: C در برابر Rust](/fa/posts/sec-memory-safety-c-vs-rust/) نشان داد یک اندیس بد چه می‌کند. این‌جا یک ماشین دنبال ورودی‌هایی می‌گردد که چنین اندیسی می‌سازند.

parser هدف مناسبی است، چون بایت‌هایی را می‌خواند که دیگری کنترل می‌کند. یک بررسی جاافتاده در آن می‌تواند به {{< term "denial-of-service" "حمله‌ی انکار سرویس" >}} (سرویس crash می‌کند یا گیر می‌کند) یا چیزی بدتر تبدیل شود. {{< term "fuzzing" "fuzzing" >}} یعنی دادن تعداد زیادی ورودی تولیدشده و جهش‌یافته به برنامه تا چیزی بشکند. مکمل [تست خاصیت‌محور](/fa/posts/eng-property-based-testing/) است: آن قاعده‌ای را که شما بگویید بررسی می‌کند، fuzzing اول فقط می‌پرسد «آیا crash می‌کند؟».

> فقط دفاعی. parser ۶۰ خطی خودم را، در تست خودم، روی ماشین خودم fuzz کردم. به هیچ چیز بیرونی دست نزدم. سه باگ عمدی‌اند. دمو یک مثال محلی است. اجرای اولیه Go 1.26 داشت؛ برای این بازنویسی با Go 1.27.3 دوباره اجرایش کردم. پوشه‌ی دمو parser نهایی و اصلاح‌شده را دارد، پس برای نشان‌دادن دوباره‌ی باگ‌ها هر نسخه‌ی باگ‌دار را (همان سه اشتباه، یکی‌یکی) در یک نسخه‌ی موقت دوباره ساختم و آن‌ها را fuzz کردم. fuzzer تصادفی است، پس شمارش‌ها و زمان‌ها در هر اجرا فرق می‌کنند و هرجا مهم بود می‌گویم.

## parser

اسم فرمت `TLV1` است (type، length، value). با چهار بایت `TLV1` شروع می‌شود و بعد هر تعداد رکورد دارد. هر رکورد یک نوع (۱ بایت)، یک طول (۲ بایت، big endian) و بعد به همان تعداد بایت مقدار است:

- نوع ۱ بایت‌های ساده است؛
- نوع ۲ «تکرار» است: یک شمارنده‌ی ۴ بایتی، یک اندازه‌ی ۱ بایتی و یک بایت پرکننده، یعنی «شمارنده ضرب در اندازه بایتِ پرکننده بساز»؛
- نوع ۳ متن با escapeهای backslash است، مثل `\n`.

هدف fuzz کوچک است. یک تابع تست معمولی Go است که `*testing.F` می‌گیرد:

```go
func FuzzParse(f *testing.F) {
	f.Add([]byte("TLV1\x01\x00\x03abc"))
	f.Add([]byte("TLV1\x02\x00\x06\x00\x00\x00\x03\x02x"))
	f.Add([]byte("TLV1\x03\x00\x04a\\nb"))
	f.Fuzz(func(t *testing.T, b []byte) { Parse(b) })
}
```

بدنه‌ی `f.Fuzz` کل harness است: چند بایت بگیر، `Parse` را صدا بزن و نتیجه را نادیده بگیر. اگر `Parse` panic کند یا گیر کند، شکست است. چیز دیگری لازم نیست.

سه فراخوانی `f.Add` {{< term "seed-corpus" "مجموعه‌ی بذر" >}} است، ورودی‌های سالمی که fuzzer از آن‌ها شروع می‌کند، یکی برای هر نوع رکورد. نمونه‌های واقعی بهترین بذرند. از آن‌جا، fuzzer {{< term "coverage-guided-fuzzing" "پوشش‌محور" >}} است: نگاه می‌کند هر ورودی به کدام قسمت‌های کد می‌رسد، هر ورودی را که به چیز تازه‌ای برسد نگه می‌دارد و بیشتر جهشش می‌دهد. شمارنده‌ی `new interesting` در خروجی همین است: چند ورودی برای رسیدن به کد تازه نگه داشته شده‌اند.

## باگ ۱: طول باور می‌شود

در نسخه‌ی باگ‌دار اول، `Parse` بدون اینکه بررسی کند `n` بایت واقعاً باقی مانده، `b[pos+3 : pos+3+n]` را می‌برد. fuzzش کردم:

```
$ go test -fuzz=FuzzParse -fuzztime=200000x
fuzz: elapsed: 0s, execs: 289 (2489/sec), new interesting: 1 (total: 4)
--- FAIL: FuzzParse (0.12s)
    testing.go:2078: panic: runtime error: slice bounds out of range [:12343] with capacity 24
    Failing input written to testdata/fuzz/FuzzParse/a3c431880a157b71
```

(stack trace را بریده‌ام. Go 1.27.3 جزئیات بیشتری از Go 1.26 چاپ می‌کند و عدد capacity در هر اجرا فرق می‌کند.) `-fuzztime=200000x` یعنی «بعد از ۲۰۰۰۰۰ اجرا بایست»؛ این‌جا بعد از ۲۸۹ اجرا شکست خورد، که با ۲۵۱ در اجرای اولیه هم‌حدود است. اسم فایل hash محتواست، پس همان ورودی crashکننده همان اسم قبلی را گرفت.

فایل ورودی را بعد از **minimize** شدن توسط Go نگه می‌دارد. minimize یعنی fuzzer ورودی crashکننده را تا جایی که هنوز crash می‌کند کوچک می‌کند، تا به‌جای یک انبار نویز کوچک‌ترین نمونه را داشته باشید:

```
go test fuzz v1
[]byte("TLV1\x0200")
```

این‌طور بخوانید: `TLV1`، نوع ۲، و دو بایت طول نویسه‌های `0` و `0` هستند، یعنی `0x3030`، یعنی ۱۲۳۳۶. parser می‌خواست ۱۲۳۳۶ بایت از ورودی‌ای ۷ بایتی بردارد. حالا crash ذخیره شده است، پس `go test` ساده آن را دوباره اجرا می‌کند و شکست می‌خورد، تا وقتی که اصلاح شود:

```go
if n > len(b)-pos-3 { return nil, ErrFormat }
```

یعنی پیش از استفاده از طول، آن را با چیزی که واقعاً باقی مانده مقایسه کنید. فایل ذخیره‌شده در `testdata/fuzz` به‌عنوان یک تست {{< term "regression" "رگرسیون" >}} دائمی می‌ماند، پس این باگ هرگز بی‌سروصدا برنمی‌گردد. آن را commit کنید.

## باگ ۲: محاسبه‌ی int32

نسخه‌ی باگ‌دار دوم باگ ۱ را اصلاح کرده بود ولی اندازه‌ی رکورد «تکرار» را با عددهای ۳۲ بیتی علامت‌دار حساب می‌کرد. همان دستور، crash تازه:

```
--- FAIL: FuzzParse (0.12s)
    panic: runtime error: makeslice: len out of range
    Failing input written to testdata/fuzz/FuzzParse/1461c70ced3bd442
```

(باز هم با یک stack trace که بریده‌ام.) ورودی minimizeشده این است:

```
[]byte("TLV1\x02\x00\x06A00020")
```

نوع ۲، طول ۶ و مقدار `A00020`. شمارنده چهار بایت اول است، `A000`، یعنی `0x41303030`. اندازه بایت بعدی است، `'2'`، یعنی ۵۰. کد من `int32(count) * int32(size)` را ضرب می‌کرد. این حاصل‌ضرب در ۳۲ بیت جا نمی‌شود و به یک عدد **منفی** دور می‌زند (این‌جا حدود منفی ۱٫۱۵ میلیارد). total منفی از بررسی `total > maxTotal` رد می‌شود، چون از بیشینه کمتر است، و بعد `make` با «len out of range» می‌شکند.

این یک {{< term "integer-overflow" "سرریز عدد صحیح" >}} در محاسبه‌ی طول است. می‌توانست جور دیگری باشد: اگر حاصل‌ضرب به یک عدد مثبت کوچک دور می‌زد، بافر فقط کوتاه می‌شد. اگر بررسی اصلاً نبود، یک فیلد ۴ بایتی می‌توانست گیگابایت‌ها بخواهد. راه حل این است که در `uint64` حساب کنید و پیش از تخصیص با یک سقف مقایسه کنید:

```go
total := uint64(count) * uint64(val[4])
if total > maxTotal { return nil, ErrFormat }
```

## باگ ۳: گیرکردن

نسخه‌ی باگ‌دار سوم backslash آخر را اشتباه مدیریت می‌کرد. در `unescape` اندیس فقط وقتی جلو می‌رفت که بعد از backslash نویسه‌ای بود؛ با backslash در انتهای ورودی، حلقه تا ابد می‌چرخید. این شکست فرق دارد، چون هیچ چیز panic نمی‌کند:

```
fuzz: elapsed: 3s, execs: 180125 (60020/sec), new interesting: 21 (total: 26)
fuzz: elapsed: 6s, execs: 180125 (0/sec), new interesting: 21 (total: 26)
...
--- FAIL: FuzzParse (60.98s)
    fuzzing process hung or terminated unexpectedly: exit status 2
    Failing input written to testdata/fuzz/FuzzParse/7c12144b9877ed15
```

(خط‌های پیشرفتِ تکراری وسط را حذف کرده‌ام.) شمارنده‌ی exec روی ۱۸۰۱۲۵ می‌ایستد و `0/sec` نشان می‌دهد: workerها داخل ورودی‌ای گیر کرده‌اند که هرگز برنمی‌گردد. در اجرای اولیه Go بعد از حدود ده ثانیه تسلیم شد؛ در این اجرای دوباره حدود یک دقیقه طول کشید، پس این زمان را وابسته به ماشین و نسخه بدانید. ورودی ذخیره‌شده minimize نشده، چون minimize کردن یک hang کند است، پس کمی نویز دارد:

```
[]byte("TLV1\x03\x00\x04a\x1cJ\\nb")
```

(بایت‌های دقیق از اجرایی به اجرای دیگر و نسبت به اجرای اولیه فرق می‌کنند؛ اسم فایل هم با آن‌ها عوض می‌شود.) این‌طور بخوانید: نوع ۳، طول ۴ و مقدار چهار بایتی `a`، یک نویسه‌ی کنترلی، `J` و یک backslash آخر. `nb` بعد از آن نویز اضافه است. همان backslash آخر حالت مورد نظر است. اجرای دوباره‌ی یک hang با `go test` ساده هم گیر می‌کند، پس timeout بدهید: `go test -run=FuzzParse/7c12144b9877ed15 -timeout 5s` چاپ کرد `panic: test timed out after 5s`. اصلاح این است که اندیس را در هر مسیر جلو ببرید (`i += 2` بدون شرط)، تا هر دور حلقه دست‌کم یک بایت مصرف کند.

## بعد از اصلاح‌ها

با parser نهایی و سه ورودی ذخیره‌شده در `testdata/fuzz/FuzzParse/`، یک `go test -v` ساده بذرها و ورودی‌های ذخیره‌شده را مثل تست‌های معمولی اجرا می‌کند:

```
$ go test -v -run=FuzzParse
--- PASS: FuzzParse (0.00s)
    --- PASS: FuzzParse/seed#0 (0.00s)
    --- PASS: FuzzParse/seed#1 (0.00s)
    --- PASS: FuzzParse/seed#2 (0.00s)
    --- PASS: FuzzParse/1461c70ced3bd442 (0.00s)
    ...
```

(فهرست با دو ورودی ذخیره‌شده‌ی دیگر، `a3c431880a157b71` و `da26de22b41b4c2d`، ادامه دارد که بریده‌ام. فایل سوم همان hang ذخیره‌شده‌ی اجرای اولیه است.) بعد گذاشتم fuzzer دوباره بگردد، با بودجه‌ی بزرگ‌تر:

```
$ go test -fuzz=FuzzParse -fuzztime=2000000x
fuzz: elapsed: 8s, execs: 2000000 (140601/sec), new interesting: 4 (total: 42)
PASS
```

دو میلیون اجرا، بدون crash. این **اثبات درستی parser نیست**؛ فقط یعنی این جست‌وجو مشکلی پیدا نکرد. تعداد را گزارش می‌کنم، نه سرعت را: execs در ثانیه به ماشین و برنامه‌های دیگری که روی آن اجرا می‌شوند بستگی دارد.

## ویژگی‌ها و تفاوت‌ها

تا این‌جا تنها «oracle»، یعنی چیزی که به fuzzer می‌گوید باگ پیدا کرده، این بود که «panic کرد یا گیر کرد». این یکی رایگان است. oracle بهتر یک خاصیت است. `FuzzRoundTrip` بررسی می‌کند که رمزکردن یک رکورد نوع ۳ و دوباره parse کردنش همان داده را برمی‌گرداند:

```go
rs, err := Parse(Encode([]Record{{3, d}}))
if err != nil || len(rs) != 1 || !bytes.Equal(rs[0].Data, d) {
	t.Fatalf("round trip failed for %q: %v %v", d, rs, err)
}
```

اینجا ۵۰۰۰۰۰ اجرا را گذراند، پس باگ منطقی پیدا نکردم. {{< term "differential-testing" "fuzzing تفاضلی" >}} را اجرا نکردم: parser شما را روی همان ورودی با پیاده‌سازی دیگری مقایسه می‌کند (مثلاً یک زیرمجموعه‌ی JSON در برابر `encoding/json`) و هر اختلاف را گزارش می‌دهد. شکلش همان است.

## در پروژه‌های واقعی

- CI: به fuzzing در pull request بودجه‌ی کوتاه بدهید (`-fuzztime=30s`) و شبانه بودجه‌ی بلند. [طراحی pipeline برای CI/CD](/fa/posts/eng-ci-cd-pipeline-design/) را ببینید.
- C و C++: libFuzzer و AFL++ ابزارهای رایج‌اند و OSS-Fuzz آن‌ها را در مقیاس بزرگ اجرا می‌کند؛ Rust ابزار `cargo-fuzz` را دارد. فقط اسمشان را می‌آورم؛ اجرایشان نکردم.
- fuzzer را با یک sanitizer مثل {{< term "addresssanitizer" "AddressSanitizer" >}} برای C جفت کنید، چون یک باگ حافظه در C ممکن است خودش crash نکند. Go و Rust {{< term "memory-safety" "امنیت حافظه" >}} را می‌دهند، ولی برنامه‌هایشان باز هم می‌توانند panic کنند و گیر کنند.
- فرهنگ‌واژه‌ی کلیدواژه‌ها و fuzzing ساختارآگاه به فرمت‌هایی که checksum یا گرامر دارند کمک می‌کند، جایی که بایت‌های تصادفی از اولین بررسی رد می‌شوند.

## چطور fuzzing به نتیجه برسد

- فایل‌های `testdata/fuzz` را commit کنید؛ تست‌های رگرسیون شما هستند.
- بذر از نمونه‌های واقعی از بذر خالی بهتر است.
- parserهای خودتان را fuzz کنید، هرگز سرویس‌های دیگران را.
- هر تخصیصی را که به ورودی بستگی دارد سقف بگذارید.
- سکوت اثبات نیست.

## تمرین

یک رکورد نوع ۴ اضافه کنید که طول ۴ بایتی‌اش مستقیم در `make([]byte, n)` استفاده شود. بگذارید fuzzer مشکل را پیدا کند، بعد سقف و یک تست رگرسیون اضافه کنید.

## قدم بعدی

مقاله‌ی بعد «لاگ، audit و واکنش به حادثه» است. درباره‌ی باگ‌هایی است که با همه‌ی این‌ها باز هم رد می‌شوند: آن‌وقت مهم این است که بتوانید بفهمید چه اتفاقی افتاد.
