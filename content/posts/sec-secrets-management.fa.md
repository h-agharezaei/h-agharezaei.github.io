یک `config.env` با یک رمز عبور داخلش commit کنید. متوجه می‌شوید و در commit بعدی فایل را پاک می‌کنید. حالا working tree تمیز است. بعد `git show HEAD~1:config.env` را اجرا می‌کنید و رمز روی صفحه چاپ می‌شود. گیت هیچ‌چیز را فراموش نمی‌کند: working tree تمیز است، تاریخچه نه.

این فقط یکی از راه‌هایی است که یک راز بیرون می‌رود. راز به لاگ، پیام خطا، فهرست پروسه‌ها و محیط پروسه‌های فرزند هم نشت می‌کند. [TLS و گواهی x509 در عمل](/fa/posts/sec-tls-x509-certificates/) با «کلیدها را از repository دور نگه دارید» تمام شد؛ این مقاله درباره‌ی این است که رازها با این همه چطور بیرون می‌روند، بعد از نشت چه باید کرد، و چطور رازها را طوری بارگذاری و استفاده کنیم که کمتر بیرون بروند. منظور من از **راز** هر چیزی است که هویت را ثابت می‌کند یا داده را باز می‌کند: رمز عبور، کلید API، کلید امضا، کلید خصوصی، رشته‌ی اتصال پایگاه داده. روی [پیکربندی، لاگ ساخت‌یافته و خطا در Go](/fa/posts/go-config-logging-errors/) بنا شده؛ ذخیره‌ی رمز عبور مقاله‌ی جدا دارد، [ذخیره‌ی امن پسورد: argon2 و bcrypt](/fa/posts/sec-password-hashing/)، و کلیدهای امضا در [session یا JWT؟](/fa/posts/sec-sessions-vs-jwt/) آمدند.

> فقط دفاعی. هر رازی در این مقاله آشکارا ساختگی است (`AKIAFAKEFAKEFAKE1234`، `tok_FAKE_0123456789abcdef` و مانند آن) و فقط برای دمو ساخته شده. همه‌چیز محلی با Go 1.27.3 و git روی macOS با معماری arm64 اجرا شد (در `go.mod` خود دمو عدد 1.26 نوشته شده)، در repositoryهای یک‌بارمصرف داخل یک پوشه‌ی موقت که بعداً پاکش کردم؛ اسکنر هیچ‌وقت به repository واقعی دست نزد. gitleaks، trufflehog، `git filter-repo`، Vault و KMS ابری را اجرا نکردم؛ فقط توضیح داده شده‌اند. مسیرها به `<tmp>` کوتاه شده‌اند و جاهایی که نوشته‌ام مقدار رازها را در خروجی ماسک کرده‌ام.

## گیت یادش می‌ماند

یک repository یک‌بارمصرف ساختم، یک `config.env` ساختگی با دو راز ساختگی commit کردم و در commit بعدی فایل را پاک کردم. این جست‌وجوی تاریخچه است و بعد محتوای commit قدیمی (مقدارها را با `sed` ماسک کردم، پس فقط چند نویسه‌ی اول پیداست):

```
$ git log --all --oneline --name-only -S AKIAFAKEFAKEFAKE1234
cf59da8 remove secrets from the repo
config.env
9ef7259 add config
config.env
$ git show HEAD~1:config.env      (masked by me)
AWS_ACCESS_KEY_ID=AKIA****
DB_PASSWORD=hunt****
```

`-S` از گیت commitهایی را می‌خواهد که دقیقاً همین رشته را اضافه یا حذف کرده‌اند. هر دو commit به `config.env` دست زده‌اند: یکی اضافه‌اش کرد و بعدی حذف. و `git show HEAD~1:config.env` فایل را همان‌طور که در commit قدیمی‌تر بود چاپ می‌کند. شناسه‌ی commitها در هر اجرا فرق می‌کند.

بعد از یک نشت واقعی چه باید کرد؟ به این ترتیب:

1. **اول rotate کنید.** فرض کنید راز از قبل کپی شده است، با یک clone، یک cache در CI یا یک scraper. راز تازه صادر کنید و قدیمی را باطل کنید.
2. بعد اگر می‌خواهید از repository پاک شود، تاریخچه را بازنویسی کنید. مستندات خود گیت برای `git filter-branch` برای این کار `git filter-repo` را توصیه می‌کند. این‌جا نصب نیست، پس اجرایش نکردم.
3. بعد جلوی بار بعد را بگیرید، با عادت‌های بقیه‌ی این مقاله.

## جلوگیری از commit بعدی

شاید فکر کنید `.gitignore` مشکل را حل می‌کند. برای فایلی که از قبل tracked است کمکی نمی‌کند. در دمو `*.env` را به `.gitignore` اضافه کردم: `other.env` تازه نادیده گرفته شد، ولی `new.env` که قبل از قاعده اضافه شده بود در `git ls-files` ماند.

```
.gitignore:1:*.env	other.env
new.env
```

خط اول `git check-ignore -v` است که توضیح می‌دهد چرا `other.env` نادیده گرفته می‌شود. خط دوم `git ls-files` است که هنوز `new.env` را فهرست می‌کند.

نگهبان بهتر یک {{< term "git-hook" "hook از نوع pre-commit" >}} است: اسکریپتی که گیت پیش از هر commit اجرا می‌کند. مال من یک اسکریپت shell است که در diff مرحله‌ای (staged) دنبال الگوهایی می‌گردد که شبیه راز هستند. فایلی با یک توکن ساختگی را stage کردم و commit را امتحان کردم:

```
pre-commit: staged changes look like they contain a secret; commit blocked
exit status: 1
```

commit انجام نشد. ولی `git commit --no-verify` این hook را رد می‌کند، پس نگهبان است نه دیوار. اشتباه صادقانه را می‌گیرد، که رایج‌ترین نوع است.

## یک اسکنر کوچک

hook فقط به چیزی که می‌خواهید commit کنید نگاه می‌کند. {{< term "secret-scanning" "اسکن راز" >}} (secret scanning) همین ایده روی کل repository و تاریخچه‌اش است. مال من حدود ۵۰ خط Go است با دو ایده. اول، دو عبارت منظم: یک شناسه‌ی کلید به سبک AWS (`AKIA` و بعد ۱۶ نویسه) و یک انتساب مثل `password = چیزی`. دوم، {{< term "shannon-entropy" "آنتروپی شانون" >}}: معیاری از اینکه نویسه‌های یک رشته چقدر غیرقابل‌پیش‌بینی‌اند. `aaaaaaaa` آنتروپی ۰ بیت در هر نویسه دارد؛ یک توکن تصادفی خیلی بیشتر. اسکنر توکن‌های بلندی را که بیش از ۴٫۲ بیت در هر نویسه دارند علامت می‌زند (آستانه‌ی خود من است). کل تاریخچه‌ی repository نشتی‌دار را به آن دادم (`git log -p --all`) و مقدارها ماسک شده‌اند:

```
line 13  aws-access-key-id  AKIA****
line 14  assigned-secret    PASS****
line 28  aws-access-key-id  AKIA****
line 29  assigned-secret    PASS****
scanned 36 lines, 4 findings
```

هر راز دو بار پیدا می‌شود، چون `git log -p` خط را یک بار وقتی فایل اضافه شد نشان می‌دهد و یک بار وقتی حذف شد. شماره‌ی خط‌ها جای خط در همین جریان متن است، نه در یک فایل.

بعد یک repository تمیز. یک خط `go.sum`، یک جمله‌ی README درباره‌ی رمز عبور، و یک hash چهل‌نویسه‌ای commit در README دارد:

```
line 22  high-entropy       Zk3k**** (5.24 bits/char)
scanned 22 lines, 1 findings
```

این یافته مثبت کاذب است: checksum یک ماژول از خط `go.sum` است که چون hash است تصادفی به نظر می‌رسد. hash مربوط به commit زیر آستانه ماند، چون رقم‌های hex فقط ۱۶ نویسه‌ی ممکن دارند و آنتروپی هر نویسه‌شان کمتر است. این بده‌بستان هر اسکنری است: آستانه را پایین بیاورید در نویز غرق می‌شوید، بالا ببرید کلید واقعی را از دست می‌دهید.

## لاگ و خطا

رازها بیشتر از خود برنامه‌ی شما نشت می‌کنند تا از repository. یک logger از نوع JSON هر چیزی را که بدهید چاپ می‌کند. دمو یک login را با توکن ساختگی به چهار شکل لاگ می‌کند و بعد همان توکن را با `fmt` چاپ می‌کند:

```
{"level":"INFO","msg":"login","user":"alice","token":"tok_FAKE_0123456789abcdef"}
{"level":"INFO","msg":"login","user":"alice","token":"[REDACTED]"}
{"level":"INFO","msg":"login","user":"alice","tok":"tok_FAKE_0123456789abcdef"}
{"level":"INFO","msg":"login","user":"alice","tok":"[REDACTED]"}
fmt %v plain string: tok_FAKE_0123456789abcdef
fmt %v Secret type:  [REDACTED]
```

خط‌به‌خط بخوانید. خط ۱ یک logger ساده است: توکن را چاپ می‌کند. خط ۲ از hook به نام `ReplaceAttr` استفاده می‌کند که هر attribute به نام `token` را پنهان می‌کند، و کار می‌کند. خط ۳ ضعفش را نشان می‌دهد: همان توکن با نام کلید دیگر (`tok`) مستقیم رد می‌شود. خط ۴ طراحی بهتر است: نوع `Secret` با متد `LogValue`، تا مقدار هرجا لاگ شود خودش را پنهان کند. دو خط آخر همین را برای `fmt` نشان می‌دهند: رشته‌ی ساده توکن را چاپ می‌کند، ولی `Secret` که متد `String` هم دارد `[REDACTED]` چاپ می‌کند. این از `slog` و `fmt` محافظت می‌کند. encoder دیگری از `LogValue` خبر ندارد: وقتی در یک برنامه‌ی موقت یک `Secret` را به `json.Marshal` دادم، توکن آشکار چاپ شد. پس بر اساس نوع پنهان کنید، ولی رازها را از ساختارهایی که serialize می‌کنید هم دور نگه دارید.

پیام خطا هم همین‌طور نشت می‌کند. دمو یک خطا با رشته‌ی اتصال داخلش می‌سازد و بعد خطای امن‌تر را:

```
error before: connect failed: dsn=postgres://app:FAKE-db-pass-123@127.0.0.1:5432/orders
error after:  connect failed: host=127.0.0.1:5432 user=app
```

خطا از چند لایه بالا می‌رود و به لاگ‌ها و جلوی چشم کاربرها می‌رسد، پس هرگز نباید رمز را با خودش ببرد.

## متغیرهای محیطی و آرگومان‌ها

{{< term "environment-variable" "متغیر محیطی" >}} رشته‌ای است که پروسه از والد خود می‌گیرد. راحت است، ولی یعنی هر پروسه‌ی فرزند به‌طور پیش‌فرض همه‌ی آن را می‌گیرد. آرگومان‌های خط فرمان حتی عمومی‌ترند: در فهرست پروسه‌ها دیده می‌شوند. دمو یک برنامه‌ی فرزند را چهار طور اجرا می‌کند:

```
inherited: child sees FAKE_DEMO_SECRET = FAKE-env-value-123
explicit:  child sees FAKE_DEMO_SECRET = 
ps args:    ./demo wait --api-key=FAKE-cli-key-456
ps eww:     FAKE_DEMO_SECRET=FAKE-env-value-123
```

به‌طور پیش‌فرض فرزند راز والد را می‌بیند (`inherited`). با `cmd.Env` که صریحاً روی یک فهرست حداقلی تنظیم شده، نمی‌بیند (`explicit`، مقدار خالی). دو خط آخر یک فرزند طولانی‌مدت خودم را با `ps` نگاه می‌کنند: آرگومان `--api-key=...` برای هر کسی که بتواند `ps` اجرا کند دیده می‌شود، و `ps eww` محیط پروسه را چاپ کرد (دمو فقط متغیر ساختگی را از آن خروجی نشان می‌دهد). این را فقط روی macOS آزمایش کردم. روی Linux معادلش `/proc/<pid>/environ` است که اجرا نکردم. پس برای فرزندها `cmd.Env` را صریحاً تنظیم کنید و راز را به‌صورت آرگومان ندهید.

## بارگذاری رازها

اشتباهی که بیشتر می‌بینم مقدار پیش‌فرض است:

```
bad fallback:  key="dev-secret"
fail closed:   FAKE_SIGNING_KEY is not set
```

تابع اول وقتی متغیر نیست به `"dev-secret"` برمی‌گردد، پس یک تنظیم فراموش‌شده در production بی‌صدا به کلیدی تبدیل می‌شود که هر کسی کد را خوانده بلد است. تابع دوم خطا برمی‌گرداند و برنامه بالا نمی‌آید. همیشه به‌جای حدس‌زدن در شروع برنامه شکست بخورید.

جایگزین رایج متغیرهای محیطی قرارداد `NAME_FILE` است: متغیر مسیر یک فایل را نگه می‌دارد و برنامه راز را از فایل می‌خواند. بارگذار حالت (mode) فایل را هم بررسی می‌کند و فایلی را که دیگران می‌توانند بخوانند رد می‌کند:

```
mode 0644:     db_password has mode 0644, want 0600 or stricter
mode 0600:     value="FAKE-file-secret" err=<nil>
```

`0644` یعنی مالک می‌تواند بخواند و بنویسد و بقیه می‌توانند بخوانند. `0600` یعنی فقط مالک. مدیرهای راز (Vault، KMS ابری) روی این‌ها audit و rotation اضافه می‌کنند؛ هیچ‌کدام را اجرا نکردم.

## رمزنگاری با کلید

گاهی راز همان کلیدی است که داده‌ی دیگری را حفاظت می‌کند. {{< term "aes-gcm" "AES-256-GCM" >}} روش استاندارد رمزکردن است و برای هر پیام زیر یک کلید به یک {{< term "nonce" "nonce" >}} یکتا (عددی که یک بار استفاده می‌شود) نیاز دارد. برای نشان‌دادن اینکه با شکستن این قاعده چه می‌شود، دو پیام بی‌ضرر ساختگی را با همان nonce صفر رمز کردم و مقایسه کردم:

```
same nonce: c1^c2 == p1^p2 ? true
knowing p1, p2 = "pay mallory 999 US"
```

خط اول می‌گوید XOR دو متن رمزشده با XOR دو متن اصلی برابر است: جریان کلید حذف شد. خط دوم پیامدش را نشان می‌دهد: اگر یکی از متن‌های اصلی را بدانید (اینجا پیامی که با `pay alice 0010 USD` شروع می‌شود)، دیگری را می‌توانید حساب کنید. برای هر بار یک nonce تازه از `crypto/rand` بگیرید؛ `seal` در دمو همین کار را می‌کند و یک تست بررسی می‌کند که رمزکردن یک ورودی دو بار خروجی متفاوت می‌دهد.

ایده‌ی دوم {{< term "envelope-encryption" "رمزنگاری پاکتی" >}} (envelope encryption) است. هر رکورد با کلید داده‌ی تصادفی خودش (DEK) رمز می‌شود. این کلید کوچک بعد با یک کلید اصلی (KEK) رمز می‌شود («wrap») و شناسه‌ی کلید اصلی کنار رکورد ذخیره می‌شود. چرا؟ به‌خاطر {{< term "key-rotation" "چرخش کلید" >}} (rotation): وقتی کلید اصلی را عوض می‌کنید فقط کلید کوچکِ wrap‌شده را دوباره wrap می‌کنید، نه همه‌ی داده را:

```
stored key id: kek-1  wrapped DEK bytes: 60  data bytes: 50
after rewrap:  kek-2  data unchanged: true
old record, kek-1 retired: unknown key id kek-1
rewrapped record: "card-last4=0000 (fake)" err=<nil>
wrong record id (AAD): cipher: message authentication failed
```

رکورد `kek-1` و یک کلید wrap‌شده‌ی ۶۰ بایتی (۱۲ بایت nonce، ۳۲ کلید، ۱۶ برچسب) ذخیره کرده. بعد از rewrap، `kek-2` را می‌گوید و بایت‌های داده دقیقاً همان‌اند. بعد `kek-1` را بازنشسته کردم: رکورد قدیمی دیگر باز نمی‌شود (unknown key id) ولی رکورد rewrap‌شده هنوز باز می‌شود. برای همین شناسه‌ی کلید باید با هر متن رمزشده ذخیره شود. خط آخر شناسه‌ی رکورد را به‌عنوان additional authenticated data نشان می‌دهد: رمزگشایی رکورد با شناسه‌ی دیگر (`order-8` به‌جای `order-7`) شکست می‌خورد، که جلوی جابه‌جاکردن متن رمزشده بین ردیف‌ها را می‌گیرد.

وقتی رازهایی مثل توکن را مقایسه می‌کنید از `subtle.ConstantTimeCompare` ({{< term "constant-time-comparison" "مقایسه‌ی زمان‌ثابت" >}}) استفاده کنید تا زمان صرف‌شده لو ندهد چند بایت اول درست بوده است. دمو برای همین فراخوانی `constant-time equal: true` چاپ می‌کند. پاک‌کردن راز از حافظه موضوع دیگری است: Go راه قابل‌اعتمادی برای آن نمی‌دهد (رشته‌ها تغییرناپذیرند و runtime می‌تواند نسخه نگه دارد)، پس قولی نمی‌دهم.

## مهار خسارت

- بعد از نشت اول rotate کنید؛ پاک‌کردن یک commit کافی نیست.
- هرگز برای راز مقدار پیش‌فرض نگذارید؛ در شروع برنامه شکست بخورید.
- بر اساس نوع پنهان کنید نه نام کلید، و رازها را از خطاها دور نگه دارید.
- فایل با حالت 0600 را بر متغیر محیطی و هر دو را بر آرگومان ترجیح دهید.
- با هر متن رمزشده یک شناسه‌ی کلید ذخیره کنید تا rotation ممکن باشد.

## تمرین

به اسکنر فلگ `--history` اضافه کنید که commit هر یافته را چاپ کند، و یک allowlist تا مثبت کاذب `go.sum` دیگر نمایش داده نشود.
