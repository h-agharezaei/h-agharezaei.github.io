از یک اپ logout می‌کنید. آیا کوکی یا توکنی که یک دقیقه پیش استفاده می‌کردید هنوز کار می‌کند؟ بستگی دارد سرور چه چیزی درباره‌ی شما به یاد دارد. با {{< term "session" "نشست" >}} (**session**) سمت سرور، logout فوری است، چون سرور رکوردش را پاک می‌کند و کوکی در مرورگر شما حالا به هیچ‌چیز اشاره نمی‌کند. با {{< term "jwt" "JWT" >}}، سرور اصلاً رکوردی نگه نداشته، پس چیزی برای پاک کردن ندارد و توکن تا وقتی منقضی شود معتبر می‌ماند.

کل انتخاب به همین تفاوت برمی‌گردد و در دو جمله جا می‌شود. در session، سرور به یاد دارد شما کی هستید و مرورگر فقط یک شناسه‌ی بی‌معنا با خودش دارد. در JWT، کلاینت claimهای امضاشده درباره‌ی خودش را با خود می‌برد و سرور هیچ‌چیز به یاد ندارد. بقیه‌ی این مقاله از همین نتیجه می‌شود. این اولین تصمیم بعد از login موفق است، همان‌جا که [ذخیره‌ی امن پسورد: argon2 و bcrypt](/fa/posts/sec-password-hashing/) تمام شد. زمینه یک API کوچک شبیه سفارش‌هاست از [ساخت API با net/http در Go](/fa/posts/go-http-api-stdlib/). HttpOnly و CSP از [تزریق و XSS](/fa/posts/sec-injection-xss/) می‌آیند.

> فقط دفاعی. یک برنامه‌ی کوچک Go (go.mod می‌گوید Go 1.25؛ دوباره با Go 1.27 اجرایش کردم) با `github.com/golang-jwt/jwt/v5` نسخه‌ی v5.2.1 که روی 127.0.0.1 گوش می‌دهد و فقط خودم با `curl` ازش استفاده کردم. رازی که در آن هست یک نمونه‌ی دورانداختنی است. **در مرورگر امتحان نکردم**؛ فقط headerها را دیدم. دمویی جداست و ادامه‌ی دموی قبلی نیست.

## session سمت سرور

اول مدلی که سرور به یاد می‌سپارد. هنگام login سرور یک شناسه‌ی تصادفی می‌سازد، `id -> user` را در یک جدول نگه می‌دارد و شناسه را در یک کوکی به مرورگر می‌دهد. در هر درخواست بعدی مرورگر کوکی را پس می‌فرستد و سرور شناسه را جست‌وجو می‌کند. شناسه به‌تنهایی معنایی ندارد؛ فقط یک کلید است.

در دمو ۱۶ بایت تصادفی با `crypto/rand` می‌سازم، با hex کدشان می‌کنم (یعنی ۱۲۸ بیت تصادفی بودن، پس کسی نمی‌تواند شناسه‌ی کاربر دیگر را حدس بزند) و map را در حافظه نگه می‌دارم:

```go
http.SetCookie(w, &http.Cookie{Name: "sid", Value: id, Path: "/",
	MaxAge: 3600, HttpOnly: true, Secure: true, SameSite: http.SameSiteLaxMode})
```

`curl -i` header پاسخ را نشان می‌دهد (شناسه با `<id>` جایگزین شده؛ هر بار تصادفی است):

```
HTTP/1.1 200 OK
Set-Cookie: sid=<id>; Path=/; Max-Age=3600; HttpOnly; Secure; SameSite=Lax
```

شناسه ۳۲ نویسه‌ی hex بود. پرچم‌های بعد از آن از کوکی محافظت می‌کنند:

- {{< term "httponly" "HttpOnly" >}} کوکی را از JavaScript صفحه پنهان می‌کند، پس یک باگ XSS نمی‌تواند آن را بخواند.
- `Secure` یعنی مرورگر فقط روی HTTPS آن را می‌فرستد.
- {{< term "samesite" "SameSite" >}}`=Lax` محدود می‌کند مرورگر کوکی را چه وقت به درخواست‌هایی که از سایت‌های دیگر شروع می‌شوند بچسباند.
- `Max-Age=3600` باعث می‌شود بعد از یک ساعت منقضی شود.

توجه: مرورگر ممکن است کوکی `Secure` را که روی http ساده می‌رسد ذخیره نکند (بعضی برای localhost استثنا می‌گذارند). من فقط header را دیدم و کوکی را دستی با `-H "Cookie: ..."` فرستادم.

حالا نکته‌ی اصلی این طراحی. logout عضو map را پاک می‌کند، پس ابطال فوری است. دمو login می‌کند، از کوکی استفاده می‌کند، logout می‌کند و دوباره همان کوکی را به کار می‌برد:

```
GET /me      -> hello alice [200]
POST /logout -> logged out  [200]
GET /me      -> unauthorized [401]
```

همان کوکی تا logout کار می‌کند و درست بعدش رد می‌شود، چون سرور دیگر آن شناسه را نمی‌شناسد. هزینه‌ی این مدل: هر درخواست یک جست‌وجو می‌خواهد، و با چند سرور باید محل نگهداری مشترک باشد (دیتابیس یا cache). map من با ری‌استارت از بین می‌رفت.

## JWT

مدل دیگر حافظه را به کلاینت می‌برد. JWT رشته‌ای است از سه بخش base64url که با نقطه جدا شده‌اند: یک header، یک payload از claimها (حقایقی مثل اینکه کاربر کیست و توکن کی منقضی می‌شود) و یک امضا. سرور دو بخش اول را با یک کلید محرمانه امضا می‌کند. بعداً می‌تواند امضا را بررسی کند و بدون جست‌وجوی چیزی به claimها اعتماد کند.

دمو یک توکن را با HS256 (یعنی HMAC با SHA-256) امضا می‌کند و دو بخش اول را decode می‌کند. مقدار `exp` یک timestamp یونیکسی است و به زمان اجرا بستگی دارد:

```
parts: 3
header: {"alg":"HS256","typ":"JWT"}
payload: {"exp":1793817402,"role":"user","sub":"alice"}
signature bytes: 32
```

`alg` می‌گوید چطور امضا شده، `sub` کاربر است، `role` یک claim است که خودم اضافه کردم و `exp` زمان انقضاست. امضا ۳۲ بایت است، اندازه‌ی خروجی SHA-256. دقت کنید که payload را بدون دانستن هیچ کلیدی خواندم. JWT امضا شده است، **رمزگذاری نشده**: هر کس توکن را داشته باشد می‌خواندش، پس هرگز رازی در آن نگذارید. امضا فقط تغییر را تشخیص می‌دهد. برای دیدنش، `role` را به `admin` تغییر دادم، امضای قبلی را نگه داشتم و هر دو توکن را بررسی کردم:

```
verify original: <nil>
verify tampered: token signature is invalid: signature is invalid
```

اصلی تأیید می‌شود (`<nil>` یعنی بدون خطا). نسخه‌ی ویرایش‌شده رد می‌شود، چون امضا روی payload قدیمی حساب شده بود.

## alg none و algorithm confusion

header فیلدی به اسم `alg` دارد و همین یک تله است. بعضی کتابخانه‌های قدیمی JWT شناخته شده بود که به `alg` داخل خود توکن اعتماد می‌کردند، پس مهاجم می‌توانست `none` (اصلاً بدون امضا) یا خانواده‌ی دیگری از الگوریتم را انتخاب کند. دفاع این است که سرور تصمیم بگیرد، نه توکن. verifier من الگوریتم را ثابت می‌کند و `exp` را الزامی می‌کند:

```go
jwt.Parse(tok, keyFunc, jwt.WithValidMethods([]string{"HS256"}), jwt.WithExpirationRequired())
```

چهار توکن بد را در برابر verifier خودم ساختم: یکی با `alg=none`، یکی با HS512 که با همان راز امضا شده، یکی منقضی‌شده و یکی بدون `exp`. هر چهار رد شدند:

```
verify alg=none: token signature is invalid: signing method none is invalid
verify alg=HS512: token signature is invalid: signing method HS512 is invalid
verify expired: token has invalid claims: token is expired
verify no exp: token has invalid claims: token is missing required claim: exp claim is required
```

حمله‌ی RS256-به-HS256 را امتحان نکردم. با الگوریتم ثابت‌شده باید با همین قاعده رد شود، ولی این استدلال است، نه اجرا.

## مشکل ابطال

حالا نیمه‌ی دیگر آغاز مقاله. بعد از «logout» توکن JWT هنوز سالم است، چون سرور چیزی نگه نداشته. endpoint خروج در دمو فقط می‌تواند از کلاینت بخواهد توکن را دور بیندازد، و کلاینت می‌تواند نگهش دارد:

```
POST /jwt/logout        -> logged out (client discards token)
GET  /jwt/me            -> hello alice [200]
```

خط دوم مشکل است: همان توکن بعد از logout هنوز پذیرفته می‌شود. دو جواب رایج هست. یکی `exp` کوتاه (چند دقیقه) به‌علاوه‌ی یک refresh token که بتوانید ابطالش کنید. دیگری فهرست ممنوعه (denylist) از شناسه‌ی توکن‌ها (claim به اسم `jti`) که سرور بررسی‌اش می‌کند. denylist را امتحان کردم: logout شناسه‌ی `jti` توکن را به آن اضافه می‌کند و بررسی در هر درخواست اجرا می‌شود.

```
POST /jwt/logout?denylist=1
GET  /jwt/me            -> unauthorized: revoked [401]
```

حالا توکن رد می‌شود. اما ببینید چه کردیم: سرور حالا state نگه می‌دارد و در هر درخواست جست‌وجویش می‌کند، که یک session است با چند قدم اضافه. این کشمکش واقعی است. JWT خالص بدون محل نگهداری مشترک مقیاس می‌گیرد ولی زودتر از موعد ابطال‌پذیر نیست؛ لحظه‌ای که ابطال اضافه کنید، بخشی از یک session را از نو ساخته‌اید.

## CSRF

با کوکی یک خطر دیگر هم می‌آید. مرورگر کوکی را خودکار می‌چسباند، پس یک وب‌سایت دیگر می‌تواند مرورگر شما را وادار کند با کوکی واردشده‌ی شما یک POST تغییردهنده‌ی وضعیت به سایت ما بفرستد. این {{< term "csrf" "CSRF" >}} است. `SameSite=Lax` کمک می‌کند و یک توکن مخصوص هر session که باید در header فرستاده شود لایه‌ی دوم است. session دمو یک مقدار CSRF تصادفی دارد؛ `/csrf` آن را به کلاینت واردشده برمی‌گرداند و `/transfer` آن را در `X-CSRF-Token` لازم دارد. بدون توکن درخواست رد می‌شود؛ با توکن پذیرفته:

```
POST /transfer (no token)       -> csrf token missing or wrong [403]
POST /transfer (X-CSRF-Token)   -> transfer accepted [200]
```

سرور توکن را با `subtle.ConstantTimeCompare` مقایسه می‌کند، همان‌طور که مقاله‌ی پسورد برای هش‌ها کرد. CSRF این‌جا در یک مرورگر واقعی انجام نشد؛ این فقط بررسی سمت سرور را نشان می‌دهد.

## توکن را کجا نگه داریم (نظر شخصی)

این بخش نظر من است، نه اندازه‌گیری:

- **در کوکی (HttpOnly):** XSS نمی‌تواند بخواندش، ولی به SameSite و دفاع در برابر CSRF نیاز دارید.
- **در localStorage یا حافظه‌ی JavaScript و با header از نوع Bearer:** CSRF ندارد، ولی هر باگ XSS می‌تواند توکن را بخواند.
- **نظر من:** برای یک وب‌اپ کلاسیک، session با کوکی پیش‌فرض ساده‌تر و امن است. JWT به درد فراخوانی سرویس‌به‌سرویس یا توکن‌های کوتاه‌عمر بین سیستم‌ها می‌خورد.

## راه‌های آسان اشتباه کردن

- **راز یا داده‌ای که ممکن است لازم شود ابطال کنید در payload نگذارید.** هر کس توکن را دارد می‌خواندش و بعداً نمی‌توانید ویرایشش کنید.
- **هنگام login شناسه‌ی session را عوض کنید.** این از session fixation محافظت می‌کند، یعنی وقتی مهاجم پیش از ورود کاربر یک شناسه‌ی شناخته‌شده را می‌کارد. نمایش ندادم.
- **راز HS256 بلند و تصادفی باشد.** راز ضعیف را می‌شود آفلاین و از روی یک توکن حدس زد.
- **همیشه `exp` را بررسی و الگوریتم را ثابت کنید.**
- **توکن کامل یا شناسه‌ی session را هرگز لاگ نکنید.** لاگ جایی است که این‌ها نشت می‌کنند.

## قدم بعدی

مقاله‌ی بعد «OAuth2 و OIDC» است. این‌جا دیدیم سرور بعد از login چه نگه می‌دارد؛ آن مقاله می‌پرسد اصلاً login را چه کسی انجام می‌دهد.
