یک endpoint سفارش را در نظر بگیرید که بدنه‌ی درخواست را مستقیم در struct به اسم `Order` می‌خواند. کدش مرتب به نظر می‌رسد: یک خط، و همه‌ی فیلدها پر می‌شوند. اما حالا همه‌ی فیلدها دست مشتری است، از جمله قیمت و وضعیت. مشتری می‌تواند کتابی ۱۵۰۰ سنتی را با قیمت ۱ سنت و با وضعیت «paid» سفارش بدهد. کسی از روی عمد باگ ننوشته است. فقط هیچ‌کس این سؤال را نپرسیده: «اگر کلاینت دروغ بگوید چه؟»

{{< term "threat-modeling" "مدل‌سازی تهدید" >}} (**threat modeling**) عادتِ پرسیدن همین سؤال در زمان مناسب است: روی کاغذ، پیش از نوشتن کد یا وقتی تغییر دادنش هنوز ارزان است. با این روش مشکلاتی مثل مشکل بالا را یک‌جا پیدا می‌کنیم، نه یکی‌یکی و بعد از اینکه ضرر زدند. در این مقاله یک سیستم کوچک را با آن بررسی می‌کنیم. سیستم، سرویس `orders` است: همان API از [ساخت API با net/http در Go](/fa/posts/go-http-api-stdlib/) که Postgres پشتش است ([Postgres با pgx و sqlc در Go](/fa/posts/go-postgres-pgx-sqlc/)) و برای رویدادها NATS JetStream دارد. این اولین مقاله‌ی یک سری درباره‌ی نوشتن نرم‌افزار امن‌تر هم هست، پس هر اصطلاح را سر جایش توضیح می‌دهم.

> فقط دفاعی. همه‌ی دموها برنامه‌ی کوچک Go خودم روی `127.0.0.1` هستند، فقط با کتابخانه‌ی استاندارد. همه را دوباره با Go 1.27 اجرا کردم (اجرای اول با Go 1.26 بود) و خروجی‌های زیر خروجی واقعی‌اند. هیچ‌چیز علیه سیستم دیگران نیست. «خطای دیتابیس» در دموی ۲ متن ساختگی است و از اجرای واقعی Postgres نیامده.

## چهار سؤال

مدل‌سازی تهدید سنگین به نظر می‌آید، اما در اصل چهار سؤال ساده است:

۱. چه چیزی را می‌سازیم؟
۲. چه چیزی می‌تواند خراب شود؟
۳. می‌خواهیم چه کاری برایش بکنیم؟
۴. آیا کارمان را به اندازه‌ی کافی خوب انجام دادیم؟

این چهار سؤال چارچوبی رایج است و به شخص خاصی نسبتش نمی‌دهم. بقیه‌ی مقاله همین سؤال‌ها را روی یک سرویس پیاده می‌کند. سؤال ۱ به یک نقاشی نیاز دارد.

## سؤال ۱: سیستم را بکشید

مدل تهدید با یک نقاشی ساده شروع می‌شود: چه چیزی با چه چیزی حرف می‌زند. این هم نقاشی سرویس سفارش:

```
 [ Client ] --1 HTTPS--> ( Orders API ) --2 SQL--> =Postgres=
  external      |            process   \--3 publish--> =NATS JetStream=
                |                                       |
   ===== trust boundary =====          ( Worker ) <--4--/
```

سه نوع شکل داریم. `[ ]` یک موجودیت بیرونی است، چیزی که خارج از کنترل ماست (کلاینت). `( )` یک پردازش است، کدی که خودمان اجرا می‌کنیم. `= =` یک محل نگهداری داده است. فلش‌ها جریان داده بین آن‌هاست: ۱ فراخوانی API توسط کلاینت، ۲ حرف زدن API با دیتابیس، ۳ منتشر کردن یک رویداد توسط API، و ۴ مصرف همان رویداد توسط worker.

خط علامت‌های مساوی مهم‌ترین بخش است. اسمش {{< term "trust-boundary" "مرز اعتماد" >}} (**trust boundary**) است: جایی که داده از چیزی که کنترلش نداریم به چیزی که کنترلش را داریم می‌رسد. این‌جا درست همان‌جاست که اینترنت به API می‌رسد. هر چیزی که روی جریان ۱ می‌آید، هر قدر هم کلاینت مهربان به نظر برسد، غیرقابل‌اعتماد است. جریان‌های ۲ تا ۴ داخلی‌اند، ولی باز از یک پردازش به پردازش دیگر می‌روند، پس آن‌ها هم یک نگاه دوباره می‌خواهند.

## سؤال ۲: STRIDE، فهرستی برای «چه چیزی می‌تواند خراب شود»

«چه چیزی می‌تواند خراب شود؟» سؤال خیلی بازی است؛ آدم‌ها یا خشک‌شان می‌زند یا فقط مشکلاتی را فهرست می‌کنند که از قبل می‌شناسند. {{< term "stride" "STRIDE" >}} فهرستی است که به این سؤال ساختار می‌دهد. اسمش شش حرف است و هر حرف یک نوع تهدید:

- **S**poofing (جعل هویت): وانمود کردن به اینکه شما کس دیگری هستید (توکن ورود جعلی یا دزدیده‌شده).
- **T**ampering (دست‌کاری): تغییر دادن داده‌ای که نباید بتوان عوضش کرد (قیمت یک سفارش).
- **R**epudiation (انکار): کاری را انجام دادن و بعد منکرش شدن، چون کسی ثبت نکرده که چه کسی انجامش داده.
- **I**nformation disclosure (افشای اطلاعات): نشان دادن داده به کسی که نباید ببیند (یک خطای خام دیتابیس).
- **D**enial of service (از کار انداختن سرویس): در دسترس نبودن سرویس برای بقیه، یعنی {{< term "denial-of-service" "denial of service" >}} (یک درخواست خیلی بزرگ یا خیلی کند).
- **E**levation of privilege (ارتقای دسترسی): گرفتن حقی بیشتر از آنچه به شما داده‌اند (خواندن سفارش کاربر دیگر).

روی اجزای نقاشی‌تان، چه جعبه‌ها و چه فلش‌ها، می‌روید و برای هر کدام این شش سؤال را می‌پرسید. برای سرویس سفارش به این جدول رسیدم:

| عنصر | تهدید | راه مقابله |
|---|---|---|
| API، جریان ۱ | **S**: توکن دزدیده‌شده یا جعلی | بررسی توکن، انقضای کوتاه |
| API، جریان ۱ | **T**: کلاینت `price_cents` را تعیین می‌کند | فقط فیلدهای مجاز، قیمت‌گذاری سمت سرور (دمو ۱) |
| API | **R**: ثبتی از اینکه چه کسی چه کرد وجود ندارد | لاگ ساختاریافته با request ID، [کانفیگ، لاگ ساختاریافته و خطا در Go](/fa/posts/go-config-logging-errors/) |
| API | **I**: خطای خام به کلاینت می‌رسد | خطای عمومی به‌علاوه‌ی لاگ (دمو ۲) |
| API | **D**: درخواست خیلی بزرگ یا خیلی کند | سقف اندازه‌ی بدنه، timeout (دمو ۳)، [Rate limit و cache در Go](/fa/posts/go-rate-limiting-caching/) |
| API | **E**: کاربر سفارش کاربر دیگر را می‌خواند | بررسی مالکیت در هر خواندن |
| Postgres | **I**: لو رفتن اعتبارنامه‌ها | رمزها بیرون از لاگ، کاربر دیتابیس با کمترین دسترسی |
| NATS | **T/E**: هر کسی می‌تواند رویداد منتشر کند | TLS و احراز هویت، [JetStream در پروداکشن: cluster، retention و امنیت](/fa/posts/nats-jetstream-production/) |
| NATS به worker | **T**: پیام تکراری یا replay شده | [Idempotency و معنای exactly-once در JetStream](/fa/posts/nats-jetstream-idempotency/) |

جدولی مثل این فهرستی از سؤال‌هاست با اولین جواب‌ها، نه اثباتی که سیستم امن است. من فقط سه ردیف از این جدول را بازتولید و رفع کردم (T روی API، I روی API و D روی API)، چون در یک دموی کوچک محلی جا می‌شدند. بقیه برای این آمده‌اند که شکل کامل کار را ببینید؛ آن‌ها را این‌جا اجرا نکردم.

## سؤال ۳: چه کار می‌کنیم؟ سه دمو

هر دمو یک شکل دارد: یک سرور ساده‌لوحانه، بعد یک سرور اصلاح‌شده، و یک درخواست یکسان به هر دو. هر دو از یک برنامه و در یک نسخه‌ی موقت اجرا می‌شوند: `api naive <addr>` و `api fixed <addr>`، هرکدام روی یک پورت تصادفی loopback (در دستورهای زیر برای خوانایی `127.0.0.1:8101` و `8102` نوشته‌ام).

### دمو ۱: دست‌کاری

ضعف اسمش {{< term "mass-assignment" "mass assignment" >}} است: سرور همه‌ی فیلدهای درخواست را در یک شیء داخلی کپی می‌کند، پس کلاینت می‌تواند فیلدهایی را تعیین کند که هرگز نباید دستش باشد. endpoint ساده‌لوح بدنه را مستقیم در `Order` می‌خواند؛ پس سفارشی می‌فرستم که قیمت و وضعیت خودش را تعیین می‌کند:

```
$ curl -s -X POST 127.0.0.1:8101/orders -d '{"sku":"book","qty":1,"price_cents":1,"status":"paid"}'
{"id":1,"sku":"book","qty":1,"price_cents":1,"status":"paid"}
```

سرور همان را پذیرفت: قیمت ۱ و وضعیت paid. فروشگاه همین الان کتابی را به یک سنت فروخت.

نسخه‌ی اصلاح‌شده سه کار را متفاوت انجام می‌دهد. بدنه را در یک نوع ورودی کوچک با فقط دو فیلد، `sku` و `qty`، می‌خواند ({{< term "allow-list" "فهرست مجاز" >}} یا allow-list: فقط همین‌ها پذیرفته می‌شود و بقیه رد). قیمت را از یک کاتالوگ سمت سرور برمی‌دارد. و وضعیت را خودش تعیین می‌کند. همان درخواست مخرب، و بعد یک درخواست عادی:

```
$ curl -s -X POST 127.0.0.1:8102/orders -d '{"sku":"book","qty":1,"price_cents":1,"status":"paid"}'
{"error":"bad request"}
$ curl -s -X POST 127.0.0.1:8102/orders -d '{"sku":"book","qty":2}'
{"id":1,"sku":"book","qty":2,"price_cents":1500,"status":"pending"}
```

درخواست اول رد می‌شود، چون `DisallowUnknownFields` باعث می‌شود decoder با دیدن `price_cents` یا `status` خطا بدهد. درخواست دوم فقط دو فیلد مجاز را دارد؛ قیمت ۱۵۰۰ از کاتالوگ سرور آمده و وضعیت `pending` را هم سرور گذاشته است. اصل همان اصل هر مرز اعتماد است: کلاینت می‌گوید چه می‌خواهد (`sku` و `qty`)؛ بقیه‌ی چیزها را سرور تعیین می‌کند.

### دمو ۲: افشای اطلاعات

وقتی داخل سرور چیزی خراب می‌شود، ساده‌ترین کار این است که متن خطا را به کلاینت برگردانیم. handler ساده‌لوح دقیقاً همین کار را با `err.Error()` می‌کند. خطای این دمو را خودم و به سبک خطای یک driver دیتابیس ساخته‌ام. ببینید به کلاینت چه می‌گوید:

```
{"error":"query orders: ERROR: column \"total_cents\" does not exist (SQLSTATE 42703) [host=db.internal port=5432 user=orders_app]"}
```

همین یک خط اسم یک ستون، نوع خطای دیتابیس (کد SQLSTATE)، اسم و پورت یک میزبان داخلی و کاربر دیتابیس را لو می‌دهد. هیچ‌کدام تنهایی آسیب‌پذیری نیستند، ولی برای کسی که دنبال چیزی می‌گردد نقشه‌ی رایگانی از داخل سیستم است.

handler اصلاح‌شده جزئیات کامل را در لاگ خود سرور می‌نویسد و به کلاینت یک پیام ثابت می‌دهد، به‌علاوه‌ی یک request ID که کلاینت می‌تواند هنگام درخواست پشتیبانی بگوید:

```
{"error":"internal error","request_id":"a1b2c3"}
level=ERROR msg="request failed" path=/orders/1/total error="query orders: ERROR: ..." request_id=a1b2c3
```

خط اول چیزی است که کلاینت می‌گیرد. خط دوم لاگ سرور است: خطای واقعی، با همان `request_id`، تا برنامه‌نویس بتواند پیدایش کند. (خط لاگ بالا با `...` کوتاه شده؛ در اجرای واقعی کل متن خطا آمده است.) این ID در دمو ثابت است؛ در کد واقعی برای هر درخواست یکی ساخته می‌شود.

### دمو ۳: از کار انداختن سرویس

دو راه برای از دسترس خارج کردن یک سرور هست که تقریباً هیچ هزینه‌ای برای مهاجم ندارند، و هر دو را امتحان کردم.

**بدنه‌ی خیلی بزرگ.** یک بدنه‌ی ۵۰ مگابایتی (همه صفر) را به endpoint ای فرستادم که فقط ورودی‌اش را می‌خواند و دور می‌ریزد. سرور ساده‌لوح همه‌اش را خواند: `{"read":"52428800"}` (یعنی ۵۰ بار ۱٬۰۴۸٬۵۷۶ بایت). با `http.MaxBytesReader` روی ۱ مگابایت همان درخواست با `{"error":"body too large"}` رد می‌شود.

**کلاینت خیلی کند.** این‌جا کلاینت بزرگ نیست، فقط کند است. یک probe کوچک Go یک اتصال باز می‌کند، نصف یک header را می‌فرستد و بعد هر ۲۰۰ میلی‌ثانیه یک بایت دیگر، بدون اینکه هیچ‌وقت تمامش کند. این الگوی {{< term "slowloris" "slowloris" >}} است: تعداد زیادی از این اتصال‌ها می‌توانند ظرفیت یک سرور را پر کنند، در حالی که تقریباً هیچ منبعی از مهاجم مصرف نمی‌کنند. سرور بدون timeout: `still open after 4s, giving up`، یعنی probe بعد از ۴ ثانیه منتظر ماندن را رها کرد. سرور با `ReadHeaderTimeout` یک‌ثانیه‌ای: `server closed after ~1.0s`. این سرور دیگر منتظر headerی که هرگز تمام نمی‌شود نمی‌ماند. مصرف حافظه یا throughput را اندازه نگرفتم، فقط اینکه اتصال باز ماند یا نه.

## سؤال ۴: خوب عمل کردیم؟ رتبه‌بندی و بازبینی

معمولاً وقت نداریم همه‌چیز را یک‌جا درست کنیم، پس تهدیدها را با احتمال ضرب‌در تأثیر، هرکدام از ۱ تا ۳، رتبه‌بندی می‌کنم. این قضاوت خودم برای همین سرویس است، نه اندازه‌گیری:

| تهدید | احتمال | تأثیر | امتیاز |
|---|---|---|---|
| قیمتی که کلاینت تعیین می‌کند | ۳ | ۳ | ۹ |
| سفارش کاربر دیگر | ۲ | ۳ | ۶ |
| خطاهای پرجزئیات | ۳ | ۲ | ۶ |
| درخواست کند یا بزرگ | ۲ | ۲ | ۴ |

اول امتیازهای بالاتر را درست کنید. بعد جواب سؤال ۴ را به شکل یک تاریخ بازبینی یا یک محرک بنویسید تا واقعاً اتفاق بیفتد. یک الگوی ساده کافی است:

```markdown
# Threat model: <system>
Scope / out of scope:
Diagram: (elements, flows, trust boundaries)
| Element | S | T | R | I | D | E | Mitigation | Owner | Status |
Top risks (L x I):
Review date / trigger (new feature, new dependency):
```

## زنده نگه داشتن مدل

- **وقتی معماری عوض می‌شود، نمودار را دوباره بکشید.** مدل قدیمی از نبودن مدل بدتر است، چون درباره‌ی سیستمی که دیگر وجود ندارد حس امنیت می‌دهد.
- **تهدید روی فلش‌ها به اندازه‌ی تهدید روی جعبه‌ها واقعی است.** پیام بین API و worker را هم می‌شود replay یا جعل کرد، درست مثل اینکه API با یک بدنه‌ی بد صدا زده شود.
- **راه مقابله‌ی بدون مسئول، آرزو است.** کنار هر ردیف یک اسم و یک وضعیت بگذارید.
- **ابزار هم هست.** OWASP Threat Dragon و Microsoft Threat Modeling Tool دو مورد از آن‌هایی‌اند که می‌شناسم. فقط اسم می‌برم؛ این‌جا استفاده‌شان نکردم.

## تمرین

یک عنصر به نمودار اضافه کنید، مثلاً یک cache با Redis بین API و Postgres، و شش ردیف STRIDE آن را بنویسید. کدام امتیاز بالاتری می‌گیرد؟
